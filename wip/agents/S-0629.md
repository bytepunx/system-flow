## Decisions

- Remedy: the planner's. A `permission_prompt` check whose `claude -p` ends on the harness's usage limit has no outcome: flai records nothing, opens no thread, logs the refusal, and checks the version again after the reset. Every other failure stays final, as ADR-0106 § 2 decided. A new ADR refines § 2, since ADR-0106 cannot be edited. The limit is read with the ADR-0214 usage reader from the check's stream-json, not by matching Claude Code's text.
- Changed from the planner's draft: a refusal that names no reset time is checked again an hour later, not at the next look, so a limit with no reset does not start a refused `claude -p` at every look. T-2749 and T-2750 say so.
- Not done here: feeding the check's refusal into the host's budget state (ADR-0209 § 5). The check is not an agent run, and holding every start on it is a wider change.
- The existing `failed` record of 2.1.311 in `~/.flai/serve/claude-checks.json` stays: the host's state is the operator's, and the version has moved on.
- Plan: three layers, one task each, as the planner drafted. T-2750 waits for T-2749 because the code builds the rule the ADR decides; T-2751 waits for T-2750 because the docs and the issue's close reason describe the code as built. Each task goes to one task sub-agent.
