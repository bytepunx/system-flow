# S-0105 Operators should be able to control and configure flai via the dashboard

## Context

Host actions and the host's settings have been shell-only by design since S-0078 (ADR-0029): "None is enabled until you enable it by name, in a shell on the host; nothing a dashboard can ask for changes that." S-0105 asks for those operations in the dashboard, per project. The dashboard's writes are `flai` commands that hostapi builds from validated values and runs in the project, some of them gated by a host action.

## Current state

All three tasks are done and the criterion is met, so the story goes to review.
- A new host action, `settings`, is turned on and off only in a shell.
- With it on, the dashboard's Settings page changes everything the operator chose:
  - host actions;
  - the default agent (committed);
  - the agent's name, minutes, and command;
  - harnesses;
  - checks and their time limit;
  - import folders;
  - the MCP and dashboard tokens.
- Each change is a flai command hostapi builds from checked values, journalled as that command.
- Settings the host keeps for every project need `settings` on for every project.
- The decision is in [ADR-0039](../../design/adrs/0039-a-settings-host-action-turned-on-only-in-a-shell-lets-the-dashboard-change-the.md), which refines ADR-0029. The design, the operator guide, and the user docs are updated.
- `scripts/flai-test.sh` (lint, unit, integration, smoke) and `scripts/flaiover-test.sh` (435 tests, Node 24) pass, as do `flai check --strict` and `lint-md`.
- A flaiover test runs every settings write through the real flai against a temporary configuration.

The trial used a throwaway project, a scratch `flai serve` started with `--config` (not the variable), and a dashboard on port 5205. The operator's serve and `~/.flai/config.json` were untouched (same checksum before and after).
- **Settings off:** every section was read-only and named its command.
- **`flai serve enable settings`, this project only:**
  - push was turned on from the page, and landed in the scratch config, so the `--config` pass-through works;
  - the default agent was committed with the dashboard's trailer;
  - the host-wide Save stayed disabled.
- **`--all-projects`:** these were set from the page and landed exactly, including `work on {story}; echo $HOME` as one argument:
  - the agent's name, minutes, and command;
  - the claude-code arguments;
  - a check;
  - an import folder.
- **MCP token:** rotated and shown once; it matched the file.
- **Dashboard token:** rotated from the page. The old token was then refused (401) and the new one accepted (200). The browser stayed logged in across a reload.
- **Off again:** `flai serve disable settings --all-projects` in the shell made the next write a 403 naming the command.
- **Journal:** all nine lines were there.

The trial found three things, fixed in 67167f9:
- a rotated MCP token restarted serve's server without `--exit-with`, so it outlived serve (checked live after the fix: it goes with serve);
- journal lines only named the kind of setting, and now give the flai command;
- two wording warts.

## Decisions
- The operator decided on 2026-09-23, asked at the start of the story:
  - A new host action, `settings`, is the only consent. It is turned on and off in a shell alone, and it lets the dashboard change the rest.
  - All four areas are exposed: host actions; agent settings; checks and import folders; tokens and the MCP server.
  - Commands (the agent command, harness programs and arguments, checks) are editable from the dashboard too. Whoever holds the dashboard token can then run anything on the host while `settings` is on.
- Settings kept in the host's configuration apply to every project: the agent's name, attended minutes, and command; the harnesses; the checks; the import folders; the dashboard token. The dashboard changes those only when `settings` is on for every project (`flai serve enable settings --all-projects`). Settings that belong to one project (its host actions, its default agent, its MCP token) need `settings` on for that project.

## Open questions
- I decided, without asking, that settings the host keeps for every project need `settings` on for every project: the agent's command, harnesses, checks, import folders, and the dashboard token. One project's consent would otherwise change what every project runs. Is that right, or should one project's `settings` be enough? The alternative is per-project copies of those settings.
- The operator chose four areas. Still shell-only after this story: the `flai config` keys (`dashboard.image`, `tag`, `port`, `bind`, `push_key`, `push_known_hosts`, `template.repo`, `author`, `worktrees.relative_paths`), `flai serve start/stop`, and `flai mcp start/stop` (which `flai serve` keeps running anyway). Should any of these follow?
