## Decisions

- Kept the planner's five tasks and four layers. Layer 1: T-2628 (`Repo.SaveAll`) and T-2632 (`check.Items`), run together: neither waits on the other and they share no path. Layer 2: T-2641 (`itemedit.ApplyForecasts`) waits for both, since it calls `SaveAll` and `check.Items`. Layer 3: T-2647 (the replanner) waits for T-2641, since it calls `ApplyForecasts`. Layer 4: T-2655 (the measurement and the design docs) waits for T-2647, since it measures that replanner.
- T-2632 writes `check.Items` in a new file, `flai/internal/check/items.go`, not in `check.go`. S-0598 (cause 8) changes `check.go` too, and a new file keeps the two branches from conflicting there. T-2632's and the story's touches were changed to match.
- A forecast write blocks only on an error on the item's own file, as `itemedit.Apply` does. It does not compare against a check run before the write, because forecasts are values flai owns. That keeps the write to one scoped check.
- `itemedit.ApplyForecasts` takes the caller's item list, and the replanner passes the items its replay read. T-2647's sub-agent found that when the batch read the items again itself, a forecast another writer changed between the replay and the write was overwritten with no conflict, as `Apply` did before. With the replay's own copies (from `repo.List`, which hands out copies), the ADR-0184 merge base is what the replay read: such a forecast is refused and warned of, and a change to another part is kept. `TestAReplanRefusesAForecastAnotherWriterChangedAfterTheReplay` pins it.
- `flai test` ran once over `itemedit` and `serve` after T-2647, not after T-2641 as well: that run covers `itemedit`'s importers, `serve` among them, and every tier passed.
- T-2655 measured in a `tar` copy of the main checkout without `.git`, since `flai guard` refuses a sub-agent `git clone`. In both runs the check's git rules found no repository; server-performance.md says so.
- Conversations: MS-0352 with S-0606, which conflicts on `repo.go` (S-0606 adds `parsed.stale` after the write in `Save`, which S-0599 moved into `saveLocked`). Proposed: whichever story rebases second puts that line in `saveLocked`, so `SaveAll` marks the snapshot stale too. Awaiting S-0606's reply. MS-0359 with S-0605 and MS-0355 with S-0598 are settled: whichever story lands second keeps both causes' sections in `server-performance.md`, in cause order.
