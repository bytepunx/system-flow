# S-0104 Flai should spawn and manage agents in response to Kanban changes

## Context

Second of E-0008's two stories. S-0103 gave each story an `agent` (harness, model, config), copied from the project's default (ADR-0037). S-0079 already has `flai serve` start one operator-set command for a project when a story enters ready. It starts at most one agent at a time, only while nobody is attending, and only with the action enabled (`flai serve enable agent`). It records `running`/`last`/`waiting` per project in `serve/agents.json`, which `agent.status` serves to the dashboard's host-agent notice. Nothing starts a harness by name, runs more than one agent, or shows an agent per story.

## Decisions
- S-0104's branch is stacked on `story/S-0103`, whose code it needs (a story's `agent`). S-0103 is in review, not accepted. Once it is, `flai stream sync` rebases this branch onto main and drops the commits that are already there.
- The operator's consent stays where S-0079 put it: nothing starts unless the agent action is enabled for the project on the host. What an agent may do (permission mode, allowed tools) and which program is run are host settings. A story names the harness, the model, and tunables the adapter checks, never flags or programs, because anyone who can edit a story in the dashboard would otherwise choose what runs on the operator's host.
- One agent per story, many per project, up to the in-progress limit. An agent started for a story still in ready counts against the limit, until it moves the story to in progress.

- An agent that ends with an unanswered question of its own on its story has not failed: it waits, and flai starts it again as itself, in its session, when the question is answered. The trial showed a model ending its turn instead of holding `wait_for_events`, so whether the answer reaches it cannot depend on the model. The prompt still asks it to wait, which keeps its process and context.
- A resumed agent is not held back by the in-progress limit or by someone attending: its story is already its own.
- An agent that fails is not retried by itself. Its story waits, red, until someone moves it to ready again, so a failing harness cannot spend in a loop.
- Only a story's narrative (`S-*.md`) counts as someone attending, not a README. The agent's MCP servers are flai's alone (`--strict-mcp-config`). Both came from the trial.
- "Created in ready": flai creates stories in backlog, so a story is worked when it enters ready by any path, including one made and moved at once.
