## Decisions

- **The way OpenCode asks: hold in `tool.execute.before`, not `permission.asked`** ([ADR-0262](../../design/adrs/0262-an-opencode-agent-s-protected-write-is-held-and-asked-in-the-flai-guard-plugin.md)). S-0406's finding 2 shows `opencode run` replies to every `permission.asked` itself, at once, and does not await the plugin's event hook, so the plugin would lose the race; `tool.execute.before` is awaited with no timeout. The guard holds there through `guard.Hold` and `ask.Asker.Hold`, four minutes, the stdio bound of ADR-0124.
- **Criterion 2's "the configuration sets `ask`" is not built as written.** An `ask` rule is refused by `opencode run` after the owner allowed, so with the plugin present the adapter writes no rule on a protected path, and without it writes the deny rules. `--auto` is not passed. Asked on a thread whether the criterion may say so.
- **The plan, as the planner drafted it, kept.** Layers: T-1695 (the ADR); T-1696 (the guard's hold) and T-1697 (the adapter's configuration and `Ask: true`) together, since both wait only for the ADR and share no path; T-1698 (the plugin), after T-1696, whose exit codes it relies on; T-1699 (the integration test), after T-1697 and T-1698, since it runs both; T-1700 (the docs), after T-1699, to describe what the test showed.
- **T-1698 is mine, not a sub-agent's.** Both plugin copies are under `.opencode/`, a protected path (D-0514), so `flai guard` refuses a sub-agent the write. The ADR leaves the plugin's code as it is; the change is its comment and the template's changelog line.
