## Decisions

- The planner's four tasks are kept as drafted. The remedy is an OS file lock (`flock` on unix, `LockFileEx` on Windows) on a lock file that stays in place, so the kernel frees it when its holder dies and no lock is ever broken by its age.
- Layer 1 is T-1510 alone: the `flai/internal/filelock` package that the later tasks use.
- Layer 2 is T-1511 (activity) and T-1512 (guard record, serve agents state). Both wait on T-1510 for the package. They share no path, so they run together.
- Layer 3 is T-1513, closing I-0140. It waits on T-1511 and T-1512, because the issue closes only once every lock with the cause is fixed.
- Lock files now stay in place after unlock. Removing one would let a waiter that already has it open lock an unlinked file while a newcomer locks a fresh one. As a result, the guard leaves one empty `<session>.json.lock` per session in `.flai-cache/guard`, which nothing lists. It is accepted as harmless and not cleaned up.
- T-1512 inlined `lockRecord` into `RecordChange` as one `filelock.Lock` call. Its serve test uses child processes, because `agentsMu` already serializes goroutines within one process.
- The task sub-agents may run targeted `go test -race -count=N -run <Test>` repeats. A flaky race needs many runs as evidence, and `flai test` runs each tier once. All other tests go through `flai test`.
