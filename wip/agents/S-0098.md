# S-0098 Enable importing a project into flai from the dashboard

## Context

The dashboard lists only projects whose `flai serve` connection has proven itself, and `flai serve` serves only registered projects, which need a `system-flow.yaml` with a key. The container holds no project files (ADR-0031), so it cannot look for repositories itself. A repository that was never set up with flai therefore cannot appear on the board today, and something on the host has to name the candidates. `flai import` (S-0006) already converts a repository in place, but it does not run tests or commit, and it runs unattended only with `--yes`.

## Current state

Done; all four tasks and all five criteria.

- T-0350: `flai import --commit` refuses a non-git or dirty repository, runs the host's checks or the tests it detects, commits exactly what the import wrote and moved when they pass, and otherwise leaves it uncommitted and exits 5.
- T-0351: `flai serve import add|remove|list` names folders (`import_roots`). `flai serve` offers each git repository in them without a manifest over a candidate connection (`kind: candidate`, only `import.preview` and `import.run`, journalled). It registers the repository once imported, with a key from the folder's name, unique among what it serves.

## Next steps
None: in review. Once this ships, `flai serve import add <folder>` on the host offers that folder's repositories on the board.

## Decisions
- The operator decided in conversation (2026-09-23):
  - Candidates come from scanning folders the operator names on the host. `flai serve` lists every git repository under them that has no `system-flow.yaml`, and the board shows each as not imported.
  - After migrating, tests run as detected from the repository: checks configured on the host if any, otherwise what the repository itself has (its own Makefile's `test` target, `go test ./...` for `go.mod`, `npm test` for a real `package.json` test script, and so on). The result says which ran, or that none were found.
  - If the tests fail, nothing is committed: the migrated files stay uncommitted in the working tree and the failures are shown.
- Naming a folder to scan is the operator's say over importing from it: no separate host action gates `import.run` for repositories under a named folder. Running a repository's tests executes its code on the host, and the operator opted in by naming the folder. The operator guide says so.
- A declined import is not remembered: declining shows that another project must be picked, and picking the repository again prompts again (criteria 4 and 5).
- Import from the board refuses a repository with uncommitted changes, so the commit holds the migration and nothing of the operator's; the commit names only the paths import wrote or moved.
- A repository imported with failing tests is still registered and served as a project. The import did happen (the manifest is there, uncommitted), so it is no longer a candidate, and served is the only way it stays on the board. The failures and "not committed" are shown when it is imported.
- The key a board import gives a project is the folder's name made safe (`widget`, `web-app`), kept unique against the projects already served, instead of the template's default of the name's initials, which collide easily. The candidate's connection names it as `import-` plus that key.
- Candidates go to the dashboards the served projects already dial; with no project served yet there is no dashboard to offer them to. They answer only `import.preview` and `import.run`.
