## Decisions

- Every hold goes through `workitem.Holds.Of`, so the launcher, `wait_for_work`, `flai board`, `inbox`, the card, and move warnings got the `after` hold without changes of their own.
- `Repo.Holds(items)` looks up a named story that `items` lacks through `Repo.Get`. `flai serve` and `Repo.Move` read only active items, and an accepted story is archived.
- A story held both ways gets code `after`, and its reason goes on with `; also held (overlap): …`, so that "starts when" stays true.
- A story named in `after:` that does not exist keeps the hold, like a cancelled one. `flai check` reports it as an error.
- `flai check` reports each cycle once, on its lowest story. `story.after` findings are errors, so an edit that makes one is refused.
- MCP `item_edit` clears `after` with an empty list, as it clears `touches`, not with a `clear_after` flag. It now names the check's findings when it refuses an edit.
- T-0476 went before T-0475, because T-0475 must wait for S-0129 (TH-0022).
- ADR-0046 says an older flai ignores `after:`. That is not so: `ParseItem` is strict, so an older flai refuses the item and every listing that reads it. This is recorded in `work-hierarchy.md`. The host's flai (1.18.5) must be upgraded before any story is given `after`.
