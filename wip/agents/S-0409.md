## Decisions

- **Plan, three layers.** Layer 1: T-1701 (the translation, `flai/internal/harness/opencodeagents.go`) and T-1703 (the guard's tests in `flai/internal/guard`). Layer 2: T-1702 (the adapter wires the agents into `OPENCODE_CONFIG_CONTENT` and starts a strategic agent with `--agent`), after T-1701, whose function it calls. Layer 3: T-1704 (the integration test) and T-1705 (the docs), both after T-1702 and T-1703, since the test drives the wired adapter and the guard, and the docs say what they do. No two tasks of a layer share a path.
- **T-1703 waits for nothing.** The planner put it after T-1701. The guard already reads an OpenCode sub-agent's `agent` name and judges it read-only from `.claude/agents/<name>.md` (`guard.ReadOnlyAgents`), so T-1703 depends on the naming rule only (the OpenCode agent keeps the definition's name), not on T-1701's code.
- **T-1705 runs beside T-1704.** The planner put it after T-1704. The docs describe the adapter and the guard, not the test.
- **The agents land in `OPENCODE_CONFIG_CONTENT` under `agent`,** beside `mcp.flai` (ADR-0260): no file in the worktree, so the move to review is never refused for a generated file. OpenCode merges them over the project's own `opencode.json`.
- **The strategic definitions come from the role files** through `roles.Generate`, as the claude-code adapter takes them (ADR-0236), not by reading `.claude/agents/<name>.md`, which are links into `.flai-cache`. The explorer and the verifier are read from `.claude/agents/` with `readDefinition`. The curator and a role a project defines run the same way: they share the code path.
- **Permissions, not `tools`.** Each translated agent gets an ordered `permission` object: each OpenCode tool the table knows that the definition does not grant is `deny`, `flai_*` is `deny` before the granted flai tools are `allow`, and a definition with no `Edit` or `Write` has `edit: deny`. No `"*": "deny"`, which would also deny `external_directory` and `doom_loop`.
