## Decisions

- The planner's seven tasks are kept, in its four layers. Layer 1: T-2396, the ADR every other task builds on. Layer 2: T-2400 (the record's per-commit verdict) and T-2403 (serve's job) together, no common path. Layer 3: T-2407 waits for T-2400's answer from the record and T-2403's request function; T-2411 waits for T-2403's journal fields; no common path. Layer 4: T-2415 (prompt and scripts) waits for T-2407's tool shape; T-2417 (conventions and docs) for T-2407 and T-2411.
- ADR-0229 settles the job. The request is a file under the project's `.flai-cache/verify/jobs/`, as `RequestMerge`'s is, so neither the CLI nor the MCP server needs serve's state folder; serve not taking it within ten seconds is how the asker learns serve is not running.
- The job runs the close-out script where the worktree has one, so the commit and the three sync rounds stay where they are; serve's `flai verify --record-issues` where it has none.
- A `verified` event goes only to its story's agent and to readers with no story, so other stories' agents are not woken by it. That needs `flai/internal/inbox/inbox.go`, added to T-2403.
- The record keys a verdict by the head commit, kept only for a clean worktree, and the job keeps it under the close-out's own commit too, since that commit holds what the run verified.
- The journal marks an answer from the record by a `detail` beginning `from the record` (metrics.md § Close-outs), since ADR-0229 names no field for it.
- The MCP `verify` tool stays among the guard's reads: a sub-agent or the orchestrator asking at a verified commit gets the record, and a story in review has nothing to commit.
