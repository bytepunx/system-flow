## Decisions

- Plan: layer 1 T-3164, the package. Layer 2 T-3165 (the command) and T-3166 (the start and the check): both call the package and share no path, so they run together. Layer 3 T-3167, the docs, which describe both.
- Until S-0751's image job, a start refuses only a missing image, naming `flai image status`. A stale image is warned of in the serve log and the start goes on: refusing it would stop every start on this host, whose images carry none of ADR-0295's recipe and base labels yet.
- Pulled images are not judged by a digest list here: no list exists until S-0734, and flai pulls nothing until S-0740. Every image is judged by its labels, as ADR-0295 judges a built one.
- The expected recipe is computed for the project's layer from its Dockerfile, with no build arguments until S-0745 adds `agent.image.args`. The harness images' recipe is not compared until S-0740 embeds their Dockerfiles in flai.
- The recipe is `sha256:` over the Dockerfile's bytes, then `\n--target=<target>\n`, then each build argument but `BASE` and `FLAI_VERSION` as a `NAME=value\n` line, sorted. A script can make the same sum with `sha256sum`.
- The flai an image must hold is the project's flai: the version `<flai.command> version --json` prints in the main checkout when the manifest names `flai.command`, else the running flai's (ADR-0295 §3). It is resolved only when docker says an image is present, so a check with no docker runs no command.
- An image with no `dev.system-flow.flai` label is stale (another flai version); one with no recipe label, where a recipe is expected, is stale (another Dockerfile).
- The refusal and the `agent.image` finding name `flai image status`, as the story's criterion 4 says. ADR-0295 names `flai image ensure` there, which S-0740 builds; that story renames them.
- The strategic agents keep the layer image for now: ADR-0295 §6 moves them to the harness image in S-0751.
- T-3165 ran in a task worktree, task/T-3165, since `flai/cmd` builds the serve and check packages T-3166 was changing. Its three files were copied into the story worktree once both were back. The worktree and branch are removed.
- T-3166 needed two test fakes outside its touches, in `flai/internal/serve/verifyjob_test.go` and `flai/internal/check/scope_test.go`, moved to the new `{{json .}}` inspect and the `check.ImageProbe` struct. I made those edits myself. scope_test.go overlaps S-0761's claim: told on MS-0549.
- `flai check` reads the host's `--image` per project from the config file `FLAI_CONFIG` names, else `~/.flai/config.json`, with `config.Parse`. `config.Load` would write a missing file. So the check and flai serve judge the same images.
- On this host `flai image status` now reports both agent images stale. They carry flai 1.86.12, from `scripts/agent-image.sh`'s `git describe`, against the tree's `dev`, and no recipe or base label. `make agent-images` does not clear that until S-0760 makes the script label `dev` and the recipe. Until then, `flai check` on the main checkout warns `agent.image` stale (advisory), and each container start logs `container agent image stale` and goes on.

That is a difference in wording only. `flai check` reads `FLAI_CONFIG` or `~/.flai/config.json`, never a `--config` flag. `flai image status` takes stories' agents from `AgentOf`, where the start uses `StartAgentOf`; it differs only for a host command harness, which runs no container.
