# S-0111 flai self-upgrade never installs into a project: a binary run from a checkout upgrades into ~/.flai/bin, and flai host restarts on what was installed

## Context

The operator's `flai` is the repository's `bin/flai`: `~/.zshenv` puts `/home/alex/git/bytepunx/system-flow/bin` on PATH ahead of `/usr/local/bin`. Running `flai self-upgrade` therefore wrote 1.15.1 into the checkout's `bin`, which `scripts/flai.sh` rebuilds from the tree, and which no other machine has. (This session's own shell resolved the stale `/usr/local/bin/flai` 1.10.1 instead, and reported that version by mistake.)

## Current state

The only task is done and every criterion is met, so the story goes to review.
- The fix: `flai self-upgrade` with no `--dir`, run by a flai inside a system-flow project, installs to `$FLAI_INSTALL_DIR` or `~/.flai/bin` instead of over itself. It says so, and asks the flai there whether it is up to date. `flai host upgrade` restarts the host on the installed path. An installed flai outside any project is replaced in place, as before.
- Tests cover installing from a checkout, the up-to-date answer from the home copy, `FLAI_INSTALL_DIR`, replacing in place outside a project, and the host's restart target.
- Tried live with real binaries and a scratch HOME: a checkout's flai 1.15.0 upgraded from a stand-in 1.99.0 release left the checkout at 1.15.0 and installed 1.99.0 into the home folder, and the second run said it was the latest. The operator's own `~/.flai` was not touched.
- `scripts/flai-test.sh` (lint, unit, integration, smoke) passes, as do `flai check --strict` and `lint-md`. The design and the user guide are updated.

## Next steps
1. The operator reviews and accepts, and the push releases the fix.
2. On the operator's machine, `flai self-upgrade` run once from the checkout then installs into `~/.flai/bin`. `~/.zshenv` should put `$HOME/.flai/bin` ahead of the checkout's `bin`, or drop the checkout's `bin` from PATH. That file is the operator's, and this story does not change it.
