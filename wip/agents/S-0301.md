# S-0301 flai upgrade consistently pulls an old template no matter what

## Context

`flai upgrade` keeps rendering an old template (1.0.18 while v1.0.60 is tagged). It has three causes:

- The cache clones each repo@ref once and never fetches it again, so `main` stays at its first clone.
- `upgrade.go` replaces `--ref` with the manifest's `template.ref` whenever `--template` is not given.
- An edited `template.version` in `system-flow.yaml` makes upgrade report "already at", and then write the old version back.

## Current state

All six tasks are done and committed on story/S-0301, synced with main. All four criteria are ticked. A fresh verifier runs the close-out before review.

S-0301's work, by area:

- **`--ref`:** it wins and is recorded.
- **Default version:** `flai new`, `import`, and `upgrade` take the newest release tag.
- **Edits to `system-flow.yaml`:** upgrade asks on an edit that disagrees with the newest, and refuses without a terminal. The version a project is at is the lock's.
- **Cache:** branch clones are fetched again.
- **Docs:** ADR-0103 and the docs say the same.

## Decisions

- 2026-10-06: The planner drafted T-1057, T-1060, T-1062, T-1064, T-1065, and T-1066 (TH-0209) while I wrote T-1078, T-1081, T-1084, and T-1086 for the same plan. I kept the planner's tasks and cancelled mine as duplicates.
- 2026-10-06: Two of the planner's assumptions are changed in the task bodies:
  - **A ref follows releases.** A ref that is empty, the template's default branch, or a version tag follows the template's releases, so it resolves to the newest tag. The config's default stays `main`. Every config and manifest written so far holds `main`, and changing the default to empty would leave every existing install on the branch, failing criterion 2.
  - **Upgrade asks only on an operator edit.** It asks only when `system-flow.yaml` differs from the lock (the operator edited it) and that differs from the newest tag. A recorded tag equal to the lock's is not a pin, so the next upgrade takes the newest without asking (criterion 3). The choices are the manifest's version, the newest, or change nothing. The lock is never a target.
  - Also, the version a project is at is the lock's, which fixes the "already at" revert (T-1064).
- 2026-10-06: Layers and waits:
  - **Layer 1:** T-1057 (`upgrade.go`, the `--ref` fix), T-1060 (`internal/template`, tags and refetch), and T-1062 (ADR and design). They share no path.
  - **Layer 2:** T-1064 waits for T-1057 (same lines of `upgrade.go`), T-1060 (calls `Latest`), and T-1062 (implements its ADR). T-1065 (`new.go`, `import.go`) waits for T-1060 and T-1062. It shares no path with T-1064.
  - **Layer 3:** T-1066, the docs and the regenerated reference, waits for T-1064 and T-1065.
- 2026-10-06: T-1064 and T-1065 ran in task worktrees, since both build `flai/cmd`. Each defined a method named `releaseRef`. I kept T-1065's, in `new.go`, and `upgrade.go` calls it for a `--ref`, normalising `1.0.60` to `v1.0.60`.
- 2026-10-06: When the template's tags cannot be listed, the commands differ. With no `--ref`, `flai upgrade` stops with an error naming `--ref`, since falling back to the manifest's ref could apply an older cached clone. `flai new` and `flai import` warn and use the configured ref.
- 2026-10-06: The task sub-agents' review found three more documents that described the old behaviour: `docs/operators/settings.md`, `docs/operators/runbooks/migrate.md`, and `docs/users/conventions.md`. I updated them, and also the `--ref` help of `new` and `import`.
- 2026-10-06: The story's touches are narrowed from the folder `flai/cmd` to the files its tasks name, as the planner proposed, so it no longer overlaps S-0299's `flai/cmd/guard.go`.
