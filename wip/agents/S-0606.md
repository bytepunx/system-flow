## Decisions

- The planner's five tasks stand, with their layers: layer 1 T-2615 (item store snapshot) and T-2616 (watcher slow tier), which wait for nothing and share no path; layer 2 T-2617 (`item.get`, after T-2615, whose snapshot it reads) and T-2618 (serve wiring, after T-2615 and T-2616, whose snapshot and slow tier it turns on), which share no path; layer 3 T-2619 (measure and record, after T-2617 and T-2618, since it measures both together). Each layer's two tasks run at once, one task sub-agent each.
- The snapshot is kept per item folder, not as one list per root: a change marks only its folder stale, and a stale folder refreshes through today's stat-and-compare path, so a change under `kanban/stories` never re-stats the archive. A folder whose refresh read a file within the racy window stays stale.
- A write made by a flai subprocess that flai serve itself runs (the host API's `runFlai`, the merge queue's, the formula scheduler's) marks the project root stale when the subprocess returns, so that serve's next read and the dashboard's read after a write see it without waiting 300 to 600 ms for the watcher. T-2617's touches gain `flai/internal/hostapi/writes.go`, T-2618's `flai/internal/serve/mergequeue.go` and `flai/internal/serve/formula_schedule.go`.
- The watcher callback tells the store of a path before it notifies the dashboard and before serve's looks run, so the reads either makes next are fresh.
- `item.get` keeps its get then list (T-2617): with the snapshot on, `Repo.Get` answers from the folder snapshots with no glob or stat, so a single-list finder in `hostapi` would only copy `Repo.Get`'s ID rules. The sub-agent's finder was taken out in review.
- flai serve marks a served root's item folders stale once a minute (T-2618), as a net for a change made before the watcher's first look, which the watcher never reports, and for two changes to an archive folder within one timestamp step. It costs one stat pass a minute.
- The host API marks the root stale after every flai write it runs, at the call sites in `methodsFrom` and `Publish` rather than in `runFlai`, so that a test's stub runner is covered too.
- T-2619 measured both targets of criterion 3 missed at load 110 to 172 (walk about 45 ms CPU, `item.get` 171 to 346 ms a call). Two tasks follow: T-2697 (layer 4) makes `item.get` copy only what it answers, through a new `workitem/view.go`, leaving `store.go` and `repo.go` as agreed with S-0600 and S-0599; T-2698 (layer 5, after T-2697, since it measures it) measures again and records it. The walk's choice is the operator's, asked on TH-0908.
- Conflicts with S-0598, S-0599, S-0600, S-0601, S-0603 in `server-performance.md` and `flai-cli.md` are settled section by section: S-0606 changes only its own cause 16 section and its own paragraphs, and whoever rebases second keeps both.
- TH-0908 answered 2026-11-09T07:32Z: the operator confirmed the orchestrator's recommendation of option 1. `wip/threads`, `wip/messages`, `design/digest`, `design/issues`, and `design/adrs` go on the watcher's slow tier too, flai's issue and ADR writes become atomic (write and rename), and criterion 3 stays as written. Three tasks follow: one makes the issue and ADR writes atomic (`flai/internal/issues`, `flai/internal/adr`); one, after it, puts the five folders in serve's `slowPaths` and tests that a flai issue write and an ADR write are seen at the next fast look; one, after that, measures the walk again and records the five folders and the reason under cause 16 and in `flai-cli.md`.
