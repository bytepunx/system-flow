# S-0101 Flai serve, dashboard, and mcp commands should work in parent folders without system-flow.yaml

## Context

In an empty folder `flai serve` already works (start, status, stop, actions, journal, import list). `flai dashboard` (every subcommand) and `flai mcp` (stdio, `http`, `start`, `status`, `token`) fail at once with "no system-flow.yaml found": each looks for the project first.

## Current state

Done; all three tasks and both criteria.

- T-0356: every `flai dashboard` subcommand works in a folder with no `system-flow.yaml` up the tree, using the host's configuration alone. `flai dashboard` there starts or reports the shared container and `flai serve`, registers the projects below the folder, names the folder for import, and records the dashboard (`serve/dashboards.json`) so that `flai serve` offers it repositories to import with no project served. `stop` stops the container once no project is left, and forgets the address.
- T-0357: `flai mcp` on stdio there serves every project below the folder (`workitem.FindProjects`, found again every 5 s). `inbox`, `wait_for_work`, and `wait_for_events` span them all and name each project. Every other tool takes `project`, needed only when there is more than one. With no project it starts and says so. HTTP MCP stays per project and says what to run instead.
- T-0358: [ADR-0036](../../design/adrs/0036-a-folder-that-is-not-a-project-is-served-whole-by-flai-mcp-and-flai-dashboard.md), the flai design, and the user and operator guides.

The real trial ran this branch's flai under a scratch configuration, with Docker on 127.0.0.1:5198 and a scratch work folder holding two projects and a plain git repository:

- **`flai mcp`, empty folder:** it started and answered `inbox` with no projects and `wait_for_work` waiting for a ready story.
- **`flai mcp`, parent folder:** `inbox` listed `alpha` and `beta`, and `wait_for_work` handed over `alpha`'s ready story. `item_get` without `project` listed the two, and with `project: beta` answered.
- **`flai dashboard` in the parent folder:** it started the container and `flai serve`, registered `alpha` and `beta`, and named the folder. The dashboard then listed `alpha`, `beta`, and `import-plain` (not imported), and served `beta`'s board.
- **Status and stop:** `flai dashboard status` there said "no project here" and what `flai serve` serves. Stopping in each project and then in the folder stopped the container and forgot the address, and `flai serve stop` ended the trial.

`scripts/flai-test.sh` (lint 0 issues), the template check, and `flai check --strict` are clean.

## Decisions
- The operator decided in conversation (2026-09-23):
  - `flai mcp` in a folder with no `system-flow.yaml` serves every system-flow project in the folder and below it. `inbox` and `wait_for_work` span them all, so an agent pulls from any of them, and the other tools take a project key.
  - `flai dashboard` in a folder with no `system-flow.yaml` starts the dashboard and `flai serve` without registering a project, and names that folder for import, as `flai serve import add .` would, saying so.
- Mine, found in the trial: `flai dashboard` in a folder also registers the system-flow projects below it. Without that, the projects `flai mcp` serves in the same folder would not be on the board until `flai dashboard` ran in each. It is the folder's counterpart of registering the project a command runs in, and ADR-0036 says so.
- `flai mcp` over HTTP stays per project: its state, token, and address live in a project's `.flai-cache`, and `flai serve` already keeps one per project (ADR-0034). Outside a project, `flai mcp http`, `start`, `status`, `stop`, and `token` say what to run instead.
- Each project keeps its own `wait_for_events` cursor in folder mode, so an agent moving between a project and its parent folder does not see changes twice. `wait_for_work`'s since-when, which threads count as new, is the folder's.
- In folder mode, `wait_for_work` looks at every project's threads before handing over a story to pull. Projects are taken in key order and stories in each project's pull order.
