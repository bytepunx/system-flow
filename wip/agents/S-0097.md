# S-0097 Agents should connect to the MCP and consistently monitor for ready tickets

## Context

An agent could already see ready stories and `can_pull` in `inbox`, and hold `wait_for_events`, which wakes on any change at all; whether to pull was left to the agent to work out, and the instructions said to pull "when nothing is in progress", which read board-wide is wrong once several agents share a board. An agent started by `flai serve` was told to end its session when nothing was left to pull.

## Current state

Done; all three tasks and all three criteria.

- T-0347: the `wait_for_work` MCP tool (`internal/mcpserver/work.go`) answers at once with one of three reasons:
  - `resume`: the agent's own story is still in progress, known by its narrative's `agent`.
  - `thread`: threads awaiting it were written to since `wait_for_work` last answered.
  - `pull`: the first ready story in pull order, when the in-progress limit leaves room.

  Otherwise it waits, re-deciding on every change to thread, kanban, and narrative files. A timeout carries `waiting_for` (`room` or `ready`).
- T-0348: the MCP instructions, the template's work-management and session-start conventions (copied above this repository's markers), `CLAUDE.md` and its template, this repository's project addition, the design, and the user guide all tell an idle agent to hold `wait_for_work` and pull what it names. An agent `flai serve` started now waits for the next story instead of ending its session.
- T-0349: tried against a real `flai mcp http` built from this branch, on a scratch project, with agents driven over HTTP:
  - With the limit full (another agent's story in progress) it timed out `waiting_for: room`. When that story went to review, it handed over the ready story 0.3 s later.
  - Two agents told to pull the same story: the second's `item_move` was refused ("already in-progress").
  - The agent that pulled it was sent back to it (`resume`).
  - With room and nothing ready it timed out `waiting_for: ready`, then handed over a story 0.3 s after it was made ready.

## Next steps
None: in review. The instructions reach agents once a flai with them is installed, since `.mcp.json` runs the installed `flai`. The template's conventions change with the next template release.

## Decisions
- A tool, not only instructions: an agent told "pull when there is room" still has to poll `inbox` or re-check after every `wait_for_events` wake. A tool that waits for the condition itself makes waiting for room, and for a ready story, one call.
- A thread wakes `wait_for_work` only when written to since it last answered. Otherwise a thread the agent cannot answer would wake it over and over; `inbox` still lists every thread awaiting it.
- The pull itself stays `item_move` (then `flai stream open`) rather than being done by `wait_for_work`: moving a story is the agent's decision, and the rule that refuses a second move to in-progress already settles two agents racing for one story.
- The session-start rule for an agent `flai serve` started changes from "end the session when nothing is left to pull" to "hold `wait_for_work`", following the story's third criterion. It stays consistent with `flai serve` starting one agent per project only while none is attending: a waiting agent is attending, and pulls the next story itself. A baseline convention change, made in the template (this repository's process for its conventions) and copied above the marker.
- `can_pull` is still the board-wide in-progress limit: "capacity" in the criteria is the board's WIP limit, shared by every agent.
