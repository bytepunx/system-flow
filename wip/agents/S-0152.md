# S-0152 Identify issues with responses from the server side

## Context

S-0152 (research, E-0012): instrument the server side so that slow board and page loads can be traced to their cause without the transport (WebSocket channel, MCP) in the numbers, then write stories for the fixes. Dashboard requests reach flai serve as JSON-RPC over the channel (`flai/internal/channel`) and are answered by `flai/internal/hostapi`; MCP tools by `flai/internal/mcpserver`. Work is in `.flai-cache/worktrees/S-0152` on `story/S-0152`.

## Current state

T-0544, T-0545, T-0546 done and committed on `story/S-0152`: `flai/internal/perf` times every channel and MCP request beneath its transport (`request answered` events, `FLAI_SLOW_REQUEST`), phases are marked in hostapi, mcpserver, and each git or flai process (`execx.Timed`), `flai hostapi --timing` and `FLAI_PPROF_ADDR` exist, and `design/system/server-performance.md` records the measurements and seven causes. T-0547 (stories for the causes) in progress.

## Next steps

2. Run `make flai-test` (all tiers and lint) and `flai check --strict`, tick the criteria, commit, move S-0152 to review.

## Decisions

- `FLAI_SLOW_REQUEST` (default 500ms) sets when a `request answered` event is info rather than debug; waits (`wait_for_work`, `wait_for_events`) are never slow. Profiles are offered on a loopback address only, since they name host paths.
- Measurements were taken with this branch's flai built to a scratch path and `flai hostapi --timing` and `flai mcp` over stdio against the main checkout, read-only; the operator's `flai serve` (installed 1.25.0) was not restarted or replaced.
- Instrumentation stays in flai (Go) and does not touch `flaiover/src`, which S-0153 has in progress: flaiover already logs each request's duration (pino, S-0032), so flaiover's duration minus flai's `request answered` duration is the transport.
