## Decisions

- Plan kept as the planner drafted it. Layers: [T-3451] (verify.Tiers' suite filter, waits for nothing); [T-3453] (the batch passes the suites, so it waits for T-3451's TierOptions field); [T-3456, T-3458] together (both describe T-3453's field and behaviour, and share no file).
- Refinement of T-3453's Work: a workflow file reads as the baseline's batch: all only when it gives none of ADR-0312's keys (Workflow.UsesSuiteKeys, D-0669). A file that gives some key but no verify_at.batch names no suite for the batch, so the batch runs no tier, as design/system/workflow.md § Suites a step needs and runs says ('a key it leaves out names nothing'). The planner's wording ('a workflow with no verify_at is the baseline') would have run every suite there.
- verify.TierOptions.Suites is a []string where nil keeps every tier (every existing caller, and all) and an empty non-nil list keeps none: the zero value runs what it ran before this story. The filter runs before cover, as SelectSuite does, so a tier of a listed suite that only a left-out tier covers runs itself.
- The batch's suites come from the main checkout's workflow (Repo.Flow()) when flai serve builds Deps, as the planner chose, so that no story in a batch changes what its own batch runs.
- T-3453's touches gained flai/internal/mergequeue/land_test.go: widening the Verifier type with the suites changes its stubs there.
- Each bisection step runs the suites its batch recorded in state.json, not what the workflow names later, so a step runs no suite its batch did not.
- flai queue's batch line ends ', suites all', ', suites behavior, smoke', or ', suites none', matching the line's 'step <step>' style; a batch recorded before S-0809 shows no suites.
