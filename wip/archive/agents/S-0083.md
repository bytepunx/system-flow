# S-0083 Logging in to the dashboard works from any address, not only localhost: the session cookie is not marked Secure over plain HTTP

## Context
Reported by the operator on 2026-09-20: from anything other than localhost, a correct token led back to the login screen. Reproduced before the story was written: `POST /api/login` answered 200 with a cookie marked `Secure` over plain HTTP, by `127.0.0.1` and by the host's LAN address alike.

## Current state
In review. Branch `story/S-0083`, two commits on main at 7736c61.

- **Cause**, read in adapter-node 5.5.7's handler: with no `PROTOCOL_HEADER` configured it builds every request's URL with `https`. `isSecure()` trusted that, so the session cookie was always `Secure`, and a browser keeps a `Secure` cookie over plain HTTP only on `localhost`.
- **Fix.** `flaiover/scheme.js`, beside `server.js`: every request leaves with exactly `http` or `https` in the protocol header, from what a proxy said (first value, only those two accepted), else from the socket. `server.js` sets `PROTOCOL_HEADER` before importing the handler (a dynamic import, because adapter-node reads it at load). `ORIGIN` still overrides. The Dockerfile copies `scheme.js`.
- **Login page.** After an accepted token it asks for `/api/agent`; a 401 there means the cookie was not kept, and the page says so, with the likely cause, and stays.
- **Tests.** The scheme for a plain, a TLS, and a forwarded request, odd header values, and another header name; the cookie's attributes through the login route for HTTP by two addresses, HTTPS, forwarded HTTPS, and a wrong token; the login page's three outcomes. 299 tests, flaiover gate and build clean; lint and check clean after the last edit.
- **Documents.** Operators: how the dashboard knows it is served over HTTPS and what a proxy must send. Design: the cause and the fix. I-0031.

Tried with the branch image in a scratch project (`loginlab`, container `flaiover-loginlab` on 4395 bound to every interface for the duration, throwaway token, all removed since):

- curl: the login cookie over plain HTTP by `127.0.0.1` and by 192.168.0.162 has no `Secure`; with `X-Forwarded-Proto: https` it has; a nonsense value for that header answers 200, not an error.
- A browser by the LAN address: the login link lands on the board, a reload stays logged in, a write from the board answers 200 and is on disk, the same write without the CSRF header is 403 as designed, the cookie is not visible to script, logout gives 401 afterwards, a wrong pasted token stays on the page, the right pasted token logs in. By `localhost`: the link logs in and leaves no token in the URL.
- The console's only errors were a 404 for `favicon.ico` (the app ships `favicon.svg`; older than this story, harmless) and the 403 and 401s I provoked.

Not tried: a real TLS-terminating proxy or tunnel in front (only the header, by curl); the new "cookie was not kept" message in a real browser, since nothing I can run makes a browser drop the cookie any more (it is a component test); Safari and Firefox (Chromium only); the operator's own dashboard, which keeps the defect until this is released and it is restarted.

## Decisions
- 2026-09-20: the scheme comes from `X-Forwarded-Proto`, filled in from the connection when absent, rather than from an `ORIGIN` the operator must set. `flai dashboard` has no way to pass an origin to the container, a dashboard is reached by several addresses at once (localhost, LAN, a tunnel), and one fixed origin would be wrong for all but one.
- 2026-09-20: the header is trusted from any client. Lying about it only marks the liar's own cookie `Secure`, which their browser then drops. Restricting it to known proxies would need a list of proxies the dashboard does not have.
- 2026-09-20: only `http` and `https` are let through, because adapter-node throws on a value containing a colon, per request, and a client could otherwise produce errors at will.
- 2026-09-20: the helper is its own file beside `server.js` so it can be tested without a build; `server.js` itself needs `build/handler.js` and is covered by the run in the lab.
