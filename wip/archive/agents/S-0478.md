# S-0478 flai components list, and the components examples check, take about 2.3s for flaiover since props.mjs resolves json props' types with typescript, up from 0.4s

## Context

## Decisions

- Remedy: cache the resolved skeletons, one of the two remedies I-0166 named. A watch program in `flai serve` would help only the Components page, not `flai check` or the CLI. The cache serves all three.
- The cache is checked from stamps, not file contents. It keys on the script's hash, the sub-project, where `typescript` resolves, and each typed component's typing and json props. It stamps every path TypeScript's `sys` looks at. A missing file is stamped by its folder's time: the 12,057 missing probes come from 164 folders, so the cache goes from 3.6 MB to 1.3 MB with no loss. A hit loads no `typescript`. Measured: cold 2.7s, warm 0.43s, with output byte-identical to the uncached script.
- The cache lives in `.flai-cache/component-props/<sub-project path>/`. It is not under `.flai-cache/components/<project>/<sub-project>/`, the harness folder, because a project named like a sub-project path could collide there. It holds one file per key and keeps the four used last. The examples check reads only the components that have examples, so it has another key than the Components page's list, and with a single file the two would evict each other.
- Plan: T-2068, the cache, its tests, and the docs, is layer 1. T-2069, closing I-0166, is layer 2, after T-2068, because the cache is what fixes the issue. The story is small, so I worked both myself with no task sub-agents.
- The new tests read flaiover's installed packages, so they are integration tests that skip under `-short`. The integration tier is `queue: true`, so I run it with `flai test --all` before review.
