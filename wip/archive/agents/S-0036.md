# S-0036 Dashboard authentication with a per-project token

## Context

## Current state
Complete. flai creates `.flai-cache/dashboard.token` (0600) on first run, mounts it read-only at `/run/secrets/flaiover_token` with `FLAIOVER_TOKEN_FILE`, prints a login link, and `flai dashboard token [--rotate]` prints or replaces it (rotation restarts a running container). flaiover reads the file at start-up, requires a bearer header or the HttpOnly session cookie for everything except `/_health`, `/_ready`, `/login`, `/api/login`, and the app bundle; `/metrics` opens only with `FLAIOVER_METRICS_PUBLIC=true`; cookie-backed writes need `X-Requested-With: flaiover`; unauthenticated page loads redirect to `/login`, API calls get a bare 401. `flai check` refuses a repository whose `.flai-cache/` is not ignored. Verified on the served build with curl (401, 303, 403, bearer 200, cookie 200, wrong token 401, metrics behind the token, token absent from logs and container env, mount read-only) and in a browser (fragment consumed, history rewritten, cookie invisible to script, logout then 401). Tests: 42 flaiover unit tests, flai command and check tests. Story in review.

## Decisions
- Sessions are the token itself in an HttpOnly cookie (30 days); there is no session store, and rotation ends every session because the compared value changes.
- Without a token file flaiover refuses to start; `FLAIOVER_AUTH=off` is honoured outside production only, for `pnpm dev` without flai. `scripts/flaiover-dev.sh` creates and uses the same file as the container.
- The login page and the app bundle are open so the SPA shell can render; data is what the token protects. A GET for a page without a session is a 303 to `/login?next=`, so a bookmarked URL still works after login.
- The unblock endpoint returns 500 for a flai rule refusal ("not blocked"); pre-existing, not authentication, left for a remediation item. A block and unblock were run on this story during the smoke, so its `blocked` history carries one short "auth smoke" interval.
