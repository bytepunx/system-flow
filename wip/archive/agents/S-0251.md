# S-0251 flai stream sync's trial merge blames a story for conflicts between main and another story's stale branch

## Context

I-0064: `trialMerge` runs two-argument `git merge-tree story/A story/B`, whose merge base is the older of the two branches' bases. A, just rebased onto main, carries everything main gained since B's base, so the trial merge reports main's changes against B's as conflicts of the pair A and B (S-0203's five paths, S-0225's `template/CHANGELOG.md`).

## Current state

T-0984 and T-0985 are done and committed on story/S-0251, synced onto main. `checkSync` keeps a trial merge's conflicting path only when both stories changed it (`changedByBoth`, `branchChanges`), three new `TestSync...` tests reproduce I-0064 and fail without the filter, the help, reference, design row, and users' guide say so, and I-0064 is closed.

The verifier's close-out passed every step up to the commit (gofmt, vet, golangci-lint, `go test -race ./...`, smoke, markdown lint) and found no breach of the criteria or the conventions. It stopped at commit only because it was given no message. Its bumps of I-0073, I-0076, and I-0078 are committed as the close-out, and the touches are widened to cover them. Both criteria are ticked.

## Decisions

- The fix (proposed from I-0064's instances, as the goal asks): a pair's conflicts are the trial merge's conflicting paths that both stories changed, each story's own changes being `git diff --name-only <main>...story/<id>`, so from its own merge base with main. A path only one story changed, the other side's change coming from main, is what main brought: the later story's rebase settles it, and it is not the pair's conflict. Both instances' paths are left out by this, and a path both stories changed is still reported. Rejected: merging the stale branch with main first and trial-merging against that tree, which needs a second merge-tree per pair and fails on the stale branch's own conflicts with main, which are not the pair's either.
- Known limit, left as it was: `branchChanges` keeps git's rename detection, as `outsideClaim` always had, so a branch that renamed a file names only its new path, and a conflict reported on the old path alone would be dropped. `--no-renames` would change what the outside-the-claim check reports, which is beyond I-0064.
- Plan: two layers. T-0984 (the code, its tests, and the help text with the generated reference) first; T-0985 (the design row, the users' guide bullet, and closing I-0064) after it, since it describes what T-0984 built. No path in common.
