# S-0186 The root page asks for the projects once per load

## Context

I-0033: the root page fetched `/api/projects` up to three times per load (layout `refresh()`, page `refresh()`, page `loadGlances()`), and concurrent calls appeared to be served one after another.

## Decisions

- The root page keeps its own `projectState.refresh()` on mount rather than relying on the layout's alone. On a full load the two share one request. When the page is reached by a client-side link, its call gives fresh glances rather than a list up to 30 s old.
- `refresh()` shares only a request in flight; it caches nothing after the answer. The polling callers (`SettingsPanel`, `ImportPrompt`) wait 500 ms between calls, so each of their calls makes a new request.
- The serial calls were fixed on the client (`fetch(..., { cache: 'no-store' })`), not the server. Measured: a `cache-control: no-store` response header does not release Chromium's cache lock. Other `api()` GETs are not changed here: no story claims them, and none was measured concurrent with itself.
- flai's release history lock, which `board.get` takes, is recorded in the design and not changed. The verifier showed that publishing holds it only for local git reads: `git ls-remote` runs before the lock is taken (`preview/push.go` `Publish`, `release/remote.go` `remoteTags`). So the 1.2 s `release.pending` in the serve log is not time a glance waits. My T-0657 log entry said otherwise.
- From the verifier's review: `refresh()` aborts its request after 15 s, because every caller meanwhile shares it. A request clears the shared slot only if the slot still holds it.
