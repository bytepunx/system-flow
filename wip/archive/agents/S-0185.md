## Decisions

- The values are recorded in `system-flow.lock.yaml` (`vars`), not `system-flow.yaml`: the lock is flai's own and is already rewritten by `flai new`, `flai upgrade`, and `--relock`, while the manifest is the template's rendering and human-edited. A refinement of ADR-0015's lock, so no new ADR.
- Upgrade resolves a variable from, in order: `--var`, the manifest's own field for the five standard variables, the lock's recorded value, the template's default. The manifest wins over the lock for the five because the operator may edit `name` and `description` there.
- `flai upgrade --var` for one of the five is refused, naming the manifest key to edit: a `--var` value would be overridden by the manifest at the next upgrade.
- `flai import` still writes no lock (unchanged); an imported project records its variables at its first `flai upgrade` or `--relock`.
- From the first verifier's review (S-0185 diff, 6 findings):
  - `flai import` now collects variables before it moves folders, so the I-0041 fix covers import too.
  - `--var` at the same version re-applies that version instead of being ignored.
  - Upgrade names each variable that took its default. This covers projects made before variables were recorded, which get defaults silently otherwise.
  - A required variable recorded empty takes a newer default.
  - Tests were added for the gaps. The remark about the commit split needed no change: the operator's prompt asks for a commit per task.
- TH-0045, the conflict with S-0179 in `design/issues/summary.md`: S-0179 lands first. At sync, I regenerate the summary with `flai issue summary` rather than narrow either story. TH-0048 (S-0184) is handled the same way.
- From the final verifier: `flai upgrade` now reads the lock after the "already at" return. `--relock` rewrites an unreadable lock with a warning instead of failing. Upgrade's JSON output does not list the defaulted variables; the text output does.
