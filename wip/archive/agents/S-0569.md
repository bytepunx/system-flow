# S-0569 TestServeSaysTheFlaiIsOlderThanTheProject and TestServeStartsADefinedRoleOnAnEventAndOnASchedule fail the close-out's integration tier on timing, on a branch that does not touch flai/internal/serve

## Context

What each task found (I-0247):

- T-2522: `TestWaitForEventsAcrossAFolder` and its two `wait_for_work` siblings in `folder_test.go` slept 150 ms after starting the wait, then changed the project. On a loaded host the change could land before the wait's catch-up, which answered `changed: []` (line 371). It could also land between catch-up and the hold's first fingerprint, so the hold never saw it and timed out (lines 362, 270). Before the fix, under `GOMAXPROCS=2 -race` beside 8 busy loops pinned to the same two CPUs, the three tests failed 4 of 90 runs. Each test now waits for the wait's first progress heartbeat, which `keepAlive` sends only after `hold` has taken its snapshot, and holds up to 30 s. Under the same load they then passed 90 of 90, the slowest in 9.4 s. The same sleep-then-change pattern is in `server_test.go` and `orchestrator_threads_test.go`, outside this story's touches, and they are left as they are.
- T-2525: `project.info` came back empty because `channeltest.Conn.Ask` returns the next message flai sends, which is not always its reply. Serve's version check writes the upgrade thread. On a loaded host, the watcher's `change` notification for that thread reached the dashboard before the reply. A notification has no result and no error, so the test printed `project.info: <nil>`. The fault is in the test, not in flai. The test now asks through `askProjectInfo` until an answer names the project, within 30 s. Its three 3-second log waits are now `waitForLog`, which fails naming what it waited for. Under a pinned load it failed 1 in 20 before the fix. After it, all three tests in the file passed 20 of 20.
- T-2529: `TestHostRunsServeAndTheMCPServersAndTakesThemWithIt` failed because the project's MCP server lost a port race. Its state was neither late nor stale. The host picks the first free port in 4243–4262, and the live host holds 13 of them. Concurrent runs of the test took the same port first. The loser exited with "address already in use", and the host restarted it on the same port. So the state came fresh, but with a PID the test was not waiting for. Four concurrent copies under a pinned load reproduced it in 2 of 12 runs. The test now gives the project a port the kernel picked, remembered in its cache, and checks that the server listens there. Its failure message names the last state, the host status, and the MCP log. After the fix, 12 of 12 passed at a host load average of 108. The host's habit of restarting on a port someone else holds is recorded as an issue of its own.
- T-2528: `TestServeStartsADefinedRoleOnAnEventAndOnASchedule` failed because it raced flai serve's start, not because the host was slow. Serve takes its watcher's first snapshot in a goroutine of its own, after its first looks. The test's move landed in between, about 20 ms after "project served". So the move was already in that snapshot and was never reported. Only serve's once-a-minute look queued the run, at 60.15 s, past `waitFor`'s 30 s. Under `GOMAXPROCS=2 -race` beside 4 busy loops pinned to the same two CPUs, the unchanged test failed 5 of 10. The test now writes probe files under `docs/` until the watcher reports one, and only then moves the story. It then passed 20 of 20, the slowest in 2.34 s. The window in serve is recorded as I-0273, and serve is unchanged. One caveat: `watcherReports` reads through `channeltest.Conn.Next`, which fails after 5 s with no message, so its own 30 s bound holds only while serve sends something every 5 s.
- T-2533: the six fixed tests, covering I-0247's four test names, ran together under `GOMAXPROCS=2 -race`, pinned with 6 busy loops to CPUs 20–23, 10 times each. All 60 runs passed, in 115 s. The host's 1-minute load average was 17–20, below the task's 40. The pinned CPUs were overloaded about threefold, which is heavier contention for these tests than the host figure shows. I-0247 is closed with what fixed each test.

## Decisions

- The planner's five tasks are kept as drafted, with one change: T-2528 now waits for T-2525. Both edit test files of the one package `flai/internal/serve`, so a half-done edit of one would break the other's build and stress runs.
- Layers: (1) T-2522 (`internal/mcpserver`), T-2525 (`internal/serve`), T-2529 (`cmd`), run together: no path or package in common; (2) T-2528, after T-2525; (3) T-2533, after all four, since it runs the four fixed tests together and closes I-0247.
- The tasks' stress runs (`GOMAXPROCS=2 go test -race -count=N -run <test>`) are run with `go test` directly, an exception to running tests only through `flai test`: they are the reproduction and measurement this remediation needs, and `flai test` takes no `-count`, `-run`, or `GOMAXPROCS`. The checks of each change still go through `flai test`.
- The CPU load beside a stress run is confined with `taskset` to the CPUs the test is pinned to, so it contends with the test and not with the other agents on the host (24 CPUs, load average about 40 at the start). Each task of layer 1 takes its own CPU pair.
- The two defects in flai's own code that the tasks found are recorded as issues and left unfixed: I-0271, the host's MCP port reuse, and I-0273, serve's watcher-snapshot window. Fixing them changes non-test code beyond this story's touches. The operator chooses at acceptance which of them become stories.
- T-2533's integration-tier run is the close-out's: the story changes `flai/`, so the close-out runs the integration tier. Running it once more inside T-2533 would only repeat a run of about 10 minutes.
