# S-0236 flai dashboard resolves the image from the signed digest list and runs it by digest

## Context

S-0233 verifies flai releases before install; S-0234 publishes `flaiover_<version>.digests` and its signature on each `flaiover/vX.Y.Z` GitHub release. This story makes `flai dashboard`, `check`, `upgrade`, `status`, and `versions` choose and run the image by digest from that signed list (ADR-0070). Design: `design/system/release-signing.md` § The digest list.

## Decisions

- Plan, reviewing the planner's eight tasks, in six layers, worked one task at a time: they are moderate and mostly build on each other.
  1. T-1239: `selfupgrade` exports `Find`, `FetchAsset`, `FetchSigned`, `VerifyBlob`, and `TrustedKeys`. `List` already lists any prefix with assets, so the task is the signed fetch, not the listing.
  2. T-1240: digest list parser and cache in `flai/internal/dashboard`. It now waits for T-1239: no exported blob verifier existed (`signedByOneOf` is unexported), so the list's verification needs T-1239's, and the new package imports the one T-1239 edits.
  3. T-1241 (resolver) and T-1242 (`versions` mark), each after T-1239 and T-1240; no path in common.
  4. T-1243 (`flai dashboard`, `status`, the restart record) after T-1241; T-1245 (Updates page) after T-1242.
  5. T-1244 (`check`, `upgrade`) after T-1243: both change `dashboard.go` and `dashboard_test.go`.
  6. T-1246 (documentation) after T-1244 and T-1245, the last behaviour it describes.
- The unverifiable mark on dashboard releases reuses `listedFlai`'s fields, `unverifiable`, `signature`, `reason`, so the Updates page mirrors `HostProcesses.svelte`, rather than the planner's suggested `deployable`.
- `flai dashboard versions` keeps listing `flaiover/v*` tags and joins them with GitHub releases, so a version from before signing, a tag with no release, is listed and marked rather than dropped.
- A tag that is neither `latest` nor a version, on the signed repository, is refused by the resolver: it cannot be on a signed list. Allowing it is S-0239's `dashboard.allow_unsigned`.
- On review of T-1241 and T-1242, three copies of the unknown-key-or-bad classification existed: `selfupgrade`, the resolver, and `versions`. They became one: `selfupgrade.VerifySigned`, which `verifiedSums` uses, and `dashboard.FetchList` on it, which the resolver and `versions` use. A failed download of a release's `cosign.pub` is now a download error, not a `bad` refusal, so the resolver falls back to its cache.
- `selfupgrade.Find` treats `latest` as the newest, so `flai self-upgrade --version latest` now installs the newest rather than refusing a tag `flai/vlatest`. Kept: it is harmless and reads as asked.
- T-1242 ran in a task worktree (`task/T-1242`) beside T-1241, since `flai/cmd` imports the package T-1241 was writing. Its two files were copied back, and the worktree and branch were removed.
- T-1243 left `TestDashboardUpgradePublishedDeploysAPublishedTag` failing, because it expected the by-tag start, and T-1244 was about to change it again. So T-1244's touches gained `dashboard_versions_test.go` and the watch files, and T-1244 fixed it. The branch was red between those two commits only.
- A resolve failure that is not a refusal says "nothing was pulled, started, or swapped", since `check` and `upgrade` share it with the start.
- T-1246 also covers the stale help text of `check`, `upgrade`, `restart`, and `versions`, and a line in `docs/operators/index.md` that read as if `dashboard.tag: latest` were a build of `main`. `--published`'s refusal no longer suggests a bare `--tag`, which the resolver refuses for the signed repository.
- The verifier's review, after the first close-out passed at 98e0f8d2, met all six criteria. Its one medium finding was fixed in T-1498: a restart record an older flai wrote names the signed repository by tag, and a restart pulled that tag unverified. Its minor findings were left as they are, for these reasons:
  - `dashboard.pick` repeats `selfupgrade.Find`'s choice. It does so because `Find` answers one untyped error for "unreachable" and "no such release", and the resolver must tell them apart to fall back to its cache.
  - `chooseDashboardImage`'s `build` parameter is redundant, since `--build` rewrites the image. It is kept as the explicit statement.
  - `versions` lists releases after tags, and a `--published` refusal fetches the chosen list twice. Both cost a request, not correctness.
  - `--published --repo` checks one repository while the resolver reads the default. The trusted key decides trust either way.
