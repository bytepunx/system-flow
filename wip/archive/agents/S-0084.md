# S-0084 One flai serve per repository: a second one steps back instead of taking the dashboard's connection

## Context

I-0029: an installed flai and a tree's own flai both served this very repository with the same agent credential, replacing each other on the dashboard every few seconds (457 times in 45 minutes); whichever held the connection at the moment answered with its own version, methods, and host actions, so `push.run` looked to be missing when it was not. `flai serve`'s existing "one per user" guarantee (ADR-0029) is kept only per configuration folder, so two processes under different configurations never see each other.

T-0337 and T-0338 were already done and merged to main before the cancellation; T-0339 and T-0340 were cancelled along with the story.

Work on T-0339 was in progress and stopped mid-task, per instruction, without committing: the worktree carries uncommitted, untested-together changes for the AgentHub.adopt() refuse-vs-evict policy (flaiover/src/lib/server/agent.ts and its test) and the matching client-side backoff on a refused/replaced close code (flai/internal/channel/channel.go and its test). All four files' own checks were green in isolation (go build/vet/test, gofmt, and the full flaiover lint/check/test:unit suite) before the cancellation notice arrived, but nothing was committed. Left as is, per "leave its branch and worktree alone."

## Next steps
None: the story is cancelled. Nothing further to do here.

## Decisions
- The claim is not a distributed lock (no `flock`, no atomic compare-and-swap across processes): a race between two processes claiming in the same instant is accepted, matching the level of rigor `flai serve`'s own pre-existing single-instance check already uses for one configuration. The loser's next tick, a second later, sees the winner's fresher claim and steps back — good enough for the failure mode this story is about (indefinite fighting), not a guarantee against a one-tick coincidence.
