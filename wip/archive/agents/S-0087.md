# S-0087 Moving a story to done merges it; a publish button on the board tags and pushes everything accumulated since the last one

## Context
The operator noticed releases coming out "too small": each accepted card tags and (when enabled) pushes its own component immediately, so a run of small stories cuts a run of small releases instead of one. Discussed with the operator before this story was written; two decisions came out of it (below). `flai accept`, `release.Compute`/`Apply`/`Tag`, and the already-existing `flai release <id>` (git.md's note that it "computes the bump, tags, and pushes once it exists" is stale — it computes and tags today) already separate merge from tag from push as distinct calls, so this is mostly extension, not rewrite.

## Current state
Branch `story/S-0087`, worktree `.flai-cache/worktrees/S-0087`. Tasks T-0313–T-0318.

- **T-0313 done** (`6771e32`): `acceptItem` (`flai/cmd/accept.go`) stops at merge, move to done, archive, and one plain commit — no bump, no tag, no push. Removed `--no-release`/`--deliver`/`--remote`/`--no-push`/`--no-publish` from `flai accept` and `flai move ... done`, since none of them mean anything once accept never releases. `hostapi`'s `accept.run` no longer conditionally appends `--no-push` and is no longer journalled as a push host action, since it never pushes either way now. `push.run` (`flai push --pending`) is untouched and still works: it finds the acceptance commit pending (the `chore: [ID] accept and archive` message pattern is unchanged) and pushes it, with zero tags now since nothing creates any until publish exists.
  - Rewrote `accept_research_test.go`'s premise: it used to test how accept computed a release plan differently for research/experiment/feature natures; since accept computes no plan at all now, kept only what's still meaningful — an experiment is still refused before merging, and research/feature land the same way any story does (merged, archived, committed, no tag, nothing pushed by accept alone).
  - flaiover's existing 311 tests pass unmodified against the new flai binary (the release-plan/tags/pushed fields it used to read are simply absent now, not erroring) — its board/review UI still needs updating for the new model, which is T-0316's job, not this one's.

- **T-0314 done** (`23225ca`): `release.Pending` computes one `PendingPlan` per component: every item a `chore: [ID] accept and archive` commit names since that component's last tag (or ever, with none), reusing `Compute()`'s per-item delivery-target/touched-file logic and taking the highest level found rather than one bump per item. A code component's boundary is its git tag; a template (never tagged locally by `Tag()`) uses the commit that set its current `template.yaml` version as a stand-in. Five new tests: mixed batch takes the highest level, a component with nothing since its tag is left out, an epic in the batch is major, an empty batch, research contributes nothing to the level even alongside items that do. Caught a test-fixture gap: the shared manifest fixture (`m` in `release_test.go`) had no `Layout`, so `Repo.Get()` silently looked in the wrong directory — fixed by giving it one, which only this task's tests needed (`Compute()` alone never touches a `Repo`).

- **T-0315 done** (`38e675c`): `flai release --pending` applies every `Pending()` plan (version files + one changelog entry per component naming every item it bundles), commits once, tags (skipping any that already exist), then pushes the branch and every tag together, three tags per push (`pending.Batches`, I-0026). Resumable: the tag-creation step is idempotent by existence check; the push step re-detects what's locally ahead of the remote (`pending.Detect`) rather than only what this run tagged, so a tag from a failed prior run is found and pushed, not dropped. Added as `--pending` on the existing `flai release <id>` command rather than a new command, since both compute-and-apply a release, just over a different scope. Three new cmd-level tests, including one that breaks the remote mid-publish and confirms a rerun finishes the push without recreating the tag.

## Decisions
- 2026-09-20 (with the operator, before the story was written): a batch's bump per component is the highest delivery type among everything unpublished for it since its last tag, not a sum or one bump per story. This is what actually fixes "too small".
- 2026-09-20 (with the operator): Publish always releases everything currently merged and unpublished; no per-card selection. To hold a merged story back from a release, don't move it to done yet — review is the only place left to delay a release.
