# S-0052 Work out whether and how a board move to done can push the acceptance

## Context
An acceptance from the board is committed and tagged locally and never pushed: `flai dashboard` gives the container the host's git identity and global excludes and no credential, by design, and the dashboard shows the `git push` command. The operator was surprised by this after S-0048 and S-0051, and since then the agent session has pushed `main` and the tags from the host after every board acceptance (ten times by now, plus the template's publish). This research story decides whether and how the push should be automated. The deliverable is a finding with one recommendation, the operator's decision recorded, and follow-up stories; nothing about pushing is built here. Work is in `.flai-cache/worktrees/S-0052` on `story/S-0052`.

## Current state
Done on `story/S-0052` in one commit (d650a1d), ready for review. Nothing about pushing was built, as the story requires.

The finding is `design/system/pushing-from-the-board.md`, listed in the design index. It covers three ways to push from inside the container (an HTTPS token given to a credential helper, a deploy key mounted read-only, the forwarded agent socket) and four with the container holding nothing (a host-side pending push, the agent session, a git hook, a standing not-pushed state), each under the same headings: what `flai dashboard` would do, which hosts, what it lets a token holder and a compromised container do, scope, rotation and revocation, and what a failed push looks like. Every claim is marked tried or not tried. Tried, in a scratch project against a scratch remote served over SSH and HTTP from a container, with throwaway keys and a throwaway password, all deleted afterwards: the no-credential baseline (the image has git and no SSH client); the token from the environment and from a read-only file; what the credential permits on an unprotected remote (force push, tag, tag delete); the deploy key with an SSH client added; OpenSSH's refusal of a user ID with no passwd entry; the agent socket, then emptied, then killed; a real `flai accept` in a credential-free container (`pushed: false`); that a post-commit hook runs inside the container; what the container can know offline about unpushed commits and tags; a shell prototype of the pending push; and that a hook written from the container runs on the host as the operator at the next push. Not tried: macOS, Windows, and GitHub itself; those statements cite GitHub's and Docker's documentation. Whether repository rules bind a deploy key was not established and the finding says so.

The operator's answers (2026-09-19, in the session, recommended answer first for each) are quoted in the finding: reached by them alone over a public tunnel; an unattended push is acceptable, for every acceptance; a standing not-pushed state, no retry. On the credential they first asked whether a key could be mounted from the host; answered, and asked again with a dedicated deploy key recommended, they chose their own SSH key, mounted.

Decision recorded as ADR-0026 (accepted, refines ADR-0018), because it changes what the container may be given and the security posture. The finding keeps its recommendation (opt-in credential, dedicated key, standing state) and says where the decision differs and that it is the operator's to make.

Follow-up stories under E-0006, each with goal, criteria, notes, and touches, in backlog and unplaced: S-0062 (the container pushes when given a key), S-0063 (standing not-pushed state, `inbox`, `flai push --pending`), S-0064 (the container cannot leave hooks or configuration that run on the host). The hook exposure is also recorded as I-0022. `docs/operators/index.md` is unchanged: what operators are told stays true until S-0062 is built. `flai check --strict` is clean.

The finding records both, and S-0062 builds "a key the operator names" with the safer choice documented first, so a dedicated key stays one path away.
- 2026-09-19, agent: the questions were asked in the session with the question tool rather than through a thread, which T-0170 allows; the operator was present.

## Open questions
- S-0064 should probably come before or with S-0062: a container holding a key is a better target, and the hook route is the other way to the operator's credentials. The order is the operator's.
- An HTTPS fine-grained token was the best scoped credential found and is not queued: this repository's remote is SSH. Worth a story if a project with an HTTPS remote asks.
