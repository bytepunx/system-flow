# S-0081 The dashboard can restart, upgrade, and stop itself through flai on the host

## Context
A host action, in the shape S-0078 (push) and S-0079 (agent) already established, for restarting, upgrading, and stopping the shared dashboard container from its own page. Off until the operator enables it.

## Current state
Branch `story/S-0081`, worktree `.flai-cache/worktrees/S-0081`. Tasks T-0322–T-0325, all done. All three acceptance criteria ticked. In review.

- **T-0322 done** (`bc43e15`): `flai dashboard restart`, `check`, and `upgrade`. `restart` cycles the container's process with whatever image it is already running — never a fresh pull, so a floating tag like `latest` cannot silently upgrade it. `check` pulls the configured image and reports whether it differs from what is running, changing nothing. `upgrade` does the same pull and, if it differs, starts the new image as a **temporary container on a loopback ephemeral port of its own** (`docker run -p 127.0.0.1::<port>`, discovered with `docker port`), polls its `/_health` for up to ~10s (20 attempts, 500ms apart — a count, not a wall-clock deadline, so a test can make every attempt instant), and only then stops the running container and starts the new image at the real name and port. If the temporary container never answers healthy, it is removed and the running container is never touched. The docker primitives this relies on were checked against real Docker on throwaway containers and images before the unit tests were written. A mutation check (making the health probe fake always succeed) confirmed the "never stopped until healthy" test would fail without the ordering the implementation uses.
- **T-0323 done** (`392840b`): `ActionDashboard` gates `dashboard.restart`/`upgrade`/`stop`; `dashboard.status` and `dashboard.check` are reads (matching `push.pending`'s precedent of a read that does real work). A new `spec.describe` field lets a host action report its own journal-outcome shape instead of assuming push/publish's `pushed`/`unpushed` fields. Found and fixed two real bugs surfaced by wiring this through `--json` for the first time: `dashboard stop --json` printed plain text, not JSON, when the container was not running; `dashboard upgrade`'s health-check failure was a `--json` **success** payload with `outcome:"failed"` inside it rather than a real non-zero exit. Fixed both.
- **Found and fixed along the way, I-0034**: three leftover references to S-0080's ADR (renumbered 0032→0033 while resolving that story's rebase conflict onto main, since S-0087 had already claimed 0032) were still pointing at the old number and a now-deleted file path — in files a *later* commit of that same rebase touched, after I'd already checked the renumbering. Recorded, fixed on this branch (not main directly — the standing rule is that main only changes through the accept flow), closed.
- **T-0324 done** (`13572d0`): `/api/dashboard` (`GET` = `dashboard.status`, `POST {action}` for `check`/`restart`/`upgrade`/`stop`); `/host` (`HostPanel.svelte`), linked from the header's host flai badge and the nav. A restart, or an upgrade that swaps, stops the very container answering the request that asked for it: the client races the fetch against a short client-side timeout and treats a network error or that timeout as "proceeding", then polls status until the dashboard answers again and reports whether the version changed.
- **T-0325 done** (`735702d`, `2a5f016`): tried end to end against real Docker, driven from the actual `/host` page with Playwright — not the CLI, not fakes. Two real, load-bearing bugs found and fixed this way, documented fully below and in Decisions/Open questions since they reshape the design's safety claim, not just a detail.
  1. **I-0035**: a restart, a swapping upgrade, or a last-project stop stops the container answering its own request. The request's context is a child of the WebSocket connection's; that connection dying — as a *direct effect of the command still running* — cancelled the context, and `exec.CommandContext` turned that into a SIGINT to the `flai` subprocess mid-operation. The first live restart left **no container running at all**: killed between `docker stop` and `docker run`. Fixed with `internal/hostapi`'s new `spec.detachTimeout`: these three writes now run with their own background context (restart 90s, upgrade 6m, stop 60s), not the request's. Verified fixed against the identical live scenario afterward.
  2. Two client-side bugs the same session surfaced: `HostPanel.svelte`'s `stop` handler used a plain `fetch` with no disconnect handling, so a genuine last-project stop threw an unhandled rejection instead of reporting anything (restart and upgrade already raced their fetch against a timeout; stop didn't); an upgrade that changed nothing still said "Reconnected", which is untrue — nothing was ever touched. Both fixed: `stop` now races the same way as the other two, and only `restart` (always disruptive) or an upgrade whose outcome is `"upgraded"` waits to reconnect.
  - All five of the task's checks passed against real Docker: restart while the page is open; check finding a genuine update without touching anything; a real upgrade swap (new container object, old one gone); an upgrade to an image that never serves `/_health`, the previous container proven untouched by ID before and after; stop behaving exactly like `flai dashboard stop`.
  - Isolation method changed from the plan: a nested `docker:dind` daemon's own network path hung on real image pulls (a classic dind bridge/MTU symptom — small control requests worked, blob transfers didn't) after ~10 minutes fighting it. Pivoted to a throwaway `flai` binary built from a **scratchpad copy** of this worktree's source with `sharedContainerName` renamed to `flaiover-s0325-scratch`; the real source was never touched (diffed to confirm before and after each rebuild). Ran against the host's real Docker daemon, alongside the operator's own `flaiover` container, distinguishable only by name — confirmed with `docker ps` before, during, and after that the operator's container and `flai serve` (PID 33376) were never touched. A local `registry:2` container supplied real, pullable image references for `check`/`upgrade` (both always pull; a purely local, unpushed tag fails exactly as a real misconfigured registry would, which is itself correct and was seen once before switching to the registry). Every scratch resource (registry, containers, images including a deliberately-broken one, the scratch `flai serve` by exact PID, temp dirs) confirmed gone afterward.

## Decisions
- 2026-09-22: the channel methods take no image or tag from the dashboard — `dashboard.check`/`dashboard.upgrade` always act on whatever this host's own configuration names, never a value the browser supplies. A dashboard token that could steer *what* the host pulls and runs, not just *whether* it does, is a materially different and larger grant than every other host action makes; the CLI's own `--tag` stays a local, operator-only convenience.
- 2026-09-22: `dashboard.upgrade`'s failure is a plain non-zero exit (an unmapped one, `channel.CodeInternal`), not a new mapped exit code like `Conflict`/`Refused`. It isn't a structured, recoverable condition the caller acts on differently — it's an ordinary command failure, and the existing generic `describe()`/`outcome()` machinery already handles "err != nil" correctly for any spec.
- 2026-09-22: blue-green over "stop, start, hope" — proven necessary, not just nicer, because the third acceptance criterion ("an upgrade that fails leaves the previous container running") is false under any design that stops the old container before the new one is confirmed working.
- 2026-09-22: `flai dashboard restart` reuses the exact ref (`.Config.Image`) the container is already running, resolved before stopping it, rather than the currently configured tag — so restarting is never accidentally an upgrade, even with a floating tag.
- 2026-09-22: T-0325's isolation switched from a nested Docker daemon to a throwaway-binary, real-daemon approach after the dind path proved unreliable (see Current state). The real worktree source was diffed against the patched scratchpad copy before every use to confirm it stayed identical to what will actually ship.
- 2026-09-22: **`dashboard.restart`, `dashboard.upgrade`, and `dashboard.stop` run their command with a background context (`spec.detachTimeout`), not the request's.** This is the one decision in this story that overrides something implicit in the existing host-actions design (ADR-0029's spec/`writeMethods` machinery, which ties every write's exec to the request context — correct for push/agent/accept, none of which can sever their own connection). Not written as a new ADR: it refines an implementation detail of ADR-0029's mechanism, not the decision ADR-0029 itself records (host actions, off until enabled, journalled); the living design (`dashboard-host-channel.md`) carries the new mechanism and the reason for it.

## Open questions
None. One thing worth the operator knowing, not a question: T-0325's real-Docker pass is what found both defects in this story; the unit and component tests, written first, did not and structurally could not, since they mock the very layer (a connection dying as a side effect of the command it carries) where the bug lived. This is not a reason to trust unit tests less in general — it is a reason this story's "tried end to end" task was worth doing exactly as designed, and a reminder that S-0082 (checks for a story in review, run on the host) is going to want the same kind of live check for anything that touches how the dashboard's own connection to flai behaves.
