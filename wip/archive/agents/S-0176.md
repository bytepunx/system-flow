# S-0176 The story's agent plans which tasks can run in parallel and works them with sub-agents

## Context

Experiment: the story's agent plans its tasks into layers by `after` and `touches`, and works each layer's tasks at once with sub-agents. This story is itself the first planned run: its tasks are worked by sub-agents, layer by layer, and its logs are the first evidence. Worktree: `.flai-cache/worktrees/S-0176`, branch `story/S-0176`.

## Decisions

- The plan, in layers. Layer 1: T-0677 (task `after`: workitem, check, cmd edit and task, MCP write tools, work-hierarchy, user guide) and T-0678 (conventions in template and here, `harness.Prompt`). No `after` between them; their `touches` do not overlap, though both are in the flai Go module, so a half-done edit in one can break the other's `go test` of a package that imports it. That interference is part of what layer 1 tests.
- Layer 2: T-0679 (task plan computed in flai, `flai show`, board card summary, move warning) after T-0677, because it reads a task's `after`, which T-0677 makes valid. T-0680 (flaiover page and card) after T-0677: it shows a task's `after`, and holding it to layer 2 lets that layer test one worktree per task (flai and flaiover touch nothing in common). T-0679 and T-0680 run at once against the JSON contract fixed in both tasks' notes (`plan` beside `item` and `children`; `tasks` on a story's board card), so the dashboard does not wait for the data.
- Layer 3: T-0681 (worktree evidence) after T-0679 and T-0680, because it reports what both layers did. T-0682 (measurement and recommendation) after T-0678, T-0679, T-0680, and T-0681, and TH-0059's answer.
- This story's own tasks do not carry `after` in main's `wip/`: the flai installed on the host (and the MCP server and dashboard that read main) refuses `after` on a task until a release with T-0677 is installed. The plan lives in these Decisions; the replays, which run with this branch's flai, carry it in their own clones.
- Layer 2's task worktrees are made by hand (`git worktree add -b task/T-nnnn ... story/S-0176`) rather than by the Agent tool's worktree isolation, so each starts from the story branch and not from the checkout the session started in.
- A cancelled task holds no task that waits for it and sits in no layer; a done task keeps its layer, so the plan does not shift as tasks finish (both layer 2 sub-agents asked; decided here, unlike a story's `after`, where a cancelled story keeps the hold: a cancelled task's work is not coming, and the story's agent replans).
- The replays run from scratch scripts under `/tmp/s0176`, not a script in `scripts/`: they need a helper that imports flai's internal harness to print the command `flai serve` would run, and they are this experiment's, not a tool the project keeps. agent-context.md describes the method so it can be repeated.
- Mode per layer: layer 1 shares the story's worktree; layer 2 gives each task its own worktree, made by hand, and the story's agent merges each back. This tests both of the fifth criterion's options in one story.
- Sub-agents for tasks were to be Claude Code forks, as the story asks, but the Agent tool refused `fork` in this headless session, so each task runs as a `general-purpose` sub-agent with a self-contained prompt: the task file, the story, the narrative's plan, the conventions to read, what it may touch, and the sibling working beside it. Handing a sub-agent an edit goes against `delegation.md` ("Never hand a sub-agent an edit"); the story is the operator's instruction to try it, so this story follows the story. The guard (ADR-0060) still refuses a sub-agent's flai writes and git history writes, so only this agent commits, moves items, and syncs.
