# S-0590 flai import writes no system-flow.lock.yaml, so the import formula's flai check --strict step fails on layout.lock

## Context

I-0302: `flai import` renders the template (`runImport`, `flai/cmd/import.go`) but saves no `system-flow.lock.yaml`, unlike `flai new` (`flai/cmd/new.go`). The import formula's first step, `flai check --strict`, then fails on `layout.lock`.

## Current state

S-0590 is in review. The close-out passed every step at 1b6fd21, integration and smoke included. `flai import` saves `system-flow.lock.yaml` from the render's hashes and commits it with `--commit` and `--formula`. `TestImportFormulaCommitsTheLockSoCheckFindsNoLayoutLock` reproduces I-0302. The docs say so, I-0302 is closed, and both criteria are ticked.

## Decisions

- Kept the planner's three tasks unchanged after checking the code: `runImport` renders with no `lock.Save` after it, and `commitImportPaths` stages no lock.
- Plan, three layers, one task each: T-2570 (the fix, its test, the help and reference) first; T-2571 (user guide and design) after T-2570, because it describes what T-2570 builds; T-2572 (close I-0302) after both, because the issue closes only once the fix and its documents are in. Nothing runs together.
- T-2571 names step 4 of flai-cli.md's Import flow, not step 6 as the task said: the code writes the lock right after the render, which is step 4.
- T-2572 does not run the integration tier on its own: the close-out runs it for a story that touches `flai/`, and review waits on that run, so running it twice would buy nothing.
- The lock records the render's hashes, so a file the import kept counts as the project's own: the next `flai upgrade` reports it as a conflict and does not overwrite it. Hashing the current files, as `upgrade.Relock` does, would let an upgrade overwrite it as baseline.
