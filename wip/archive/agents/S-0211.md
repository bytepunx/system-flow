# S-0211 Planning runs again when a story changes, when work ahead of it completes, and on a schedule

## Context

flai serve starts the planner only on the operator's word (ADR-0082). This story has it plan again on an edit, when work ahead completes or the order changes, and on a schedule, within the `plan` host action and the manifest's `planning.replan` and `planning.schedule` (ADR-0084).

## Decisions

- ADR-0084 records the design; it refines ADR-0082, whose "nothing starts it on a move or a timer" this story reverses on the operator's word in its criteria.
- The `plan` host action gates every trigger, the deterministic replan included: off, flai serve writes nothing on its own.
- `planning.replan`: `never` does nothing, `deterministic` (default) replays forecasts, `agent` replays and queues the planner for the stories whose delivery moved. Reading the criterion so, `never` and `deterministic` differ.
- An edit replans only a story already planned (a forecast or a value exists): "older than the edit" needs one to be older.
- Edits by `planner-*` agents are ignored, so a planner's own writes never queue it again. A `cost_of_delay` edit counts only when its inputs changed after the value.
- The deterministic replan keeps the story's own forecast duration and moves the delivery and basis, so the planner's adjusted duration is not undone; only stories with a forecast are written, one commit by `flai`.
- The schedule is a five-field cron in UTC or `daily` (00:00 UTC), parsed by flai's own small package, no dependency.
- Coalescing: the queue holds a story once, triggers merged; one queued planner at a time per project; the operator's runs bypass the queue.
- The trigger is a structured `- Trigger:` line on the activity entry, optional, rather than text in the summary.
- The replanner's watermark is in memory from serve's start; nothing is persisted.
- `flai touches` saved items without an edit notice, so a touches change reached no agent and could not trigger a replan; fixed in this story (`flai/cmd/touches.go`), since criterion 1 names touches.
- The replay's one commit holds the items it wrote and `wip/agents/index.md`, which `itemedit.Apply` rewrites, as `flai edit`'s own commit does.
- Each forecast the replay rewrites runs `flai check` twice through `itemedit.Apply`, about a second per story; stated in the design as a known cost rather than optimised without a measurement.
- Task sub-agents ran T-0822 and T-0825 in task worktrees, because a sibling's tests built what they changed; their diffs were applied to the story branch rather than merged, keeping its history linear.
- Plan, by layer (a task waits only for what it uses; tasks of one layer share no path):
  - Layer 1: T-0820 (cron package), T-0821 (planning replay), T-0822 (trigger on runs and activity entries). Independent packages.
  - Layer 2: T-0823 (manifest keys) waits for T-0820, whose parser validates the schedule.
  - Layer 3: T-0824 (serve replanner) waits for T-0820 to T-0823, which it uses; T-0825 (settings page) waits for T-0823 only and shares no path with T-0824, so they run together.
  - Layer 4: T-0826 (design and user docs) waits for T-0824 and T-0825, whose behavior it describes.
