# S-0272 An agent with an open question ends instead of waiting: flai serve restarts it on the answer, and wait_for_events keeps a timeout only for an agent with work in hand

## Context

E-0017 measured 650 turns across 38 story runs that woke from `wait_for_events` with nothing to report. flai serve already starts an agent again when the question it ended on is answered (`serve/agents.go`, `asking` and `answered`), so a story's agent whose only pending work is a question can end instead of holding. TH-0215: the operator accepted the planner's seven tasks in three layers, with criterion 4 kept here.

## Decisions

- Layers, as planned and accepted on TH-0215: layer 1 T-1087 (`mcpserver/server.go`), T-1090 (`harness`), T-1094 (conventions and template copies), T-1097 (ADR, `metrics.md`, `work-hierarchy.md`) share no path and wait for nothing. Layer 2: T-1101 waits for T-1097's definition, T-1104 for T-1087's `end`. Layer 3: T-1112 describes what all the others built.
- `wait_for_events` ends a story's agent by serve's own rule: `FLAI_STORY` names the story, a thread on it awaits an answer to this agent (its last entry is the agent's, or the agent opened it and a recommendation awaits confirmation), and no task of the story is in progress. The same rule as `serve.awaitsAnswer`, so that an agent told to end is one serve starts again on the answer. Events behind the cursor are reported first.
- The multi-project `wait_for_events` (`folder.go`) keeps its timeout: flai serve starts a story's agent with the single-project `flai mcp`, and `folder.go` is claimed by stories waiting to start.
- Empty wakes are recorded in the story's `usage` front matter (`usage.empty_wakes`), counted from its agents' logs when flai serve measures usage, and `flai stats` sums them from the items. That is how tokens already reach stats (ADR-0051), so the count survives the host's logs and archiving. Added `usage/usage.go`, `usage_test.go`, and `design/system/work-hierarchy.md` to the touches for it (ADR-0105).
