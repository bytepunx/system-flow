# S-0082 Checks for a story in review are run on the host and shown on the review page

## Context

A fifth host action (ADR-0029's pattern, after `push`, `agent`, and S-0081's `dashboard`): named commands, configured in the manifest or the host's own config, run in a story's worktree from the review page, with live output and a real cancel. Same shape as `dashboard.restart`/`upgrade`/`stop`: a detached `flai checks run` subprocess, state kept in a per-story file under `serveDir`, not tied to any one connection.

## Current state

All five tasks, including T-0330's real end-to-end verification, are done. All three acceptance criteria are ticked. S-0082 is ready to move to review.

- T-0326: `checks:` in the manifest and `flai serve checks set/timeout/clear/show`; the host's config wins over the manifest's when both name commands, never merged.
- T-0327: `flai checks run/status/cancel/tail`. Detach into a process group; `TerminateGroup`/`KillGroup` reach the whole tree, verified against a real spawned grandchild. Cancel is a sentinel file the run's own process watches, never a signal from a second process.
- T-0328: the `checks` host action gates `checks.run`/`checks.cancel`; `checks.status`/`checks.tail` are ungated reads. `checks.run`'s `detachTimeout` is 2 hours (a ceiling, not the real bound — that is `flai serve checks timeout`, enforced inside `flai checks run` itself), so a browser leaving the page mid-run cannot kill it via connection-context cancellation (S-0081's lesson, reused).
- T-0329: `/api/items/[id]/checks` (GET `checks.status` + `checks_enabled`; POST `run`/`cancel`) and `/api/items/[id]/checks/tail` (NDJSON, reusing `/accept`'s pattern exactly). A Checks section on `Review.svelte`, gated the way `HostPanel.svelte` gates its own buttons; while a run is active it polls `checks.status` and drives the tail endpoint in a loop, stopping itself once `running` is false; a page opened after the run ended still shows the outcome and duration.
- T-0330: real Playwright verification against a scratch project, scratch `flai serve`, and a scratch flaiover dev server (no Docker, hand-written registry files) confirmed all five behaviours for real: live output, a cancel that reaches a spawned grandchild, a finished run's outcome/duration surviving a page revisit, a real timeout, and a refused concurrent run. No bugs found; no code changes needed.

## Next steps
1. Move S-0082 to review; `flai check --strict` and `scripts/lint-md.sh` clean in the main checkout first.

## Decisions

- No new ADR: this is the fifth instance of ADR-0029's host-actions pattern, not a new architectural decision, consistent with how S-0081's `dashboard` action also needed none.
- `flai checks run` blocks until the whole sequence ends, the same shape `dashboard upgrade` already uses; the review page does not wait on that response for its own UI — it races the request against a short wait and falls back to polling `checks.status` and driving the tail loop, the same shape `HostPanel.svelte`'s own restart/upgrade already uses for a slow action that may or may not answer quickly.
