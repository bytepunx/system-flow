## Decisions

- Plan, in two layers. Layer 1 is T-0727 (`flai/cmd/release.go`, `flai/internal/release/remote.go` and its test, a new `flai/cmd/release_moved_test.go`, the generated reference) and T-0728 (the two `work-management.md` copies). Layer 2 is T-0729 (the design and user guide), which waits for T-0727 because it describes T-0727's behaviour.
- Criterion 3 asks whether flai names the tags or deletes them. flai deletes them itself, and only release tags (`<component>/vX.Y.Z` of a code component) of the push batches that did not reach the remote. It decides that the remote moved by asking the remote again after the failed push, past the kept answer. Any other push failure keeps its tags, so a rerun resumes as before (S-0087).
- Every push batch goes with `--atomic`. Without it git pushes the tags of a batch whose branch the remote refuses, which would leave on the remote the tags flai deletes here. Tags of an earlier tags-only batch (more than three tags, I-0026) did reach the remote and may already have started a release workflow, so flai keeps them, names them, and says to merge rather than rebase, so the commits they tag stay in history.
- T-0727's sub-agent added `release.CheckRemoteAfresh` (drops the kept answer for the root) and `release.IsReleaseTag`. It treats a failed push as "moved" only when the push carried commits and the fresh check finds the branch ahead. I reviewed the diff and the tests (a pre-push hook moves the remote mid-push), and they pass. Left out: `flai push --pending` (`preview.Push`) still pushes without `--atomic` and deletes nothing. It is the operator's tool outside the workflow (ADR-0067), so it is a candidate follow-up rather than this story's scope.
- T-0729's sub-agent wrote the recovery into `pushing-from-the-board.md` (in the current-state note), `docs/users/flai.md`, and the `release --pending` row of `flai-cli.md`. I reviewed it and committed it as is.
- The close-out was held for S-0198 rather than narrowing either story's touches. S-0198's agent was waiting for S-0242 (TH-0076). The designer chose on TH-0077 that S-0242 goes to review first with the `wip.overlap` warnings standing. That departs from "move to review only when the close-out ends clean" on the operator's instruction.
- (Earlier:) The close-out is held for S-0198 rather than narrowing either story's touches. Both edit the same three docs, and the convention says overlapping stories wait. Recorded on TH-0073.
