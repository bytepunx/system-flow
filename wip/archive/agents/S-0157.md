# S-0157 Pending releases are worked out without starting a git process per accepted item

## Context

Cause 2 of `design/system/server-performance.md`: every board works out pending releases with 25 git processes (75 ms). The story asks for under 15 ms with at most 3 git processes, and `PendingIDs` answering exactly as today.

Measured on this repository before starting (one process each, warm): `show-ref --head --tags -d` 4.7 ms, a subjects-and-messages `git log` of the whole history (706 commits) 11.5 ms, the same with `--name-only` 155 ms, the template's `git log -S` 9 to 14 ms, bare process start about 3.4 ms. No single cold read fits 15 ms, so the history is kept between calls and the key check is one `show-ref`.

## Decisions

- `git diff-tree --stdin` and `git log --name-only --no-renames` give the same files for every commit of this repository, its two merges (no files from either) and the root included: checked over all 706 commits. Files of a commit are read once by either and kept by hash.
- Commit per task, as the operator's start instruction says, rather than only when the story lands (`git.md`): the operator's instruction wins.
- A cold read (first look after `flai serve` or `flai mcp` starts, and every one-shot `flai board`) takes four git processes: `show-ref`, a whole-history `git log` of messages, the template's `git log -S`, and one `diff-tree --stdin`. No single cold read fits 15 ms on this repository (the history log alone is 11 ms), so the criterion is met by the kept history: one process while HEAD and the tags are unchanged, two or three after an acceptance or a publish.
- `Pending` with a manifest that names no project returns nothing without asking git, as before (the mcpserver fixtures have none).
- The per-process implementation lives on in `history_test.go` as the reference; `componentBoundary` and `acceptedIDsIn` moved there, as nothing else uses them.
