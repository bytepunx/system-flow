# S-0392 A project chooses local or pull-request acceptance in system-flow.yaml, and flai reaches its GitHub remote through a forge contract with a token the host names

## Context

First story of E-0021: the `acceptance` setting in the manifest, the forge contract in `flai/internal/forge` with a GitHub REST adapter, the host's forge token variable, `flai forge check`, and a gated integration test. Nothing opens or merges a pull request yet.

## Current state

In review. All seven tasks done and all six criteria ticked. The close-out passed every step at 2cf21471: check, unit, integration, and smoke tiers. It recorded I-0161, the components.examples warnings outside the story, which come from svelte not being installed in flaiover.

## Next steps

1. The operator reviews and accepts S-0392.
2. Someone with a branch that has an open pull request can run the forge integration test with FLAI_FORGE_TEST_HEAD to read real checks and reviews.

## Decisions

- **Plan, the planner's kept.** Layer 1: T-1602 (manifest), T-1603 (forge package), T-1604 (host config and `flai serve forge`), T-1605 (ADR), with no path in common. Layer 2: T-1606 (`flai forge check`) waits for T-1602, T-1603, and T-1604, whose setting, contract, and token variable it reads; T-1607 (integration test) waits for T-1603, whose adapter it drives. Layer 3: T-1608 (docs) waits for T-1605 and T-1606, whose decision and command it describes.
- **T-1604 touches `flai/cmd/serve.go` too.** The `flai serve` subcommands are registered there.
- **T-1605 written by the story's agent after layer 1.** The ADR records the shapes the code took, so it follows the code rather than running beside it.
- **The host's forge entries are a top-level `forges` map in the configuration, keyed by forge.** `flai serve forge` is not under `flai serve agent`, so the entry sits beside `agent.providers` rather than inside it.
- **The forge is bound to one repository when it is made.** The contract's calls take a branch or a pull request, never an owner and a name, so a GitLab adapter can hold a project path instead.
- **The token is read through a function at each call.** The adapter never holds it, so it is read only when flai calls the forge.
- **An unknown acceptance value is refused at load, not only reported by `flai check`.** The criterion asks for validation at load, and a typing error must not let a project that chose `pull-request` merge locally. The cost, every command stopping until the value is fixed by hand, is in ADR-0165's consequences.
- **Reviewed and kept from the task sub-agents.**
  - T-1603: a skipped or neutral check counts as passed, as GitHub counts a required check; `ErrForbidden` beside the errors asked for; rulesets and classic protection both read, 403 or 404 on either meaning none; paging stays on the API's host so the token goes nowhere else.
  - T-1604: `config` reuses `manifest.ForgeGitHub` and a new `manifest.IsEnvName` rather than copies of them, changed in review.
  - T-1606: a package-level `githubAPIBase` is the test seam, not an environment variable a user would see; only `owner/name` is printed, never the remote URL.
  - T-1607: read-only against a real repository; it never opens, updates, or merges a pull request.
- **Checked against the real repository once.** The integration test and `flai forge check` ran against `bytepunx/system-flow` with `GITHUB_TOKEN` taken from `gh auth token` for the one run, never printed: read yes, push yes. The integration test was run with `go test -run` by hand, since it needs variables `flai test` does not set.
