# S-0072 flai on the host dials the dashboard and the two speak JSON-RPC: the channel and nothing else

## Context
First story after S-0071's finding and ADR-0029 (both still in review on `story/S-0071` when this was pulled; read them there). Builds the channel only: `flai serve` on the host dials the dashboard's agent endpoint with a WebSocket, JSON-RPC 2.0, mutual proof of a credential, pings, reconnection, status on both sides, one method `project.info`. The clone stays mounted and the dashboard behaves as before. The operator moved it to ready while I held `wait_for_events`.

Constraints: nothing under `~/.flai` (flai's home for serve state is the directory of the resolved config file, so tests and this repository use `.flai-cache`); never the operator's running dashboard (scratch containers on other names and ports); stop scratch processes by PID or container name (I-0025).

## Current state
All five tasks done; six commits on `story/S-0072` (6be39e7 Go peer, c94dfa5 flai serve, a9ecc88 flaiover endpoint and hub, e77fd42 flai dashboard integration, 95d815d documentation and two small fixes). `make flai-test`, `make flaiover-test` (297), and `make flaiover-build` pass; flai builds for linux, darwin, and windows. In review, waiting for the operator.

Tried end to end on this host (WSL2, Docker Engine) with a scratch project that had its own flai home, a locally built image (`flaiover:s72`) on port 4396, and `flai serve` started by `flai dashboard`: connected in the same second the server listened; `/api/agent` answered `project.info` over the channel; `flai serve status` and `flai dashboard status` agreed; the board and item pages still served from the mount, with and without a flai connected; after `docker restart` the connection was back 434 ms after the command returned; `flai serve` frozen with SIGSTOP (by PID) was marked not connected after 10 s with 5 s pings, which is why the ping is now 4 s (the mechanism is unit tested on both sides; the 4 s value was not measured again end to end); back 1 s after SIGCONT; killed by PID, the state file was removed and status said not running; `flai serve start` brought it back and a second start said it was already running; the header showed connected, then not connected with the command in its tooltip, in a real browser. `flai dashboard stop` unregistered the project. Everything was removed; the operator's dashboard was not touched (Up throughout).

Not tried: macOS and Windows with Docker Desktop; a new flai against the published 0.19.1 image (reasoned: the old server has no upgrade handler, the dial fails, `flai serve` retries quietly and status says why).

## Decisions
- 2026-09-20: flai's "home" for serve is the folder of the resolved config file, not a fixed `~/.flai`: tests and this repository (whose `FLAI_CONFIG` is in `.flai-cache`) then never touch the operator's home, which the standing constraint forbids me to write. The cost: two configs mean two `flai serve` processes. Documented.
- 2026-09-20: with the clone still mounted, the container could rewrite `flai serve`'s registry when it lives in the clone, and point flai at another root or dashboard. The registry folder and the credential are therefore added to ADR-0027's read-only mounts.
- 2026-09-20: `flai dashboard stop` unregisters the project, so `flai serve` does not dial a dead port forever.
- 2026-09-20: `server.js` force-closes connections five seconds after SIGTERM. adapter-node's own entry waits for them, which is how the operator's dashboard stayed "Up" without listening in I-0025.
- 2026-09-20: documents name ADR-0029 and S-0071's finding in words, not links, because they were not on main when this was written.
- 2026-09-20: the credential never travels. flai dials without it; `hello` carries flai's nonce, the dashboard answers with its nonce and HMAC(key, "dashboard|c|s"), flai answers with HMAC(key, "flai|s|c"). A flai that dials the wrong port gives nothing away, and the dashboard serves nothing before the second proof.
- 2026-09-20: until S-0080 there is one container per project, so `flai serve` holds one connection per registered project, each with that project's credential.
