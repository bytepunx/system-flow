## Decisions

- The planner's tasks stand unchanged: each maps to one instance of I-0380, and the fifth documents them and closes the issue.
- Layers: layer 1 is T-3595, T-3596, T-3597, T-3598, which share no path and run at once; layer 2 is T-3599, which waits for all four because it documents the blocker name, the queue kind, the refusal text, and the check finding they choose, and closes I-0380 only once all four are done.
- Layer 1 shares the story's worktree rather than one worktree per task: the four change different packages. T-3595 and T-3598 both add test files in flai/cmd, so each sub-agent prefixes its test helpers with its own task's subject to avoid the name collisions D-style parallel tasks met before.
- LimitedColumns and DefaultWIPLimits are read only by workitem's own tests (boardview_test.go, board_update_test.go), so retiring them in T-3598 touches no other task's files.
- Review of T-3595: while the merge queue batches, the operator's own acceptance would have enqueued a story that changes the workflow file, and the queue now refuses it as ineligible. AcceptOptions.LandsByHand, set by preview.ChangesWorkflowFile in flai accept, keeps Enqueues() false, so the operator lands such a story by hand. ADR-0221 still asks for a verify at its head. A test covers it. The same gap for protected paths (ADR-0106) predates this story and is left alone.
- Review of T-3595: the dry run printed 'OperatorOnly: ' with an empty list when only the workflow file changes. It now prints the sentence alone.
- Review of T-3597: Board.Save writes only the limited states' names, so a limit wip/kanban/board.md keys by an alias was dropped silently. LoadBoard now moves such a limit under the state's name, since ADR-0301 §6 says every write names the current state. A limit given under the name wins. A test is in boardview_test.go. board.wip-state reports the key only when it names no limited state.
- T-3597's scope choice: a story-scoped check leaves board.wip-state out, as ADR-0133 does for board.wip-limit. A story that changes wip/kanban/board.md sees the finding as inside it. A story that changes the workflow file keeps it as a note outside, which its close-out records in an issue. Inside, it would fail a close-out on a line of main's board that the story cannot remove. Dropped, it would hide the limit the next board write will lose.
- The queue reads the workflow file's change from the story's last passing verify (its Paths), not from git, so the queue's git does not grow with the stories in review (S-0698). The acceptance itself reads the whole diff, which catches a branch that deletes the file.
- The dashboard's Review.svelte shows operator_only only beside a protected path, so the review page does not yet show the workflow-file case. That needs a flaiover change outside this story; it is recorded as an issue.
