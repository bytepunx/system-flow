# S-0181 The host's flai says when it is older than the tree it serves, and an older flai reads newer work items

## Context

The host's flai lags the tree whenever a release is accepted and not installed: it acted on rules it did not have (I-0049) and refused the tree on unknown front-matter fields (I-0051). The story makes listings tolerant, adds `flai.minimum` to the manifest, and has serve, the MCP inbox, and the dashboard's host badge say when the host's flai is behind.

## Current state

Done: every task is done and every criterion checked. Six commits on `story/S-0181` (393af98, ed36434, 8fc5f04, d9c2669, d5b35c8, d03cc0c). A fresh verifier found all six criteria met and asked for one fix (a misplaced doc comment in `check.go`) and three small ones (RaiseMinimum reading any git error as a change, an untested folder-mode log, a misplaced settings row), all fixed in d03cc0c. It also found that publishing S-0181 itself would have raised the minimum, because the fields file is new: a file the previous tag lacked now raises nothing. Lint, all Go tiers, the flaiover suite, the markdown lint, and the install test pass. The smoke tier's `flai check --strict` warns only on the main checkout's `wip/`: `wip.overlap` with S-0189 (also in progress), `threads.archived` on TH-0032, and `markdown.MD029` in S-0189's TH-0057. None of those is this branch's to fix (TH-0056 asks about exactly this).

## Next steps

1. The operator reviews and accepts S-0181. The first flai release after it publishes `front-matter-fields.txt` with no raise; the next release that changes it raises `flai.minimum`.

## Decisions

- Unknown front-matter keys are kept verbatim as `workitem.Field` (the key's lines up to the next top-level key) and appended by `Marshal`, rather than refusing writes: the criterion says no write drops a field, and keeping them lets an older flai still move items.
- The listing warning goes through `slog.Default()`, which the CLI root now sets to its logger, and is deduplicated per file and field set per process, so `flai serve` and `flai mcp` (which list often) say it once.
- The minimum is checked in `manifest.Load`, the one place every command, `flai serve` (`Entry.Unavailable`), hostapi, and `workitem.Open` pass through, so it applies before any item is read. A dev build is never below it.
- "A release that adds a front-matter field raises it" is mechanical: `flai/internal/workitem/front-matter-fields.txt` lists the fields, a test keeps it equal to the code, and `release.RaiseMinimum` raises `flai.minimum` in the publish commit when that file changed since the previous `flai/v*` tag. This repository's manifest gets no minimum now: this story adds no field.
- `system-flow.yaml` is flai-owned beyond name/description/dashboard (CLAUDE.md); `flai.minimum` is written only by the release tooling, listed among the keys flai owns in project-manifest.md.
- Raising the minimum writes a version whose binaries GoReleaser builds only after the tag is pushed, so a host below it stops on the project until it can upgrade. The verifier asked whether that is acceptable. Kept, as the criterion asks, with a publish-time warning (`flai.minimum raised: … upgrade the host's flai once the release's binaries are built`) and a note in the operator guide. Any change to the fields file raises it, a removed field too, which is conservative.
- `flai serve` warns when it starts serving a project, not when a release lands while it runs; the inbox and the badge ask again every minute, so they follow a release.
- Out of scope, as the story's notes allow: upgrading the host automatically after a publish. The template's `template.yaml` `min_flai` (printed, not enforced) is a different thing and was left alone.
- Went to review although the close-out did not end clean. `scripts/close-out.sh S-0181` passed lint and every test tier, then stopped at `flai check --strict` on 0 errors and 14 warnings, none from this branch: 10 `wip.overlap` with S-0189 (also in progress, touching the same packages; the touches are true, so narrowing them only to clear the check would hide a real overlap), `item.archive` on E-0013 and E-0014 (moved to done by the operator at 11:02, not yet archived), `threads.archived` on TH-0032, and `markdown.MD029` in S-0189's TH-0057. The worktree had nothing left to commit. S-0181 goes to review with these recorded, as S-0187 did; TH-0056 asks the designer whether such warnings should stop a close-out.
