# S-0233 flai self-upgrade, flai host upgrade, and install.sh verify the release's signature before installing it

## Context

S-0233 makes `flai self-upgrade`, `flai host upgrade`, and `install.sh` verify `checksums.txt.sig` with the release key before they install a release (ADR-0070). S-0232 put the key in `flai/internal/buildinfo/cosign.pub` and signs `checksums.txt` in `release-flai.yml`.

## Current state

S-0233 is ready for review. All six tasks are done, and the close-out passed every step, integration and smoke included. `scripts/install-published-test.sh` passed against the latest published release, 1.44.0, which is signed. All six criteria are ticked. I-0142 records the listing's cost per signed release.

## Next steps

1. The operator reviews S-0233 and accepts it, or sends it back.
2. At release, say in the notes that older flais install the release that brings this check without verifying it, and that every upgrade after it is verified.

## Decisions

- Kept the planner's five tasks and their plan, in three layers:
  - Layer 1: T-1226 (Go verification in `selfupgrade`) and T-1227 (`install.sh`). They share no path and run together.
  - Layer 2: T-1228 (the mark in `--list` and `host versions`) waits for T-1226, because it uses T-1226's verification and changes the same files.
  - Layer 3: T-1229 (Updates page) waits for T-1228, whose JSON field it reads. T-1230 (docs) waits for T-1227 and T-1228, because it describes what they built and regenerates the reference from T-1228's help text. The two share no path and run together.
- Added `design/system/release-signing.md` to T-1230's touches. Its section "How a release is verified before it is installed" describes the check this story changes.
- An unknown key is told apart from a bad signature by the `cosign.pub` each release publishes. When the signature verifies with that key and no embedded key matches it, the key is unknown. When it verifies with neither, the signature is bad.
- `install.sh` decodes the base64 signature that cosign writes with `openssl base64 -d -A`. That needs nothing beyond `openssl`, which the check already requires.
- Shared `docs/users/flaiover.md` with S-0359 on MS-0069, and `docs/users/flaiover.md` and `flai/cmd/host.go` with S-0237 on MS-0071. S-0233 changes only the Updates page's flai release list, and `host upgrade` and `host versions` in `host.go`.

- Added T-1464 after T-1228, because T-1226 and T-1227 left the smoke tier failing. The local release server served no signature, and `bin/flai` trusts only the embedded key. T-1464 waits for T-1228, since both change `signature.go`. It ran in layer 3 beside T-1229 and T-1230, with no path in common.
- A test build may trust one more key, set only through the linker's `-X` flag (`buildinfo.testReleaseKey`). No release build sets it, and a test checks `.goreleaser.yaml`. selfupgrade trusts it beside the release key, but release stamps never do. The alternative, an environment variable, would let anyone who can set the environment add a trusted key.
- A failed download while a list checks signatures fails the list. A release that could not be checked is never marked as one that cannot be verified.
- Recorded I-0142 rather than caching signature checks in this story. The listing costs two downloads per signed release, which is cheap today with two signed releases, and grows with each release.
- Corrected the sentence in `release-signing.md` "How flai is released" that said nothing is signed. I told S-0237 on MS-0071.
