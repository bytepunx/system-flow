# S-0095 Multiple projects can be managed by a single flai serve process

## Context

S-0080 already let one dashboard serve several projects: `AgentRegistry` routes each flai connection to a per-project hub, `?project=` routes each request, and a switcher appeared once a second project connected, reloading the page on a pick. What was missing for this story: the active project was not named in the top bar with one project, a switch was a full reload, and live changes were wired to whichever hub a `Repo` resolved when it first started watching, so the default `Repo` (and the inbox webhook) at startup bound to a placeholder that never connects.

## Current state

Done; all three tasks and both criteria.

- T-0341: each `Repo` is bound to its own project key for its asks and its watcher, which listens at the registry (now re-emitting every hub's events with the key).
- T-0342: the switcher always names the active project; a pick remounts the page in place (`{#key projectState.current}` in the layout), which reopens its event stream for the new project; the inbox and host badges restart for it; nav links carry `?project=`; the list is re-asked every 30s and on focus.
- T-0343: tried for real with this tree's dashboard (vite dev on :5195), one scratch `flai serve` under its own configuration, and two, then three, scratch projects, in a real browser. The switcher listed both projects. Picking Alpha showed Alpha's overview in place. On Alpha's board a CLI move in Alpha appeared live. Switching to Beta on the board showed Beta's board in place. A CLI move in each project then showed only Beta's on Beta's board. Switching back to Alpha showed the move made meanwhile. A third project registered while the page was open joined the switcher without a reload. The trial found one more thing, fixed: with several projects and none chosen, the header said "No flai on the host is connected" while two were.

## Next steps
None: in review.

## Decisions
- Pages are remounted on a switch rather than each taught to react to the project: every page loads in `onMount` and opens its own `EventSource`, so a keyed remount is one change in the layout that covers every page, present and future, and closes the old stream with the page.
- A nav link's `?project=` is added to an already `resolve()`d path, with an eslint disable naming why, following `InboxView.svelte`'s precedent.
- Left as found: `projectState.pick` updates the URL with `history.replaceState`, which SvelteKit warns about (S-0080's code). Nothing in the trial misbehaved because of it, since the page keys on `projectState.current`, not `page.url`; moving it to `$app/navigation`'s `replaceState` is a small follow-up if the warning matters.
- Left as found: links inside pages (a board card's `/items/S-0001`) do not carry `?project=`; in the app the chosen project is in memory and in `localStorage`, so following them works, but such a link copied into another browser opens on that browser's choice.
