# S-0062 The container pushes an acceptance when the operator has given it a key

## Context
ADR-0026 (S-0052): the operator decided that an acceptance from the board should be pushed by the container when they have opted in by naming an SSH key, and chose their own key over the dedicated deploy key that was recommended. This story builds "a key the operator names": the opt-in on the host, the checks that refuse a key that cannot work or is unsafe to mount as it is, pinned host keys, the passwd entry OpenSSH needs, the SSH client in the image, and documentation with the safer choice first. `flai accept` already pushes whenever it can, so only the environment git runs in changes. Work is in `.flai-cache/worktrees/S-0062` on `story/S-0062`.

## Current state
Done on `story/S-0062` in two commits (e40d717, 0aa5390), ready for review.

flai: `cmd/dashboard_pushkey.go`. The opt-in is the host config key `dashboard.push_key` or `--push-key`, never the manifest, and off by default: with neither, nothing about a key is run, mounted, set, or written, pinned by `TestDashboardGivesTheContainerNoKeyByDefault`. With a key named, before anything starts, `flai dashboard` refuses with the reason and what to do: a missing file, a directory, a file looser than 0600, a file that is not a private key, a key with a passphrase, a path docker cannot mount, no `origin`, an `origin` that is not an SSH URL, and a remote host with no `known_hosts` entry on this machine. It copies the host's own entries for the remote (`ssh-keygen -F`, hashed or not, a non-standard port as `[host]:port`) to `.flai-cache/dashboard.known_hosts`, writes `.flai-cache/dashboard.passwd` with root and the host's user, mounts the key and both files read-only, and sets `GIT_SSH_COMMAND` to use only that key and that file, with strict host key checking, batch mode, no agent, and no user configuration. `--push-known-hosts` and `dashboard.push_known_hosts` name the file host keys come from; added because the lab could not be run without touching the operator's own `known_hosts` otherwise, and useful for a curated file of a provider's published keys. The start message, `--json`, and `flai dashboard status` say which key the container holds, by fingerprint and comment. Windows hosts are refused for now. `flaiover/Dockerfile` adds `openssh-client-default`. `make flai-test` passes, 0 lint issues; one test asks the real `ssh-keygen` so the passphrase and not-a-key refusals do not rest on remembered messages.

Tried end to end in the scratchpad with throwaway keys, a scratch SSH remote in a container on the docker bridge address, and a scratch project; never this repository, its remote, or the operator's keys or `known_hosts`; all removed afterwards. With the branch's image started by the branch's `flai dashboard --push-key`: the container ran as `flaiover` (the generated passwd entry), held the key and the pinned host keys read-only and no agent socket; `POST /api/items/S-0001/accept` ended merged, done, archived, committed, tagged, pushed, `pushed: true`, and the remote had the acceptance commit and `cli/v1.1.0`. Without a key: nothing mounted or set, status said it holds no credential, and the second acceptance ended `not-pushed` with `cli/v1.2.0` only local. The real `flai dashboard` refused a passphrase key, an empty known hosts file, and a public key before starting anything. As user ID 4321, which the image does not know, a push failed without the passwd entry and succeeded with the one `flai dashboard` generates; that case was run with docker directly and a world-readable copy of the throwaway key, because the key cannot be given to another user without root. Not tried: macOS, Windows, a real provider, and a template component's publish from the container (it pushes to a second remote with the same key; the code path is the existing one).

Documentation: a new section "Pushing what the board accepts" in `docs/operators/index.md` with a key made for the repository first, then the operator's own key and what it exposes, the agent never forwarded, the checks, the repository rules, and revocation; the security posture; both user documents; `flai-cli.md`; `flaiover-dashboard.md`; `design/tech/docker.md`; and the finding of S-0052 now says this part is built.

## Decisions
- 2026-09-19, operator: continue through the ready stories in their order; S-0062 was next.
- 2026-09-19, agent: `GIT_SSH_COMMAND` in the container's environment, not `core.sshCommand` through `GIT_CONFIG_*`: the excludes file already uses `GIT_CONFIG_COUNT=1`, and an environment variable needs no renumbering and is what the research tried.
- 2026-09-19, agent: the passwd entry is a generated file mounted read-only over `/etc/passwd` with two lines, root and the host's user. Nothing in the image runs as any other user when `flai dashboard` starts it, and it needs no change to the image's entrypoint.
- 2026-09-19, agent: S-0064 (the container cannot leave hooks that run on the host) is not ready, so it is not done first as S-0062's notes suggest. The order is the operator's; it is raised again at review.
- 2026-09-19, agent: the agent will not turn the push key on in the operator's configuration. Naming their own key is their act; the documentation gives the two commands.
- 2026-09-19, agent: the operator's acceptance from the board was refused in the preview: "S-0062 touches flai, flaiover but no tag says which it delivers to". The agent had created S-0062, S-0063, and S-0064 in S-0052 without component tags, and E-0006 has none to fall back on. Fixed by tagging S-0062 and S-0063 `[cli, dashboard]` (they deliver to flai; flaiover is touched incidentally) and S-0064 `[cli]`. Nothing had been merged; the preview shows this error before anything changes.

## Open questions
- The operator's own key very likely has a passphrase, and `flai dashboard` will then refuse it, by design (ADR-0026). Their choices at that point are a key made for the repository, which the refusal and the operators' documentation lead to, or a passphrase-less personal key, which the documentation does not recommend. Said at review so it is not a surprise.
- S-0064 (the container cannot leave hooks that run on the host) is still in backlog. With a key in the container it matters less for reaching credentials and more for stopping a compromise spreading to a shell on the host. Recommended soon after this.
- A template component published by an acceptance from the container goes to a second remote (`git@github.com:bytepunx/system-flow-template.git`). A dedicated deploy key opens one repository, so with the recommended key the template publish would fail from the container while the main push succeeds; with the operator's own key both work. Not tried. If the operator moves to a dedicated key, the template repository needs the same public key added as a deploy key (GitHub refuses one key on two repositories, so in practice a second key and an SSH host alias), or the template publish stays a host-side step. Worth a note in S-0063 or a small story.
