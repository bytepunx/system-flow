## Decisions

- Remedy: the one TH-0929 approved. `flai serve` refuses a container start when the MCP URL's host is loopback, the network is not `host`, and `docker info` says the engine is not Docker Desktop. The default bind stays `127.0.0.1` (S-0506 measured that Docker Desktop under WSL2 cannot reach a `docker0` bind).
- The planner's two tasks stand as written. Layer 1: T-2735, the check in `container.go`, called from `startOf` in `agents.go`, with tests in `container_test.go`. Layer 2: T-2736, the documents and the issue's close, after T-2735 because they quote its refusal. No two tasks share a layer, so nothing runs at once.
- The check sits in `startOf` after `mcpEnv`, since it needs the URL; it runs only when the adapter is handed one. Every container start, a story's and a strategic agent's, goes through `startOf`, so both are covered.
- The engine's kind is read with `docker info --format '{{.OperatingSystem}}'`; `Docker Desktop` is Docker Desktop's answer. It is read once per launcher, and kept only when docker answered. A `docker info` that cannot answer warns and does not refuse, as TH-0929 accepted.
- The refusal names the network's gateway from `docker network inspect <network>`, and falls back to naming that command when it cannot be read.
- An ADR records the refusal, as the orchestrator asked on TH-0929: a start flai serve refuses is a tool-enforced rule.
