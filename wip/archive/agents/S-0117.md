## Decisions

- A system-flow repository under an `import_roots` folder that is not registered is served, not offered (criterion 3). Naming a folder for import is already the operator's say over what is in it, and `flai serve` already serves the projects below the folder it was started in (S-0102) and `flai dashboard` in a folder registers those below it (S-0101). Offering it would need the dashboard to show a second kind of candidate: a candidate's connection answers only the import methods, and the switcher would offer to import a repository that is already imported. It is served without being written to the registry, as the folder's projects are, so removing the folder from `import_roots` stops it.
- `flai import` registers only when a host runs for the config (criterion 1); otherwise it registers nothing and names `flai dashboard` in the project, which registers it, starts the dashboard if needed, and starts the host. The entry is the one `flai dashboard` would write, from `dashboardSettings`. The board's import runs the same command; `flai serve` then registers it again for the dashboard it was offered on, replacing the entry by root, so the board's behaviour is unchanged.

- Commits are made per task, as the operator's start instruction says, rather than only at review as `git.md` says; the operator's instruction takes precedence.

- Below an `import_roots` folder only git repositories count as projects to serve, as only they count as candidates; below the folder `flai serve` was started in, any folder with a manifest still does (S-0102). A test fixture with a manifest inside another repository is not served.
