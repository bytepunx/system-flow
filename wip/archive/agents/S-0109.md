# S-0109 A detached host write is journalled as started before it acts, so a retry after serve went away is answered, not repeated

## Context

TH-0006: a serve restart asked for from the dashboard ran twice, because `hostapi`'s journal of completed writes is in memory, the serve that took the request died before recording it, and the new serve acted on the dashboard's retry. S-0107 worked around it in flaiover with `retry: false`. This story fixes it in flai: `flai/internal/hostapi/writes.go` (`methodsFrom`, `journal`), wired in `flai/cmd/serve_actions.go`, the file beside serve's state in `flai/internal/serve`.

## Decisions

- Only detached writes (`spec.detachTimeout` set) get the record that outlives serve: they are the ones whose own success can end serve or the connection, and whose command is not killed with the request. Other writes keep the in-memory journal: a lost connection cancels their command.
- A repeat found under way, or started by a serve that ended before recording the outcome, is answered as a success with `{"repeat": {request_id, started, under_way}}` and a warning saying it was not done again, not with a new error code: flaiover maps unknown codes to 500, and a serve restart whose serve ended is the restart having happened.
- If the record cannot be written, the write is refused: acting unrecorded is the defect this story removes.
- flaiover keeps `retry: false` for serve, all, and upgrade: a dashboard may be answered by an older flai without the record. No flaiover change in this story.
- A refinement of ADR-0029's delivery rule (a repeat of an under-way write is answered too), not a reversal: a living-design edit, no ADR.

- A serve restart asked for from the dashboard leaves no line in `serve/journal.jsonl`, because the serve that would write it is the one that ends. That was true before this story too, and is outside its criteria. It is recorded in the story's Notes and raised in the review report as a candidate follow-up story, not held here as an open question.
