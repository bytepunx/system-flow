## Context

## Current state
Complete and verified on the served build (API and browser). Threads are files under `wip/threads/` (`TH-nnnn`, ADR-0020) with a validated anchor (path, optional heading, optional item), status open/answered/resolved, participants, and dated entries; `flai thread new|reply|resolve|list|show`; unresolved threads on a story or its tasks are mirrored into the narrative's `## Open questions` between markers. `flai check` validates schema, file names, anchors, headings, and open threads on archived items. The dashboard reads threads, exposes list/new/reply/resolve through flai with the manifest owner as author, and renders a Threads panel under every document and item with reply, resolve, and new-thread forms (heading picker on documents). First story worked on its own branch in a worktree; `scripts/env.sh` now routes caches, config, and the token to the main checkout from a worktree.

## Decisions
- Thread IDs are `TH-nnnn`, their own sequence, four digits like everything else; `flai thread` accepts any padding.
- Status is derived from who spoke last: a reply from anyone but the opener sets `answered`, the opener's follow-up sets `open`, so a resolved thread reopens on any reply. No separate "reopen" command.
- Only item-anchored threads mirror into a narrative; document threads surface through `flai thread list` and, from S-0039, the MCP inbox. Recorded in the first thread on this story.
- The dashboard posts as the manifest `owner` until identities arrive with the hub (S-0043).
- The threads folder is optional in `flai check` so existing fixtures and projects stay clean; the template ships `wip/threads/README.md`.
- Working in a worktree: `scripts/env.sh` detects the linked worktree from `.git` and points `.flai-cache` at the main checkout, so one token, one config, and one pnpm store serve every worktree; `bin/` stays per tree.
