## Decisions

- Kept the planner's four tasks as TH-1229 approved them. Layers: T-3380, then T-3381, then T-3382, then T-3383. Each waits for the one before: the code cites the ADR, the commands call T-3381's function, and the issue closes once every writer takes the lock.
- ADR-0306 uses a board lock of its own, `.flai-cache/board.lock`, not the items lock. A move saves items while it holds the board lock, and each save takes the items lock, so the board lock has to come first. `filelock` is not reentrant, so the items lock cannot serve for both. The board lock is never taken while the items lock or the checked-write lock is held. No checked edit or checked creation writes the board.
- ADR-0306 is proposed, as T-3380's Done when asks. The operator accepts it at review.
- Every write drops a name that is not an active story in a state the workflow orders (`State.Order`), along with its placed entry, and keeps the rest in their order. A name whose file does not parse is kept. A placement still reorders the list, ready stories before backlog, as `Board.Place` already does.
- T-3382's sub-agent found that a stale name's placed entry survived a placement, because Place drops the name before NormalizeOrder runs. NormalizeOrder now also drops a placed entry whose story is not an active ready or backlog story, as ADR-0306 §4 says. The test covers it.
- In `flai accept`, an epic's acceptance takes no board lock and reads no board: Move reads the board only for a story, and an epic's acceptance writes none.
- `flai order --apply` calls `ReadyOrderKeeping` inside `UpdateBoard`, so its reads happen under the lock. That lists the items twice under the lock. Splitting `ReadyOrderKeeping` into a function over a given board and items would avoid that, but it is not needed for correctness.
