# S-0220 The orchestrator answers threads, or recommends an answer, as its permission allows

## Context

With `answer_threads: recommend` the orchestrator replies to a thread awaiting the operator with a recommendation and its source, which the operator confirms; with `autonomous` it answers with a source, and escalates as a recommendation when it has none or the question is the operator's judgement. The planner drafted eight tasks in four layers (TH-0136, resolved by the operator). S-0218, which gave the orchestrator its role, permissions, guard, and decision log, is done.

## Decisions

- The planner's eight tasks are kept as drafted, with their `touches` and `after`. Layers: 1 T-0894 (the entry marks and `Confirm`, which every other task builds on); 2 T-0902 and T-0906 (each waits for T-0894's marks; no shared path); 3 T-0908, T-0910, T-0912 (each waits for T-0902: T-0908 shares `mcpserver/server.go` with it, T-0910 reads its `recommendation` and `source` parameters, T-0912's prompt names them; no shared path among them); 4 T-0913 (waits for T-0908's `inbox.designer` fields) and T-0914 (waits for T-0906, T-0908, T-0910, T-0912, whose parts it drives together).
- The operator resolved TH-0136 without correcting the planner's nine assumptions, so they stand: a recommendation is a mark on an ordinary entry; confirming is the operator's alone (CLI and dashboard, no MCP tool); flai enforces escalation only by refusing an unsourced answer in `autonomous`; the metrics add fields and change none.

- T-0894: a recommendation is a heading suffix `(recommendation)`, a source the entry's last line `Source: <path> § <heading>` (ADR-0090, refines ADR-0020). A recommendation is refused from the opener and on a resolved thread; a recommender cannot confirm its own; any later reply by someone other than the opener withdraws a pending recommendation. The task sub-agent was refused `flai adr new` by the guard, so I created ADR-0090 and set its topics (I-0062 bumped); a `/tmp` write was refused by the permission prompt (I-0082 bumped).

- T-0906: a recommendation ends no wait; waits record whether the orchestrator's answer or the operator's confirmation ended them (`wait_threads_orchestrator_seconds`, `waiting.weeks[].threads.orchestrator` and `.confirmed`), ADR-0091 refines ADR-0081. I exported `threads.Entry.Confirms` so metrics does not copy the confirmation prefix; the sub-agent was refused `flai adr new` again, so I created ADR-0091.
- T-0902: `flai thread reply --recommend --source`, `flai thread confirm`, MCP `thread_reply` `recommendation`/`source`, host API `thread.confirm`; in role `orchestrate`, `thread_reply` writes the decision log entry with the source. I moved the sub-agent's `ParseSource` from `mcpserver` into `threads`, and added `thread.confirm` to flaiover's `REQUIRED_METHODS` in T-0902 rather than T-0913, since the host API's contract test fails without it. Widened the story's touches with `docs/operators/settings.md` (regenerated flag index) and `flaiover/src/lib/server/agent.ts`.
- T-0912: the orchestrator is a long-running session and the operator may change `answer_threads` while it runs, so its prompt states the rules for each value and tells it to read the current value from `system-flow.yaml`, rather than baking the value in. The task's test checks the rules for all three values instead of "none when unset".
- T-0912: finished by me after a restart: the convention's rules for `answer_threads` in both copies, template 1.0.55, and a section "Answering threads (S-0220)" in `design/system/strategic-agents.md`, where I also corrected the guard's description, which said it did not tell `recommend` from `autonomous`; T-0910 made it do so.
