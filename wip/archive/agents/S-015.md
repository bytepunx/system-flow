# S-015 Docker image build and publish

## Context
The image is how flai dashboard delivers flaiover (brief item 5, ADR-0007). Constraints gathered by earlier stories: it must run as an arbitrary UID because flai dashboard passes --user (S-009); it must bundle a flai binary from the same commit because writes and metrics delegate to it (ADR-0016, S-013); it listens on 3000; the repository is mounted at /project and flai's config and cache live under /project/.flai-cache so nothing needs a writable home. Publishing goes to ghcr.io/bytepunx/flaiover (design/tech/docker.md) with tags latest, semver, major, sha; the repository is private so pulls need a GHCR login, which the operator docs must say.

## Current state
All three tasks done, story in review. flaiover/Dockerfile builds flai (golang:1.26-alpine, version from build args) and flaiover (node:24-alpine, pnpm via corepack, pruned to production) into a node:24-alpine runtime with tini and git, flai at /usr/local/bin/flai, PORT 3000, HOST 0.0.0.0, PROJECT_DIR /project, FLAI_BIN, HOME=/tmp, USER 65532 by default. .dockerignore keeps the context to flai/ and flaiover/. scripts/flaiover-image.sh and make flaiover-image build flaiover:local with the checkout's flai tag and commit. Verified: flai dashboard --image flaiover --tag local against a fixture copy as UID 1000 served the manifest, board (writable), stats, and performed a move through the bundled flai with host ownership preserved. release-flaiover.yml pushes to ghcr.io/bytepunx/flaiover with latest (main), semver and major (flaiover/v tags), and sha tags. Docs updated. All tiers green. Committed at review and pushed; the image workflow runs on this push.

## Next steps
1. Operator approves; `flai accept S-015 --by alex --trailer ...` tags flaiover/v0.5.0; the workflow publishes 0.5.0, 0, and sha tags. Then verify the published image with `docker login ghcr.io` and `flai dashboard --pull`, and tick the last criterion.
2. The image is 667 MB; a slimmer runtime (drop dev-only transitive deps, consider a distroless node) is an improvement story, not a blocker.
3. Next E-003 pull: S-032 observability (request logs, /_health, /_ready, /metrics, traces, local collector).

## Decisions
- Build context is the repository root so one Dockerfile compiles flai and flaiover from the same commit; the flai version is the latest flai/v tag reachable from HEAD.
- Runs as USER 65532 by default and under any --user: nothing in the image needs a writable home (HOME=/tmp) and flai's state lives under the mounted project.
- tini as PID 1 so signals reach node and zombie flai processes are reaped; git is installed because flai's release and template commands may need it inside the container later.
- The image workflow also runs on pushes to main that touch flai/ or flaiover/, publishing latest, so the dashboard the operator pulls always matches main; release tags add the semver tags.
