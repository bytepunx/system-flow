# S-0292 flai serve's orchestrator test that waits for the stopped run's activity fails under the close-out's full parallel test run

## Context

I-0090: `TestTheOrchestratorIsStoppedWhenTheActionIsTurnedOff` failed under S-0285's close-out with "never happened: its activity logged" after 5.07 s, and passed alone.

## Current state

## Decisions

- Cause: the stub wrote `orchestrator-<pid>.txt`, which `given` waits for, before it printed `stream-orchestrator`, the run's usage. The test stops the run once `given` returns. Under load the TERM can land before `cat` writes the stream, so the log holds no usage, `logRunEnd` finds no spend and logs nothing, and the wait times out. Shown with `sleep 0.5` injected before `cat`: both subtests failed with the same message after 5.08 s; in the new order, with the same delay, they passed.
- The fix is in the test fixture, not in flai serve. A run stopped before it spent anything logs no activity, and that is right: `logRunEnd` logs spend, and there was none. Nothing in `orchestrate.go` or `activity.go` changes, so the design is unchanged.
- No permanent delay stays in the stub to pin the order: it would slow every orchestrator test, and the doc comment says why the order matters.
- One task, T-1016, one layer. It touches `orchestrate_test.go` and `design/issues`. The planner's three-layer draft (TH-0174) arrived after T-1016 was written and its cause found; T-1017, T-1018, and T-1019 are cancelled because T-1016 covers them. The planner's other candidates, a late reap and a double settle, would not explain a run that ends quickly but never logs.
