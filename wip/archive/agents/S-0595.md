# S-0595 Build in-depth Deploy UI

## Context

The Deployments page showed one Deploy button, which flai refused with "names no deploy command" for a block with no `deploy`. The setup lived only on the Klusters page; a build was one step with one log; step logs reached the page only as a 4 KB tail after the step ended. Design: [ADR-0263](../../design/adrs/0263-a-kluster-block-may-list-components-each-built-as-its-own-step-with-its-own-log.md), refining ADR-0254 and ADR-0259.

## Decisions

- ADR-0263 decides the design without a thread: a `kluster.components` list built one step per component (`build-<name>`), every step written `pending` before the first runs, a `kluster.log` read by offset for the live feed, and the Deployments page's in-page rail (`PageSidebar`, hash-kept panes) with Overview, Build, Logs, Access, and Setup. Reason: each criterion needs it, and the existing patterns (settings catalog, PageSidebar, polling with `upgraded`) give one obvious shape; the operator reviews it at acceptance.
- The Build "sub-page" is a hash-kept pane of the in-page rail, not a route: flaiover has no nested layout, and the item page's panes are the existing pattern.
- Criterion 1 is met through `settings.manifest` from the dashboard. The `settings` host action is still turned on once in a shell (ADR-0039), which is not an edit of `system-flow.yaml`.
- Components build one at a time, stopping at the first failure; parallel builds are left to a later story (ADR-0263 § Alternatives).
- As built, refining ADR-0263 without changing it: a teardown appends one pending `teardown` step to the record it finds rather than planning afresh; `kluster.log` also answers `reset` for a missing log asked at an offset above 0; the panes' hashes are `#overview`, `#build`, `#logs`, `#access`, `#setup`. `design/system/kluster.md` records them.
- `hostapi/settings.go` gained a `components` branch in `settingArg` (T-2598), since `settings.manifest` would otherwise have refused the JSON list.
- Plan, by layers:
  - Layer 1: T-2598 (manifest `components` and its setting kind) and T-2599 (host read `kluster.log`, and `REQUIRED_METHODS`). No shared path; neither reads the other.
  - Layer 2: T-2600 (deploy steps per component, pending plan) waits for T-2598's `Kluster.Components`; T-2601 (flaiover server route and types) waits for T-2599's answer. No shared path.
  - Layer 3: T-2602 (`LogFeed`) and T-2603 (`DeploySettings`) wait for T-2601's route and types. No shared path.
  - Layer 4: T-2604 (Deployments page) waits for T-2602 and T-2603; T-2605 (Klusters page step 4) waits for T-2603. No shared path.
  - Layer 5: T-2606 (design and guides) waits for the code it describes, T-2600, T-2604, and T-2605. One docs task, since `kluster.md` would otherwise be touched by tasks of one layer.
