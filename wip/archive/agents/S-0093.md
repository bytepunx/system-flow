# S-0093 The watcher's debounce is tested by driving its ticks, not by racing a wall clock

## Context
The operator reported that flai's "Behavior tests" step (`go test -race -short -count=1 ./...` in `.github/workflows/flai.yml`) failed on main after S-0087 was pushed, and pasted the failure: `TestAFileStillBeingWrittenIsReportedOnce` saw `wip/a.md` seven times, wanted once. This is the same test that failed on 2026-09-20 after S-0078 and was recorded as I-0030 with the remedy "drive the clock or the ticks itself instead of sleeping". That remedy was not carried out; the second failure is the trigger.

## Current state

The story is in review.

## Decisions
- The watcher was never wrong. A runner that stalls for two ticks between writes makes it correctly report the file as settled midway; the seven reports were seven true settles. The defect was a test asserting a count that a stalled goroutine can change, so the fix is in how the test observes the debounce, and `Run`'s behavior is byte-for-byte the same.
- Extracted the per-tick logic into an unexported `debounce` type with a `tick(snapshot) []string` method, rather than injecting a fake clock or ticker into `Watcher`. The logic never read the clock, only the ticker's rhythm decided when it ran, so the smaller seam is the snapshot, and the tests need no timing at all.
- Kept the real-ticker end-to-end test (`TestReportsChangedAddedAndRemovedFilesUnderTheWatchedPathsOnly`) because it is the only test through `snapshot` and `Run` together. It waits for an exact report with a 3 s deadline, so slowness makes it slower, not wrong. It was exposed to the same class of problem through `os.WriteFile` truncating before it writes, so the helper now writes to a scratch file beside the root and renames into place.
- I did not reproduce the CI failure. Forty-eight spinning processes on 24 cores did not slow the old test's writer loop enough. The evidence that this is the cause is the arithmetic in the operator's output (a 3.64 s run is the 3 s poll timeout plus about 0.64 s of writer loop that should take 0.12 s) and I-0030's earlier diagnosis. The fix is by construction, checked by a mutation: making the debounce report on every change fails four of the new tests.

## Open questions
None. One observation for the operator, not a question: nothing in `flai.yml` runs the tests again on a failure. A rerun made the first failure go away, which is how it went unfixed for a day. I did not touch the workflow.
