# S-0079 A story moved to ready starts an agent on the host, with the command the operator configured

## Context
The gap the operator hit on 2026-09-20: a move to ready changed a file and nothing on the host was told. The criteria settle the sensitive parts (no default command, the operator's argument list, never a shell, tried only with a stub), so it was built without questions. Stacked on `story/S-0085` (`git merge --ff-only`), because both change `hostapi`, `REQUIRED_METHODS`, and the same design rows: accept S-0085 first.

## Current state
In review. Branch `story/S-0079`: three commits of its own on top of S-0085's four.

- **Host action `agent`**, off by default, per project like `push`. `flai serve agent set [--name] [--attended-minutes] -- <program> [args...]`, `show`, `clear`. The command is an argument list in the host's configuration with no default, outside `config.Keys`.
- **`flai serve` starts it itself** (`internal/serve/agents.go`); no method of the channel asks for it. On a change under `kanban/`, or when an agent it started ends: a story has entered ready, the action is enabled and a command set, `CanPull`, no started agent alive, nobody attending. The first look only learns what is ready, so a restart starts nothing. One per project at a time; the reason a story waits is kept.
- **Attending** is the newest mtime among `.flai-cache/mcp/*.json` and `wip/agents/*.md` (not the generated index) being younger than `attended_minutes`, 6 by default.
- **The command runs** as it stands in the project's directory, detached, with `{story}` and `{root}` replaced, `FLAI_AGENT`, `FLAI_STORY`, `FLAI_SESSION`, `FLAI_STARTED_BY` set, output to a log. The story is the first ready one in pull order, its ID checked.
- **Seen where:** `serve/agents.json`, the journal (starts and failures), `agent.status` (read-only), and `HostAgentNotice` on the board. `agent.status` is in `REQUIRED_METHODS`.
- **Convention:** session-start baseline says what a session flai started does first and that it ends when nothing is left to pull; template first, identical here; the template renders and checks.
- Gates clean after the last edit: `make flai-test` (with flaiover's 311 tests), `make flaiover-test`, `make flaiover-build`, `make check`, `make lint-md` in the worktree and the main checkout, `make template-test`.

Tried in a scratch project (`agentlab`, own `FLAI_CONFIG`, its own single `flai serve`, container `flaiover-agentlab` on 4398, branch image; all removed since, no stub left running) with a stub command that records what it was given and waits to be released. Never a real agent command.

- Nothing enabled, a story made ready from the CLI: nothing started, nothing journalled.
- Command set and action enabled with no restart; a story made ready from the CLI: the stub ran in the project's directory as `builder` with `FLAI_STORY` and `FLAI_STARTED_BY`; an argument `$(touch ...)` arrived literally and the file was never made.
- The dashboard was told (`/api/host-agent`): enabled, the command's name, running for which story.
- A story made ready from the dashboard while the first ran: not started, waiting "still running".
- The first session moved its story in progress and ended: the next was started within a second.
- Two in progress, its agent ended: waiting "the in-progress limit leaves no room".
- A fresh MCP cursor, a story entering ready: waiting "an agent is attending", naming the file.
- A command that does not exist: reported with the system's reason, journalled as failed.
- The journal: two starts and the failure, with PIDs and log paths.

Not tried: the board notice in a browser (component tests and the API only); a real agent command, on purpose; `flai serve` restarted while a started agent still runs, beyond the unit test that a restart starts nothing (an orphan's end is not seen by the new `flai serve`, so the next story waits for another to enter ready); Windows, where the tests are skipped; many projects at once.

## Decisions
- 2026-09-20: `flai serve` performs the action itself from what the watcher sees; the dashboard asks for nothing. The criterion wants it to fire for a move from the CLI or an agent too, which the dashboard never sees, and "never built from anything the dashboard sent" is simplest when the dashboard sends nothing.
- 2026-09-20: the session is given the first ready story in pull order, not the one that entered ready. That is what the conventions tell any agent to pull, and the operator's order stays the only order. Tried: S-0002 entering ready started a session for S-0001, which was first.
- 2026-09-20: attending is judged from file times, six minutes by default: one more than the longest a waiting agent goes without rewriting its cursor. It errs towards not starting: a designer's log entry on a narrative also counts for those minutes.
- 2026-09-20: what was ready when `flai serve` began is not news. A restart that started sessions nobody asked for would be the worse surprise; the cost is that stories made ready while it was down wait for the next one to enter.
- 2026-09-20: `{story}` and `{root}` are replaced inside arguments, because a program run without a shell cannot expand `$FLAI_STORY` in its own argument, and `claude -p "... {story}"` is the obvious command.
- 2026-09-20: the started process is detached and outlives `flai serve`. A session at work should not die because its starter was restarted.
- 2026-09-20: the dashboard is told the command's name, never its arguments: they are the operator's and may hold a prompt or a path.

## Open questions
- 2026-09-20: a story that stayed ready while someone was attending is not picked up when they leave; only the next entry into ready, or a started agent's end, looks again. A slow periodic look (every few minutes, only when something is waiting) would close that. Wanted?
- 2026-09-20: the config gains a key (`agent`) that an older flai reading the same file refuses, as with `host_actions`. Same question as in S-0085 about strict parsing.
