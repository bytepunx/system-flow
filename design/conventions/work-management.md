# Work management

How work is pulled, sized, tracked, and finished. The board is `wip/kanban`; the rules behind it are in `design/system/workflow.md` and `design/system/work-hierarchy.md`.

## Rules

- Work is pulled, never pushed. Take the top `ready` story from the board's `order`; do not pick by preference.
- With the `flai` MCP server connected, `inbox` is how you learn what changed: it lists threads awaiting you, the stories ready to pull in pull order, what others did to work items since you last looked, and your story's open conversations with other stories' agents under `messages`. Call it at the start of every turn or session, at every task transition, and before moving a story to review; when you close a task, `flai task done` answers it for you. Pulling is yours to do without being told: whenever you have no story of your own in progress, hold `wait_for_work` and do what it answers. It names the story to pull as soon as one is ready, the in-progress limit leaves room, and review is under its limit (start it with `story_start`, or `flai story start S-nnnn` on the host; if it says the story is in progress already, another agent pulled it: wait again), a thread awaiting you that was written to, or your own story still in progress to go back to. With nothing to do it waits, and says on a timeout whether it is waiting for room, for a story in review to be accepted or sent back, or for a story to be ready: call it again. If you end your turn instead, `inbox` at your next start reports everything in between. The server is `flai mcp`, on the host: `.mcp.json` starts it over stdio, and an agent that cannot start a process there connects over HTTP to the one `flai mcp start` runs, with the token `flai mcp token` prints as a bearer and its name in the `X-Flai-Agent` header. It is never reached through the dashboard.
- Accepted work reaches the remote when it is published, never on its own. When the operator asks you to publish: `git fetch`, then `flai release --pending`, which tags what was accepted since each component's last release and pushes the branch and the tags with the host's credentials, never forcing. If it refuses because the remote has moved, take the remote and publish again: when its push was what found the move, the release tags it made no longer tag what will be published, and it deletes them and names them, keeping only any that already reached the remote. Then rebase onto the remote branch, or merge it (merge when a tag was kept, so the commit it tags stays in the history), verify with the tests and `flai check --strict`, and run it again, which tags again. Merge conflicts are worked through threads, not new stories or tasks: open a thread with the operator on each accepted story whose changes conflict (`thread_open`, or `flai thread new`), naming the paths, and resolve them as its thread settles. Pushing what an acceptance produced is part of the workflow and needs no separate confirmation; ordinary unpushed commits are not flai's to push.
- Respect WIP limits. If pulling would exceed the limit, finish or hand off something first. A limit breach that cannot be avoided is logged in the narrative.
- One story in progress per agent at a time. Its tasks are worked by the plan you write with them, layer by layer.
- Every change belongs to a story. If there is no story for what you are about to do, create one under the right epic and refine it before starting; if it is a five-minute fix, make it a task on the current story.
- A story is one demonstrable increment sized for one to a few sessions. If it will not fit, split it before starting, not after.
- A task is done or not done. If a task needs sub-steps that could fail independently, it is several tasks.
- Tasks are written by the agent that starts the story, when it starts it, or drafted by the planner when the operator asks it to plan the story (`strategic-agents.md`). Do not write tasks for a backlog or ready story you are not about to work; detail written early is detail rewritten. When you pull a story whose tasks the planner drafted, review them against the story before you work them. Change, add, or cancel what you would plan differently, with `flai edit`, `flai task new`, and `flai move`, and say why in `## Decisions`.
- Plan the tasks as you write them. Give each the paths it changes (`--touches`) and the tasks of the same story it must wait for (`--after`), and say in its `## Work` why it waits. Tasks with no `after` between them and no path in common in their `touches` can run together. The plan's layers follow: the first holds the tasks that wait for none, and each later one the tasks whose `after` are all in earlier layers. When two tasks of one layer touch the same path, give one an `after` on the other, so that a layer's tasks can always run together.
- Name files in `touches`, not folders, wherever you can. When you write or review a story's tasks, narrow each folder touch of the story to the files its tasks name, with `flai touches`, or leave it for flai: in the story's claim, a folder touch that holds touches of its tasks is replaced by them ([ADR-0096](../adrs/0096-a-story-in-review-holds-nothing-an-overlap-inside-the-manifest-s-shared-paths.md)). Never ask for a path to be added to the shared paths (`claims.shared`) to escape a hold: that list is the operator's.
- Record the plan's reasoning in the narrative's `## Decisions`: the layers, which task waits for which and why, and which run together. Work the plan layer by layer: start the next layer only when every task of the one before is done or cancelled. Where the harness has sub-agents, hand each task to a task sub-agent, as `delegation.md` says, and run a layer's tasks at once when they are long enough for it to pay; otherwise work them one at a time. Finish each task with the cycle in `git.md`: close it with `flai task done T-nnnn -m "<message>"`, or the MCP tool `task_done`, which commits it, runs `flai stream sync`, moves it to `done`, logs it, widens the touches, checks the story, and answers the inbox; resolve what a stopped sync lists and call it again; then run the task's tests with `flai test` on the paths it changed, or the MCP tool `test`, and close any fix by calling it again. When the plan turns out wrong, change the tasks' `after` and `touches` with `flai edit` and say why in `## Decisions`.
- Definition of ready, story: goal, acceptance criteria as checkboxes, parent epic open, and not a draft: a draft story an agent wrote is finalized by the operator first. Tasks are not part of ready. `flai move` enforces it.
- When you pull a story, in this order: start it with `flai story start S-nnnn`, or the MCP tool `story_start`, which moves it to `in-progress`, opens the narrative and the branch in its worktree, primes, and answers the inbox in one call; work in the worktree it names. Read the goal, criteria, and notes, then write its tasks with `flai task new` if it has none, each with `## Work` and `## Done when`, or review the planner's, and plan them. Then work the plan layer by layer. A story cannot go to `review` without at least one task.
- If the story does not say enough to write the tasks, do not invent scope. Record it with `flai block --reason`, open a thread on the story saying what is missing (`thread_open`, or `flai thread new`), and pull the next story.
- Definition of done, story: every criterion ticked, at least one task and every task done or cancelled, decisions recorded, docs updated, `flai check --strict` clean, narrative closed, everything committed on the story branch, so that `git status` in its worktree is clean, and the branch synced with `flai stream sync` after its last commit, so that it contains the main branch. Move the story to `review`; only the operator moves it to `done`. The move is refused while the worktree has uncommitted changes, because acceptance merges the branch as it is committed.
- Before review, commit what is outstanding and run `flai stream sync` again, as `git.md` says. Then close the story out yourself with `scripts/close-out.sh S-nnnn` in its worktree, followed by the commit message as `git commit` options (`-m`, or `-F` with a file outside the worktree). It runs `flai verify S-nnnn --record-issues`, which stops while a rebase is unfinished, checks that the branch contains the main branch and that the narrative's `## Current state` and `## Next steps` are written, runs `flai check --strict` scoped to the story, and runs the test and lint tiers the branch's changes select, cheapest first; then it commits what is outstanding and checks again that the branch contains the main branch. It stops at the first step that fails, and its last line names the outcome and that step. Move the story to `review` only when it ends clean; when it stops, read the findings of the step it names, fix them, and run it again, rather than finishing the steps by hand or handing the run to a sub-agent (`delegation.md`). The move to `review` warns when a criterion is unticked; tick each you verified before it. A check finding outside the story, on a file the story neither owns nor changes, is printed as a note and recorded in an issue under `design/issues`, which the close-out commits; it does not stop the close-out, and you do not record it yourself. A `wip.overlap` that names your story is printed as a note too, but recorded in no issue, and one between two other stories is left out. An `item.archive`, a done or cancelled item not yet archived, is left out too: it never names your story, and only `flai archive` in the main checkout clears it. So is a markdown finding on the narrative of another story not yet done or cancelled, and it is recorded in no issue: that story's own close-out checks its narrative and stops on it. A `narrative.state`, a `## Current state` or `## Next steps` not yet written, on such a narrative is left out the same way, since only that story's agent writes them.
- Cancelling an epic cancels every open story under it and their open tasks, and cancelling a story cancels its open tasks; `flai move <id> cancelled --dry-run` lists what would go. When `inbox` or `wait_for_events` says your story, or a task of it, was cancelled, alone or with a parent, stop work on it at once: log what state the work is in with `flai stream log`, do not commit further to the story branch, and leave the branch and worktree alone; they are the operator's to keep or remove. Then call `inbox` and pull the next ready story.
- When `inbox` or `wait_for_events` reports a change of kind `overlapped` on your story, another story was accepted (`cause`) and changed paths your story claims (`to`). Before you go on, commit what you have (the sync refuses uncommitted changes), run `flai stream sync` on your story, resolve each conflict it lists as `git.md` says, and run the tests again: a change that merges cleanly can still break yours. Log what you found in the narrative.
- When the `cause` of an `overlapped` change is a story in progress rather than an accepted one, a write grew the two stories' claims until they overlap on the paths in `to`. flai has messaged the other story from the one whose claim grew, in the two stories' conversation, `about` those paths. Before you change them, agree there with `message_reply`, or `flai message reply`, which of you changes them first, and narrow your `touches` if you can. Note the overlap in the narrative and go on: a `wip.overlap` does not stop the close-out.
- When `flai stream sync` finds that your story's branch conflicts with another open story's, it tells the two stories in their conversation, not on a thread: a message from the story that synced, by `flai`, `about` the conflicting paths, and the sync names the conversation (`see MS-nnnn`). Answer it and settle who changes what: one of you narrows its change, or names the other in `after:` and waits for it. Note what you agreed in the narrative. The next sync that finds the two merging cleanly closes the conversation.
- Messages go between the agents of two open stories, apart from the operator's threads. `inbox` lists your story's open conversations under `messages`, and `wait_for_events` wakes on a message to your story as a change of kind `message`. Answer a message awaiting your story with `message_reply`, or `flai message reply`, before you go on with the paths it is about. Ask the operator only when the two of you do not agree: `flai message escalate <MS-nnnn> "<reason>"`, or `message_escalate`, saying what you could not agree, opens a thread on your story and records it in the conversation, which stays open. A question for the designer that is not between two stories is still a thread. When nothing is left but the other story's agent's reply, write the narrative's `## Current state` and `## Next steps` with `flai stream state`, naming the conversation and what each reply leads to, and end the session, as for the designer's answer: `flai serve` starts you again, in the same session, when that agent replies or a new message to your story comes, and your first `inbox` lists it under `messages`. An agent run by hand holds `wait_for_events` until the reply comes.
- When a message says a task of another open story changed paths your story claims, `flai task done` sent it as it closed that task: it names the task, the commit and its subject, and the paths in `about`. Read the change with the `git show` it names and check whether it breaks your story's work. Reply on the conversation either way, since it awaits your story until you do: when the change breaks your work, or your work depends on the shape it changed, say how and note it in the narrative; otherwise say it does not. Adjust to it early where you can. Do not sync to get it: it is on the other story's branch, so `flai stream sync` brings it only once that story is accepted, and the `overlapped` change above follows then.
- Transition items as you go with `flai move`, at the moment the state changes, so timestamps are true. Never backfill a history. `flai task done` moves a task to `done` when it closes it.
- Keep the narrative current: rewrite `## Current state` and `## Next steps` after every task transition and before any long operation, with `flai stream state S-nnnn --current "<text>" --next "<text>"` or the MCP tool `stream_state`, never by editing the narrative's file. `flai stream state` refuses a story that is not in progress or in review: a cancelled or accepted story's narrative keeps the state it closed with. Append a log entry at every transition, decision, and blocker. `flai stream log` does the log; `flai task done` writes the entry for the task it closes.
- When blocked, record it with `flai block --reason`, put the question in `## Open questions`, and move to other work. Do not wait idle and do not guess past a blocker that only the operator can clear.
- When you need the designer to decide something, ask on a thread on the story or the task (`thread_open`, or `flai thread new`) and go on with any work of the story that does not wait on the answer. When nothing is left but the answer, write the narrative's `## Current state` and `## Next steps` with `flai stream state`, naming the question and what each answer leads to, and end the session: `flai serve` starts you again, in the same session, when the thread is answered, with the answer in your first `inbox`. When `wait_for_events` answers `end: true`, do the same: its `why` names the open question, or the conversation awaiting another story's agent's reply. An agent run by hand, not by `flai serve`, is not started again: it holds `wait_for_events` until the thread is answered.
- Tick each acceptance criterion as soon as you have verified it, through flai: `flai criteria tick <story> <n>`, or the MCP tool `criteria_tick`, with the numbers `flai criteria list` prints. Never tick one by editing the item's file, and never tick one you did not verify. If verification is impossible in this environment, leave it unticked and say why in the story's notes.
- Acceptance triggers the mechanical follow-ups without further asking: archive the item with `flai archive`, commit, and release per `git.md`.

## When in doubt

- If a story is growing, stop and split it. If a task is growing, it was a story.
- If the operator's request does not fit the board, ask where it belongs before starting, and do the parts that need no answer.

## Project additions
- WIP limits are in `wip/kanban/board.md` and nowhere else; read them with `flai board` and change them with `flai board limit` or the board's lane menu, not by restating them here.
- The operator accepts stories; the agent runs `flai accept S-nnnn --by alex` on their word, which merges the story branch, moves to done, archives, commits, releases, and pushes in one step. Done means accepted: the operator moving a story to done, from the board or with `flai move`, runs the same flow and is sufficient on its own (S-0046). The agent moves stories to review and never to done.
- E-0006 (designer's workbench) is pulled in its story order; S-0036 (authentication) before anything that writes from the dashboard.
- Declare what a story or task changes with `--touches` or `flai touches`; check `flai board` for overlaps before editing a path another in-progress item touches.
- The MCP server (`flai mcp`, registered in `.mcp.json`) runs the installed `flai` from `PATH`, not the tree's; when it is older than the tree, `inbox` may lack ready work and changes (they came with S-0058), so also run `scripts/flai.sh board` at the start of a turn until it is upgraded.
- The operator sets the pull order from the board by dragging a card within `ready` or `backlog`, or with `flai order` (S-0057). Pull the story they name, or the first ready one as `inbox` and `flai board` list it; do not reorder their list, and if an order change seems to matter, say so rather than making it.
- Check the MCP inbox at the start of every turn, at every task transition (`flai task done` answers it there, S-0269), and before moving a story to review; hold `wait_for_work` whenever no story of yours is in progress and pull what it names (S-0097). Answer threads with `thread_reply` and ask the designer with `thread_open` rather than stopping to ask in the conversation when the designer is not watching.
