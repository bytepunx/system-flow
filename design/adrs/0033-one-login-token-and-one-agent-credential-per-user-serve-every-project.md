# ADR-0033 One login token and one agent credential per user serve every project

## Context

[ADR-0029](0029-the-dashboard-reaches-a-project-only-through-flai-on-the-host.md) already named the end state: "one flai per user" and "one dashboard for every project ... comes after the mount is gone." The mount went in S-0075; until now `flai dashboard` still started one container per project, each generated by [ADR-0018](0018-dashboard-token.md) and refined by [ADR-0031](0031-the-dashboard-s-container-holds-nothing-of-the-project-a-port-and-two-secrets.md) into its own pair of secrets — a login token and the credential `flai serve` proves itself with — kept under that project's own `.flai-cache`. A user working on several projects on the same host ran several containers, several logins, and several credentials for the one `flai serve` that already held every connection.

S-0080 builds the end state: one container, reached with one login, backed by one `flai serve` proving itself with one credential, for every project registered with it.

## Decision

**The login token and the agent credential are per user, not per project.** `flai dashboard` generates each once, on first use, and keeps them beside `flai serve`'s own state (`serveDir()` — `.flai-cache/serve` inside a project when `flai serve` has not been told otherwise, or wherever the host's flai configuration points it), never under any one project's `.flai-cache`. A second, third, or later project pointed at the same `flai serve` is handed the same two files; none of them generates its own.

**One container, named for what it is, not for a project.** The container is named `flaiover`. `flai dashboard` in any project checks whether it is already running: if so, it registers the project with the running container and starts nothing; if not, it builds or pulls the image and starts it with the shared secrets. `flai dashboard stop` unregisters a project and only stops the container once no project is left registered. `flai dashboard status` lists every project it currently serves.

**The credential proves who flai is, not which project a connection speaks for.** flai still dials one WebSocket per registered project ([ADR-0029](0029-the-dashboard-reaches-a-project-only-through-flai-on-the-host.md)); each connection's `hello` still names its one project, and every ordinary request still carries a project key that flai checks against the project that connection declared. A request naming a project a given connection did not `hello` as is refused (`CodeUnknownProject`, `flai/internal/channel/channel.go`) — unchanged from before this story, and exercised now with two projects sharing the one credential (`TestASharedCredentialDoesNotLetOneProjectAnswerForAnother`, `flai/internal/serve/serve_test.go`) so that sharing a credential is not mistaken for sharing an identity: it lets flai prove itself once, not answer for a project it never registered.

**flaiover routes by the key each connection names, not by which secret proved it.** `AgentRegistry` (`flaiover/src/lib/server/agent.ts`) performs the one handshake with the shared key and then keeps a per-project `AgentHub`, chosen by the `project.key` named in `hello`. `AgentRegistry.solo()` is the backward-compatible case: while exactly one project has ever connected, every page and API route that asks for "the" project (no `?project=` query parameter) is handed that one hub, so a single-project dashboard needs no configuration change at all. The moment a second project connects, the query parameter and the switcher (`ProjectSwitcher.svelte`) govern which project a browser tab is looking at; the choice is remembered per browser, not asked of the server.

**A project's old per-project secrets become inert, not migrated.** A `.flai-cache/dashboard.token` or per-project agent key file written by a release before this story is simply not read once that project registers with the shared container; `flai dashboard` neither deletes it nor warns about it. This follows [ADR-0031](0031-the-dashboard-s-container-holds-nothing-of-the-project-a-port-and-two-secrets.md)'s precedent for the retired push key: an old file that nothing reads any more is left for the operator to remove, not treated as an error or silently migrated. Operator documentation (T-0311) says the old files can be deleted once every project on the host has moved to the shared container.

## Consequences

- One login, not one per project: the operator (or anyone they share a link with) authenticates once for every project the host's `flai serve` knows about.
- A compromised container still reaches only what ADR-0029's channel offers, project by project; sharing one credential across projects does not widen what a proven connection may ask for, because the project-key check is unchanged and per-connection.
- `flai dashboard status`, run from any project, now shows every project the shared container serves, not just the one it was run from.
- An operator with several projects already running their own per-project containers meets, on the next `flai dashboard` in any of them, one shared container in place of that project's own; the others keep running their old containers until each is restarted in turn, at which point it joins the shared one instead of starting its own.
- The old per-project `.flai-cache/dashboard.token` and agent key files are dead weight once a project has moved over; nothing deletes them automatically, matching how ADR-0031 left an unused push key for the operator to clear rather than erroring on it.

## Alternatives considered

- **Keep a credential per project, share only the container.** Simpler to reason about per-project blast radius, but reintroduces exactly the "several credentials for one flai serve" friction this story removes, and gives the operator N logins to keep straight for one dashboard.
- **Migrate old per-project secret files into the shared ones automatically.** Silently overwriting a file with another project's decision about it was rejected for the same reason ADR-0031 rejected refusing to start over a retired push key: an old file with a purpose that has quietly ended should be explained, not acted on for the operator.
- **Widen the project-key check into a registry-level allow-list instead of a per-connection check.** Would need flai to track which keys are valid across every registered project on every connection, for a property the existing per-connection check already gives for free, since each connection only ever claims the one project it `hello`'d as.
