# ADR-0203 flai may run a story's agent in a container from a baseline image it builds, with a harness of its own as the entrypoint, so that flai chooses the mounts, the tools, the guard, the permission prompt, and the pricing of each model call across hosted and local models

## Context

A story's agent is Claude Code run headless on the host by `flai serve`, as the operator, with the operator's home, keys, and every path on the machine in reach; what it may do is `--allowedTools`, `flai guard` as a hook, and `permission_prompt` for a protected write ([ADR-0038](0038-flai-serve-starts-a-story-s-own-agent-through-an-adapter-with-what-the-operator.md), [ADR-0060](0060-a-claude-code-pretooluse-hook-flai-guard-refuses-any-sub-agent-s-call-that.md), [ADR-0086](0086-flai-serve-gives-a-claude-code-agent-flai-s-permission-prompt-as-its-permission.md)). Its model calls go to one provider per session ([ADR-0129](0129-a-story-s-agent-names-a-provider-beside-its-harness-and-model-and-the-providers.md)), so a local model cannot take a role beside Claude. Every harness meets flai through neutral contracts, and a loop of flai's own was kept as a later option ([ADR-0130](0130-every-harness-meets-flai-through-neutral-contracts-an-adapter-s-capabilities-a.md)).

S-0496 asked whether Docker Agent could mix a Claude subscription with local models and proposed a `docker-agent` adapter ([ADR-0202](0202-flai-gains-a-docker-agent-harness-adapter-that-runs-a-story-s-agent-as-a-docker.md)). It can, but the operator finds its prerequisites and limitations no clear win: Docker Desktop 4.63 or a standalone plugin; a `claude-code` harness that ignores its toolsets, so `flai mcp` cannot be given to it, and runs `claude` with `--dangerously-skip-permissions`, so Claude Code's permission prompts and with them `permission_prompt` are off inside it; two agent loops, one inside the other, each with a guard that sees only its own calls; cost priced from the models.dev catalogue at $0 for a local or unknown model; sessions in `~/.cagent/session.db` outside the project; telemetry to Docker on by default; and global hooks in `~/.config/cagent/` that run inside every agent and that no agent file can suppress. Each is a surface flai would adopt but not control.

The operator asked S-0497 for the other way round: a baseline Docker image flai builds, whose entrypoint is a harness flai writes, so that flai chooses what is mounted, which tools exist, how `flai mcp` and `flai guard` are reached, and how cost is captured per harness, model, and agent, across hosted and local models, with Kubernetes and the operator's secrets service, signet, as later directions. The analysis is [agent-adapters.md, A container harness of flai's own](../system/agent-adapters.md#a-container-harness-of-flais-own), written on 2026-10-25: it states the shape, what it gives against each of flai's concerns, and weighs it against Claude Code on the host and against Docker Agent in one table.

## Decision

flai may run a story's agent in a container from a baseline image it builds, with a harness of its own as the entrypoint, so that flai chooses the mounts, the tools, the guard, the permission prompt, and the pricing of each model call, across hosted and local models.

- **The image.** `ghcr.io/bytepunx/flai-agent`, built from this repository and signed and listed as `flaiover`'s image is ([ADR-0070](0070-releases-are-signed-with-a-cosign-key-pair-verified-before-they-are-installed.md)): a small Linux base, `git`, the `flai` binary, and the inner harnesses the build bakes in, Claude Code first. A project may add one layer, named in its manifest, for the tools its test tiers need. `flai serve` runs the image by the digest a signed release names, as `flai dashboard` does, and never an image it did not list.
- **The harness.** `flai agent run` is the entrypoint. It reads one start request on standard input, the `Request` the adapters take today, fetches by name what the request names as secrets, starts the inner loop, and writes neutral usage events to standard output, which `flai serve` reads as it reads a log today. It is a `container` harness adapter under ADR-0130's contracts: `Start` builds the `docker run` argument list; `Capabilities` are `Resume`, `Guard`, `Ask`, `RoleModels`, `StrategicAgents`, and `Cost` true; `Reader` reads the events the harness wrote.
- **The inner loop.** A story's agent, or a role, runs either on a CLI harness baked into the image, driven as the adapters drive it today, or on a loop of flai's own that speaks `anthropic-messages`, `openai-chat`, or `openai-responses` to the provider the agent or role names. A model named through a provider entry with a `base_url` on the host or in a sidecar is a local model. The mixture the operator asked for is a Claude Code story's agent on the subscription with roles as nested loops on local models, or a local model's loop with a Claude Code role.
- **Mounts.** The story's worktree alone, read-write, at its host path; the story's own folder under `.flai-cache` for its session store and logs; and, for a baked-in Claude Code, its login state read-only. Nothing else: no home, no `~/.ssh`, no `~/.flai`, no main checkout, no `wip/`.
- **flai's MCP server.** The host's, over HTTP ([ADR-0030](0030-mcp-is-served-by-flai-on-the-host-over-stdio-and-http-and-the-dashboard-s-api.md)), reached with the agent's bearer token and its name in `X-Flai-Agent`. Every write to the project but the worktree's files, `task_done`, `stream_sync`, moves, threads, the narrative, runs on the host in the worktree the container mounts, so the container holds no git credential and no `.git` of the main checkout.
- **The guard and the permission prompt.** In flai's loop, `Decide(Call)` is called before every tool call, the loop knowing which sub-agent calls; on a baked-in CLI harness, `flai guard` runs as its hook, as today. A protected write is the guard's hold-and-ask on a thread, with a bound flai sets. The protected list gains the image's own files: the manifest layer, the start request, and the harness's configuration.
- **Usage and cost.** Each model call is one event: harness, agent, model, provider, tokens, and the cost the response carried where the gateway gives one. Where it did not, the provider's spend log prices the run ([ADR-0132](0132-a-story-s-cost-comes-from-its-provider-s-spend-log-when-it-has-a-provider-from.md)); a local model is priced by a rate the operator sets on the host per provider and model, `agent.providers.<name>.rates.<model>`, and marked `policy` in `priced_by`, a fourth value beside `gateway`, `harness`, and `estimate`, summed as the lowest-confidence source as ADR-0132 sums the others. `priced_by` is kept per model on an item's usage, so a story on two sources reports both.
- **Secrets and configuration.** The start request and the image carry names only. `flai serve` passes the key a provider's `key_env` names into the container's environment, as into a child today; where the host names a secrets service, the harness fetches the key at start with a short-lived identity instead, and no key crosses the host's configuration or the container's environment.
- **First story.** A spike with no adapter: the image built by hand with `claude` and `flai` in it, the worktree and the login state mounted, `flai mcp start` on the host, one story of this repository worked end to end, and the facts the analysis leaves open settled: the login inside a container, the bind mount's speed on WSL2, the HTTP server's coverage of `task_done`, `stream_sync`, and `permission_prompt`, and what a local model answers as `usage`.

## Consequences

Trade-offs, against flai today and against Docker Agent:

- Against flai today, nothing a story's agent has now is given up while Claude Code is baked in: the subscription, Claude Code's prompt, caching, and tools, `flai guard`, and `permission_prompt` all run inside the container as they run on the host. What is added is a boundary: the agent sees the worktree and one cache folder, not the machine. The price is Docker Engine as a requirement of running agents, which `flai dashboard` already makes of running the dashboard, an image to pull and keep in step, and a start that is slower than a process by the container's start.
- Against Docker Agent, the two reach the same mixture of a subscription and local models. Docker Agent reaches it sooner, with a loop, hooks, a session store, and sub-agents that exist today; this reaches it later, by building the loop flai has twice declined to build. In return it keeps what Docker Agent cannot give: one guard that sees every call once, from the harness that made it; a permission prompt that stays on inside the subscription path; cost read from the response of the call that incurred it; no vendor telemetry; sessions kept with the project; and a run that is the same artefact on a laptop and in a cluster. The effort is Large where Docker Agent's is Medium: the loop is an MCP client, a tool loop with streamed `tool_use` and `tool_calls`, a session store, context compaction, and nested loops, beside the image and its release pipeline.
- Two inner loops where Docker Agent has one vendor's: a baked-in Claude Code and flai's own, each with its guard reader and usage reader. The contracts of ADR-0130 are built for exactly this, and the Claude Code reader exists.
- A local model's cost is the machine's, which no log carries; the `policy` rate is the operator's figure, not a measurement, and `flai stats` must say so. ADR-0051's rule that cost is measured, never tabulated, is bent for local models alone, where there is nothing to measure.
- A fourth `priced_by` value changes `design/system/metrics.md`, the contract between `flai stats` and the dashboard, which this ADR is the record for; the dashboard's usage views show it beside the cost.

Limitations:

- A loop of flai's own has none of Claude Code's system prompt, prompt-caching defaults, built-in tools, or the harness behaviour the conventions assume (the Agent tool, `run_in_background`, forks, `parent_tool_use_id`): a role on it is only as good as the loop and the model, and the conventions name Claude Code's tools in places that would read as advice a local-model role cannot follow. The explorer is the role most likely to work on a local model, the verifier next, a task sub-agent last, as ADR-0202 found.
- Only the worktree's files are the container's to write. A test that needs the main checkout, a sibling worktree, or a tool outside the image fails inside it until the project's layer carries the tool; the template's tiers must say what they need.
- A bind mount at the host path is a local shortcut: on WSL2 a mount from the Linux filesystem is fast and from the Windows one is slow, and in a cluster there is no host path at all. The clone path, the branch pushed back as pull-request acceptance pushes it ([ADR-0166](0166-under-pull-request-acceptance-flai-serve-pushes-a-story-s-branch-and-opens-or.md)), is the one that reaches Kubernetes, and changes how `task_done` reaches the worktree.
- A session store of flai's own must survive a restart after a thread is answered, as `--resume` does today, and the baked-in Claude Code's own session lives in its configuration folder, which a read-only mount of the login cannot hold: it needs a writable per-story configuration folder, `CLAUDE_CONFIG_DIR`, in the story's cache folder, which the spike checks.
- `flai mcp start` over HTTP exists for an agent that cannot start a process; whether it carries every tool the stdio server does, with the agent named by header, is unverified, and the container's route to the host's listener differs per network mode and per platform.

Security concerns:

- The container is a boundary flai draws, not a sandbox: `docker run` as the operator's user with a read-write mount of the worktree is isolation from the rest of the machine, not from the worktree, and the Docker socket must never be mounted into an agent's container, since it is the host. The agent's network is the operator's to set, `--network` per harness on the host, and a default that reaches only the providers and the host's MCP listener is the safe one.
- The subscription inside a container is the unmodified `claude` binary run by a platform, which Anthropic's terms allow for an end user's own plan; a login state copied into an image, or shared across projects, is not that, and the login must stay the operator's, mounted read-only per run, never baked in or published.
- Keys reach the container by environment from `key_env`, visible to every process in it, as to every process of a child on the host today; a secrets service fetch at start narrows that to the harness, which holds the key in memory and sets it for the inner loop alone. The image, the start request, and the logs carry names only, and the harness redacts the environment it passes on from every log line.
- The image is a supply chain of its own: a base image, `git`, and `claude` pulled at build time. The release pipeline pins them by digest, signs the image, and `flai serve` runs only a digest a signed release names; a project's own layer is the project's risk and is named in its manifest, so `flai check` can warn on an unsigned one.
- A container that mounts the worktree can still write `.claude/settings.json` and `.mcp.json` inside it: the protected list and `permission_prompt` stand as they do on the host ([ADR-0106](0106-a-story-whose-branch-changes-a-path-claude-code-protects-is-accepted-by-the.md)), and an agent's own `flai` inside the image is the one the release shipped, not one the agent built.

Directions this keeps open, settled by their own ADRs when they are taken:

- **Kubernetes.** The same image runs as one Job per agent run; `flai serve`, or a controller built from it, creates the Job with the start request, the worktree becomes a clone of the story branch pushed back to the host's repository or the forge, `flai mcp` is reached as a Service, and secrets come from the secrets service, since no host environment exists to inherit. Nothing in the harness changes; only the mount becomes a clone and the environment becomes a fetch.
- **signet.** The harness fetches a given agent's secrets and configuration at start from signet with a short-lived identity flai serve mints for the run, and the provider entries on the host name signet paths beside `key_env`. What signet's API is, how an identity is minted and bounded, and what configuration beyond keys it serves are settled when that story is written; this ADR names the seam, the harness's fetch at start, and nothing more.
- **One container per sub-agent.** Nested loops in one container are the first form; a role that needs its own image, its own tools, or its own network, or a cluster that schedules it elsewhere, gets a container of its own started by the harness through flai serve, with the task's ID in its start request so that usage is apportioned as ADR-0071 has it.

What becomes easier: an agent that cannot reach what the story does not claim, a local model in a role with no gateway, cost read per call from the response that made it, a run that moves from a laptop to a cluster unchanged, and a harness whose every surface is flai's to probe. What becomes harder: building and keeping a loop, an image, and a release pipeline for both, and documenting a second way to run an agent. What is given up until the spike reports: nothing; S-0497 builds nothing, and ADR-0202 stays proposed beside this one for the operator to choose between.

## Alternatives considered

- Claude Code on the host, as today: no boundary, one provider per session, no local model in a role; kept as the default, since nothing here replaces it for a project without Docker.
- Docker Agent as the adapter ([ADR-0202](0202-flai-gains-a-docker-agent-harness-adapter-that-runs-a-story-s-agent-as-a-docker.md)): the mixture sooner, at the price of a vendor's loop, hooks, schema, sessions, and telemetry inside flai's agents, and a subscription path with Claude Code's permission prompts off; not chosen by this ADR, left for the operator to weigh beside it.
- Docker Agent as the inner loop of flai's container: flai's mounts, tools, and telemetry switch around Docker Agent's loop, without writing one; it keeps every limitation of that loop, the ignored toolsets, the two guards, the catalogue pricing, and is worth one measurement in the spike before it is ruled out.
- A loop of flai's own on the host, with no container (Option E of [agent-adapters.md](../system/agent-adapters.md#options-compared)): the same loop with none of the boundary, the Kubernetes path, or the controlled tools; the container is what makes the loop worth building.
- A sandbox the harness brings, Docker Agent's `--sandbox` VM or Claude Code's own: neither carries the subscription's `claude` and its login into the sandbox, so the path the operator wants to keep is the one they cannot isolate.
