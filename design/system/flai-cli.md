# flai CLI

`flai` is a single static Go binary. It creates and imports projects, manages work items, validates a repo against the standard, prints metrics, and runs the dashboard. It is designed to be used by humans at a terminal and by agents through non-interactive flags.

Source: `./flai` in this monorepo. Module `github.com/bytepunx/system-flow/flai`.

## Configuration

`~/.flai/config.json`, created on first run with defaults. Overridable with `FLAI_CONFIG` and `--config`.

```json
{
  "template": {
    "repo": "https://github.com/bytepunx/system-flow-template",
    "ref": "main"
  },
  "dashboard": {
    "image": "ghcr.io/bytepunx/flaiover",
    "tag": "latest",
    "port": 4242,
    "bind": "0.0.0.0",
    "push_key": "",
    "push_known_hosts": ""
  },
  "cache_dir": "~/.flai/cache",
  "author": "alex",
  "worktrees": {
    "relative_paths": false
  }
}
```

`host_actions`, `agent`, `checks`, and `import_roots` live in the same file, are absent until set, and are not among `config.Keys`: `flai serve` subcommands manage them (see the `flai serve` rows below). Every key is documented for users in [docs/users/flai.md](../../docs/users/flai.md#configuration).

Template repo cloning goes into `cache_dir/templates/<hash of repo+ref>` and is refreshed with `flai template update`. A local path in `template.repo` is used directly without cloning, which is how this monorepo develops against `./template`.

## Commands

| Command | Purpose |
|---------|---------|
| `flai new <dir>` | Create a new conforming monorepo from the template. Prompts for variables when stdin is a terminal; `--var k=v` sets them, `--defaults` never prompts. `--template` and `--ref` override the config source, `--layout key=name` renames a folder, `--force` overwrites, `--no-git` skips `git init`. |
| `flai import [dir] [--commit] [--trailer]` | Analyse an existing repo, propose the layout, prompt for folder names, create missing structure, offer to move existing markdown into it, write `system-flow.yaml`. `--commit` (S-0098, [ADR-0035](../adrs/0035-repositories-under-folders-the-operator-names-can-be-imported-from-the-board.md)) then runs the repository's tests and commits the import when they pass; see Import flow. |
| `flai serve import add\|remove\|list <folder>` (S-0098, ADR-0035) | The folders whose git repositories without a manifest `flai serve` offers the board for import, kept in the host's configuration as `import_roots` (not among `config.Keys`). `list` shows what `serve.FindCandidates` finds there now: the folders three levels deep, not into a repository, hidden folders, or build output, each with its key (`import-` and the folder's name made safe, unique among the served projects' keys). The git repositories there that have a manifest are served by `flai serve` instead (S-0120, [ADR-0045](../adrs/0044-a-system-flow-repository-under-a-folder-named-for-import-is-served-whether-or.md)). |
| `flai serve project add [folder]`, `remove <key\|folder>`, `list` (S-0121) | The registry of served projects (`serve/projects.json`) managed on its own, with why a project is not showing. `add` requires `system-flow.yaml` in the folder itself (the current one by default), resolves the dashboard address as `flai dashboard` does (`dashboardSettings`), and registers through `registerProject`, which `flai dashboard`'s `connectServe` and `connectServeFolder` call too: the main checkout as the root, the shared agent credential made when missing, then `serve.Dir.Register`; it starts `flai host` when none runs. `serve.Dir.Register` refuses a key another root already has, naming that root, so every writer of the registry (these, `flai dashboard`, the board's import) refuses it. `remove` finds the entry by key first, then by folder (a folder inside a project or a worktree of it names the project), calls `serve.Dir.Unregister`, as `flai dashboard stop` does, and touches no file of the project and not the container; a project served only because `flai serve` was started above it, or because it is below a folder named for import (S-0120), is refused as not registered, naming the folder; a registered one below an import folder is unregistered and the answer says `flai serve` goes on serving it from there (`importRootOf`, from `serve.FindBelow`). Before `serve.Run` drops the connection of a project that left the registry or is now served under another key, it sends the notification `removed` (`serve.Removed`), so the dashboard's switcher drops it; a project that is only unavailable, or a changed entry with the same key, is not removed. `serve.Entry.Unavailable` says why a registered project cannot be served (the folder is gone, not a folder, no manifest, a manifest that does not load or has no key, an unreadable credential); `serve.Run` skips such an entry, logs `registered project not served` once and `registered project can be served again` once, and writes the reasons to its state as `unavailable` by root. `flai serve status` works the reasons out itself, running or not (`unavailable` in `--json`). `list` (and `--json`, `projectListing`) shows each registered project, each served below the folder `flai serve` was started in, and each served below a folder named for import (`from`: registry, folder, or import), with key, root, dashboard address, and `state`: connected with `since`, not-connected with `last_error`, connecting, unavailable with `reason`, or not-running. Then the import candidates (`serve.FindCandidates` over `import_roots`) and the projects below the folders that `flai serve` does not serve, with why (`belowImportRoots`: its state's `unserved` while it runs, `serve.Place` otherwise). `flai dashboard`, `flai import` (`serveImported`), and `add` all register through `registerProject`, which builds the entry with `serveEntry`. |
| `flai check [dir] [--strict]` | Validate manifest and layout, every item in kanban and archive (front matter, ID and file name, parents and children, state history and sequence, acceptance criteria, sections), narratives and index, board limits and order, design/docs front matter including ADRs, and the conventions folder (front matter, unique order, marker and project additions, length, README index), and design/issues (schema, unique IDs, file names, summary freshness), the manifest (`manifest.key` warns when `system-flow.yaml` has no `key`, which API responses use to name the project, ADR-0024), and the clone itself: `git.relative-worktrees` warns when `extensions.relativeWorktrees` is set and the git on `PATH` is older than 2.48, read from `.git/config` because that git refuses the repository (ADR-0022). | `flai block <id> --reason`, `flai unblock <id>` | Open and close blocked intervals. |
| `flai board [--all]` | Stories per column with nature, age in column, blocked flag, WIP counts, and the pull order, with `backlog` and `ready` laid out in it (S-0057); `--all` adds epics and tasks. |
| `flai order <story> --before <id> \| --after <id> \| --top \| --bottom` | Places a ready or backlog story in its column's pull order (S-0057) and rewrites `order` in `board.md`: ready stories, then backlog stories, stale names dropped, the unplaced tail of the backlog left unnamed. | `flai push --pending [--publish] [--dry-run]` | On the host, push what is merged and not pushed (S-0063, ADR-0026). Before deciding what to push it tags: everything `release.Pending` finds accumulated and unreleased since each component's last tag (the same computation `flai release --pending` uses) is applied (version file, changelog, committed) and tagged on HEAD (S-0094) — acceptance alone tags nothing (S-0087), and this is the one place it happens, before the push, not a separate step to remember; `--dry-run` only previews the plan. It then pushes the branch and every tag reachable from it and not from the remote-tracking branch (a release just tagged here, one a prior `flai release --pending` tagged but could not push, or both) with the host's credentials. "nothing pending" otherwise; ordinary commits are left to `git push`; refuses when the two have diverged; never forces. The question is asked offline (`flai/internal/pending`): commits ahead, the items accepted, the tags reachable from the branch and not from the remote-tracking branch, commits behind. `flai board` prints it and `board --json` carries it as `unpushed`. Tags go three to a push and the branch with the last of them (`pending.Batches`, I-0026): GitHub creates no tag events when one push carries more than three tags, so a workflow that releases on a tag never ran; the branch goes last because unpushed tags are found through it, so an interrupted push is still reported. `--publish` (S-0078) also publishes each template component whose `template.yaml` differs between the remote-tracking branch and the checkout, asked before the push because nothing is ahead afterwards, as `flai template push --tag` does and never forced; a publish that fails after the push names the command to finish it. A remote that has moved exits 3 (`exitPushDiverged`) with a `conflict:` message, so a caller that is not a person tells it from a failure |
| `flai stats [--since 30d] [--type story] [--by nature\|type\|parent] [--json]` | The aggregates in [metrics.md](metrics.md) as a table; `--json` adds per-item values, weekly throughput, burn-up (whole set and per parent), cumulative flow, and aging. |
| `flai stream open <story-id> [--no-branch]`, `flai stream log <story-id> "<entry>"` | Create a narrative from the template and, in a git repository, branch `story/<id>` from the main branch checked out in a worktree under `.flai-cache/worktrees/<id>` (ADR-0019; `wip/` is written in the main checkout from anywhere); append a timestamped log entry. With the config key `worktrees.relative_paths` on and git 2.48 or newer the worktree is created with `--relative-paths`; on an older git flai warns and creates an ordinary one (ADR-0022). `FLAI_AGENT` and `FLAI_SESSION` identify the writer. `index.md` is regenerated from the active narratives after every open, log, move, and archive. |
| `flai stream answer <story-id> "<question>" "<answer>" [--by]` | Answers a hand-written bullet under a narrative's `## Open questions` (one mirrored from a thread has its own `flai thread reply` instead, S-0090): removes it, exactly as `<question>` reads (an inbox `question` entry's own title), and records it with `<answer>` under `## Decisions` ([agent-narrative.md](agent-narrative.md): "Answered questions move to Decisions"). | `flai stream diff <story-id>` | The story branch against its merge base with the main branch (S-0041): per file the path, status (added, modified, deleted, renamed), additions, deletions, and unified hunks; binary files without hunks; a file's patch and the whole result are capped and marked `truncated`. Read with git in the main checkout, so it does not need the worktree. `--json` is what the dashboard's review page shows. |
| `flai migrate ids [--dry-run]` | Widen every work item and issue ID to four digits: rename items and narratives in kanban and archive, and issues under `design/issues`, with `git mv` (plain rename outside git) and rewrite references in the layout folders, the root markdown and yaml files, and each project's root markdown files. A manifest that does not parse is still an error. |

| `flai release --pending [--dry-run]` (S-0087, [ADR-0032](../adrs/0032-accepting-a-story-merges-it-publishing-is-a-deliberate-batched-step-over.md)) | Publish everything accumulated: `release.Pending` finds, per component, every accepted item since that component's last tag (or ever, with none) and takes the highest delivery level among them, one bump for the batch, not one per item; a component with nothing since its last tag is left out. Completes a story that is done but unarchived. `--dry-run --json` is the dashboard's preview (branch, blockers, uncommitted). Uncommitted changes under `wip/` are expected; anything else is refused unless `--yes` includes it in the acceptance commit. A dry run never refuses for them: it lists them in `uncommitted`, with or without `--yes`, so the choice is made before confirming (S-0051). |

| `flai host`, `host start [serve\|mcp\|all]`, `host stop [serve\|mcp\|all]`, `host restart <serve\|mcp\|all>`, `host status`, `host check`, `host upgrade` (S-0106, [ADR-0040](../adrs/0040-one-flai-host-per-machine-runs-flai-serve-and-each-project-s-mcp-server-as-its.md)) | One process per machine that runs `flai serve` and each served project's `flai mcp http` as its children (`internal/host`, with `cmd/host.go`'s `hostLauncher` saying how to start each). It binds `127.0.0.1:4241` (`FLAI_HOST_ADDR`, `host.AddrEnv`) before anything else, which is what makes it one per machine; a second host is refused with the first one's `/_health` (pid, version, config, started: the one route without a token) as `AlreadyRunningError`. The control API on that address needs `Authorization: Bearer` with the token the host makes at each start, hands its children in `FLAI_HOST_URL` and `FLAI_HOST_TOKEN`, and writes to `host/token` (0600) beside the config; a request with an `Origin` is refused. Routes: `GET /status`, `POST /process {process, action}` (`serve`, `mcp`, `all`; `start`, `stop`, `restart`; a restart of a stopped one starts it; a stop keeps it stopped until a start), `PUT /mcp {roots}` (the projects whose MCP server to keep: missing ones started, others stopped), `GET /check` (`flai self-upgrade --check --json`), `POST /upgrade` (`flai self-upgrade --json`; when it installed, the host answers, stops its children, and `Run` returns `ErrRestart`, on which `cmd` replaces the process with the new binary, `host.Reexec`: `syscall.Exec` on Unix, a new process on Windows). A child is started from the binary on disk, with `--config` and `--exit-with <host pid>`, its output appended to its log (`serve/serve.log`, the project's `.flai-cache/mcp-http.log`); one that ends unasked is started again after a backoff from 1 s doubling to 30 s, reset after a minute of running; when `Run` returns every child gets SIGTERM and after `hostGrace` (15 s) SIGKILL. A `flai serve` or MCP server already running that the host did not start is `external`: used, never stopped, looked at again every 15 s. MCP addresses are `mcpAddrFor`'s, with those given to other roots left out. State `host/state.json` (pid, version, started, updated, addr, config, children with name, root, state `running`\|`waiting`\|`external`\|`stopped`, pid, since, version, restarts, last exit, last error), rewritten every second and stale after ten; log `host/host.log`. `flai host` runs in the foreground; `start` detaches it in the working directory (which `flai serve` inherits, so a folder is served whole, S-0102) and waits for its state; `stop` signals it and waits; `status` asks the API, else reads the state, and names a host that runs for another config. |
| `flai serve`, `flai serve start`, `stop`, `status` (S-0072, ADR-0029) | flai's process on the host that dashboards are reached through: one per user, serving every project registered with it. For each project it opens a WebSocket to that project's dashboard (`/agent`), the two prove to each other that they hold the agent credential without sending it (HMAC over two nonces), and then speak JSON-RPC 2.0: the dashboard asks, flai answers from a table of named methods (`internal/channel`), checked against the project key on every request. The methods are `flai hostapi`'s, below. It also watches each project's design, docs, and wip folders and its manifest (`internal/watch`: a poll every 300 ms, a file reported once it has looked the same for one tick) and sends the dashboard a `change` notification with the repository-relative path; nothing is queued for a dashboard that is not connected. Pings every 4 seconds, reconnection with backoff and jitter from 250 ms to 4 s, a 16 MiB cap on a message, cancellation by notification. Bare `flai serve` runs in the foreground; `start` runs it detached without root and waits for its first state; `stop` terminates it; `status` (and `--json`) says whether it runs, since when, and for each registered project the dashboard address and whether it is connected or why not. Registry (`projects.json`), state (`state.json`, rewritten every second, stale after ten), and log live in a `serve` folder beside flai's config file, so a repository with its own `FLAI_CONFIG`, and every test, has its own. A second `flai serve` refuses while the first is alive Since S-0098 it also offers the board, over candidate connections, the repositories under the folders named with `flai serve import` (see `flai serve import`, and the dashboard channel's candidates). Since S-0096 each served project's HTTP MCP server is kept running; since S-0106 `flai host` does it and `flai serve` starts no MCP process: `internal/serve/mcp.go`'s `mcpTeller` tells the host every served root (`MCP.Keep`, `cmd`'s `hostMCP` over the host's client) when the set changes and every 15 s, and nothing when `flai serve` stops, so a restart of serve leaves the servers running ([ADR-0040](../adrs/0040-one-flai-host-per-machine-runs-flai-serve-and-each-project-s-mcp-server-as-its.md), superseding ADR-0034). Outside a host (no `FLAI_HOST_URL`) it keeps none. `flai serve start` starts the host, or asks the running one to start serve; `stop` asks the host to stop serve and terminates one the host did not start; a hidden `--exit-with` ends it when the host is gone. ## Import flow

`flai import` is the deliberate, interactive path for existing repos.

1. Scan the tree. Detect existing `design`, `docs`, `wip`, `adr`, `adrs`, `architecture`, `documentation` folders and any markdown outside code folders. Detect sub-projects by build files (`go.mod`, `package.json`, `pyproject.toml`, `Cargo.toml`).
2. Present a proposal: which folders will be created, which existing folders look like they map to `design`, `docs`, or `wip`, which candidate folders (`adr`, `adrs`, `architecture`, `doc`, `documentation`) move whole into the structure, which loose markdown needs a decision, and which sub-projects were found.
3. Ask for folder names, offering existing folders and the template defaults; `--layout key=name` sets them without asking.
4. Move candidate folders (confirmed one by one in a terminal), then render the template files that do not already exist. Nothing is overwritten; a conflicting file in a moved folder stays where it was and is reported.
5. For each loose markdown file, ask: `design/system`, `design/adrs`, `docs/<audience>`, leave in place, or skip all remaining. Non-interactive runs leave files in place. Moves are `git mv` when the file is tracked.
6. Write `system-flow.yaml` with the detected sub-projects, run `flai check`, print a summary and next steps.
7. Have the host flai serve it (S-0120): when `flai host` runs for the config (`host.Dir.ReadStatus`), register the project with `flai serve` using the entry `flai dashboard` writes (`serveEntry`: key and name from the manifest, the main checkout, `dashboardSettings`' dial address, the shared agent credential, created if missing) and say the dashboard's address; when `flai serve` is stopped under the host, say `flai serve start`. With no host, register nothing and name `flai dashboard` in the project. `--json` carries this as `serve` (`served`, `dashboard`, `reason`, `next`, `root`). A board import runs the same command and `flai serve` then registers it again for the dashboard it was offered on, which replaces the entry by root.

The template's `repo_url` defaults to the `origin` remote made a web address (`webURL`: scp-like, `ssh://`, `git://`, and `http(s)://` remotes become `https://host/path` without credentials, port, or `.git`; a local path or `file://` gives none). `checkRepoURL` refuses a `repo_url` that is not an http or https URL with a host and a path, at the prompt and, for `--var`, before `flai import` or `flai new` changes anything (S-0120).

`--dry-run` prints the proposal and stops (`--json` gives the analysis, the plan, and, since S-0098, the tests `--commit` would run). `--yes` accepts every default. A tree that already has a manifest is refused unless `--force`. With `--json` the proposal's text is no longer printed ahead of the JSON.

`--commit` (S-0098) makes the import one step that ends in a commit:

- Before anything, it refuses a directory that is not a git repository, or has uncommitted changes (`git status --porcelain`), so the commit holds the import and nothing of the operator's.
- After the import it runs tests. It runs the host's `checks.commands` when any are set (`{root}` is the repository; `{story}` is empty). Otherwise `importer.DetectTests` finds the repository's own tests: its own Makefile's `test` target (a Makefile the template brought does not count) stands for everything; otherwise, at the root and in each sub-project, `go test ./...` for `go.mod`, `pnpm`/`yarn`/`npm test` for a `package.json` test script that is not npm's placeholder, `cargo test`, and `python3 -m pytest`. Each runs as an argument list, never through a shell, in turn and all of them, within the checks timeout (15 minutes unless set). Each start and end is logged, which is the progress the board shows.
- When every test passed or none were found, it stages exactly the paths the import wrote and moved (a `git mv` source is already staged) and commits `chore: bring <name> under system-flow (flai import)` with `--trailer` lines.
- When a test fails it commits nothing, leaves the import in the working tree, answers with each test's outcome and the last 8 KiB of its output, and exits 5 (`exitImportNotCommitted`).

## Internal structure

```text
flai/
├── main.go
├── cmd/                 # one file per cobra command
├── internal/
│   ├── config/          # ~/.flai/config.json
│   ├── manifest/        # system-flow.yaml
│   ├── template/        # clone, cache, render
│   ├── workitem/        # parse, validate, transition, ID allocation, board, narratives, archive
│   ├── atomicfile/      # replace a file in one step: a reader sees the old or the new, never half (S-0100)
│   ├── execx/           # git and docker behind a Runner interface
│   ├── logx/            # slog setup per the logging convention: levels incl. fatal, env and flag
│   ├── narrative/       # wip/agents files
│   ├── check/           # reference validator, rule names are stable identifiers
│   ├── conventions/     # loads and validates design/conventions
│   ├── issues/          # design/issues: record, bump, close, summary
│   ├── release/         # semver plan from item, commits, and manifest components; tags and version files
│   ├── lock/            # system-flow.lock.yaml
│   ├── upgrade/         # classify add, merge, replace, conflict; apply with a policy
│   ├── publish/         # push a local template to its remote: clone, replace, commit, tag, push
│   ├── metrics/         # reference implementation of metrics.md
│   ├── importer/        # scan, plan, moves with git mv
│   ├── dashboard/       # docker run/stop
│   ├── host/            # flai host: children, control API, one per machine (S-0106)
│   ├── harness/         # a story's agent as a command to start: claude-code, the operator's command (S-0104)
│   └── ui/              # prompts and tables
└── testdata/
```

External processes: `git` and `docker` are invoked as subprocesses and must be on `PATH`. See ADR 0010.

Work items, `board.md`, narratives and their index, and threads (with the block mirrored into a narrative) are written with `atomicfile.WriteFile`, a temporary file beside the target renamed over it (S-0100). They are read while they change: by the MCP server's `inbox` and `wait_for_events`, by `flai serve`'s watcher, and by the dashboard through flai. `os.WriteFile` truncates first, and a reader in between saw an empty file ("no front matter", I-0036).

Front matter is parsed with goccy/go-yaml but written by a small purpose-built emitter, so timestamps stay unquoted, sequences stay indented, and a `flai` edit never rewrites lines it did not change. Item bodies come from the template's `items/` when the project's template is in the cache, else from copies embedded in the binary.
