# flai CLI

`flai` is a single static Go binary. It creates and imports projects, manages work items, validates a repo against the standard, prints metrics, and runs the dashboard. It is designed to be used by humans at a terminal and by agents through non-interactive flags.

Source: `./flai` in this monorepo. Module `github.com/bytepunx/system-flow/flai`.

## Configuration

`~/.flai/config.json`, created on first run with defaults. Overridable with `FLAI_CONFIG` and `--config`.

```json
{
  "template": {
    "repo": "https://github.com/bytepunx/system-flow-template",
    "ref": "main"
  },
  "dashboard": {
    "image": "ghcr.io/bytepunx/flaiover",
    "tag": "latest",
    "port": 4242
  },
  "cache_dir": "~/.flai/cache",
  "author": "alex"
}
```

Template repo cloning goes into `cache_dir/templates/<hash of repo+ref>` and is refreshed with `flai template update`. A local path in `template.repo` is used directly without cloning, which is how this monorepo develops against `./template`.

## Commands

| Command | Purpose |
|---------|---------|
| `flai new <dir>` | Create a new conforming monorepo from the template. Prompts for variables when stdin is a terminal; `--var k=v` sets them, `--defaults` never prompts. `--template` and `--ref` override the config source, `--layout key=name` renames a folder, `--force` overwrites, `--no-git` skips `git init`. |
| `flai import [dir] [--commit] [--trailer]` | Analyse an existing repo, propose the layout, prompt for folder names, create missing structure, offer to move existing markdown into it, write `system-flow.yaml`. `--commit` (S-0098, [ADR-0035](../adrs/0035-repositories-under-folders-the-operator-names-can-be-imported-from-the-board.md)) then runs the repository's tests and commits the import when they pass; see Import flow. |
| `flai serve import add\|remove\|list <folder>` (S-0098, ADR-0035) | The folders whose git repositories without a manifest `flai serve` offers the board for import, kept in the host's configuration as `import_roots` (not among `config.Keys`). `list` shows what `serve.FindCandidates` finds there now: the folders three levels deep, not into a repository, hidden folders, or build output, each with its key (`import-` and the folder's name made safe, unique among the served projects' keys). |
| `flai check [dir] [--strict]` | Validate manifest and layout, every item in kanban and archive (front matter, ID and file name, parents and children, state history and sequence, acceptance criteria, sections), narratives and index, board limits and order, design/docs front matter including ADRs, and the conventions folder (front matter, unique order, marker and project additions, length, README index), and design/issues (schema, unique IDs, file names, summary freshness), the manifest (`manifest.key` warns when `system-flow.yaml` has no `key`, which API responses use to name the project, ADR-0024), and the clone itself: `git.relative-worktrees` warns when `extensions.relativeWorktrees` is set and the git on `PATH` is older than 2.48, read from `.git/config` because that git refuses the repository (ADR-0022). One `path:line: level: rule: message` per finding. Errors exit 1; `--strict` makes warnings exit 1. |
| `flai epic new`, `flai story new --epic E-0001`, `flai task new --story S-0004` | Create an item from the body template, allocate the next ID, link to parent. `--body-stdin` reads the body below the heading from standard input (S-0059), and creation is then one step (`flai/internal/itemnew`): `flai check` before and after, anything the item introduces refuses it with exit 4 and the findings as `{ refused }`, the file removed, the parent restored, and the ID not spent. `--autocommit` commits the item and its parent, path limited, as `chore: [ID] create <type>: <title>` with `--trailer` lines, unless `dashboard.autocommit` is false. `--print-body` prints the body the project's template gives the type and creates nothing. A story gets the project's default agent, with `--harness`, `--model`, and `--agent-config key=value` (repeatable) laid over it (S-0103); another type given them is refused. |
| `flai move <id> <state>` | Transition an item with rule validation. `--reason` required for `cancelled` and for review to in-progress; `--by` defaults to `FLAI_AGENT` when it is set, else the config author, as for `flai block`, `unblock`, and threads, so an agent's moves are recorded as the agent's (S-0058). Warns on WIP limit breaches. A move to `cancelled` cancels everything open under the item too (ADR-0028): the items are listed first, a terminal is asked unless `--yes`, `--dry-run` lists and changes nothing, `--json` answers `{ id, status, cancelled[], left_behind[], warnings[] }`, and the narratives, story branches, and worktrees of cancelled stories are named and left as they are (S-0070). Moving a story from review to done is acceptance and runs the `flai accept` flow with its flags (S-0046). |
| `flai show <id>` | One item with history, blocks, and children. |
| `flai block <id> --reason`, `flai unblock <id>` | Open and close blocked intervals. |
| `flai board [--all]` | Stories per column with nature, age in column, blocked flag, WIP counts, and the pull order, with `backlog` and `ready` laid out in it (S-0057); `--all` adds epics and tasks. |
| `flai order <story> --before <id> \| --after <id> \| --top \| --bottom` | Places a ready or backlog story in its column's pull order (S-0057) and rewrites `order` in `board.md`: ready stories, then backlog stories, stale names dropped, the unplaced tail of the backlog left unnamed. Refuses epics, tasks, other states, and a reference in another column, with the reason. `--json` prints `{ id, status, sequence, order }`. Rules in [workflow.md](workflow.md). |
| `flai push --pending [--publish] [--dry-run]` | On the host, push what is merged and not pushed (S-0063, ADR-0026). Before deciding what to push it tags: everything `release.Pending` finds accumulated and unreleased since each component's last tag (the same computation `flai release --pending` uses) is applied (version file, changelog, committed) and tagged on HEAD (S-0094) — acceptance alone tags nothing (S-0087), and this is the one place it happens, before the push, not a separate step to remember; `--dry-run` only previews the plan. It then pushes the branch and every tag reachable from it and not from the remote-tracking branch (a release just tagged here, one a prior `flai release --pending` tagged but could not push, or both) with the host's credentials. "nothing pending" otherwise; ordinary commits are left to `git push`; refuses when the two have diverged; never forces. The question is asked offline (`flai/internal/pending`): commits ahead, the items accepted, the tags reachable from the branch and not from the remote-tracking branch, commits behind. `flai board` prints it and `board --json` carries it as `unpushed`. Tags go three to a push and the branch with the last of them (`pending.Batches`, I-0026): GitHub creates no tag events when one push carries more than three tags, so a workflow that releases on a tag never ran; the branch goes last because unpushed tags are found through it, so an interrupted push is still reported. `--publish` (S-0078) also publishes each template component whose `template.yaml` differs between the remote-tracking branch and the checkout, asked before the push because nothing is ahead afterwards, as `flai template push --tag` does and never forced; a publish that fails after the push names the command to finish it. A remote that has moved exits 3 (`exitPushDiverged`) with a `conflict:` message, so a caller that is not a person tells it from a failure |
| `flai stats [--since 30d] [--type story] [--by nature\|type\|parent] [--json]` | The aggregates in [metrics.md](metrics.md) as a table; `--json` adds per-item values, weekly throughput, burn-up (whole set and per parent), cumulative flow, and aging. |
| `flai stream open <story-id> [--no-branch]`, `flai stream log <story-id> "<entry>"` | Create a narrative from the template and, in a git repository, branch `story/<id>` from the main branch checked out in a worktree under `.flai-cache/worktrees/<id>` (ADR-0019; `wip/` is written in the main checkout from anywhere); append a timestamped log entry. With the config key `worktrees.relative_paths` on and git 2.48 or newer the worktree is created with `--relative-paths`; on an older git flai warns and creates an ordinary one (ADR-0022). `FLAI_AGENT` and `FLAI_SESSION` identify the writer. `index.md` is regenerated from the active narratives after every open, log, move, and archive. |
| `flai stream answer <story-id> "<question>" "<answer>" [--by]` | Answers a hand-written bullet under a narrative's `## Open questions` (one mirrored from a thread has its own `flai thread reply` instead, S-0090): removes it, exactly as `<question>` reads (an inbox `question` entry's own title), and records it with `<answer>` under `## Decisions` ([agent-narrative.md](agent-narrative.md): "Answered questions move to Decisions"). Refuses if none matches. `--by` defaults through `FLAI_AGENT`, then the config author, same as `flai thread reply`. |
| `flai stream diff <story-id>` | The story branch against its merge base with the main branch (S-0041): per file the path, status (added, modified, deleted, renamed), additions, deletions, and unified hunks; binary files without hunks; a file's patch and the whole result are capped and marked `truncated`. Read with git in the main checkout, so it does not need the worktree. `--json` is what the dashboard's review page shows. |
| `flai migrate ids [--dry-run]` | Widen every work item and issue ID to four digits: rename items and narratives in kanban and archive, and issues under `design/issues`, with `git mv` (plain rename outside git) and rewrite references in the layout folders, the root markdown and yaml files, and each project's root markdown files. Idempotent. |
| `flai archive [id...] [--dry-run]` | Move done and cancelled items and their narratives to `wip/archive`. Default: every closed epic whose stories are archived, every closed story with its tasks, and closed tasks whose story is gone from the board. |
| `flai dashboard [--image] [--tag] [--port] [--bind] [--no-serve] [--pull] [--attach] [--open] [--build]`, `flai dashboard stop\|status\|logs` | Pull the flaiover image if missing (on an unauthorized pull from a non-Hub registry, `docker login` with `GITHUB_TOKEN`, `GH_TOKEN`, or `gh auth token` and one retry, else an error naming the `read:packages` scope; `--build` builds `flaiover:local` from `flaiover/` in the monorepo instead) and run it detached as `flaiover-<project>`, published on `dashboard.bind` (default every interface), as the host user so that it can read its two secrets, and given nothing of the project: no volume, no `PROJECT_DIR`, no git identity, excludes file, read-only git paths, or push key (S-0077, [ADR-0031](../adrs/0031-the-dashboard-s-container-holds-nothing-of-the-project-a-port-and-two-secrets.md), superseding ADR-0022, ADR-0026, and ADR-0027; `dashboard_guard.go` and `dashboard_pushkey.go` are gone). Precedence: flags, manifest `dashboard`, config. `--push-key`, `--push-known-hosts`, and the config keys `dashboard.push_key` and `dashboard.push_known_hosts` are retired but still accepted, hidden from help, so an old configuration loads and can be cleared: set, the start message (and `retired` in `--json`) names them, says they are ignored, and points at `flai push --pending`. Status and the already-running message inspect the real container; `status` lists a running container's mounts outside `/run/secrets` (`stale_mounts`) and says it was started by an older flai and should be restarted. Since S-0072 it also creates the agent credential (`.flai-cache/dashboard.agent-key`, mode 0600, never the login token), mounts it at `/run/secrets/flaiover_agent_key` with `FLAIOVER_AGENT_KEY_FILE`, registers the project with `flai serve` (key, root, the address to dial: the bind address, or `127.0.0.1` when bound to every interface, and the credential's path) and starts `flai serve` when none runs; `--no-serve` skips both. The credential and, when flai's config lives in the clone, the `serve` folder are added to the read-only mounts of ADR-0027. `stop` unregisters the project and leaves `flai serve` running; `status` adds `host_flai`: running, registered, connected and since when, or the last error In a folder with no `system-flow.yaml` up the tree (S-0101, [ADR-0036](../adrs/0036-a-folder-that-is-not-a-project-is-served-whole-by-flai-mcp-and-flai-dashboard.md)) every subcommand works with the host's configuration alone. `flai dashboard` starts or reports the shared container and `flai serve`, registers the projects `workitem.FindProjects` finds below the folder, names the folder for import (`import_roots`), and records the dashboard (`serve/dashboards.json`) so that `flai serve` offers it repositories to import with no project served. `stop` unregisters nothing of its own, stops the container once no project is left, and forgets the recorded address. A manifest that does not parse is still an error. |
| `flai upgrade [--dry-run] [--force] [--keep-all\|--replace-all] [--relock]` | Bring the project to the template version at the configured source: add new files, merge marker files above the marker, replace files unchanged since applied (per `system-flow.lock.yaml`, ADR-0015), report the rest as conflicts with keep, replace, or diff; refuses a dirty tree; `--relock` records a hand-assembled project. |
| `flai prime [--cat] [--json]` | Print `design/conventions` in read order, README first, as paths or contents, so an agent or hook loads the norms in one call; the open-issues summary follows when non-empty. |
| `flai release <id> [--dry-run] [--deliver] [--apply]` | Compute the semver release for one item per the git convention (delivered component gets the delivery-type bump, touched components a patch; the delivered component is `--deliver`, else the one the item's tags and then its epic's tags name among the components its commits touched, the most touched files winning and the earlier tag breaking a tie, else the only touched one; a tag naming an untouched component never delivers, S-0047) and with `--apply` create the tags and version bumps. A `research` story plans no release ([ADR-0025](../adrs/0025-research-is-accepted-without-a-release.md)): `skipped` gives the reason and `unreleased` lists `{ component, files }` for each component its commits touched; an `experiment` story is an error. |
| `flai release --pending [--dry-run]` (S-0087, [ADR-0032](../adrs/0032-accepting-a-story-merges-it-publishing-is-a-deliberate-batched-step-over.md)) | Publish everything accumulated: `release.Pending` finds, per component, every accepted item since that component's last tag (or ever, with none) and takes the highest delivery level among them, one bump for the batch, not one per item; a component with nothing since its last tag is left out. Applies (version files, one changelog entry naming every item the batch bundles), commits, tags — skipping a tag that already exists, from a prior run that tagged but failed to push — then pushes the branch and every tag together, three tags to a push (`pending.Batches`, I-0026). Resumable: rerun after a partial failure finishes what is left, without redoing what already tagged or pushed. `--dry-run` prints every pending plan and changes nothing. |
| `flai accept <id> [--by] [--trailer]` | The operator's acceptance in one step, and nothing more since S-0087: preflight, before anything changes (committer identity; the workflow's rules for done, open tasks and unticked criteria, checked on a copy since S-0041; the story worktree readable by git; an experiment refused, ADR-0025), rebase and fast-forward the story branch into main and remove its worktree, move to done, archive, commit. No tag, no version bump, no push: publishing what has accumulated is `flai release --pending`, a deliberate step of its own. Completes a story that is done but unarchived. `--dry-run --json` is the dashboard's preview (branch, blockers, uncommitted). Uncommitted changes under `wip/` are expected; anything else is refused unless `--yes` includes it in the acceptance commit. A dry run never refuses for them: it lists them in `uncommitted`, with or without `--yes`, so the choice is made before confirming (S-0051). |
| `flai issue new "<title>" --class <c> [--cost] [--note]`, `flai issue bump <id> [--cost] [--note]`, `flai issue close <id> --reason`, `flai issue list [--all]`, `flai issue summary` | Record, increment, and close recurring friction in `design/issues`; every command regenerates `summary.md` (average and total cost, most expensive first). |
| `flai template show`, `flai template update`, `flai template use <repo> [--ref]` | Inspect, refresh, and switch the template source. |
| `flai template push [dir] [--remote] [--ref] [--tag] [--dry-run] [--force]` | Publish a locally developed template to its git remote: clone the branch, replace contents, commit with the version, push, and with `--tag` push `v<version>` (refused if it exists). Defaults from `publish` in `template.yaml`. Git errors surface verbatim; no retries; no force push unless `--force`. `flai release --pending` and `flai push --pending --publish` call it for template components (S-0087). |
| `flai config get [key]`, `flai config set <key> <value>`, `flai config path` | Read and edit `~/.flai/config.json` by dotted key; `path` prints the resolved file without creating it. Keys: `template.*`, `dashboard.*`, `cache_dir`, `author`, and `worktrees.relative_paths` (boolean, default false, ADR-0022). |
| `flai version` | Version, commit, build date. |
| `flai serve`, `flai serve start`, `stop`, `status` (S-0072, ADR-0029) | flai's process on the host that dashboards are reached through: one per user, serving every project registered with it. For each project it opens a WebSocket to that project's dashboard (`/agent`), the two prove to each other that they hold the agent credential without sending it (HMAC over two nonces), and then speak JSON-RPC 2.0: the dashboard asks, flai answers from a table of named methods (`internal/channel`), checked against the project key on every request. The methods are `flai hostapi`'s, below. It also watches each project's design, docs, and wip folders and its manifest (`internal/watch`: a poll every 300 ms, a file reported once it has looked the same for one tick) and sends the dashboard a `change` notification with the repository-relative path; nothing is queued for a dashboard that is not connected. Pings every 4 seconds, reconnection with backoff and jitter from 250 ms to 4 s, a 16 MiB cap on a message, cancellation by notification. Bare `flai serve` runs in the foreground; `start` runs it detached without root and waits for its first state; `stop` terminates it; `status` (and `--json`) says whether it runs, since when, and for each registered project the dashboard address and whether it is connected or why not. Registry (`projects.json`), state (`state.json`, rewritten every second, stale after ten), and log live in a `serve` folder beside flai's config file, so a repository with its own `FLAI_CONFIG`, and every test, has its own. A second `flai serve` refuses while the first is alive Since S-0098 it also offers the board, over candidate connections, the repositories under the folders named with `flai serve import` (see `flai serve import`, and the dashboard channel's candidates). Since S-0096 it also keeps each served project's HTTP MCP server running ([ADR-0034](../adrs/0034-flai-serve-keeps-each-served-project-s-http-mcp-server-running.md); see `flai mcp http` below). Since S-0102, started in a folder that is not a project (its working directory, which `flai serve start` passes on), it treats the folder as `flai dashboard` there does ([ADR-0036](../adrs/0036-a-folder-that-is-not-a-project-is-served-whole-by-flai-mcp-and-flai-dashboard.md), an added case). `Options.Folder` is looked in every `ScanEvery` for projects (`workitem.FindProjects`), which are served for the first dashboard, by address, that the registered projects or a recorded one reach, for as long as it runs and without being written to the registry. The folder is also an import root. `Status` carries `folder` and `folder_projects`, and `flai serve status` lists them. |
| `flai serve enable\|disable <action> [--all-projects]`, `flai serve actions`, `flai serve journal [-n N]` (S-0078, ADR-0029) | Host actions: what `flai serve` does on the host as the operator because a dashboard asked. There are four: `push`, `agent`, `dashboard` (S-0081), and, since S-0082, `checks`. Each is off until enabled by name, per project (the main checkout's path) or for all (`*`), in `host_actions` of the host's configuration, which is not among `config.Keys`, so `flai config set` cannot reach it; `internal/hostapi` has no method that reads or writes the configuration or the journal, and a test holds that. `hostapi.Host{Enabled, Record}` is the operator's say, wired by `cmd` to read the configuration at every question (no restart) and to append to `serve/journal.jsonl` (0600) beside the state. A spec with `action` is refused while disabled with `Disabled` (-32012, HTTP 403) and `Data{action, enable}`, journalled as `disabled`; a spec with `uses` does without the action when it is off and is journalled when it is on. `accept.run` (`flai accept`) never pushes or releases since S-0087 and is not gated on `push` at all any more, closing I-0028 differently than before: there is nothing left for it to do unasked. `push.run` is `flai push --pending --publish`; `publish.run` (S-0087, [ADR-0032](../adrs/0032-accepting-a-story-merges-it-publishing-is-a-deliberate-batched-step-over.md)) is `flai release --pending`, the same gate, since both act with the operator's credentials; both map exit 3 to `Conflict`. `publish.preview` is a read (`flai release --pending --dry-run`), not gated. `dashboard.restart`, `dashboard.upgrade`, and `dashboard.stop` (S-0081) gate on `dashboard` and wrap `flai dashboard restart\|upgrade\|stop`; `dashboard.status` and `dashboard.check` are reads, not gated, matching `publish.preview`'s precedent (`dashboard.check` still pulls an image to compare it, a read that does real work, like `push.pending`'s dry-run fetch). `checks.run` and `checks.cancel` (S-0082) gate on `checks` and wrap `flai checks run\|cancel`; `checks.status` and `checks.tail` are reads, not gated, `checks.tail` streaming its run's own log lines as `$/progress`. `dashboard.restart`\/`upgrade`\/`stop` and `checks.run` set `spec.detachTimeout`: a write whose own success (or, for checks, the operator simply closing the page) can end the request's own connection runs with a background context instead, so that connection dying does not cancel the command through it (found live, S-0081's T-0325). `project.info` reports `host_actions` so the dashboard can say what will happen; it is asked fresh, not remembered, because no file of the project changes with it |
| `flai serve agent`, `agent set [--name] [--attended-minutes] -- <program> [args...]`, `agent harness [<name>] [--program] [--reset] [-- args...]`, `agent show`, `agent clear` (S-0079, S-0104, ADR-0029, [ADR-0038](../adrs/0038-flai-serve-starts-a-story-s-own-agent-through-an-adapter-with-what-the-operator.md)) | The second host action, `agent`, is not asked for by any method of the channel: `flai serve` performs it itself (`internal/serve/agents.go`). Per served project a launcher is told of every changed path under `kanban/` and `threads/` by the watcher, of the end of an agent it started, and every minute. It starts an agent for each ready story in pull order that is not blocked, has no agent running, entered ready after the launcher's first look (a restart of `flai serve` starts nothing), and has had no agent started since it entered ready. It stops when the in-progress limit is reached, counting a running agent whose story is still in ready as a story in progress, or when someone is attending: the newest mtime among `.flai-cache/mcp/*.json` and the story narratives `wip/agents/S-*.md` is younger than `attended_minutes` (6), leaving out the cursor and narrative of agents it started. A story that names no harness while no command is set waits, which is not a failure. Each run is started through `internal/harness`: `harness.For` picks the adapter from the story's `agent.harness`, or `command` when it names none. `claude-code` builds `claude -p <prompt> --output-format stream-json --verbose --mcp-config {flai: this flai's mcp} --strict-mcp-config --name "<key> <story>" --session-id <uuid> [--model] [--effort] [--max-budget-usd] [--fallback-model]` and then the operator's arguments (default `--permission-mode acceptEdits --allowedTools Bash,mcp__flai`). It is `exec`ed in the project's directory, detached (`serve.Detach`), with `FLAI_AGENT` `<name>-<story>`, `FLAI_STORY`, `FLAI_SESSION`, `FLAI_STARTED_BY=flai-serve`, its output in `serve/agents/<key>-<story>-<time>.log`. When it ends, `judge` reads where it left the story: review or done is `worked`; an open thread on the story whose last entry is the agent's is `asked`, with the thread; anything else is `failed`, with where and whether blocked and the exit code. An `asked` run is started again, as the same agent in the same session (`--resume`), as soon as its thread has an entry by someone else or is resolved, whatever the limit or anyone attending. A run whose process is gone and that no launcher waits for (it outlived an earlier `flai serve`) is judged at the next look. State per project in `serve/agents.json`: `stories` (each story's newest run, with harness, model, session, outcome, why, thread), and `running`, `last`, and `waiting` as before. Every start and failure is a journal entry with action `agent`. `agent.status` (`hostapi`, read-only, asked fresh by the dashboard) reports `enabled`, that state with the command's name and never its arguments, and `stories`: `serve.Activity`, each story's `working`, `waiting` (running with a question of its own open or its story blocked, or `asked`), `failed`, or `worked`. The configuration is read at every look, so enabling, disabling, and new commands need no restart |

## Import flow

`flai import` is the deliberate, interactive path for existing repos.

1. Scan the tree. Detect existing `design`, `docs`, `wip`, `adr`, `adrs`, `architecture`, `documentation` folders and any markdown outside code folders. Detect sub-projects by build files (`go.mod`, `package.json`, `pyproject.toml`, `Cargo.toml`).
2. Present a proposal: which folders will be created, which existing folders look like they map to `design`, `docs`, or `wip`, which candidate folders (`adr`, `adrs`, `architecture`, `doc`, `documentation`) move whole into the structure, which loose markdown needs a decision, and which sub-projects were found.
3. Ask for folder names, offering existing folders and the template defaults; `--layout key=name` sets them without asking.
4. Move candidate folders (confirmed one by one in a terminal), then render the template files that do not already exist. Nothing is overwritten; a conflicting file in a moved folder stays where it was and is reported.
5. For each loose markdown file, ask: `design/system`, `design/adrs`, `docs/<audience>`, leave in place, or skip all remaining. Non-interactive runs leave files in place. Moves are `git mv` when the file is tracked.
6. Write `system-flow.yaml` with the detected sub-projects, run `flai check`, print a summary and next steps.

`--dry-run` prints the proposal and stops (`--json` gives the analysis, the plan, and, since S-0098, the tests `--commit` would run). `--yes` accepts every default. A tree that already has a manifest is refused unless `--force`. With `--json` the proposal's text is no longer printed ahead of the JSON.

`--commit` (S-0098) makes the import one step that ends in a commit:

- Before anything, it refuses a directory that is not a git repository, or has uncommitted changes (`git status --porcelain`), so the commit holds the import and nothing of the operator's.
- After the import it runs tests. It runs the host's `checks.commands` when any are set (`{root}` is the repository; `{story}` is empty). Otherwise `importer.DetectTests` finds the repository's own tests: its own Makefile's `test` target (a Makefile the template brought does not count) stands for everything; otherwise, at the root and in each sub-project, `go test ./...` for `go.mod`, `pnpm`/`yarn`/`npm test` for a `package.json` test script that is not npm's placeholder, `cargo test`, and `python3 -m pytest`. Each runs as an argument list, never through a shell, in turn and all of them, within the checks timeout (15 minutes unless set). Each start and end is logged, which is the progress the board shows.
- When every test passed or none were found, it stages exactly the paths the import wrote and moved (a `git mv` source is already staged) and commits `chore: bring <name> under system-flow (flai import)` with `--trailer` lines.
- When a test fails it commits nothing, leaves the import in the working tree, answers with each test's outcome and the last 8 KiB of its output, and exits 5 (`exitImportNotCommitted`).

## Internal structure

```text
flai/
├── main.go
├── cmd/                 # one file per cobra command
├── internal/
│   ├── config/          # ~/.flai/config.json

│   ├── atomicfile/      # replace a file in one step: a reader sees the old or the new, never half (S-0100)

│   ├── logx/            # slog setup per the logging convention: levels incl. fatal, env and flag
│   ├── narrative/       # wip/agents files
│   ├── check/           # reference validator, rule names are stable identifiers
│   ├── conventions/     # loads and validates design/conventions
│   ├── issues/          # design/issues: record, bump, close, summary
│   ├── release/         # semver plan from item, commits, and manifest components; tags and version files
│   ├── lock/            # system-flow.lock.yaml
│   ├── upgrade/         # classify add, merge, replace, conflict; apply with a policy
│   ├── publish/         # push a local template to its remote: clone, replace, commit, tag, push
│   ├── metrics/         # reference implementation of metrics.md
│   ├── importer/        # scan, plan, moves with git mv
│   ├── dashboard/       # docker run/stop
│   ├── harness/         # a story's agent as a command to start: claude-code, the operator's command (S-0104)
│   └── ui/              # prompts and tables
└── testdata/
```

External processes: `git` and `docker` are invoked as subprocesses and must be on `PATH`. See ADR 0010.

Work items, `board.md`, narratives and their index, and threads (with the block mirrored into a narrative) are written with `atomicfile.WriteFile`, a temporary file beside the target renamed over it (S-0100). They are read while they change: by the MCP server's `inbox` and `wait_for_events`, by `flai serve`'s watcher, and by the dashboard through flai. `os.WriteFile` truncates first, and a reader in between saw an empty file ("no front matter", I-0036).

Front matter is parsed with goccy/go-yaml but written by a small purpose-built emitter, so timestamps stay unquoted, sequences stay indented, and a `flai` edit never rewrites lines it did not change. Item bodies come from the template's `items/` when the project's template is in the cache, else from copies embedded in the binary.
