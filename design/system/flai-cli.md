# flai CLI

`flai` is a single static Go binary. It creates and imports projects, manages work items, validates a repo against the standard, prints metrics, and runs the dashboard. It is designed to be used by humans at a terminal and by agents through non-interactive flags.

Source: `./flai` in this monorepo. Module `github.com/bytepunx/system-flow/flai`.

## Configuration

`~/.flai/config.json`, created on first run with defaults. Overridable with `FLAI_CONFIG` and `--config`.

```json
{
  "template": {
    "repo": "https://github.com/bytepunx/system-flow-template",
    "ref": "main"
  },
  "dashboard": {
    "image": "ghcr.io/bytepunx/flaiover",
    "tag": "latest",
    "port": 4242,
    "bind": "0.0.0.0",
    "push_key": "",
    "push_known_hosts": ""
  },
  "cache_dir": "~/.flai/cache",
  "author": "alex",
  "worktrees": {
    "relative_paths": false
  }
}
```

`host_actions`, `agent`, `checks`, and `import_roots` live in the same file, are absent until set, and are not among `config.Keys`: `flai serve` subcommands manage them (see the `flai serve` rows below). Every key is documented for users in [docs/users/flai.md](../../docs/users/flai.md#configuration).

Template repo cloning goes into `cache_dir/templates/<hash of repo+ref>` and is refreshed with `flai template update`. A local path in `template.repo` is used directly without cloning, which is how this monorepo develops against `./template`.

## Commands

| Command | Purpose |
|---------|---------|
| `flai new <dir>` | Create a new conforming monorepo from the template. Prompts for variables when stdin is a terminal; `--var k=v` sets them, `--defaults` never prompts. `--template` and `--ref` override the config source, `--layout key=name` renames a folder, `--force` overwrites, `--no-git` skips `git init`. | `flai import [dir] [--commit] [--trailer]` | Analyse an existing repo, propose the layout, prompt for folder names, create missing structure, offer to move existing markdown into it, write `system-flow.yaml`. `--commit` (S-0098, [ADR-0035](../adrs/0035-repositories-under-folders-the-operator-names-can-be-imported-from-the-board.md)) then runs the repository's tests and commits the import when they pass; see Import flow. |

## Versions: the host's flai and the tree

The flai installed on the host serves MCP and starts agents, and it lags the tree it serves whenever a release is accepted and not installed (S-0181, I-0049, I-0051). Three things keep that from going unnoticed or breaking the board:

- **It reads past what it does not know.** Work items, threads, and issues are decoded leniently on the paths that list and serve them; an unknown front-matter key is kept, written back unchanged, logged once per file, and reported by `flai check` ([work-hierarchy.md](work-hierarchy.md#fields-an-older-flai-does-not-know)).
- **It says when it is behind.** `release.FlaiOutdated(runner, root, running)` finds the newest `flai/vX.Y.Z` tag reachable from the project's HEAD (`git tag --merged HEAD --list 'flai/v*'`) and, when the running flai is a release below it, answers `Outdated{running, newest, upgrade, message}`; a dev build, a project with no such tag, and a git that cannot say answer nothing. An answer is kept a minute per project and running version. `flai serve` logs `flai is older than the project it serves` (warn) when it starts serving such a project; the MCP `inbox` carries `flai_outdated` on every call while it is true, and the server's instructions tell the agent to tell the designer; `project.info` carries `flai_outdated`, and the dashboard's host badge then reads `host flai: upgrade to X.Y.Z`, its title naming both versions and the upgrade. The upgrade is `buildinfo.UpgradeCommand`: `flai host upgrade`, or `flai self-upgrade` where no flai host runs.
- **It stops below the project's minimum.** `flai.minimum` in `system-flow.yaml` names the oldest flai release that may read the project; `manifest.Load` refuses a flai below it with `manifest.TooOldError` before any item is read, so commands, `flai serve` (the project is unavailable, with the reason), and `flai mcp` (folder mode logs `project not served` once per reason) stop and name the version needed. `flai release --pending` (and `flai push --pending` with `auto-publish`, the operator's shell tool) raise it to the release being published when `flai/internal/workitem/front-matter-fields.txt`, the list of fields flai reads that `TestFieldsFileIsTheCode` keeps equal to the code, changed since the previous `flai/v*` tag (`release.RaiseMinimum`, in the publish commit, with the warning `flai.minimum raised`: upgrade the host's flai once the release's binaries are built). A first release, and a fields file the previous tag did not have (the release of S-0181 itself), raise nothing; a git that cannot say is an error. Any change raises it, a removed field too, which is conservative. So the release that adds a front-matter field is the minimum from then on ([project-manifest.md](project-manifest.md)).

Version comparison is `buildinfo.Semver` and `buildinfo.Below`: `X.Y.Z` with an optional `v`, a pre-release or build suffix ignored; anything else is not a release and is never below or above anything.

## Import flow

`flai import` is the deliberate, interactive path for existing repos.

1. Scan the tree. Detect existing `design`, `docs`, `wip`, `adr`, `adrs`, `architecture`, `documentation` folders and any markdown outside code folders. Detect sub-projects by build files (`go.mod`, `package.json`, `pyproject.toml`, `Cargo.toml`).
2. Present a proposal: which folders will be created, which existing folders look like they map to `design`, `docs`, or `wip`, which candidate folders (`adr`, `adrs`, `architecture`, `doc`, `documentation`) move whole into the structure, which loose markdown needs a decision, and which sub-projects were found.
3. Ask for folder names, offering existing folders and the template defaults; `--layout key=name` sets them without asking.
4. Move candidate folders (confirmed one by one in a terminal), then render the template files that do not already exist. Nothing is overwritten; a conflicting file in a moved folder stays where it was and is reported.
5. For each loose markdown file, ask: `design/system`, `design/adrs`, `docs/<audience>`, leave in place, or skip all remaining. Non-interactive runs leave files in place. Moves are `git mv` when the file is tracked.
6. Write `system-flow.yaml` with the detected sub-projects, run `flai check`, print a summary and next steps.
7. Have the host flai serve it (S-0120): when `flai host` runs for the config (`host.Dir.ReadStatus`), register the project with `flai serve` using the entry `flai dashboard` writes (`serveEntry`: key and name from the manifest, the main checkout, `dashboardSettings`' dial address, the shared agent credential, created if missing) and say the dashboard's address; when `flai serve` is stopped under the host, say `flai serve start`. With no host, register nothing and name `flai dashboard` in the project. `--json` carries this as `serve` (`served`, `dashboard`, `reason`, `next`, `root`). A board import runs the same command and `flai serve` then registers it again for the dashboard it was offered on, which replaces the entry by root.

The template's `repo_url` defaults to the `origin` remote made a web address (`webURL`: scp-like, `ssh://`, `git://`, and `http(s)://` remotes become `https://host/path` without credentials, port, or `.git`; a local path or `file://` gives none). `checkRepoURL` refuses a `repo_url` that is not an http or https URL with a host and a path, at the prompt and, for `--var`, before `flai import` or `flai new` changes anything (S-0120).

`--dry-run` prints the proposal and stops (`--json` gives the analysis, the plan, and, since S-0098, the tests `--commit` would run). `--yes` accepts every default. A tree that already has a manifest is refused unless `--force`. With `--json` the proposal's text is no longer printed ahead of the JSON.

`--commit` (S-0098) makes the import one step that ends in a commit:

- Before anything, it refuses a directory that is not a git repository, or has uncommitted changes (`git status --porcelain`), so the commit holds the import and nothing of the operator's.
- After the import it runs tests. It runs the host's `checks.commands` when any are set (`{root}` is the repository; `{story}` is empty). Otherwise `importer.DetectTests` finds the repository's own tests: its own Makefile's `test` target (a Makefile the template brought does not count) stands for everything; otherwise, at the root and in each sub-project, `go test ./...` for `go.mod`, `pnpm`/`yarn`/`npm test` for a `package.json` test script that is not npm's placeholder, `cargo test`, and `python3 -m pytest`. Each runs as an argument list, never through a shell, in turn and all of them, within the checks timeout (15 minutes unless set). Each start and end is logged, which is the progress the board shows.
- When every test passed or none were found, it stages exactly the paths the import wrote and moved (a `git mv` source is already staged) and commits `chore: bring <name> under system-flow (flai import)` with `--trailer` lines.
- When a test fails it commits nothing, leaves the import in the working tree, answers with each test's outcome and the last 8 KiB of its output, and exits 5 (`exitImportNotCommitted`).

External processes: `git` and `docker` are invoked as subprocesses and must be on `PATH`. See ADR 0010.

Every request `flai serve` answers over the channel, and every request `flai mcp` answers on stdio or HTTP, is timed inside flai from when it was read to when its answer is ready to write, and logged once as `request answered` with its method or tool, duration, size, and phases (S-0152). `perf.Track` marks a phase in the context the request carries; the host API's read methods mark opening the repository, listing items, loading the board, threads, narratives, the check, documents, and search, the reads a command also prints (S-0159) mark their work under a phase of its own, such as `release.pending` or `stats.compute`; and `execx.Timed` and the write table mark each process flai starts. The dashboard's own duration for a request, less flai's, is the transport. `flai hostapi --timing` times one method with no transport at all, and `FLAI_PPROF_ADDR` offers Go's profiles on a loopback address. What the measurements found is in [server-performance.md](server-performance.md).

`release.Pending`, which every board asks through `PendingIDs`, reads git through a history kept per repository root for the life of the process (S-0157, `flai/internal/release/history.go`). `git show-ref --head --tags -d` gives HEAD and every tag and is the key: while it is unchanged, that is the only process. When it changes, one `git log` reads the commits added since the kept HEAD with their files; when HEAD moved where the kept commits do not reach, the whole history is read again. The files of an accepted item's commits not yet read come from one `git diff-tree --stdin`, and the template's boundary from `git log -S` on its version line, asked again only when that version changed or a commit added since touched `template.yaml`. A commit's subject, parents, the IDs its message names in brackets, and its files never change for its hash and are kept; the plans are worked out again at every call from the work items, whose tags and nature can change without a commit. The first call in a process, and every one-shot `flai board`, reads the whole history: four processes. The per-process computation it replaced is kept in `history_test.go` as the reference a test holds it to.

Work items, `board.md`, narratives and their index, and threads (with the block mirrored into a narrative) are written with `atomicfile.WriteFile`, a temporary file beside the target renamed over it (S-0100). They are read while they change: by the MCP server's `inbox` and `wait_for_events`, by `flai serve`'s watcher, and by the dashboard through flai. `os.WriteFile` truncates first, and a reader in between saw an empty file ("no front matter", I-0036).

A process keeps the work items it has parsed (S-0156). `workitem.Repo.List` and `Repo.Get` go through a process-wide store in `flai/internal/workitem/store.go`, keyed by file path, because `flai serve`'s methods open a `Repo` per request. Each list walks the item folders and stats each file; a file is parsed again only when it is new, or is not the same file (`os.SameFile`: renamed over, as git and editors do), or its modification time or size changed, and a file gone from the walk leaves the store. A file read within two seconds of its modification time is read again on every list until it is older, so that a same-size write in the same timestamp tick is never missed (the racy-git rule). Each caller gets its own deep copy of every item, so that one that changes an item changes nothing another sees. One caller at a time refreshes a folder, so that lists at once share one read. On this repository a warm list of every item, archive included, takes 3 to 5 ms against 105 to 120 ms before. A short-lived command pays one stat per file, and a second list in the same command is cheaper.

Front matter is parsed with goccy/go-yaml but written by a small purpose-built emitter, so timestamps stay unquoted, sequences stay indented, and a `flai` edit never rewrites lines it did not change. Item bodies come from the template's `items/` when the project's template is in the cache, else from copies embedded in the binary.
