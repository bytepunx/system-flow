# Strategic agents

The planner, the orchestrator, the analyzer, and the curator are agents that work above a story (E-0016). What each does and never does is the convention [strategic-agents.md](../conventions/strategic-agents.md). This document is how flai runs them. The planner runs when the operator asks for it and, behind the `plan` host action, on its own. The orchestrator runs, one run per project at a time, while the `orchestrate` host action is on, for the reasons the project's events give, and ends ([ADR-0209](../adrs/0209-the-orchestrator-runs-for-a-reason-and-ends-started-by-flai-serve-on-the-events.md)). The analyzer runs, one per project at a time, behind the `analyze` host action, when the operator asks for it and on a schedule, and writes one report under `design/analysis/`. The curator runs, one per project at a time, behind the `curate` host action, when the operator asks for it, after each acceptance, and on a schedule, and keeps the digest through `flai digest` alone. A role a project defines in a role file of its own runs, one run per item at a time, behind the host action its file names, when the operator asks for it and on the events and schedules its trigger names (S-0418) ([A role a project defines](#a-role-a-project-defines-s-0417)).

## Role files (S-0414)

Each role is also written down as data: one file, `design/workflows/roles/<name>.md`, under the design folder's `workflows/` ([ADR-0207](../adrs/0207-a-strategic-role-is-a-markdown-file-under-design-workflows-roles-whose-front.md), [repository-layout.md](repository-layout.md)). The ADR holds the fields, the triggers, the conditions, and the calls each permission gates; this section says how flai uses them.

- **Where.** The template ships `planner.md`, `orchestrator.md`, `analyzer.md`, and `curator.md`, and the folder's `README.md`, which lists them. A role file the template does not ship is the project's own. `roles.Load` in `flai/internal/roles` reads every `*.md` in the folder but `README.md`.
- **What it holds.** The front matter names the role (`name`, `role`), the fields of its harness definition (`definition`: `description`, `tools`, `model`), the host action that gates it (`action`), what starts it (`trigger`), the items a run takes (`item`), its `topics`, whether it may work a story (`works_story`), how its usage is charged (`charge`), and the calls the guard allows it beyond the reads every agent has: flai's MCP tools (`tools`), flai's commands (`commands`), the folders it may edit (`files`), `permissions`, and what one run is told (`start`). The body is the definition's prompt, with the baseline marker; a project adds its own below it.
- **Its charge (S-0425).** Strategic usage is per role ([ADR-0249](../adrs/0249-strategic-usage-is-per-role-a-role-s-activity-is-charged-by-its-role-file-s.md), [metrics.md](metrics.md#strategic-usage)). A role's activity is charged, under the role's name in `usage.strategic`, by the rule its file names in `charge`: `item`, to the item its run was started for and the items above it; `named`, evenly to the epics, stories, and tasks its entry names and the items above them; `issues`, evenly to the issues its entry names; `none`, to nothing. The baseline files give the planner `item`, the orchestrator `named`, the analyzer `issues`, and the curator `none`, and a built-in role with no file keeps that rule. What no item or issue takes stays in the role's project strategic total, which `flai stats` reports per role.
- **Conditions and permissions.** A call is named plainly, or as `{call, when}` under a condition flai implements in `flai/internal/roles/conditions.go`, such as `draft-only` or `to-backlog`. A file names a condition; it cannot define one. A call only the operator's settings may allow, such as an acceptance, a publish, or a move past backlog, sits only inside a `permissions` entry naming the setting: `orchestration.permissions.<p>` in the orchestrator's file, `roles.<name>.permissions.<p>` in any other. Some calls no file may name: `flai push`, git's writes, `flai accept --batch`, a move to done with `item_move`.
- **Its harness definition.** For a role a project defines, flai generates it from `name`, `definition`, the role's agent's model, and the body when it starts the role, and `flai serve` passes it in `--agents` and selects it with `--agent <name>`, writing nothing under `.claude/` (S-0417, [How a defined role runs](#how-a-defined-role-runs)). For the four built-in roles, flai generates the whole definition from the role file too since S-0553 ([ADR-0207](../adrs/0207-a-strategic-role-is-a-markdown-file-under-design-workflows-roles-whose-front.md) §4, [ADR-0236](../adrs/0236-a-built-in-role-s-claude-code-definition-is-generated-into-flai-cache-agents-by.md)). `startOf` in `flai/internal/serve/agents_start.go`, the start every run goes through, gives the role its file (`builtinFile`, `roles.Builtin`): the project's, or flai's baseline copy when the project lacks it or it does not parse. The claude-code adapter generates the definition from it at every start and passes it in `--agents`: `name`, `definition.description`, `definition.tools`, `definition.model` with the role's agent's model over it, and as the prompt the body, the baseline text and the project's additions below the marker, without the marker line and the `### Start prompt` section (`roles.Prompt`). It reads nothing under `.claude/`, so a project with no `.claude/agents/<name>.md` starts the role all the same.
- **Its start prompt (S-0554).** The body says what the role is; the start prompt says what one run is for. Since S-0554 the start prompt is the file's too: its front matter's `start`, a Go `text/template` written as a block scalar, `start: |` ([ADR-0250](../adrs/0250-a-role-file-s-start-prompt-is-a-text-template-in-its-front-matter-s-start-field.md)). `harness.Prompt` renders it for every strategic run, built-in or defined, over the run's fields (`startPrompt`, `startFields`, `roles.StartFields`), and trims the whitespace around it. The fields are `.Name`, `.Root`, `.Role`, `.RoleName`, `.File`, `.Body`, `.Item`, `.Kind`, `.AskedOn`, `.Reasons`, each with `.Line` and `.Prime`, `.Primed`, `.PrimeForms`, `.Queue`, `.Focus`, `.Since`, and `.Inputs`, each with `.Name` and `.Value`; ADR-0250 §2 says what each holds, and the roles [README](../workflows/roles/README.md#the-start-prompt) lists them. A project adds to it under a `### Start prompt` heading in `## Project additions`, below the marker: the text to the next heading of level three or above, or the end of the body, is rendered over the same fields and appended after a blank line (`Role.RenderStart`). `roles.Prompt` leaves that section out of the definition's prompt, so it changes what a run is told and not what the role is. A built-in role's file with no `start` renders the baseline's `start` flai carries; a defined role's renders `roles.DefaultStart`, which says what the old `definedPrompt` said ([What a defined role is told](#what-a-defined-role-is-told)). A start prompt that does not render stops the start, naming the file and `flai check`. `harness.go` keeps the story agent's prompts and none of the strategic roles' text; the four baseline files, here, in the template, and embedded in flai, carry the text that was `planPrompt`, `orchestratePrompt`, `analyzePrompt`, and `curatePrompt`.
- **A session started by hand.** Claude Code reads `.claude/agents/` for a session the operator starts. There each built-in role's `.claude/agents/<name>.md` is a committed relative link to `../../.flai-cache/agents/<name>.md`, the git-ignored file `flai role definition --write` generates. `flai role definition <name>` prints the generated definition as a Claude Code agent file. `flai role definition --write [<name>...]` writes each named role's, or every built-in role's when none is named, and prints `ln -sf ../../.flai-cache/agents/<name>.md .claude/agents/<name>.md` for each built-in role whose file is not the link yet, for the operator to run once, since flai writes nothing under `.claude/`. The generated file is never edited: after a role file changes, `flai role definition --write` writes it again. Until it runs in a checkout, such as a fresh clone or a story's worktree, the link dangles and a hand-started session there has no such agent. The template ships no `.claude/agents/<name>.md` for the four; a project made before S-0553 keeps its copies, since `flai upgrade` removes nothing, until the operator replaces each with the link. `flai guard` reads a built-in role's tools from its generated definition, never from `.claude/agents/`. So a strategic agent's prompt and definition are changed in its role file alone.
- **It runs as the operator.** A defined role's session runs on the host, as the built-in roles' do: as the operator's user, with the operator's git and forge credentials and the provider's key. `flai guard` holds it to its file for flai's MCP tools, flai and git command lines, and file edits; a role given `Bash` has the operator's shell for anything else. A role file is code the operator runs, so it changes only through a story the operator accepts, and no role's `files` may include `design/workflows/` (ADR-0207 §7).
- **Checks.** `flai check` reports, as errors, `roles.file` for a file that does not parse, misses a field, or names an unknown condition, trigger, event, setting, item kind, tool, or command, or the trigger `continuous`, which no role takes since [ADR-0209](../adrs/0209-the-orchestrator-runs-for-a-reason-and-ends-started-by-flai-serve-on-the-events.md) §1; `roles.grant` for a call outside the permission that gates it, or one no setting allows; and `roles.definition` for a `definition` missing its description or tools, or listing a tool the role's rules refuse, and for a built-in role's `.claude/agents/<name>.md` that exists and is neither the link nor a file whose description, tools, model, and prompt equal the generated definition, naming the first that differs; a missing file, or a link whose target is missing, is no finding (ADR-0236). Since S-0425 `roles.file` also reports a `charge` of `item` on a role whose `item` is `none`, whose runs have no item to charge. Since S-0554 `roles.file` also reports a `start`, or a `### Start prompt` section, that does not parse or names a field outside ADR-0250 §2: `flai check` renders it over a run with every field empty and over one with every field set (`checker.start`). It reports an entry in a built-in role's `trigger` that the role's launcher does not serve, naming those it serves, and a schedule entry without `when: each-ready-story` on a role that takes an item, whose run would have no item to be on ([Its triggers](#role-files-s-0414)). Since S-0571 it also reports a schedule entry under `when: each-ready-story` on a defined role whose `item` does not list `story`, which no ready story could start. It reports `roles.baseline`, an advisory warning `--strict` passes over, for each of `planner.md`, `orchestrator.md`, `analyzer.md`, and `curator.md` the project lacks, saying flai runs the baseline in its place and naming `flai upgrade`, which adds the file (S-0419).
- **Commands.** `flai role list [--json]` prints every role with its file, action, triggers, item kinds, topics, charge, calls, and permissions; `flai role show <name> [--json]` adds its definition and its body; `flai role definition <name>` prints its generated harness definition, and `--write` writes it under `.flai-cache/agents/` ([flai-cli.md § Commands](flai-cli.md#commands)). Since S-0568 (I-0245) `flai guard` lets every agent run `flai role` alone, `list`, `show`, and `definition`, every sub-agent and every strategic agent's own call among them, and refuses them `flai role run`, which starts an agent, and `flai role definition --write` in any form, which writes the definitions (`guard.flagReads`, `readsRoles`).
- **Upgrade.** `flai upgrade` merges a baseline role file as it merges a convention: the front matter and the body above the marker come from the template, the project's text from the marker on stays, and so do its `topics` when it changed them. So a project's `### Start prompt` section stays, while its edit of `start` or `trigger` lasts only until the next `flai upgrade` (ADR-0250 §3). A project that wants a built-in role told or started otherwise for good turns the role's action off and defines a role of its own. A baseline file the project lacks is added.
- **The guard (S-0416).** `flai guard` decides every strategic role's own calls from its role file ([ADR-0207](../adrs/0207-a-strategic-role-is-a-markdown-file-under-design-workflows-roles-whose-front.md) §5): the planner's, the orchestrator's, the analyzer's, the curator's, and those of any role a project defines, whose session has `FLAI_ROLE` set to the file's `role`. The reads every agent has pass. Each MCP tool, flai command, and file edit the file lists passes, under its condition when it names one; a `files` entry is a folder, under which the role may edit (`under-folder`). An entry inside a `permissions` entry passes only while the operator has its setting on: `orchestration.permissions.<p>` for the orchestrator, `roles.<name>.permissions.<p>` for any other role ([project-manifest.md](project-manifest.md)). The guard reads the setting from the manifest at each call. An entry `flai check` reports as `roles.grant` is never granted. Everything else is refused, naming the role, the rule, and the file, and saying to ask the operator with `thread_open` on the item: `the role <name> cannot <call>: <rule>. Ask the operator with thread_open on the item if it needs doing (<file>, ADR-0207).`
  - A built-in role with no file in the project is held to flai's baseline copy of it (`flai/internal/roles/baseline/`). A defined role with no file, or any role whose own file does not parse, fails closed: its reads pass, and every write is refused, naming the file and `flai check`.
  - The built-in roles' rules in Go (`Guard.plan`, `Guard.orchestrate`, `Guard.analyze`, `Guard.curate`) only word a refusal the file makes, so their messages are as before. The sections below give each role's rules as its baseline file lists them.
  - A shell call is judged one simple command at a time, by its arguments: its words with its redirections and their targets left out (S-0613, I-0230). So `2>&1`, `2>/dev/null`, or `>/dev/null 2>&1` neither allows nor refuses a command, wherever it stands, before the subcommand too. `flai order --by throughput --apply 2>&1` passes as the line without it does, and `flai 2>/dev/null accept S-0001 --by orchestrator` is refused as the line without it is. A shell's `-c` script is judged the same way. Before S-0613 a redirection was a word: it was counted as a story, read as the subcommand, or, before the subcommand, read as the command, so a permitted call was refused and a refused one could pass.
  - Thread conditions (`own-thread`, `planner-thread`, `answer-threads`) pass only a `--by` that names the role itself. The orchestrator's own name is `orchestrator` alone.
  - A defined role writes as itself alone, as the planner does ([ADR-0210](../adrs/0210-flai-guard-holds-a-role-a-role-file-defines-to-its-own-name-and-session-as-adr.md)): a `--by`, `--placed-by`, `FLAI_AGENT`, or `FLAI_SESSION` naming another is refused. Its own name is the hook's `FLAI_AGENT`, or the name `flai serve` gives its run, `<name>` or `<name>-<item>`. Its refusals name it `the role <name>`.
  - `.claude/settings.json` runs the guard on `Edit|MultiEdit|Write|NotebookEdit` for any non-empty `FLAI_ROLE`, so a defined role's file edits are held too ([The guard](#the-guard)).
- **What reads them.** S-0415 builds a role's pack from its file, S-0416 has the guard hold a role to it, S-0417 has `flai serve` start a role a project defines from its file when the operator asks ([A role a project defines](#a-role-a-project-defines-s-0417)), and S-0418 has it start one on the events and schedules its file's `trigger` names ([On an event or a schedule](#on-an-event-or-a-schedule-s-0418)). The orchestrator's start reads its file's `trigger` since S-0536 ([Starting and stopping it](#starting-and-stopping-it)), and the planner's, the analyzer's, and the curator's since S-0554 ([Its triggers](#role-files-s-0414)). Since S-0553 each built-in role's whole definition is generated from its file, and since S-0554 its start prompt is rendered from it.
- **Its triggers (S-0554).** Each built-in role's launcher in `flai serve` reads its role file, the project's or the baseline flai carries (`roles.Builtin`), at each look, and starts the role only on the `trigger` entries the file names, under their conditions ([ADR-0250](../adrs/0250-a-role-file-s-start-prompt-is-a-text-template-in-its-front-matter-s-start-field.md) §4). An event or a schedule is judged against an entry by the function the defined roles' launchers use (`matching` in `orchestrate_reasons.go`), so a built-in role and a defined one are judged alike. Each launcher keeps how its role's runs start, its queue, its coalescing, its record, and its journal entries. `asked` stays every role's on-demand start. Taking an entry out of a file stops the role's starts on it.

  | Role | Entries its launcher serves | Baseline entries | Started |
  |------|-----------------------------|------------------|---------|
  | Planner ([Planning again](#planning-again)) | `{event: edited}`, `{event: accepted}`, `{event: cancelled}`, and `{event: reordered}`, each with or without a condition; `{schedule: <setting>, when: each-ready-story}` | `{event: edited, when: stale-figures}`; `{event: accepted}`, `{event: cancelled}`, and `{event: reordered}`, each `when: replan-agent`; `{schedule: planning.schedule, when: each-ready-story}` | Once per item, through its queue. An event entry with no condition queues the event's item when the planner takes its kind; `reordered` has none |
  | Orchestrator ([Starting and stopping it](#starting-and-stopping-it)) | Every event entry, and `{schedule: orchestration.schedule}` | As the table there lists | One run for its reasons, coalesced |
  | Analyzer ([The analysis schedule](#the-analysis-schedule)) | `{schedule: <setting>}` | `{schedule: analysis.schedule}` | Once each time a setting comes round, for all three focuses, or the formula `analysis.formula` names |
  | Curator ([The curator after acceptances and on a schedule](#the-curator-after-acceptances-and-on-a-schedule)) | `{event: accepted}`; `{schedule: <setting>}` | `{event: accepted}`; `{schedule: digest.schedule}` | Once for the acceptances seen meanwhile, coalesced, and once each time a setting comes round |

  The conditions `stale-figures`, `replan-agent`, and `each-ready-story` are implemented in `flai/internal/roles/conditions.go` since S-0554, taking what each needs as arguments (`roles.StaleFigures`, `roles.ReplanAgent`, `roles.EachReadyStory`). Replaying the forecasts after an acceptance, a cancellation, or a reorder is flai's own work under `planning.replan`, no run of the planner, and no entry gates it ([The replan policy](#the-replan-policy)).

## Formulas (S-0421)

A formula is a repeatable process written down as data: one file, `design/workflows/formulas/<name>.md`, beside the role files ([ADR-0238](../adrs/0238-a-formula-is-a-markdown-file-under-design-workflows-formulas-whose-front-matter.md), [repository-layout.md](repository-layout.md)). The ADR holds the fields and the example; this section says how flai uses them.

- **What it holds.** The front matter names the formula (`name`, the file's stem), the nature of the story it makes (`nature`, `improvement` by default), that story's goal (`description`), its `inputs`, its `steps`, and, since S-0422, its `schedule`. Each step has an `id`, a `title`, a `run`, the steps it is `after`, and, since S-0423, where it runs, `in`: `worktree`, the instance's worktree and the default, or `main`, the project's main checkout ([ADR-0240](../adrs/0240-under-publish-the-orchestrator-starts-the-baseline-publish-formula-whose-main.md)). Since S-0621 a `flai` or `script` step may name `stop`, the exits that stop the instance cleanly, such as `stop: [2]` ([ADR-0271](../adrs/0271-a-formula-step-may-name-the-exits-that-stop-its-instance-cleanly-flai-formula.md) §1, [A step that stops the run](#working-an-instance-s-0422)). The body is for a reader, with the baseline marker. `formulas.Load` in `flai/internal/formulas` reads every `*.md` in the folder but `README.md`, and reads past a key it does not know.
- **The three step kinds.** A step's `run` holds exactly one:

  | Kind | `run` | Checked |
  |------|-------|---------|
  | A flai command | `flai: <command line>` | Not that the command exists ([ADR-0238](../adrs/0238-a-formula-is-a-markdown-file-under-design-workflows-formulas-whose-front-matter.md) §6) |
  | A script | `script: <command line>` | Its first word is a file under `scripts/` |
  | A role | `role: <name>`, `prompt: <text>` | A role file defines it |

- **Inputs.** An input has a `name`, a `description`, and optionally a `default`; one without a default is required. It is used as `{{name}}` in the formula's title, a step's title, and a step's run, and filled in as text.
- **The check.** `flai check` reports `formulas.file`, an error on its line, on a formula that does not parse or misses a field, a step whose `run` is not one kind, a missing script or unknown role, an `after` naming no step, a cycle, a duplicate step id, an input used but not declared, an `in` other than `worktree` or `main`, a role step naming the planner, the orchestrator, or the curator, which no role step can start (S-0424), a `stop` on a role step, or one that is not a list of distinct exits from 1 to 255 (S-0621), and a `schedule` that does not parse or sits on a formula with an input that has no default (`checker.formulas`).
- **What run makes.** `flai formula run <name> [--input key=value]... [--epic E-nnnn]` refuses a formula with a finding, and an input missing, undeclared, or malformed, before it writes anything. It then makes, through `itemnew` as `flai story new` and `flai task new` do, one backlog story with the formula's nature, `formula: <name>`, the title with inputs filled, the description as goal, one criterion per step, and Notes naming the file and the inputs, touching its own story file; and one task per step, with `## Work` naming what the step runs, and for a step `in: main` the main checkout's absolute path to run it from, `## Done when` its exit, and for a step with `stop` the exits that stop the run and that `flai formula stop` records them, and the step's `after` as the task's. An item refused removes those made before it. `--ready` then moves the story to ready, and `--autocommit` commits them, and the move, in one commit ([flai-cli.md § Commands](flai-cli.md#commands), [What starts a formula](#what-starts-a-formula-s-0422)).
- **The instance is a story.** A story's agent pulls and works it on its branch and worktree, as it works any story; the pull order, the limits, the metrics, and acceptance treat it as any story. `flai serve` does not work it ([Working an instance](#working-an-instance-s-0422)). `flai guard` lets every agent run `flai formula list` and `show`, and only a story's agent, the operator, and a role whose file names the formula `run` ([What starts a formula](#what-starts-a-formula-s-0422)).
- **Who changes one.** A formula file is code the operator runs, as a role file is: it changes only through a story the operator accepts, and no role may edit `design/workflows/`. The template ships the folder's `README.md`, the `publish` formula since S-0423 ([Publishing a release](#publishing-a-release-s-0222)), and since S-0424 `import`, which checks and tests an import after its commit, and `analysis-cadence`, which runs the analyzer and lists the open issues its report names ([What starts a formula](#what-starts-a-formula-s-0422)).

### Working an instance (S-0422)

A story's agent works an instance on its branch and worktree, step by step ([ADR-0239](../adrs/0239-a-formula-s-instance-is-worked-by-its-story-s-agent-step-by-step-a-role-step.md), TH-0471 answer 5). `harness.Prompt` gives the agent of a story with `formula:` a paragraph of its own (`instance`), and the convention [work-management.md](../conventions/work-management.md) says the same.

- **The steps.** The tasks are the formula's steps, written already: the agent writes, reviews, adds, rewrites, and cancels none of them, save through `flai formula stop` when a step stops the run, and changes no step's words. It works them in their layers, a layer only once every task of the one before is done, each as its task's `## Work` names it. It runs each step itself, never through a task sub-agent. A flai command or a script under `scripts/` runs from the root of the story's worktree, or of the main checkout for a step `in: main`, and the agent reads its output.
- **A step that passes.** It exits 0, or its role run ends `worked`. The agent writes the exit in the task's `## Notes` and closes the task with `task_done`. When every task is done, it closes the story out and moves it to review, as any story.
- **A role step.** The agent starts the role the step names with `role_run`, or `flai role run`, with the step's prompt and inputs and the instance as the run's item, then holds `wait_for_events`. `runTrigger` in `flai/cmd/role.go` lets it, though `flai serve` started it: an agent `flai serve` started is refused, save the agent of a formula's instance, on that instance as item, for a role a role step of its formula names. Its story is `FLAI_STORY`, else the `S-nnnn` of its name `agent-S-nnnn`. Any other role, item, or agent is refused, naming why. The run goes through `serve.RunRole`, with the role's checks ([Starting a defined role](#starting-a-defined-role)), and records the trigger `formula <name> <S-nnnn>`. Its end is the `agent` event on the instance by the role's agent ([A defined role's run and how it ended](#a-defined-roles-run-and-how-it-ended)): `failed` for a failed run, `ended` for one that asked or worked. That change is the step's exit, and the prompt tells the agent not to let it pass.
- **A role step naming the analyzer (S-0424).** The built-in `analyzer` is not started through `serve.RunRole`, which refuses a built-in role, but through the analyzer's own start, `serve.Analyze`, with its checks and the `analyze` host action ([Starting an analysis](#starting-an-analysis)). Its focus is the instance's `focus` input, empty for all three; its trigger is `formula <name> <S-nnnn>`; and the run records the instance in `instance`, so its end is the `agent` event on the instance, `failed` or `ended`, as a defined role's is ([ADR-0245](../adrs/0245-a-formula-s-role-step-that-names-the-built-in-analyzer-starts-it-through-the.md)). The operator's own `flai role run analyzer` stays refused, naming `flai analyze`. No role step can start the planner, the orchestrator, or the curator: `flai check` reports one that names them.
- **A role step's usage.** The run's item is the instance, so a role whose `charge` is `item` is charged to the instance and the items above it, under the role's name (S-0425, [ADR-0249](../adrs/0249-strategic-usage-is-per-role-a-role-s-activity-is-charged-by-its-role-file-s.md) §3, TH-0800). The analyzer started for a role step keeps its own rule, `issues`.
- **A step that stops the run (S-0621).** Its command or script exits with an exit its `stop` lists, such as the publish formula's `evaluate` step's 2 when the release policy is not met ([ADR-0271](../adrs/0271-a-formula-step-may-name-the-exits-that-stop-its-instance-cleanly-flai-formula.md)), [I-0283](../issues/I-0283-a-publish-instance-with-nothing-to-release-stops-at-its-evaluate-step-down-the.md)). The run ends there, cleanly. The agent runs `flai formula stop <S-nnnn> --step <id> --exit <n>` with the step's output, in place of `task_done` ([flai-cli.md § Commands](flai-cli.md#commands)). It moves the step's task to done with the exit and the output's last 40 lines in its `## Notes`. It cancels every step task not yet run with the reason `step <id> stopped the run with exit <n>`. It ticks the step's criterion, and ticks each skipped step's with `(skipped: step <id> stopped the run with exit <n>)` added to its text. The agent then closes the story out and moves it to review, as when every task is done, and asks nothing. It neither blocks the task nor opens a thread.
- **A step that fails.** Its command or script exits other than 0 with an exit its `stop` does not list, or its role run ends `failed` or `asked`. The agent runs nothing after it. It blocks the task with `flai block`, naming the step and its exit, writes the exit and the last 40 lines of the step's output in the task's `## Notes`, and opens a thread on the story naming the step and its exit. It writes `## Current state` and `## Next steps` and ends, as for any question. `flai serve` starts it again when the thread is answered; its prompt then says (`answeredStep`) to unblock the task, run that step again as the answer says, and go on with the layers.
- **Its acceptance.** `flai accept` accepts an instance whose branch changes nothing, as it accepts any such story. The orchestrator's evidence for an instance is one item per criterion, `- <n>: T-nnnn done`, naming the task of the criterion's step, in place of changed files (`stepsUndone` in `flai/internal/preview/orchestrator.go`). Since S-0621 a criterion skipped by a stop takes `- <n>: T-nnnn skipped`, naming its step's task, which must be the instance's, cancelled, and carry the cancel's line `moved to cancelled: step <id> stopped the run with exit <n>`, with the task of step `<id>` done ([ADR-0271](../adrs/0271-a-formula-step-may-name-the-exits-that-stop-its-instance-cleanly-flai-formula.md) §4). A criterion with no such item, or one naming a task that is not done, not skipped so, or not the instance's, is the blocker `criterion_unevidenced`, naming it ([Accepting a story](#accepting-a-story-s-0221), [strategic-agents.md](../conventions/strategic-agents.md)). An instance's branch whose steps change no file carries nothing beyond main, so for an instance with no branch `story/S-nnnn` `verifiedHead` takes the `--verified` commit as verified when it is on the main branch, and its diff as empty; any other story with no branch stays the operator's (S-0585's branch was gone at its acceptance, TH-0868).

### What starts a formula (S-0422)

| Starter | What it does |
|---------|--------------|
| `flai formula run <name>` | Makes the instance in backlog. `--ready` moves it to ready as `flai move` does, by `FLAI_AGENT` when set, its epic following; a refused move removes what the run made. `--autocommit` commits the move with the items. |
| The formula's `schedule` | While the `formula` host action is on for the project, each time the schedule comes round, `flai serve` runs `flai formula run <name> --ready --autocommit --json` in the main checkout, with no inputs (`serve/formula_schedule.go`) |
| `analysis.formula` (S-0424) | Each time `analysis.schedule` comes round with the `analyze` host action on, `flai serve` runs `flai formula run <name> --ready --autocommit --json` for the formula it names, in the main checkout, in place of starting the analyzer ([The analysis schedule](#the-analysis-schedule)) |
| `flai import --formula` (S-0424) | Once the import is committed, runs `flai formula run import --input path=<root> --ready --autocommit` in the new project, so the template's `import` formula checks it and runs its tests as a story ([flai-cli.md § Import flow](flai-cli.md#import-flow)). The board's Import runs it |
| A role | A role file's command entry `flai formula run <name>` lets the role run that formula alone, with no flag but `--ready`, `--input`, `--autocommit`, and `--json` (`guard/roles.go`). The orchestrator's lists `flai formula run publish` under `orchestration.permissions.publish`, and flai itself refuses it any other formula, and `publish` while the permission is off (`orchestratorRunsFormula` in `flai/cmd/formula.go`, [Publishing a release](#publishing-a-release-s-0222)) |

**The schedule.** `schedule` in a formula's front matter is a five-field cron expression in UTC, or `daily`, as `planning.schedule` is. `flai check` reports `formulas.file` on one that does not parse, and on one on a formula with an input that has no default, since nobody is there to give it. Since S-0424 a scheduled formula may declare inputs that all carry a default, and each run takes them. The formula scheduler looks whenever the project's launcher does, beside the role scheduler, and reads the formula files at each look.

- The `formula` host action is off by default (`flai serve enable formula`). It is flai's own: a role file may not name it (`roles.ReservedActions`).
- Each instance made is a journal entry under `formula`, method `serve.formula`, by `flai serve`, saying the story, its status, its commit, and `started by schedule <spec>`. A run `flai formula run` refuses is logged at info with the last lines it wrote, and tried again at the schedule's next time.
- Times missed between two looks come round once. A schedule set or changed, or a formula added, first comes round at its next time from then. While the action is off the schedule keeps up and makes nothing. The scheduler keeps what it has seen in memory only, as the analysis scheduler does.
- The instance is ready and committed on the main branch, so the launcher starts its story's agent as any ready story's, within the in-progress limit.

## A role a project defines (S-0417)

A role file the template does not ship defines a role of the project's own ([Role files](#role-files-s-0414), [ADR-0207](../adrs/0207-a-strategic-role-is-a-markdown-file-under-design-workflows-roles-whose-front.md)). `flai serve` starts it from its file, behind the host action its file names, on an item its file takes or on none, for each trigger its file names: `asked`, when the operator asks ([Starting a defined role](#starting-a-defined-role)), and, since S-0418, an event or a schedule ([On an event or a schedule](#on-an-event-or-a-schedule-s-0418)). It works no story: the in-progress limit does not count it, and it holds no story back.

### Starting a defined role

| Way | For | What it runs |
|-----|-----|--------------|
| `flai role run <name> [<item>] [--input name=value]... [--json]` | a shell on the host | `serve.RunRole` |
| The host API's `role.run` `{name, item?, inputs?}`, each input `{name, value}` | a dashboard | `flai role run <name> [<item>] --input=<name>=<value>... --json`, gated and journalled under the action the role's file names |
| The MCP tool `role_run` `{name, item?, inputs?}` | the operator's own agent | `serve.RunRole`, as `flai role run` does; journalled under the role's action as `mcp.role_run` with the agent that asked |

Each needs the host action the role's file names on for the project: `flai serve enable <action>`, or the dashboard's Settings page while `settings` is on. It is off by default. A holder of the dashboard token can then start the role on any item its file takes. `flai serve enable` and `disable`, `flai serve actions`, `project.info`'s `host_actions`, `settings.get`, and `settings.action` take each action a defined role's file names beside flai's own (`hostapi.DefinedActions`); `flai check` refuses a file that names one of flai's own (`roles.file`). `flai serve disable` still turns off an action whose role file is gone. `role.run` refuses a name that is not kebab-case, an input name that is not one word, and an input value with a line break before flai runs.

`serve.RunRole` refuses, saying why:

- a built-in role's name: `planner`, `orchestrator`, `analyzer`, and `curator` keep their own commands, which the refusal names;
- a name no role file gives, naming the roles the project defines, and a file of that name that does not load, naming the problem `flai check` reports;
- while the host action the file names is off for the project, naming `flai serve enable <action>`;
- an item when the file's `item` is `none`; no item when it names `epic` or `story`; an item of a kind it does not take; an item that is archived, done, or cancelled;
- while a run of the role on the same item, or on none, runs: one item has one run of a role at a time;
- when the role's harness is `command` and no command is set for the project, or is one flai cannot start; an agent that names no harness falls back to the host's command, then to flai's built-in `claude-code` ([ADR-0261](../adrs/0261-a-story-or-strategic-agent-that-names-no-harness-falls-back-after-the-project-s.md));
- while the host's budget state holds the agent's provider, after a run on it ended on the usage limit: `held: <provider> usage limit (<limit>) until <until>; flai serve starts it when the limit resets`, with nothing recorded (S-0534, [flai-cli.md](flai-cli.md#the-hosts-budget-state)).

The MCP tool `role_run` and `flai role run` also refuse an agent `flai serve` started (`FLAI_STARTED_BY=flai-serve`), as `plan` does: running a role is the operator's to ask for. The one exception, since S-0422, is the agent of a formula's instance, for a role step of its formula, on the instance ([Working an instance](#working-an-instance-s-0422)). `flai guard` refuses it to a sub-agent and to every role whose file does not list it.

### On an event or a schedule (S-0418)

At every look of the project, beside the analysis and curate schedulers, `flai serve` starts each defined role whose host action is on for the events and schedules its file's `trigger` names (`serve.go`). The events and their conditions are [ADR-0211](../adrs/0211-the-orchestrator-s-trigger-vocabulary-gains-the-events-moved-thread-planned.md)'s, listed in the roles [README](../workflows/roles/README.md#triggers).

| Trigger | `flai serve` starts the role | On | The run's trigger |
|---------|------------------------------|----|-------------------|
| `{event: <event>, when?: <condition>}` | once the events it matches have coalesced | the event's item, or the item a thread is on, for a role that takes items; none for one that takes none | `<event> <ID>`, such as `moved S-0012`; joined by semicolons when coalesced, such as `moved S-0012; thread TH-0040` |
| `{schedule: <setting>}` | each time the setting comes round | none | `schedule <spec>`, such as `schedule daily` |
| `{schedule: <setting>, when: each-ready-story}` | each time the setting comes round, once for each ready story, in pull order (S-0571) | each ready story, for a role whose `item` lists `story` | `schedule <spec>` |

**Events** (`role_events.go`). At each look `flai serve` reads the inbox's events since the role's last look, under a cursor of the role's own, `flai-serve-role-<name>`, and queues as reasons those its triggers match, as it matches the orchestrator's ([Starting and stopping it](#starting-and-stopping-it)). A thread event is the role's when the thread awaits one of its agents: `<name>`, or `<name>-<item>` for a role that takes items. What the role's own agents change is no reason for it.

- **Queues.** A role that takes no item has one queue. A role that takes items has one per item: the event's, or the thread's, when the role takes its kind; a reason on no such item is not queued. The queues are kept per project, role, and item in `serve/role-reasons.json`, so a `flai serve` started again loses none.
- **Coalescing.** A queue is due once `orchestration.coalesce` (`30s` by default) has passed since its first reason: a role has no window of its own ([ADR-0209](../adrs/0209-the-orchestrator-runs-for-a-reason-and-ends-started-by-flai-serve-on-the-events.md) §2). With no run of the role on its item going, its reasons start one run, whose trigger names them all. Reasons that come while a run goes start the next run when it ends. A start, or a failure to start, takes its reasons out of the queue.
- **Refused and held.** A start the role's checks refuse ([Starting a defined role](#starting-a-defined-role)) drops its reasons and is logged in `flai serve`'s log. A start the host's budget state holds keeps them for the next look and is logged once ([flai-cli.md](flai-cli.md#the-hosts-budget-state)).
- **The action off.** Nothing is read or queued, and the queue is emptied. The look that finds the action turned on takes the events since as history, so turning it on does not act on the past.

**Schedules** (`role_schedule.go`). `{schedule: <setting>}` names the role's own `roles.<name>.schedule`, or one of `planning.schedule`, `analysis.schedule`, `digest.schedule`, and `orchestration.schedule`, which the role then shares with that built-in role. The value is a five-field cron expression in UTC, or `daily`. `flai manifest set roles.<name>.schedule=<value>` writes it. `flai check` reports as `manifest.roles` a `roles.<name>.schedule` that does not parse or never comes round, and one set on a built-in role.

- Each time the setting comes round with the action on, `flai serve` starts a role that takes no item once, on no item, under an entry with no condition. Under `when: each-ready-story` it starts a role whose `item` lists `story` once for each ready story, on that story, in the board's pull order (`roles.EachReadyStory`), as [ADR-0250](../adrs/0250-a-role-file-s-start-prompt-is-a-text-template-in-its-front-matter-s-start-field.md) §5 says (S-0571). A role that takes items, under an entry with no condition, and a role that takes no story, under `each-ready-story`, are not started, which is logged. `flai check` reports both as `roles.file`: the first since S-0554, the second since S-0571.
- A start the role's checks refuse, as while a run of the role goes on the same item, is logged, naming the item, and not tried again until the next time. A start the budget state holds is kept per item and tried at each look until it starts, or until its story is no longer ready.
- Times missed between two looks come round once. A schedule set or changed, or a role or trigger added, first comes round at its next time from then. While the action is off the schedule keeps up and starts nothing. The scheduler keeps what it has seen in memory only, as the analysis scheduler does.

### A defined role's agent

`roles.<name>.agent` in `system-flow.yaml`, merged over the project's `agent` field by field, config key by config key, and role by role (`Manifest.RoleAgent`), gives the role's harness, model, config, and roles. With neither set, the host's command starts it. A built-in role's agent stays in its own block: `roles.planner.agent`, `roles.orchestrator.agent`, `roles.analyzer.agent`, and `roles.curator.agent` are `manifest.roles` errors naming `planning.agent`, `orchestration.agent`, `analysis.agent`, and `digest.agent`. See [project-manifest.md](project-manifest.md).

### How a defined role runs

`serve.RunRole` starts the role through the harness adapter with a `harness.Request` whose `Role` is the file's `role`, whose `RoleFile` is the file, whose `Item` is the item or empty, and whose `Inputs` are the `--input` pairs in the order given. It hands the process over, as `serve.Plan` does: the command does not wait, and the serving flai settles the run.

- **Where.** In the project's main checkout. No branch, no worktree.
- **As whom.** `FLAI_AGENT` is the role's name, or `<name>-<item>` on an item, such as `reviewer-S-0042` (`harness.RoleAgent`). The environment carries `FLAI_ROLE` set to the file's `role`, `FLAI_ITEM` when the run has an item, `FLAI_SESSION`, and `FLAI_STARTED_BY=flai-serve`, and no `FLAI_STORY`. `flai guard` holds the session to its file by `FLAI_ROLE` ([Role files](#role-files-s-0414)).
- **claude-code.** The session is named `<key> <name>`, or `<key> <name> <item>`. It runs with `--agent <name>` over the definition flai generates from the file (`roleDefinition`): `definition.description` and `definition.tools`, the body without the marker's line as the prompt, and the model the role's agent names, else the file's `definition.model`, left out when that is `inherit` so that the session's holds. It is passed in `--agents` beside the explorer and the verifier. Nothing is read or written under `.claude/` for it (TH-0471). A file whose definition lacks a description or tools, or whose body is empty, is refused, naming `flai check`.
- **The operator's command.** It gets `FLAI_ROLE`, `FLAI_ITEM` when there is an item, and `FLAI_INPUTS`, the inputs as a JSON array of `{name, value}`, when there are any; `{story}` is empty.

### What a defined role is told

`harness.Prompt` gives it its file's start prompt, its `start` rendered over the run's fields with the project's `### Start prompt` additions ([Its start prompt](#role-files-s-0414)). A file with no `start` renders flai's default, `roles.DefaultStart`, which says what `definedPrompt` said before S-0554: who it is and the file that defines it; the file's body, without the marker's line; the item, to read with `item_get` with what it links, or that the run is on no item; the inputs, one line each in the order given, or that it has none. It primes with `flai prime --role <role>`, with `--epic` or `--story` and the item when it has one, and calls `inbox`. It works in the main checkout, never works around a refusal of `flai guard`, asks the operator with `thread_open` on its item for an input they own and holds `wait_for_events` until the answer, and ends with a one-line summary, which becomes the run's activity entry.

### A defined role's run and how it ended

The run is recorded in `serve/agents.json` under `roles`, by the role's name and then by its item, `""` for a run on none: the newest run of each. It has the fields a planner run has, with `role` the file's verb, `role_name` its name, `action` the host action its file names, and `trigger` what started it: `asked`, the event or schedule trigger of [On an event or a schedule](#on-an-event-or-a-schedule-s-0418), or `formula <name> <S-nnnn>` for a formula instance's role step ([Working an instance](#working-an-instance-s-0422)). `Running` and `Last` never name it. Its output is in `serve/agents/<key>-<name>-<start>.log`; each run gets a log of its own, at the first free second from its start.

When the process ends, or the next look finds it gone (`settleOrphans`), flai serve settles the run (`roleEnded`), judged as a planner run is (`judgeRole`):

| Outcome | When |
|---------|------|
| `asked` | a thread is open and its last entry is the role's: on its item, or anywhere in the project for a run on none; `thread` names it |
| `failed` | its log ends on the harness's usage limit (`runLimit`) and it did not ask, whether its exit was seen or not; `why` names the limit and its reset time, and `usage_limited` is set (S-0534) |
| `failed` | it exited with a code other than 0, or the project or its threads could not be read |
| `worked` | otherwise, an exit nobody saw included |

An `asked` run is not started again when the thread is answered, unless the role's file names a `thread` event the answer matches; otherwise the operator asks for another run. A run on the usage limit is not started again either: its end sets or extends its provider's budget state, and the operator asks again once the state clears ([flai-cli.md](flai-cli.md#the-hosts-budget-state)).

It then logs the activity in the role's own activity document, `wip/agents/<name>.md`, with `serve.LogRunEnd`, as a planner run is: the time since the last entry, the run's final reply as the summary, `- Trigger:` with the run's trigger, the run's item, when it has one, as the entry's item, and the seconds and cost measured from the run's own log ([agent-narrative.md](agent-narrative.md#strategic-agents-activity-documents)). The role may log activities within its run with `activity_log`, or `flai activity log <name> "<summary>" [--item ID]...`, its name as the kind. The run's end and each logged activity are charged by the rule the role's file names in `charge`, under the role's name, as the built-in roles' are ([Its charge](#role-files-s-0414)): under `item`, to the run's item and the items above it, a run on none charging nothing. `Repo.ActivityKinds` gives the kinds: the four built-in ones, then each role file's name under the design folder's `workflows/roles`, so `activity_log`, `flai activity log`, `wip/agents/index.md`, and `flai check`'s `activity.*` rules take a defined role's document as they take the built-in ones'.

The start, a failure to start, and the end are each a journal entry under the action the role's file names, with method `serve.role`; the start's says `started by <trigger>`, and an end that `failed` is journalled as failed, with why. `agent.status` carries the runs as `roles`. When a run starts, cannot start, or ends, `flai serve` tells the dashboard with an `agent` notification `{project, role, name, item?}`: `role` the file's verb, `name` the role's name, and `item` when the run has one. As a planner run does since S-0532, it also logs an `agent` event, with `fields.role` the file's verb, on the item the run is on, or on no item with `id` and `title` the role's name and `type` `role`: `started` with its trigger as `why`, then `ended` for `worked` or `asked`, or `failed` with its exit. The orchestrator, the analyzer, and the operator see it in `inbox` and `wait_for_events` ([flai-cli.md](flai-cli.md#the-events-wait_for_events-and-inbox-report)).

## In a container (S-0509)

The planner, the orchestrator, the analyzer, and the curator run in a container when their agent's harness is `container`, as a story's agent does ([flai-cli.md](flai-cli.md#the-container-harness-s-0508)). What the container mounts, and the rule for its writes, is [ADR-0247](../adrs/0247-a-strategic-agent-s-container-mounts-the-main-checkout-read-write-at-its-host.md), with `.git/config` read-only since [ADR-0281](../adrs/0281-a-strategic-agent-s-container-mounts-the-main-checkout-s-git-config-read-only.md):

| Mount | Where | How |
|-------|-------|-----|
| The project's main checkout, its `.git` inside it | Its host path, the working directory | Read-write |
| The checkout's `.git/hooks`, which `flai serve` makes when missing | Its host path | Read-only |
| The checkout's `.git/config`, without which `flai serve` refuses the start | Its host path | Read-only |
| The role's cache folder, `.flai-cache/agents/<role>`, `<role>` the run's `plan`, `orchestrate`, `analyze`, or `curate` | Its host path | Read-write |
| The operator's login, for an inner harness that needs it | `/run/claude-login` | Read-only |

Nothing else is mounted: no home, no `~/.ssh`, no `~/.flai`, no Docker socket. The container is named `flai-agent-<role>-<session>`, and a stop stops it by that name. pilot's start request carries the run's role, item, focus, since, and asked-on thread, so the inner harness starts with `--agent <role>` and `FLAI_ROLE` as on the host, and pilot reads the role file from the mounted checkout. The guard runs inside the container from the checkout's `.claude/settings.json` and holds each role to what it holds it to on the host: its writes are the ones its guard allows there. A role a project defines in a role file of its own is refused on the container harness.

What a strategic agent's container does not keep off the host: the whole main checkout is mounted read-write, so a shell command the guard does not see can write any file of it but `.git/hooks` and `.git/config`, every story's worktree under `.flai-cache` among them. `.git/config` can name commands git runs on the host, so it is read-only: a git command in the container that writes it fails, such as `git config` with a write, `git branch --set-upstream-to`, or `git remote add`, and no role needs one. `flai serve` refuses a role's start when `<root>/.git/config` is not a regular file, since docker would make a missing bind source a folder owned by root ([ADR-0281](../adrs/0281-a-strategic-agent-s-container-mounts-the-main-checkout-s-git-config-read-only.md)).

The container's flai reads its configuration from the role's cache folder, which holds no host action, so it cannot tell whether the merge queue batches, and the image lacks the test tiers' tools ([I-0256](../issues/I-0256-a-strategic-agent-s-container-runs-flai-with-no-host-configuration-so-the.md)). The orchestrator therefore verifies and accepts on the host, through MCP ([ADR-0278](../adrs/0278-the-orchestrator-accepts-through-an-mcp-tool-that-runs-flai-accept-on-the-host.md)): it verifies with the MCP tool `verify`, reads the verdict with `flai verify <S-nnnn> --last`, and accepts with the MCP tool `accept`, which runs `flai accept --by orchestrator` in the MCP server's process on the host, with the host's configuration. Its shell's `flai accept`, `--dry-run` included, and a `flai verify` that runs tiers refuse when `FLAI_ROLE` is `orchestrate` and the configuration flai reads lies under the project's `.flai-cache/agents/`, naming those tools; `flai verify --last`, `--job`, and `--sync-only` still run. The HTTP MCP server, a child of `flai host` with no `FLAI_ROLE` of its own, knows the orchestrator when the caller's `X-Flai-Agent` names the orchestrator's run that flai serve records for the project and that is still running, so `accept`, `queue_add`, and `release_publish` reach an orchestrator in a container. The close-out it asks for with the MCP tool `verify`, and the merge queue's batch, run in `flai serve` on the host: the close-out by the story's own harness, in the story's container for a container story ([ADR-0274](../adrs/0274-the-close-out-of-a-story-whose-agent-runs-in-a-container-runs-its-verify-in.md)), and the batch in the main checkout, after an acceptance decision.

## The planner

The planner plans one epic or one story and ends (S-0208, [ADR-0082](../adrs/0082-flai-serve-starts-the-planner-for-an-epic-or-a-story-behind-the-plan-host.md)). For an epic with no stories it drafts them, enriches each one, and drafts each one's tasks (S-0300); for a story it adds touches, a forecast, and a cost of delay value ([Enriching a story](#enriching-a-story-s-0210)), and drafts its tasks or revisits those it has (S-0255); for an epic with stories it revisits each one not done or cancelled, enriches it again, and proposes on the epic's plan thread what it would split, merge, add, or drop, drafting the additions (S-0209) and the tasks of each story it adds and of each draft it revisits that has none (S-0300). One run plans an epic's stories and their tasks: `flai serve` queues no planner for a story the epic's planner drafted. It writes through flai alone, every story it creates is a draft, and it moves nothing past backlog.

### Starting it

The operator asks for it, in one of the ways below. While the `plan` host action is on, `flai serve` also starts it on its own, on the entries its role file's `trigger` names: in the baseline, on an edit, when work ahead completes or the order changes, and on a schedule ([Planning again](#planning-again)).

| Way | For | What it runs |
|-----|-----|--------------|
| `flai plan <E-nnnn\|S-nnnn> [--json]` | a shell on the host | `serve.Plan` |
| Plan on an epic's or a story's page | the dashboard | the host API's `plan.run` `{id}`, which runs `flai plan <id> --json` |
| The MCP tool `plan` `{id}` | the operator's own agent | `serve.Plan`, as `flai plan` does; journalled as `mcp.plan` with the agent that asked |

Each needs the host action `plan` on for the project: `flai serve enable plan`, or the dashboard's Settings page while `settings` is on. It is off by default. A holder of the dashboard token can then start the planner for any epic or story that is open.

`serve.Plan` refuses, saying why:

- while the `plan` action is off for the project;
- a task, or an ID that is neither an epic's nor a story's;
- an item that is archived, done, or cancelled;
- while a planner runs for the item: one item has one planner at a time;
- when the planner's harness is `command` and no command is set for the project, or is one flai cannot start; an agent that names no harness falls back to the host's command, then to flai's built-in `claude-code` ([ADR-0261](../adrs/0261-a-story-or-strategic-agent-that-names-no-harness-falls-back-after-the-project-s.md));
- while the host's budget state holds the agent's provider, after a run on it ended on the usage limit: `held: <provider> usage limit (<limit>) until <until>; flai serve starts it when the limit resets`, with nothing recorded (S-0534, [flai-cli.md](flai-cli.md#the-hosts-budget-state)).

The MCP tool `plan` also refuses an agent `flai serve` started (`FLAI_STARTED_BY=flai-serve`): planning is the operator's to ask for. The orchestrator is the one exception: it may ask for an epic `flai plan --candidates` lists while the operator gives it `plan_backlog_epics`, and for a story it lists while the operator gives it `plan_backlog_stories` ([What it does with each permission](#what-it-does-with-each-permission-s-0219), [ADR-0119](../adrs/0119-with-plan-backlog-stories-on-the-orchestrator-asks-the-planner-for-each-backlog.md)). Besides the epics and the stories that lack a plan, the list holds a third kind since S-0524: an epic or a story planned before, on which the operator has written since its newest planner run ended ([ADR-0222](../adrs/0222-with-plan-backlog-epics-or-plan-backlog-stories-on-the-orchestrator-may-ask-the.md)). `flai guard` refuses the tool to a sub-agent, to the planner, to the analyzer, and to the curator.

### Its agent

`planning.agent` in `system-flow.yaml`, merged over the project's `agent` field by field, config key by config key, and role by role (`Manifest.PlanningAgent`), gives the planner's harness, model, config, and roles. With neither set, the host's command starts it. `flai check` reports a `planning.agent` that is not valid as `manifest.planning`. See [project-manifest.md](project-manifest.md). Its harness may be `container`: [In a container](#in-a-container-s-0509) says what the container mounts.

### How it runs

`serve.Plan` starts the planner through the harness adapter with a `harness.Request` whose `Role` is `plan` and whose `Item` is the epic or story, and hands the process over: the command does not wait, and the serving flai settles the run.

- **Where.** In the project's main checkout, where the items are. No branch, no worktree.
- **As whom.** `FLAI_AGENT` is `planner-<item>`, such as `planner-E-0016`. The environment carries `FLAI_ROLE=plan` and `FLAI_ITEM=<item>`, `FLAI_SESSION`, and `FLAI_STARTED_BY=flai-serve`, and no `FLAI_STORY`. `flai serve` drops `FLAI_STORY`, `FLAI_ROLE`, and `FLAI_ITEM` from its own environment before it adds a run's, so a planner started from a story's session is not taken for that story.
- **claude-code.** The session is named `<key> plan <item>`. It runs with `--agent planner` over the definition flai generates from its role file, `design/workflows/roles/planner.md`, the project's or flai's baseline, with the project's additions below the marker, but for its `### Start prompt` section, in its prompt and the planner's agent's model when it names one. It is passed in `--agents` beside the explorer and the verifier, and nothing under `.claude/` is read for it. `startOf`, the start every run goes through, gives it the file ([Role files](#role-files-s-0414)).
- **The operator's command.** It gets `FLAI_ROLE` and `FLAI_ITEM`, and `{story}` is empty.

### What it is told

`harness.Prompt` gives the planner the start prompt of its role file, `planner.md`'s `start` rendered over the run's fields, `.Item`, `.Kind`, and `.AskedOn` among them, with the project's `### Start prompt` additions ([Its start prompt](#role-files-s-0414)). The baseline's says: plan the item and nothing else, as the convention's section "As the planner" says; prime with `--role plan` and the item; call `inbox`; read the item and what it links; hand wide search to the explorer. Size stories, and make each story or task pass `flai check --strict` and the markdown lint. Write only through flai; never edit a file, move past backlog, finalize a draft, or overwrite the operator's inputs. When an input the operator owns is missing, ask with `thread_open` on the item and hold `wait_for_events` until it is answered. End with a one-line summary, which becomes the run's activity entry.

What it does with the item depends on its kind (S-0209, S-0255, S-0300):

| Item | Work | Thread | Summary |
|------|------|--------|---------|
| Epic with no stories | Draft the stories that deliver its outcome, each created with `draft: true` in the backlog: `item_new`'s `draft`, or `flai story new --draft`. Enrich each one as a story is enriched: touches, a forecast, a cost of delay value. Draft each one's tasks, each with `## Work` and `## Done when`, a nature, tags, `touches`, and `after`, so that they form layers: `item_new` with type task and the story as parent | One thread on the epic: the stories, their order (their `after`), each story's tasks and layers, and the assumptions made | Names by ID the stories and tasks created |
| Epic with stories | Revisit each story not done or cancelled and enrich it again: touches, forecast, cost of delay value. Draft the tasks of each story it adds, and of each story it revisits that is a draft with no tasks, as for an epic with no stories | The same one thread also proposes each story to split, merge, add, or drop; only the additions are created, as drafts. It names each story's tasks and layers. A finalized story is never cancelled or rewritten without asking | Names by ID the stories and tasks created and the stories revisited |
| Story with no tasks | Enrich it: touches, a forecast, a cost of delay value. Draft the tasks that deliver its outcome, each with `## Work` and `## Done when`, a nature, tags, `touches`, and `after`, so that they form layers, created in the backlog: `item_new` with type task, or `flai task new` | One thread on the story: the tasks, their order and layers, and the assumptions made | Names by ID the tasks created |
| Story with tasks | Enrich it, then revisit each task not done or cancelled: its `touches` and `after` enriched again, the tasks the outcome lacks created | The same one thread proposes each task to split, merge, or drop. A task the planner did not write is never cancelled, nor its title, Work, or Done when rewritten, without asking | Names by ID the tasks created and the tasks revisited |

Tasks carry no topics, so a topic a task reaches goes on the story. `itemnew.Create` refuses a task that fails `flai check --strict` or the markdown lint and leaves nothing. A task carries no draft flag. The tasks of a draft story are drafts because their story is one. The story's agent reviews the planner's tasks when it pulls the story ([work-management.md](../conventions/work-management.md)).

`planner.md` says the same in short, and since S-0419 its prompt is the body of `design/workflows/roles/planner.md` with the project's additions ([Role files](#role-files-s-0414)). It lists the planner's tools: `Read`, `Grep`, `Glob`, `Bash`, `Agent`, and flai's MCP tools for reading, `inbox`, `item_new`, `item_edit`, `item_move`, `thread_open`, `thread_reply`, `activity_log`, and `wait_for_events`. It lists no `Edit`, `Write`, or `NotebookEdit`.

### Enriching a story (S-0210)

To enrich a story, the planner runs three commands, reviews what they print, and writes what it decides. The commands write nothing. Each prints its result, and `--json` gives the structure. The guard lets every sub-agent and the planner run all three (`cliReads`).

| Command | Prints | Code |
|---------|--------|------|
| `flai touches suggest <S-nnnn> [path...] [--min 2] [--limit 20]` | The files most often changed together with the story's touches | `cmd/touches.go`, `storygit.CommitFiles`, `planning.CoChanged` |
| `flai forecast <S-nnnn>` | A duration, a delivery, and a one-sentence basis | `cmd/forecast.go`, `planning.Forecast` |
| `flai cod <E-nnnn\|S-nnnn>` | A cost of delay per week, and its basis | `cmd/cod.go`, `planning.CostOfDelay` |

#### Touches from co-change

The seeds are the story's touches, its own and those of its tasks not cancelled, read as a claim reads them (`Holds.Claim`: a sub-project's name or tag means its path), and the paths given. A story with no touches and no path given is refused.

`CommitFiles` reads the main branch's history once, in the main checkout: commits that are not merges, renames not followed, paths from the project's root. Story branches are not read, so a commit is not counted on its branch and again after acceptance. Files under the wip folder are left out, since flai writes them. So are flai's own bookkeeping commits, whose files would otherwise seem to change with everything:

| Left out | Subject |
|----------|---------|
| Acceptance | `chore: [ID] accept and archive`, with an older release in it or not |
| Creation | `chore: [ID] create …` |
| Edit by fields | `chore: [ID] edit …` |
| Release | `chore: publish …` |
| Default agent | `chore: set the project's default agent`, `chore: clear the project's default agent` |
| Import | `chore: bring … under system-flow (flai import)` |

A commit with no file left is dropped. A seed commit is one that changed a file under a seed: the file itself, or a folder that holds it. Every other file is counted by the seed commits it is in, with that count's share of them. Files counted at least `--min` times are kept, ordered by count, most first, then by path, and cut at `--limit` (0 keeps every one). The header names the seeds and how many of the commits are seed commits.

#### Forecast

A story's size is its acceptance criteria's checkboxes and its own touches counted together, at least 1. Its band is small up to 6, medium up to 12, and large from 13.

The history is the done stories with `usage.seconds` above zero and a cycle time, from first in progress to done. Each gives three ratios: agent seconds per unit of size; seconds in progress, over every spell, per agent second; and cycle time per agent second. The match takes the first rung with at least three stories:

| Rung | The done stories that share the story's |
|------|------------------------------------------|
| 1 | Nature, model (`agent.model`), and band |
| 2 | Nature and band |
| 3 | Nature |
| 4 | Nothing: all of them |

| Figure | From the matched stories |
|--------|--------------------------|
| Duration | The median seconds per unit times the size, rounded up to the minute |
| Busy factor | The median seconds in progress per agent second, at least 1: how long a story holds its place in progress |
| Cycle factor | The median cycle time per agent second, at least 1: how long from the start of progress to done |

With fewer than three stories on every rung, the duration is `planning.default_duration` (1h unset, [project-manifest.md](project-manifest.md)), both factors are 1, and the basis says so.

The delivery plays out the board from now. The lanes are the board's in-progress limit; with none, every story starts as soon as what it waits for allows. The stories are played out in this order:

| Stories | Played out |
|---------|------------|
| The story itself, in progress or in review | Delivered at its start plus its duration times the cycle factor, never before now. Nothing else is played out |
| In progress | Each holds a lane until its start plus its duration times the busy factor, and is delivered at its start plus its duration times the cycle factor, neither before now. More than the limit free a lane only once enough have finished to bring the count under it |
| In review | Not played out: they hold no lane |
| Ready, then backlog, in pull order | Each starts at the earliest free lane, but not before the delivery of any story in its `after` already played out; holds the lane for its duration times the busy factor; and is delivered at its start plus its duration times the cycle factor. The play-out stops at the story |

A story ahead with its own `forecast.duration` is played out with it; the others, and the story itself, with the duration worked out from history. Times are UTC, rounded up to the minute. `--json` adds `size`, `criteria`, `touches`, `default`, `history` (`match`, `stories`, `seconds_per_unit`, `busy_factor`, `cycle_factor`), `position` (its place among the ready and backlog stories, 0 in progress or in review), `limit`, and `ahead`, each story played out before it with its duration, `from_forecast`, start, and delivery.

#### Cost of delay

From an epic's or a story's own inputs, the value per week is:

`revenue_per_week` + `penalty_per_week` + hours of `time_lost_per_cycle` × `planning.hour_rate` × (168h ÷ `planning.cycle`)

Time lost with no `planning.hour_rate` is refused. E-0016's 10h lost per 168h cycle at 150 USD an hour is 1500 USD a week.

A story without inputs takes a share of its epic's value: the epic's worked out from its inputs, else the value recorded on it. The share is the story's duration over the sum of the durations of the epic's open stories without inputs, each its own `forecast.duration`, else the one `flai forecast` works out. On 2026-10-04 S-0210's was 2h of 30h45m over 20 stories, 97.56 USD a week.

Refused: an epic without inputs; a story without inputs that has no epic, or whose epic has neither inputs nor a value; a task; an item closed or archived. Each refusal names the `flai edit` flags that give the inputs, which are the operator's, or the orchestrator's to set: under `set_cost_of_delay`, as the operator decided them on a thread, on any open epic or story, and under `plan_backlog_stories`, for a backlog story when neither it nor its epic has any (S-0328, S-0523). Amounts are rounded to two decimals, in `planning.currency`. `--json` adds `from` (`inputs` or `epic`), the `inputs` with the hour rate, cycle, and cycles a week when time lost is among them, and the `epic` share with the stories it was apportioned over.

#### What the planner writes

The planner predicts the touches from what `touches suggest` lists, the story's goal and criteria, the design it links, and the code layout, and keeps every touch the story declares. It reviews the forecast and the value, adjusts a figure only with a stated reason, and writes the touches, the forecast's duration, delivery, and basis, and the cost of delay value through flai: `item_edit`, or `flai edit` and `flai touches`, which stamp `by` and `at` ([ADR-0074](../adrs/0074-work-items-carry-planning-data-a-story-s-draft-flag-an-epic-s-or-story-s-cost.md)). It never changes the operator's inputs.

It records why under a `### Planning` heading in the story's Notes: where each touch came from (declared, co-change, design, or layout) and why each figure stands or was adjusted. That heading is the planner's, rewritten on each run; the rest of the Notes is left as it was. The planner's start prompt, the convention's "As the planner", and `planner.md` say the same.

Since S-0468 ([ADR-0188](../adrs/0188-a-task-takes-no-folder-touch-the-planner-s-folder-touch-on-a-story-needs-the.md), I-0152) flai holds the planner to touches that name files. The planner is the writer when `FLAI_ROLE=plan` is in the environment, as the planner's session has it, or else when the author's name starts with `planner-`. A folder touch is an entry that, read as a claim reads it, names a folder of the repository tree holding at least one file; a path absent from the tree is a file to be made, and a folder wholly inside `claims.shared` does not count ([workflow.md](workflow.md#branches-and-collisions-adr-0019)).

| Write | Refused when | Through |
|-------|--------------|---------|
| A task's touches, by anyone | an entry is a folder touch | `flai task new --touches`, `flai edit --touches`, `flai touches`, `item_new`, `item_edit` |
| A story's touches, by the planner | an entry is a folder touch that the story's Notes do not name under `### Planning` | `flai edit --touches`, `flai touches`, `item_new`, `item_edit` |

A refusal writes nothing. It names the folder and how many files it holds, and says to name the files, or to leave the folder to the story's touches with a `### Planning` note. The note is read as the body will be after the write, so one `item_edit` may carry both the note and the touch. The operator's and the story's agent's story touches are not refused.

Since S-0551 ([ADR-0230](../adrs/0230-a-ready-story-whose-claim-overlaps-a-story-in-progress-is-held-only-when-a.md)) an overlap of claims holds a ready story only when a trial merge of the in-progress story's branch at the ready story's base conflicts ([workflow.md](workflow.md#branches-and-collisions-adr-0019)). So two stories that touch one file may run together, and the planner does not order them to keep them apart.

The planner writes `after` on a story only for a story whose output it reads on main: a file, a command, a schema, or a decision the named story writes and this one builds on. It never writes one for an order of preference, which the pull order sets, nor to keep two stories off one file, which the trial merge judges. It gives the reason in the story's `## Notes`, under `### Planning`, naming the story by its ID. `flai check` gives advisory warnings, which `--strict` passes over: `wip.after-reason` on a story not done or cancelled whose `after` names a story its Notes do not name, `wip.after-hub` on a story that three or more open stories name in `after`, and `touches.folder` on a story in progress whose claim keeps a folder ([flai-cli.md](flai-cli.md#commands)).

The planner's start prompt, the convention's "As the planner", and the body of the planner's role file, `design/workflows/roles/planner.md`, say these rules too.

### The guard

`flai guard` reads `FLAI_ROLE` from the hook's environment. With `plan`, it checks the session's own calls, which carry no agent ID, against the planner's role file, `design/workflows/roles/planner.md`, or flai's baseline copy when the project has none ([Role files](#role-files-s-0414), [flai-cli.md](flai-cli.md#commands), `flai guard`). The baseline file lists these:

| Kind | Passes | Refused |
|------|--------|---------|
| flai MCP tools | the reads a sub-agent has; `inbox`, `item_new` (of a story only with `draft: true`), `item_edit` (`ungated-edit`: not `draft: false`, not a cost of delay input or `clear_cost_of_delay`; a value passes), `thread_open`, `thread_reply`, `activity_log`, `wait_for_events`; `item_move` to `backlog` | every other tool; `item_new` of a story without `draft: true`; `item_edit` that finalizes a draft or sets or clears a cost of delay input; `item_move` to any other state |
| flai commands | the reads, `forecast`, `cod`, and `touches suggest` among them; `story new` with `--draft`, `epic new`, `task new`, `edit` without `--no-draft` and without a cost of delay input flag or `--clear-cost-of-delay`, `touches`, `thread new` and `reply`, `issue new` and `bump`, `move` to `backlog` | every other command that writes; `story new` without `--draft` (S-0209), since the planner's stories are drafts for the operator to finalize; `edit --no-draft`, since finalizing is the operator's; `edit` with `--revenue-per-week`, `--penalty-per-week`, `--time-lost-per-cycle`, or `--clear-cost-of-delay`, since the inputs are the operator's (S-0416) |
| git | the reads a sub-agent has | every other git command |
| File tools | | `Edit`, `Write`, `NotebookEdit` |

Each refusal names the rule broken and says to ask the operator on the item, or put it in the final summary. Other shell commands pass, as a sub-agent's do (ADR-0060). The planner's sub-agents are held as every sub-agent is. With `story new`, the last `--draft` decides: bare, or with a value that parses as true.

The planner writes as itself alone ([ADR-0143](../adrs/0143-flai-guard-refuses-a-story-s-agent-the-planner-and-the-analyzer-a-call-that.md)). The guard refuses it a flai command whose `--by` or `--placed-by` names another, and any assignment of `FLAI_AGENT` or `FLAI_SESSION` other than its own, or `unset` of either, anywhere on the command line. Its own name is the hook's `FLAI_AGENT`, or `planner-<item>` from `FLAI_ITEM`; its own session is the hook's `FLAI_SESSION`. The orchestrator keeps its own `--by` rule ([Its permissions and the guard](#its-permissions-and-the-guard)).

Claude Code runs a hook only for the tools its matcher names. `.claude/settings.json` has two `PreToolUse` entries: `Bash|mcp__flai__.*` runs the guard in every session; `Edit|MultiEdit|Write|NotebookEdit` runs it only when `FLAI_ROLE` is set, to any role, or `FLAI_STORY` is set: `[ -n "$FLAI_ROLE" ] || [ -n "$FLAI_STORY" ] || exit 0`. Until S-0416 it named the roles, `plan`, `orchestrate` (S-0218, [Its permissions and the guard](#its-permissions-and-the-guard)), `analyze` (S-0223, [The analyzer's guard](#the-analyzers-guard)), and `curate` (S-0431, [The curator's guard](#the-curators-guard)); any `FLAI_ROLE` now runs it, so a role a project defines has its file edits held ([Role files](#role-files-s-0414)). `FLAI_STORY` runs it so that a story's sub-agents write no file in a `.claude/` folder (S-0299, [ADR-0102](../adrs/0102-while-auto-approve-is-off-flai-guard-refuses-a-story-s-sub-agent-a-write-to-a.md)). In the operator's own session, with neither set, the entry exits at once. The template's file runs the installed `flai guard`; this repository's runs `scripts/flai.sh guard`.

### Checked creation

A story the planner writes through `item_new` with a body is checked as `flai story new --body-stdin` is (S-0209): `itemnew.Create` writes it, runs the rules of `flai check` a work item write can affect before and after, with it in place, the markdown lint on it among them ([ADR-0264](../adrs/0264-a-checked-write-of-a-work-item-runs-only-the-rules-the-write-can-affect-before.md)), and a finding it introduces inside the new item's story, such as a missing template section like `## Tasks` or `## Notes`, refuses it and leaves nothing. A new finding outside that story is a warning and the item stands, as for a checked edit ([ADR-0213](../adrs/0213-a-checked-creation-of-a-work-item-refuses-only-a-new-finding-inside-the-new.md)). A creation with `after` was already checked this way (S-0176). An `item_new` with neither gets the template's own body and is not checked.

### The run and how it ended

The run is recorded in `serve/agents.json` under `plans`, by item, the newest run for each, with the fields a story's run has, `item` in place of `story`, and `trigger`, what started it: `asked` when the operator asked, `orchestrator` when the orchestrator did (S-0219), otherwise the replanner's triggers ([What a run records](#what-a-run-records)). `Running` and `Last` never name a planner run, and the in-progress limit does not count it. Its output is in `serve/agents/<key>-planner-<start>.log`, beside the story agents' logs; each planner run gets a log of its own, at the first free second from its start.

When the process ends, or the next look finds it gone, flai serve settles the run (`planEnded`):

| Outcome | When |
|---------|------|
| `asked` | a thread on the item is open and its last entry is the planner's; `thread` names it |
| `failed` | its log ends on the harness's usage limit (`runLimit`) and it did not ask, whether its exit was seen or not; `why` names the limit and its reset time, and `usage_limited` is set (S-0534) |
| `failed` | it exited with a code other than 0, or the project or its threads could not be read |
| `worked` | otherwise, an exit nobody saw included |

It then logs the activity in `wip/agents/planner.md` with `serve.LogRunEnd`: the time since the last entry, the run's final reply as the summary, the run's trigger as the entry's `- Trigger:` line ([agent-narrative.md](agent-narrative.md#strategic-agents-activity-documents)), the items it planned, and the seconds and cost measured from the log ([metrics.md](metrics.md#strategic-agents-s-0206)). The log measured is the run's own, the one `serve/agents.json` records for it, not the newest planner log: several planners of one project run at once, and a run whose end is logged after another run started is measured from what it spent, not from the other run's log (I-0314). A run whose log holds nothing logs nothing. The orchestrator's, the analyzer's, the curator's, and a defined role's run ends are measured from their own logs the same way.

The items are named in this order (`plannedItems`, S-0209): the planned item; then the items under it created since the run started; then those under it created before and changed (`updated`) since. Under an epic are its stories and their tasks; under a story, its tasks. Archived items are left out, and each group is in ID order. When the items cannot be read, flai warns and the entry names the planned item alone. An `asked` planner is not started again when the thread is answered; the operator asks for another run. A run on the usage limit is not started again: its end sets or extends its provider's budget state, and the replanner's queue waits for the state to clear ([The queue](#the-queue), [flai-cli.md](flai-cli.md#the-hosts-budget-state)).

The usage apportioned to the activity's span, the same share the entry's cost is, is also charged to the item the run was started for and to every item above it, under `usage.strategic` as the planner's entry, with the entry's seconds (S-0225, [ADR-0083](../adrs/0083-a-planner-activity-s-usage-is-charged-to-the-item-it-planned-and-the-items.md), [work-hierarchy.md](work-hierarchy.md)). An activity the planner logs with `activity_log` during the run is charged the same way, its own span's share. flai serve finds the item by the run's log: the item whose newest run under `plans` kept its log in the run being measured. A planner a person runs by hand, a run that a newer run for its item has replaced, and an activity outside any run charge nothing. The charge on the items and the entry in `planner.md` are two views of one spend; nothing adds them together. A charge that fails leaves the entry logged and is warned of. Measuring a story from its agents' logs keeps what the planner spent on it.

Every start and failure is a journal entry with action `plan`. `agent.status` carries the runs as `plans`. When a planner run starts, cannot start, or ends, `flai serve` tells the dashboard with an `agent` notification that names the `item` in place of a story. Since S-0532 ([ADR-0209](../adrs/0209-the-orchestrator-runs-for-a-reason-and-ends-started-by-flai-serve-on-the-events.md) §6) it also logs an `agent` event on the item planned, `fields.role` `plan`: `started` with its trigger as `why`, then `ended` for `worked` or `asked`, or `failed` with its exit. The orchestrator, the analyzer, and the operator see it in `inbox` and `wait_for_events` ([flai-cli.md](flai-cli.md#the-events-wait_for_events-and-inbox-report)).

### Planning again

While the `plan` host action is on, `flai serve` plans again without the operator asking (S-0211, [ADR-0084](../adrs/0084-flai-serve-plans-again-on-its-own-behind-the-plan-host-action-on-an-edit-when.md)). The operator's own asking is unchanged. A replanner per served project (`internal/serve/replan.go`) looks whenever the project's launcher does: when its work items or threads change, when an agent ends, and every minute. At each look it reads the planner's role file, the project's or the baseline flai carries, and queues the planner only on the `trigger` entries the file names, under their conditions (S-0554, [ADR-0250](../adrs/0250-a-role-file-s-start-prompt-is-a-text-template-in-its-front-matter-s-start-field.md) §4, [Its triggers](#role-files-s-0414)). The baseline names three.

| Trigger | Entry | When | What `flai serve` does |
|---------|-------|------|------------------------|
| An edit | `{event: edited, when: stale-figures}` | Someone other than a planner or the story's own agent edits the goal, criteria, or touches of a backlog or ready story whose forecast or cost of delay value is older than the edit; or edits its cost of delay inputs, leaving them newer than its value (`roles.StaleFigures`) | Queues the planner for the story |
| Work ahead completes or the order changes | `{event: accepted}`, `{event: cancelled}`, and `{event: reordered}`, each `when: replan-agent` | A story is accepted or cancelled, or the pull order changes, and `planning.replan` is `agent` | Queues the planner for each story the replay moved (`roles.ReplanAgent`; [The replan policy](#the-replan-policy)) |
| The schedule | `{schedule: planning.schedule, when: each-ready-story}` | `planning.schedule` comes round | Queues the planner for every ready story, in pull order (`roles.EachReadyStory`) |

An event entry with no condition queues the event's item when the planner takes its kind, and never for an edit by a planner or by the replay; `{event: reordered}` has no item, so it queues nothing. A file without an entry starts nothing on it: a planner's file without the schedule entry queues nothing when `planning.schedule` comes round. The replay itself is flai's own work, which no entry gates ([The replan policy](#the-replan-policy)).

Edits are read from the edit notices in `.flai-cache/edits.jsonl`, which `flai edit`, `flai touches`, the dashboard, and the MCP tool `item_edit` leave ([flai-cli.md](flai-cli.md#commands)); a hand edit of a file leaves none. An edit by an agent named `planner-…` never triggers, so a planner's own writes do not start it again. Nor does an edit by the story's own agent, named by the configured agent name, `agent` by default, and the story's ID, such as `agent-S-0001` (I-0098). A story never planned, with neither a forecast nor a cost of delay value, is not planned on an edit: replanning keeps planning fresh, and planning a story first is the operator's to ask. A cost of delay value written alone triggers nothing.

#### The replan policy

`planning.replan` in `system-flow.yaml` ([project-manifest.md](project-manifest.md)) says what happens when a story is accepted or cancelled or the pull order changes:

| Value | What happens |
|-------|--------------|
| `never` | Nothing |
| `deterministic`, the default | Every ready and backlog story with a forecast duration is played out again, in pull order, with `planning.Replay`: the [forecast](#forecast)'s play-out, keeping the story's own duration. Where the delivery moved, the new delivery and basis are written; the duration stays. No agent runs |
| `agent` | The same, then the planner is queued for each story written, with the triggers, when its role file names the event under `replan-agent` |

The replay writes every story it moved in one pass through `itemedit.ApplyForecasts` (S-0599), stamped `by: flai`, with no commit per story. The pass makes the same edit `flai edit` makes. It saves the items under one hold of the items lock and writes `wip/agents/index.md` once. It then runs one check over the written items, the per-item rules and the markdown lint of their files. An error on an item's own file puts that item back. The replay passes the items it read, so each save merges against what the replay read ([ADR-0184](../adrs/0184-every-work-item-write-takes-one-items-lock-and-merges-a-copy-read-before.md)). A forecast another writer changed since the replay is refused, and a change to another part of the item is kept.

The files written, the items and `wip/agents/index.md`, are then committed together in the main checkout as `chore: replan forecasts after <triggers>`, unless `dashboard.autocommit` is false. flai serve logs `forecasts replanned` with the policy, how many moved, and the triggers. A replay that fails is warned of as `forecast not replayed`, and a write that is refused as `forecast not replanned`. The others go on.

The write costs little. In a scratch copy of this repository on a busy host, writing 20 moved forecasts took a median of 0.09 s. The old write, one checked edit per story, took 273 s ([server-performance.md](server-performance.md#cause-9-fixed-the-replanners-forecasts-written-in-one-pass-s-0599)).

#### The schedule

`planning.schedule` is a five-field cron expression in UTC (minute, hour, day of month, month, day of week), such as `0 6 * * 1-5`, or `daily`, which is 00:00 UTC. flai parses it itself (`internal/cron`, no library): `*`, values, ranges, comma lists, and steps `/n`; Sunday is 0 or 7; with both day fields given, a day either names matches. An expression that never comes round, such as February 31st, is refused. `flai check` reports one it cannot parse as `manifest.planning`.

The replanner follows each setting the planner's schedule entries name, `planning.schedule` in the baseline, with a cadence of its own. It sees a schedule come round at the next look after its time, so at most a minute late. A schedule set or changed comes round first at its next time from then. Times missed between two looks come round once.

#### The queue

The queue holds a story once: a trigger for a story already queued is added to its entry, not queued again. flai serve drains it one planner at a time per project, with its own launcher, so it sees the run end at once and starts the next. It passes over an entry whose item has a planner running, such as one the operator asked for, and comes back to it. It drops an entry whose story its agent works, whatever queued it: the story is in progress or in review, or the story's agent run is still running, such as a ready story whose agent flai serve has started. The drop is logged at info as `queued planner dropped`, with the reason (I-0098). Each other entry goes through `planCheck`, the checks `serve.Plan` makes ([Starting it](#starting-it)); an entry they refuse, such as a story accepted meanwhile, is dropped and logged at info as `queued planner dropped`, with the reason. A run the operator asks for is not queued. While the host's budget state holds the planner's provider, the entry keeps its place, and every entry after it waits too; the next look tries it again, and the hold is logged once per state (S-0534, [flai-cli.md](flai-cli.md#the-hosts-budget-state)).

#### What a run records

A run's triggers, joined by semicolons, are its `trigger` in `serve/agents.json` and the `- Trigger:` line of its activity entry in `wip/agents/planner.md` ([agent-narrative.md](agent-narrative.md#strategic-agents-activity-documents)), such as `- Trigger: accepted S-0210; reordered`.

| Trigger | Said as |
|---------|---------|
| The operator asked | `asked` |
| The orchestrator asked (S-0219) | `orchestrator` |
| The orchestrator asked again for an item planned before, after the operator wrote on a thread on it or on an item under it (S-0524) | `orchestrator; TH-nnnn`, the thread the candidate names |
| An edit | `edited <fields> by <who>`, the fields among `goal`, `criteria`, `touches`, and `cost_of_delay` |
| A story accepted | `accepted <ID>` |
| A story cancelled | `cancelled <ID>` |
| The pull order changed | `reordered` |
| The schedule | `schedule <expression>`, as written in the manifest |

`orchestrator; TH-nnnn` is one trigger, not two joined: flai reads it as the orchestrator's (`orchestratorAsked` in `internal/serve/plan.go`, [ADR-0222](../adrs/0222-with-plan-backlog-epics-or-plan-backlog-stories-on-the-orchestrator-may-ask-the.md) §3). A run of the other kinds the orchestrator asks for keeps `orchestrator`. The run's start event gives as its `why` `the orchestrator asked for it again for what the operator wrote on TH-nnnn` (`triggerWhy`). The thread goes to the planner's request as `harness.Request.AskedOn`, and to its start prompt as `.AskedOn`. The first paragraph of the baseline's start prompt then says that the orchestrator asked for the item to be planned again: it was planned before, and the operator wrote on that thread since its last plan. It tells the planner to read the thread with the MCP tool `thread_get`, or `flai thread show` on the host, and to plan what the operator asked for there, drafting the additions and revisiting the rest as the convention says (`planner.md`'s `start`). `flai plan --json` and the MCP tool `plan` answer with the `trigger` the run recorded.

#### What it keeps

What the replanner has seen is kept in memory, from flai serve's start: an edit, a move, or a scheduled time that passed while flai serve was down is not acted on. While `plan` is off it acts on nothing and drops its queue, but keeps up with what happens, so turning `plan` on does not act on the past. A `planning.replan` or `planning.schedule` that is not valid is warned of once in flai serve's log, and nothing is done for it until it is fixed.

#### On the settings page

The Settings page shows the triggers read-only, under "Planning again, for this project" (`planningTriggers` in `cmd/serve_view.go`): whether edits to a planned story start the planner, which is whether `plan` is on; the replan policy, marked when it is the default; and the schedule with its next run in UTC. A value flai cannot read is shown with its error. The section links to the Planner page, where the planning keys are edited (S-0229, [ADR-0101](../adrs/0101-with-the-settings-host-action-on-the-dashboard-edits-the-strategic-agents.md)): its settings panel writes `planning.agent`, `replan`, `schedule`, `hour_rate`, `cycle`, and `default_duration` through `flai manifest set` while the `settings` host action is on, and shows them read-only otherwise ([On the dashboard](#on-the-dashboard)). In a shell, `flai manifest set` writes the same keys, or the operator edits `system-flow.yaml` by hand. `planning.currency` is a hand edit alone ([project-manifest.md](project-manifest.md)).

## The orchestrator

The orchestrator keeps a project's work moving, and nothing else (S-0218, [ADR-0087](../adrs/0087-flai-serve-runs-one-orchestrator-per-project-behind-the-orchestrate-host-action.md)). It asks the planner to plan an epic or a backlog story, settles what a story's planner asks, finalizes drafts, promotes stories to ready, orders the ready column, answers threads, accepts stories, publishes releases, and adds, changes, or removes a sub-project a story or a thread asks for, each only while the operator's permission for it is on. It takes every figure from flai's commands and logs each decision. Unlike the planner, it has no item. `flai serve` starts it for reasons, the events it can act on, and it acts on them and ends ([ADR-0209](../adrs/0209-the-orchestrator-runs-for-a-reason-and-ends-started-by-flai-serve-on-the-events.md)).

### Starting and stopping it

The host action `orchestrate`, off by default, turns it on for a project: `flai serve enable orchestrate`, or the dashboard's Settings page while `settings` is on. While it is on, `flai serve` starts the orchestrator for reasons and the run ends when they are done ([ADR-0209](../adrs/0209-the-orchestrator-runs-for-a-reason-and-ends-started-by-flai-serve-on-the-events.md), refining [ADR-0087](../adrs/0087-flai-serve-runs-one-orchestrator-per-project-behind-the-orchestrate-host-action.md)). `flai serve` looks at every look of the project's launcher: when its work items or threads change, when an agent ends, every minute, and when queued reasons come due (`internal/serve/orchestrate.go`).

**Its reasons.** At each look `flai serve` reads the inbox's catch-up as the orchestrator would, under a cursor of its own, `flai-serve-orchestrator`, so that the orchestrator's own cursor stays where it is. It queues as a reason each event a trigger in the orchestrator's role file matches (`orchestrate_reasons.go`). The baseline file names them:

| Trigger | A reason when |
|---------|---------------|
| `asked` | the operator turns `orchestrate` on, or starts the orchestrator |
| `{event: thread, when: awaits-orchestrator}` | a thread awaits the orchestrator, or the operator in its role ([ADR-0181](../adrs/0181-a-thread-awaits-an-agent-only-when-the-agent-takes-part-in-it-or-it-is-on-the.md)) |
| `{event: moved, when: to-review}` | a story or an epic moved to review |
| `{event: moved, when: to-backlog}` | a story or an epic moved to the backlog |
| `{event: edited, when: draft-changed}` | a draft story was edited, but for the replan's forecast edits by `flai` |
| `{event: planned}` | a planner's run ended having written items |
| `{event: release-due}` | an acceptance changed what `flai release --evaluate` answers |
| `{event: ready-empty}` | the ready stories not held on `after` fell below the in-progress limit's room, once per draining ([ADR-0279](../adrs/0279-ready-empty-counts-only-the-ready-stories-not-held-on-after-and-a-move-of-a.md)). When no candidate can be promoted either, `flai serve` also asks the operator on a thread of its own on the board, which the orchestrator leaves alone ([ADR-0285](../adrs/0285-when-nothing-can-be-made-ready-flai-serve-opens-one-thread-to-the-operator-on.md), [workflow.md](workflow.md#cadence)) |
| `{event: reordered}` | the pull order changed |
| `{schedule: orchestration.schedule}` | `orchestration.schedule` came round; unset by default |

The events are [ADR-0211](../adrs/0211-the-orchestrator-s-trigger-vocabulary-gains-the-events-moved-thread-planned.md)'s. An event no trigger matches is none: a file change with no event, a task's move, an epic's move following its story, an item cancelled with its parent, and the replan's forecast edits start nothing. When the role file is missing, does not parse, or still says `continuous`, the baseline's triggers above are used (`builtinTriggers`). The queue is kept per project in `serve/orchestrate-reasons.json`, so a `flai serve` started again loses none; a reason already queued is not queued twice.

Turning the action on, or `flai serve` finding it on at its first look with no queue kept, queues one `asked` reason. Events from before are not acted on: that look takes the catch-up's events since the last as history. While the action is off, the schedule keeps up, nothing is queued, and nothing is written in the project.

| At a look | What `flai serve` does |
|-----------|------------------------|
| The action is on, reasons are queued, and no run is going | Starts one run once `orchestration.coalesce` (`30s` by default) has passed since the first reason was queued, or at once for `asked`, with every reason queued. The start takes them out of the queue, and a run that fails, on the usage limit or otherwise, gives them back ahead of those queued since ([ADR-0209](../adrs/0209-the-orchestrator-runs-for-a-reason-and-ends-started-by-flai-serve-on-the-events.md) §5) |
| The action is on and nothing is queued | Nothing. A run that ends is not started again by itself |
| The action is on and the operator holds it stopped | Nothing until they start it |
| The action is on and the last run failed less than a minute ago | Nothing until the minute has passed, so that a run that fails at once does not spin; the reasons stay queued |
| The action is on and the host's budget state holds the orchestrator's provider | Nothing, and nothing recorded; the reasons stay queued, and the minute's retry does not apply. The first look once the state no longer holds starts it (S-0534, [flai-cli.md](flai-cli.md#the-hosts-budget-state)) |
| The action is on and a run is going | Queues what arrives, for the next run. Stops the run once it has gone past `orchestration.run_timeout` (`20m` by default) |
| The action is off and a run is going | Stops it as `flai serve agent stop` stops a story's agent: marks it stopped, ends its process group, and kills the group once the grace has passed. The stop is journalled, and the run's activity is logged with the summary `stopped: orchestrate turned off` |
| The action is off and the operator holds it stopped | Lifts the hold, so that turned on again the orchestrator starts |

Reasons that arrive while a run is going start the next run at the first look after it ends, once their coalescing window has passed. A run ends when its reasons are done, when it fails, when it is stopped, or when its harness ends it.

The operator stops it and holds it stopped with **Stop** on the Orchestrator page, the write `orchestrate.stop`, or `flai serve orchestrate stop` (S-0228). The run is stopped as the action turned off stops it, and its activity is logged with the summary `stopped: stopped from the dashboard`. The hold is `held` on its run in `serve/agents.json`, kept on the run that ended. **Start**, `orchestrate.start`, or `flai serve orchestrate start` queues an `asked` reason and starts a run at once, for it and every reason queued, in the main checkout, whether or not the orchestrator was held stopped. Recording the new run lifts the hold; a start that fails lifts the hold too and keeps the reasons, and the next look tries again after the minute. Both are refused while the action is off. A stop is refused when `flai serve` has started no orchestrator for the project and when it is already held; a start, while a run is going or the run it was held on is still being stopped. A run that failed and waits to be started again is held as it is. A start while the host's budget state holds the orchestrator's provider is refused as `held: <provider> usage limit (<limit>) until <until>; …`, with nothing recorded or queued, and the orchestrator stays held stopped. Each is journalled under `orchestrate`.

A start is refused when the orchestrator's harness is `command` and no command is set for the project, when it is one flai cannot start, and when the harness refuses it. An agent that names no harness falls back to the host's command, then to flai's built-in `claude-code` ([ADR-0261](../adrs/0261-a-story-or-strategic-agent-that-names-no-harness-falls-back-after-the-project-s.md)). A project with no `.claude/agents/orchestrator.md` is not refused, since `claude-code` generates the definition from the role file (ADR-0236). A refusal is recorded as a failed run and journalled once: the same refusal at the next looks is not recorded again until a start gets past it or the action is turned off.

### Its agent

`orchestration.agent` in `system-flow.yaml`, merged over the project's `agent` as `planning.agent` is (`Manifest.OrchestrationAgent`), gives the orchestrator's harness, model, config, and roles. With neither set, the host's command starts it. `flai check` reports an `orchestration.agent` that is not valid as `manifest.orchestration`. See [project-manifest.md](project-manifest.md). Its harness may be `container`: [In a container](#in-a-container-s-0509) says what the container mounts.

### How it runs

The launcher's `orchestrate` starts it through the harness adapter with a `harness.Request` whose `Role` is `orchestrate`, whose `Reasons` are the run's reasons, one line each, and with no `Item` and no `Story`.

- **Where.** In the project's main checkout, where the items are. No branch, no worktree.
- **As whom.** `FLAI_AGENT` is `orchestrator`. The environment carries `FLAI_ROLE=orchestrate`, `FLAI_REASONS` with the reasons, one a line, `FLAI_SESSION`, and `FLAI_STARTED_BY=flai-serve`, and no `FLAI_ITEM` or `FLAI_STORY`. `roleEnv` refuses an orchestrator request that names an item or a story.
- **claude-code.** The session is named `<key> orchestrate`. It runs with `--agent orchestrator` over the definition flai generates from its role file, `design/workflows/roles/orchestrator.md`, the project's or flai's baseline, with the project's additions below the marker, but for its `### Start prompt` section, in its prompt and the orchestrator's agent's model when it names one. It is passed in `--agents` beside the explorer and the verifier, and nothing under `.claude/` is read for it. `startOf`, the start every run goes through, gives it the file ([Role files](#role-files-s-0414)). Its permission handler is flai's `permission_prompt`, as for every session `flai serve` starts ([ADR-0086](../adrs/0086-flai-serve-gives-a-claude-code-agent-flai-s-permission-prompt-as-its-permission.md)).
- **The operator's command.** It gets `FLAI_ROLE`, and `{story}` is empty.

### What it is told

`harness.Prompt` gives the orchestrator the start prompt of its role file, `orchestrator.md`'s `start` rendered over the run's fields, `.Reasons`, `.Primed`, `.PrimeForms`, and `.Queue` among them, with the project's `### Start prompt` additions ([Its start prompt](#role-files-s-0414)). The baseline's first paragraph says why it was started: by `flai serve` while the `orchestrate` action is on, for the reasons it lists, one a list item; or, with no reasons, as a run by hand is, to look at the inbox and the board once, act on what they show, and end. Then: keep the project's work moving and do nothing else, as the convention's section "As the orchestrator" says; prime with `--role orchestrate`, with the forms of its reasons when each has one ([Primed for its reasons](#primed-for-its-reasons-s-0537)); call `inbox` and read the board; hand wide search to the explorer. Act only within `orchestration.permissions` and by `orchestration.policy`, and ask when a permission is unclear. The operator may change its permissions, its policy, and the release policy, `orchestration.release`, while it runs: read them again in `system-flow.yaml` in the main checkout before each decision rather than keep what it read at the start, and when `flai guard`'s verdict on a call differs from what it read, the guard's verdict holds (S-0229). Take every figure from flai and do no arithmetic: the epics and stories to plan from `flai plan --candidates`, the drafts complete enough to finalize from `flai promote --drafts`, the order from `flai order --by` (`order_by_policy`), the stories that could go to ready from `flai promote --candidates` (`promote_candidates`), and whether a release is due from `flai release --evaluate` (`release_evaluate`). With each permission, run its command and act on what it prints ([What it does with each permission](#what-it-does-with-each-permission-s-0219)). With `plan_backlog_stories` on, after the epics, plan each story listed, one at a time; on a thread that story's planner opened, approve a plan that fits by replying and resolving, answer its questions, and for a cost of delay input take the planner's recommended figure unless the thread or the story gives reason for one of its alternatives, set the inputs with `item_edit` alone, reply naming what it set, and resolve ([A story planner's threads](#a-story-planners-threads-s-0328)). Reply on the threads awaiting the operator as `answer_threads` says, read afresh from `system-flow.yaml` each time ([Answering threads](#answering-threads-s-0220)). While `publish` is on, evaluate the release policy after each acceptance and, when it is met, publish by running `flai formula run publish --ready --autocommit`, or through `release_publish` where the project has no `publish` formula ([Publishing a release](#publishing-a-release-s-0222)). While `edit_subprojects` is on, add, change, or remove a sub-project only when a story or a thread asks for it, with `flai subproject ... --autocommit` in the main checkout, never `subproject_edit`, which commits nothing (S-0491, [ADR-0195](../adrs/0195-with-edit-subprojects-on-the-orchestrator-adds-changes-and-removes-a-sub.md)). Log each action with `activity_log`, kind `orchestrator`: what it did, on which items, why, and the policy figure behind it, as flai gave it. Act on each reason listed, log each action, then end: `flai serve` starts it again when there is more, and `wait_for_events` answers it `end: true`, `why: reasons done`, once its reasons are done ([ADR-0209](../adrs/0209-the-orchestrator-runs-for-a-reason-and-ends-started-by-flai-serve-on-the-events.md) §3, §4). Write only through flai; never edit code or documents, and never work a story. Never work around a refusal: a refusal from `flai guard` or from flai ends that attempt, which it logs and does not try again until something it depends on changes. When a decision needs the operator, ask with `thread_open` on the item, the recommended answer first, and do what needs no answer meanwhile. While the merge queue runs for the project, it is told to enqueue each story it verifies instead of accepting it (`harness.Request.Queue`, set at each start, the start prompt's `.Queue`; [Accepting a story](#accepting-a-story-s-0221)). The convention's "As the orchestrator" says the same (template 1.0.53, its threads 1.0.55, its backlog stories 1.0.71, its enqueue 1.0.104, its reasons' forms 1.1.7).

`orchestrator.md` says the same in short, and since S-0419 its prompt is the body of `design/workflows/roles/orchestrator.md` with the project's additions ([Role files](#role-files-s-0414)). It lists its tools: `Read`, `Grep`, `Glob`, `Bash`, `Agent`, and flai's MCP tools for reading, `inbox`, `board`, `item_edit`, `item_move`, `thread_open`, `thread_reply`, `activity_log`, `wait_for_events`, `plan`, `order_by_policy`, `promote_candidates`, `release_evaluate`, since S-0222, `release_publish`, since S-0328, `thread_resolve`, for a story planner's thread, since S-0403, `queue_add`, for the merge queue, since S-0491, `subprojects`, which lists the sub-projects it changes with `flai subproject` under `edit_subprojects`, and, since S-0556, `verify`, which it holds by name now that no sub-agent may call it. It lists no `Edit`, `Write`, or `NotebookEdit`. It finalizes a draft with `item_edit` giving only the story's `id` and `draft: false`.

Whether the criteria, touches, and forecast describe the same work is the orchestrator's judgement.

Under `plan_backlog_stories`, flai lets the orchestrator set less of a story's cost of delay than [ADR-0119](../adrs/0119-with-plan-backlog-stories-on-the-orchestrator-asks-the-planner-for-each-backlog.md) §4 does. The ADR lets it set the inputs and the value. flai lets it add inputs only, to a backlog story when neither the story nor its epic has any, which covers the planner's recommendation on a story planner's thread. Under `set_cost_of_delay` it adds or changes the inputs of any epic or story that is not done, cancelled, or archived, whether or not it or its epic has inputs already ([ADR-0224](../adrs/0224-orchestration-permissions-set-cost-of-delay-off-by-default-lets-the.md)): a figure the operator decided on a thread, as an answer or a recommendation they confirmed, for an epic or a story past the backlog. flai cannot tell where a figure came from, so that rule is the convention's. Under either it sets no value and removes nothing: the value stays what `flai cod` works out from the inputs, or the operator's own figure. The value stays the planner's to write: a story given inputs has changed, so `flai plan --candidates` lists it again while it lacks a value.

A planner the orchestrator starts runs as any planner does, behind the `plan` host action and `serve.Plan`'s refusals ([Starting it](#starting-it)), and is started with `serve.PlanForOrchestrator`: its run records the trigger `orchestrator` in place of `asked`, so `serve/agents.json` and the `- Trigger:` line of its entry in `wip/agents/planner.md` say who asked. For a candidate planned before, the trigger is `orchestrator; TH-nnnn`, with the thread the candidate names, and the planner's prompt names that thread (S-0524, [What a run records](#what-a-run-records)). The journal names `orchestrator` as who asked. The orchestrator never places a story by hand: the guard refuses it `flai order <story>` whatever its permissions, and under `FLAI_ROLE=orchestrate` `flai order` records any placement as the orchestrator's, which the window does not keep.

Each action is one `activity_log` entry in `wip/agents/orchestrator.md`: what it did, the items, why, and the figure flai gave behind it, such as a story's cost of delay value, its value over its duration, its forecast, or a candidate's rank. A refusal ends the attempt: the orchestrator logs it with the refusal and does not retry until something it depends on changes. The guard's refusals are also appended under `## Refusals` ([Its permissions and the guard](#its-permissions-and-the-guard)); flai's own are in the entry the orchestrator logs. `cmd/orchestrate_permissions_test.go` runs each of the five permissions on and off on a fixture board, through the guard and flai.

### Answering threads (S-0220)

`orchestration.permissions.answer_threads` is `off`, `recommend`, or `autonomous`, and lets the orchestrator reply on the threads awaiting the operator: those `inbox` marks `awaiting: "operator"`, which it lists in the orchestrator's role without `all: true` ([ADR-0181](../adrs/0181-a-thread-awaits-an-agent-only-when-the-agent-takes-part-in-it-or-it-is-on-the.md)), save those the orchestrator opened, those whose last entry is its own, those with a recommendation pending (`pending_recommendation` in `inbox`), and those whose last entry is by neither a story's agent nor a planner, such as `flai serve`'s notices. The operator may change it while the orchestrator runs, so its prompt states the rules for each value and tells it to read the value from `system-flow.yaml` each time before it acts on threads (`orchestrator.md`'s `start`).

| Value | It replies |
|-------|------------|
| `off` | Not at all |
| `recommend` | With a recommendation on each, with `thread_reply`, `recommendation: true`, and a `source`: the ADR, design section, or convention its answer rests on, as `<path>` or `<path>#<heading>`, read with `doc_get` first. The thread stays awaiting the operator, who confirms the recommendation (`flai thread confirm`, or the dashboard) or replies in its place ([ADR-0090](../adrs/0090-a-thread-entry-is-marked-a-recommendation-in-its-heading-and-cites-its-source.md)) |
| `autonomous` | With an answer and a `source` when a source settles the question, which ends the wait as the operator's answer would. With a recommendation instead, escalating to the operator, when no source settles it or the question asks for the operator's judgement: a decision not yet recorded, a change of scope, or money, such as a cost of delay input, an estimate, or spend. A cost of delay input on a story planner's thread is the exception while `plan_backlog_stories` is on ([A story planner's threads](#a-story-planners-threads-s-0328)), and so is setting a figure the operator decided while `set_cost_of_delay` is on |

flai enforces only what it can tell. The guard holds its thread calls ([Its permissions and the guard](#its-permissions-and-the-guard)): with `answer_threads` off it refuses any reply on another's thread; with `recommend` it lets only a recommendation through; with `autonomous` it lets an answer through only with a source that names a file, and tells it to cite one or post a recommendation. Whether a source settles the question, and whether the question is the operator's judgement, is the orchestrator's to decide. A recommendation ends no wait, and `flai stats` counts the waits the orchestrator ended apart from the operator's ([ADR-0091](../adrs/0091-a-recommendation-ends-no-thread-wait-and-flai-stats-reports-the-waits-the.md)). Since a recommendation ends no wait, `flai serve` reminds the operator of the one pending on a thread past `threads.remind_after`, and again every `threads.remind_every`, through the channel the host keeps, writing nothing on the thread ([ADR-0205](../adrs/0205-flai-serve-reminds-the-operator-of-a-thread-that-awaits-them-past-threads.md)).

With `orchestration.permissions.confirm_after` set, `flai serve` confirms such a recommendation in the operator's absence (S-0502, [ADR-0206](../adrs/0206-flai-serve-confirms-an-orchestrator-recommendation-the-operator-left-unanswered.md)). It looks when it looks to remind, every minute and when the project's work items or threads change, and only while the `orchestrate` host action is on (`internal/serve/confirm.go`). It confirms the orchestrator's pending recommendation on each open thread that meets all of these:

- a story's agent (`agent-S-nnnn`) or a planner opened it;
- it is not a permission prompt's thread, `Allow <tool> <path>?`;
- it is on a document, or on an item that is not done or cancelled;
- the recommendation is not marked for the operator alone, and was written `confirm_after` ago or more;
- no entry by the operator, the manifest's owner or the story's owner, follows it.

The confirmation is an entry by `flai serve`, `Confirmed the recommendation of <time> <author> after <confirm_after> with no answer from the operator (orchestration.permissions.confirm_after).`, citing the recommendation's source, and the thread becomes `answered` (`threads.ConfirmByTimeout`). The asking agent is started again as on the operator's confirmation. No digest entry is written from it, since the operator gave no answer. `flai serve` logs it, and records it in `wip/agents/orchestrator.md` as an activity of no seconds and no cost, with the trigger `orchestration.permissions.confirm_after`, naming the thread and its item. `flai stats` counts the waits it ended as `waiting.weeks[].threads.timeout`, apart from `confirmed` ([metrics.md](metrics.md#waiting)). The operator overrules it afterwards by answering on the thread.

flai cannot tell money or a change to the host from a recommendation's words, so the orchestrator marks such a recommendation for the operator alone, as its prompt and its definition tell it to. `thread_reply` with `operator_only`, or `flai thread reply --recommend --operator-only`, writes the paragraph `For the operator alone: flai serve does not confirm this after orchestration.permissions.confirm_after.` above the `Source:` line, and the entry's JSON carries `operator_only`. The mark needs a recommendation. A flai older than this reads the entry as a plain recommendation.

Each reply is logged in its decision log by `thread_reply` itself, not by the orchestrator calling `activity_log`: an entry in `wip/agents/orchestrator.md` saying `Answered TH-nnnn` or `Recommended an answer on TH-nnnn`, `citing <path> § <heading>` or `citing no source`, with the thread's story as its item. A reply posted whose log entry fails is reported as an error naming both, so the orchestrator logs it with `activity_log`.

### A story planner's threads (S-0328)

With `orchestration.permissions.plan_backlog_stories` on, the threads a story's planner opens are the orchestrator's to settle, whatever `answer_threads` says ([ADR-0119](../adrs/0119-with-plan-backlog-stories-on-the-orchestrator-asks-the-planner-for-each-backlog.md)). Such a thread's opener is `planner-S-nnnn`. On it the orchestrator:

| The planner | The orchestrator |
|-------------|------------------|
| Posts its plan | Replies approving it when it fits the story, and resolves the thread |
| Asks a question | Replies with an answer, citing a `source` when one settles it, and resolves the thread. When the question asks for a change of scope or a decision not yet recorded, it posts a recommendation instead and leaves the thread open for the operator |
| Asks for a cost of delay input | Takes the figure the planner recommends, unless the thread or the story gives reason for one of its alternatives. Sets the inputs with `item_edit`'s `cost_of_delay` alone, replies naming what it set, and resolves the thread. Under `plan_backlog_stories` alone, that is a backlog story's first inputs, when neither it nor its epic has any; any other needs `set_cost_of_delay` |

The money rule of `autonomous` does not hold here: under this permission the operator has handed the orchestrator a backlog story's first cost of delay inputs. flai still holds which inputs it may set ([What it does with each permission](#what-it-does-with-each-permission-s-0219)). On any thread, a story planner's or another, a figure the operator decided, as an answer or a recommendation they confirmed, is the orchestrator's to set on the epic or story it concerns while `set_cost_of_delay` is on ([ADR-0224](../adrs/0224-orchestration-permissions-set-cost-of-delay-off-by-default-lets-the.md)); with it off, a figure for an epic or a story past its first inputs stays the operator's to set. `thread_reply` logs each reply, as above; the orchestrator logs each cost of delay it sets, and each thread it resolves, with `activity_log`.

Two things stay as they were. Confirming a recommendation is the operator's alone ([ADR-0090](../adrs/0090-a-thread-entry-is-marked-a-recommendation-in-its-heading-and-cites-its-source.md)), save `flai serve`'s confirmation by timeout ([Answering threads](#answering-threads-s-0220)). An epic's planner's threads, opened by `planner-E-nnnn`, stay under `answer_threads`, as every other thread does. With the permission off, a story planner's threads are under `answer_threads` too.

### Accepting a story (S-0221)

With `orchestration.permissions.accept_reviews` on, the orchestrator accepts a story in review through `flai accept <S-nnnn> --by orchestrator`, the same flow as the operator's: merge, done, archive, commit, and never a release ([ADR-0093](../adrs/0093-with-accept-reviews-on-the-orchestrator-accepts-a-story-in-review-through-flai.md), refining [ADR-0032](../adrs/0032-accepting-a-story-merges-it-publishing-is-a-deliberate-batched-step-over.md)). For each story in review it:

1. Reads the story's last `flai verify` result, and asks for the close-out with the MCP tool `verify` when it did not pass or its commit is not the branch's head, then reads the verdict with `flai verify <S-nnnn> --last`; a run that did not pass is a blocker. The close-out runs on the host, in flai serve, wherever the orchestrator runs ([ADR-0278](../adrs/0278-the-orchestrator-accepts-through-an-mcp-tool-that-runs-flai-accept-on-the-host.md)). A `flai verify` the orchestrator runs on the host runs the tiers under `FLAI_ROLE=verify`, not `orchestrate`, so a story whose tests run flai's writes is not refused by the orchestrator's own checks (S-0311, TH-0260); in its container that run refuses ([In a container](#in-a-container-s-0509)). Then hands the story's worktree and that result to its verifier, which reads the result rather than running the suite, and matches each acceptance criterion to the files the branch changes that meet it (S-0270, [ADR-0110](../adrs/0110-a-story-s-agent-runs-the-close-out-which-runs-flai-verify-itself-before-review.md)).
2. Calls the MCP tool `accept` with the story, `verified`, the commit the verifier checked, and `dry_run`, which runs `flai accept <S-nnnn> --by orchestrator --dry-run` on the host, and reads the blockers.
3. With no blocker and every criterion matched, calls `accept` with the story, `verified`, and `evidence`, which runs `flai accept <S-nnnn> --by orchestrator --verified <commit> --evidence -` on the host with the host's configuration, and logs the acceptance with `activity_log`, naming the story and the commit.
4. Otherwise leaves the story in review, opens a thread on it saying what is missing, each blocker and each criterion it could not check against the diff, and logs that decision. It opens a thread on a story in review only for a reason not to accept it, and resolves that thread with a reason once the reason is gone ([ADR-0189](../adrs/0189-the-orchestrator-s-acceptance-lands-on-a-dirty-main-as-the-merge-queue-s-does.md)).

While the merge queue runs for the project, the orchestrator enqueues each story it verifies instead of accepting it, and the queue lands it as the orchestrator (S-0403, [ADR-0173](../adrs/0173-a-merge-queue-in-flai-serve-with-no-model-runs-behind-the-merge-queue-host.md), [ADR-0176](../adrs/0176-the-merge-queue-lands-each-story-of-a-passing-batch-through-flai-accept-batch.md)). The queue runs while the `merge-queue` host action is on, `accept_reviews` is on, and acceptance is local. Its prompt says whether it does ([What it is told](#what-it-is-told)).

| Step | With the queue running |
|------|------------------------|
| 1 | As above |
| 2 and 3 | It writes the evidence and enqueues the story with the MCP tool `queue_add` (`story`, `verified`, `evidence`), or `flai queue add <S-nnnn> --by orchestrator --verified <commit> --evidence <file>`. It logs each enqueue with `activity_log`: the story, its place in the queue, and the policy figure |
| 4 | As above, but it opens no thread for a blocker the queue settles: a verify not at the branch's head, a dirty main checkout, or a rebase that stops inside the manifest's shared paths |

The enqueue is refused, changing nothing, as the acceptance is: while `accept_reviews` is off; without `verified` or `evidence`; for evidence with a heading in it or that cannot be read; for a story `flai queue add` refuses; and on each orchestrator blocker of the preview below, each named by its code (`mcpserver.EnqueueByOrchestrator`). The queue's state records the commit and the evidence with the story's enqueue, as `verified` and `evidence` ([ADR-0093](../adrs/0093-with-accept-reviews-on-the-orchestrator-accepts-a-story-in-review-through-flai.md)). The orchestrator never lands, bisects, holds, resumes, or dequeues a story by hand.

The acceptance preview adds these blockers for an acceptance by the orchestrator, beside those it reports for any acceptance, and `flai accept` refuses on any blocker before anything is merged:

| Condition | Blocker when |
|-----------|--------------|
| The verifier passed at the branch head | `--verified` is missing, or names a commit that is not the story branch's head. In the merge queue's landing, `--batch` takes its place: each reason the queue does not let the story land from that batch now (below) |
| Every criterion is ticked | A criterion under `## Acceptance criteria` is unticked; each is named |
| The diff stays within the touches | A file the branch changes is under none of the story's touches, read as a claim reads them; each is named. The workflow's own records are the story's whatever it touches: the `wip` folder, the issues under `design/issues`, and an experiment's results |
| No thread is open | A thread on the story or one of its tasks is not resolved; each is named. A thread the orchestrator opened that nobody else wrote on is `own_thread_open`, which says the orchestrator resolves it; every other is `thread_open` ([ADR-0189](../adrs/0189-the-orchestrator-s-acceptance-lands-on-a-dirty-main-as-the-merge-queue-s-does.md)) |
| Main's uncommitted files are safe | The story's change, `main...story/S-nnnn`, would overwrite an uncommitted or untracked file of the main checkout outside the shared set, the files under `wip`, `design`, and `claims.shared`, which every acceptance commits: `dirty_main`, naming the files and the command that sets them aside. The checkout's other uncommitted files stop nothing. Since S-0566 this blocker is every acceptance's but the merge queue's landing, not the orchestrator's alone ([ADR-0189](../adrs/0189-the-orchestrator-s-acceptance-lands-on-a-dirty-main-as-the-merge-queue-s-does.md), [ADR-0248](../adrs/0248-every-acceptance-commits-the-main-checkout-s-uncommitted-files-under-wip-design.md)) |
| The cluster ran the change | While the `kluster` host action is on and the manifest has a `kluster:` block, the story's namespace was not deployed at its branch's head or, while `checks` is on, the checks run against it did not pass there: `kluster`, naming the namespace's last job, its commit, and its outcome. It is every acceptance's blocker, among `orchestrator_blockers` for the orchestrator's, which never passes `--without-kluster`, the operator's alone. The enqueue is not refused for it: the queue waits for the gate (S-0694, [ADR-0254](../adrs/0254-flai-runs-one-kluster-per-project-from-the-config-its-manifest-s-kluster-block.md)) |

Two things set the orchestrator's acceptance apart from the operator's by hand, so that neither waits for the operator ([ADR-0189](../adrs/0189-the-orchestrator-s-acceptance-lands-on-a-dirty-main-as-the-merge-queue-s-does.md), [I-0150](../issues/I-0150-a-story-in-review-waits-days-for-the-operator-when-the-orchestrator-s-acceptance-stops-on-a-dirty-main-a-rebase-on-a-shared-path-or-a-gate-it-raised-itself.md)):

| When | The orchestrator's acceptance | The operator's by hand |
|------|-------------------------------|------------------------|
| An acceptance stopped before its archive or commit | Finishes it when the orchestrator made its move to done, with `flai accept <S-nnnn> --by orchestrator` and no evidence. One anyone else made is refused, naming who, and stays the operator's | Finishes any |
| A thread on the story or one of its tasks that it opened and nobody else wrote on is open | `own_thread_open`: it resolves the thread with a reason once its concern is gone, then accepts; any other open thread is `thread_open` and holds the story | An open thread stops nothing; the acceptance resolves it ([ADR-0109](../adrs/0109-archiving-an-item-resolves-the-threads-still-open-on-it.md)) |

Two more were the orchestrator's alone under ADR-0189 and are every acceptance's since S-0566, by hand, from the dashboard, and by the orchestrator alike, so that none of them waits for the operator ([ADR-0248](../adrs/0248-every-acceptance-commits-the-main-checkout-s-uncommitted-files-under-wip-design.md)):

| When | Every acceptance |
|------|------------------|
| The main checkout has uncommitted files | Commits the shared set, the files under `wip`, `design`, and `claims.shared`: with the acceptance commit when the story's change would overwrite none of them, otherwise in a commit of their own before the merge, `chore: [S-nnnn] commit the main checkout's wip and design before accepting`. Leaves the rest as the merge queue's landing does ([ADR-0178](../adrs/0178-the-merge-queue-lands-each-story-in-the-main-checkout-with-git-s-own-check.md)): out of the lint fix and the acceptance commit, held only by `dirty_main`. By hand, `--yes` includes the rest in the acceptance commit; the orchestrator never passes it |
| Its rebase stops on conflicts the section merge and the generated-file steps cannot settle ([ADR-0175](../adrs/0175-a-rebase-that-stops-on-a-markdown-file-inside-the-manifest-s-shared-paths.md)) | Aborts the rebase in the story's worktree, so the branch and main are as they were, records the conflict, moves the story back to in-progress as `flai` with the paths in the reason, and opens one thread by `flai`, `Acceptance sent back: …`, naming the paths and the branch, or writes on the one still open. It exits saying the story was sent back; with `--json` it exits 4 with `{"refused": {id, reason, sent_back, branch, base, conflicts, thread}}`. With the `agent` host action on, `flai serve` starts the story's agent on that thread, resuming its session, as for a story the merge queue sent back, and resolves the thread once the story is back in review. The operator is never told to finish or abort a rebase |

The merge queue's landing, `--batch`, commits the shared set and leaves the rest the same way, and alone leaves a stopped rebase in the worktree: the queue sends a story back before its batch is built ([ADR-0176](../adrs/0176-the-merge-queue-lands-each-story-of-a-passing-batch-through-flai-accept-batch.md)).

The evidence, `--evidence <file>` or `-` for standard input, is markdown: a `Verdict:` line from the verifier's report, and one list item per criterion, `- <n>: <files>`, naming the changed files that meet criterion `<n>`. flai refuses an orchestrator's acceptance without evidence, and one whose evidence names no changed file for a criterion. It writes the evidence, with the verified commit, under `### Accepted by the orchestrator` in the story's `## Notes`, in the acceptance commit, and returns it in `--json`. The done transition is recorded `by: orchestrator`, and the dashboard's review and story pages name who accepted.

A story the orchestrator enqueued in the merge queue is accepted as the orchestrator by the queue's landing, with no turn of its own ([ADR-0176](../adrs/0176-the-merge-queue-lands-each-story-of-a-passing-batch-through-flai-accept-batch.md), [workflow.md](workflow.md#what-waits-on-an-acceptance-s-0296)). `flai serve` runs `flai accept <S-nnnn> --by orchestrator --batch <id>`:

| Differs from the steps above | How |
|------------------------------|-----|
| The verified commit | The story's rebased head in the batch that verified it. `--batch` takes the place of `--verified`, and is refused beside it |
| The evidence | None is needed: the queue's eligibility checked the story's verify, its criteria, and its threads before the batch was built. Evidence given is checked and written as above. With none given, the evidence the orchestrator enqueued the story with is taken; a story enqueued without it lands on the batch's verification alone |
| The notes | `### Accepted by the orchestrator` names the verified commit, then `- Batch: <id>`, `- Enqueued verified: <commit>`, the commit its verifier checked when it enqueued the story, the time, and the evidence given or enqueued |

The other blockers stand: every criterion ticked, the diff within the touches, no thread open, and no protected path.

flai holds the permission itself, as well as the guard: `flai accept --by orchestrator`, and `accept.run` given `by: orchestrator`, are refused while `accept_reviews` is off, naming it, and under `FLAI_ROLE=orchestrate` an acceptance with any other `--by` is refused. While the merge queue runs, `flai accept --by orchestrator` is refused but as the queue's landing or a dry run, naming `flai queue add` and `queue_add`. Under `FLAI_ROLE=orchestrate`, `--batch` is refused outright: the landing is `flai serve`'s. `item_move` refuses the orchestrator a move to done as it refuses every agent, and names `flai accept --by orchestrator` and the permission.

The orchestrator never keeps a removal of main's lines ([ADR-0155](../adrs/0155-a-rebased-story-branch-that-undoes-main-s-change-to-a-path-is-recorded-at-sync.md)). A path the story's rebased branch undoes of main's change is a blocker in the preview, as for any acceptance ([workflow.md](workflow.md#branches-and-collisions-adr-0019)). It cannot tell an intended removal from a lost change, so it leaves that blocker for the operator, on a thread, as step 4 says. flai refuses `--keep-removal` with `--by orchestrator`, and `accept.run` refuses `keep_removals` with `by: orchestrator`. The operator restores the path with `flai stream restore`, keeps the removal with a reason, or sends the story back.

Under `acceptance.mode: pull-request`, the preview also lists the forge blockers, the same for the orchestrator as for the operator ([ADR-0169](../adrs/0169-under-pull-request-acceptance-every-acceptance-the-operator-s-and-the.md)): a missing pull request, a state not read at the branch head, each required check failing or pending, each reviewer's standing requested change, and missing approvals. The orchestrator reads them in its dry run like any other blocker, and they stop it as they stop the operator: it leaves the story in review, as step 4 says. Only CI and the team's reviewers clear them. The orchestrator never approves a review: flai opens the pull request with the operator's token, and an approval by the gated party would open its own gate.

### Publishing a release (S-0222)

With `orchestration.permissions.publish` on, the orchestrator publishes what is accepted and not yet released, through the MCP tool `release_publish` alone, by the project's release policy ([ADR-0094](../adrs/0094-with-publish-on-the-orchestrator-publishes-only-through-release-publish-by-its.md), refining [ADR-0067](../adrs/0067-accepted-work-reaches-the-remote-only-when-it-is-published-and-agents-publish.md) and [ADR-0087](../adrs/0087-flai-serve-runs-one-orchestrator-per-project-behind-the-orchestrate-host-action.md)). The permission is the operator's asking that ADR-0067 requires. While it is off, the orchestrator neither evaluates nor publishes.

Since S-0423, where the project defines a `publish` formula, the orchestrator publishes by starting it, not through `release_publish` ([ADR-0240](../adrs/0240-under-publish-the-orchestrator-starts-the-baseline-publish-formula-whose-main.md)). When `release_evaluate` is met, it runs `flai formula run publish --ready --autocommit` in the main checkout and logs the instance's story ID with the policy and its figures. The instance is a story: a story's agent works the formula's steps, [publish.md](../workflows/formulas/publish.md), from the main checkout ([Working an instance](#working-an-instance-s-0422)), and the operator or `accept_reviews` accepts it. So each publish is worked, measured, and archived as any story. Under `judgement`, once it judges the unreleased work coherent and complete, it gives that reasoning as the formula's input `judgement`: `flai formula run publish --ready --autocommit --input judgement="<its reasoning>"`, one sentence with no double quote, backtick, or dollar sign, since the input is filled into step 2's command line as text. Step 2 passes it to `flai release --evaluate --require-met --judged`, which meets the policy with that reason when something is accepted and not yet released and `whole_epics` holds nothing back; with no input it stops the run, as before ([ADR-0273](../adrs/0273-under-judgement-the-orchestrator-s-judgement-reaches-the-publish-formula-as-an.md)). Under `threshold` and `theme` it gives no input, and `--judged` would change nothing. The rest of this section is `release_publish`, which stays for a project with no `publish` formula.

- `release_publish` refuses, changing nothing, while the project defines a `publish` formula, naming `flai formula run publish --ready` (`noPublishFormula` in `internal/mcpserver/orchestrate.go`).
- `flai release --pending` refuses, with exit 4, an agent `flai serve` started (`FLAI_STARTED_BY=flai-serve` or `FLAI_STORY` set) while the project's `push` host action is off, naming `flai serve enable push`. So the `push` action gates the instance as it gates `release_publish`. The operator's own shell and `--dry-run` are not held.
- A refusal, the `push` gate or a moved remote's `conflict:` (exit 3), fails its step down the formula's failure path. The instance's agent records the versions and tags, or the evaluation that stopped step 2 (`--require-met`, exit 2), in the instance's Notes.
- Step 3 runs `flai release --pending --require-pending --json` with `stop: [2]` (S-0643, [I-0320](../issues/I-0320-a-publish-instance-s-evaluate-and-publish-steps-race-a-publish-made-meanwhile.md)). When another publish, such as the operator's by hand, released the work after step 2 was met, step 3 finds nothing pending and exits 2. That stops the run cleanly, as step 2's exit 2 does ([ADR-0271](../adrs/0271-a-formula-step-may-name-the-exits-that-stop-its-instance-cleanly-flai-formula.md)). Its output's `covered_by` names each component's newest release, the one that covered the work, and the agent records it in the instance's Notes in place of the versions it would have published. Nothing holds a second publish back while an instance runs: the step tells the two apart instead.

After each acceptance, its own or one `wait_for_events` reports as a story moved to done, it calls `release_evaluate` (`flai release --evaluate`, [project-manifest.md](project-manifest.md)) and decides by the policy:

| Policy | It publishes when | Its reason |
|--------|-------------------|------------|
| `threshold` | The evaluation is met: the unreleased stories' summed cost of delay is at or over `value`, or their count at or over `count` | The figure that was met |
| `theme` | The evaluation is met: every story of the epic or tag is accepted, and one at least is not yet released | The figure that was met |
| `judgement` | It judges the unreleased work coherent and complete | Its reasoning, which the tool requires, or, with a `publish` formula, the formula's `judgement` input, which step 2 passes as `--judged` |

Under every policy, with `orchestration.release.whole_epics` set, a batch with a story whose epic is in neither review nor done is not published: the evaluation names those stories in `held_by_epic`, and is not met while one is there. Each release publishes everything accepted and not yet released, as `flai release --pending` does.

`release_publish` (`internal/mcpserver/orchestrate.go`) takes `reason`, one sentence; under `threshold` or `theme`, the evaluation's reason when it is left out. It weighs the batch as `release_evaluate` does, and refuses, changing nothing, saying why and what would allow it (`mayPublish`):

- nothing is accepted and not yet released;
- `whole_epics` holds the batch back, naming each story held, its epic, and the epic's status, or `not found`;
- under `threshold` or `theme`, the policy is not met, with the evaluation's reason;
- under `judgement`, no reason is given;
- the `push` host action is off, which `publish.run` needs too, naming `flai serve enable push`;
- the caller is not the orchestrator, or `publish` is off (`Repo.OrchestratorPermits`), as well as the guard's refusal.

Otherwise it runs what the dashboard's `publish.run` runs, `flai release --pending`, never forced, through `hostapi.Publisher`, which `flai mcp` and `flai mcp http` fill (`app.mcpPublisher`). A refusal of `flai release --pending` with exit 3, for release tags on the remote newer than this clone's (S-0174) or a remote branch that moved, is returned as flai's message unchanged, beginning `conflict:`. A push that fails after the release is tagged here is returned as a refusal too, saying that the operator puts it right and publishes again. On success it returns `policy`, `reason`, `evaluation`, `versions` (each component's level, `from`, `to`, and items), `tags`, `items` (each ID once), `pushed`, `published`, and `warnings`.

What is recorded:

| What | Where |
|------|-------|
| The run | `serve/journal.jsonl`, as `publish.run`'s are: action `push`, method `mcp.release_publish`, `by` the orchestrator, and `<policy>: <reason>` before the outcome in its detail, so a release the orchestrator cut is told apart from the operator's. A run refused for the `push` action is journalled as `disabled` |
| Each release | `activity_log`: the policy, its figures, the versions and tags, and the items bundled, as `release_publish` returned them |
| Each decision not to publish | `activity_log`, with the evaluation's figures |
| Each refusal | `activity_log`, with the refusal; and a thread to the operator with `thread_open` on the most recently accepted story of the batch, with the refusal's words and what fixes it |

After a refusal it does not try again until that thread is answered or the next acceptance, and it never works around the refusal: the guard refuses it every other way to the remote ([Its permissions and the guard](#its-permissions-and-the-guard)).

### Its permissions and the guard

`orchestration.permissions` in `system-flow.yaml` says what the orchestrator may do without the operator. Each is off when unset. `flai check` reports an unknown key or a bad value as `manifest.orchestration`, so that a misspelt permission is not silently off ([project-manifest.md](project-manifest.md)).

`flai guard` reads `FLAI_ROLE` from the hook's environment. With `orchestrate`, it reads the permissions from the manifest of the project the hook runs in, at each call, and checks the session's own calls, which carry no agent ID, against the orchestrator's role file, `design/workflows/roles/orchestrator.md`, or flai's baseline copy when the project has none: each call it lists under a `permissions` entry passes while that permission is on ([Role files](#role-files-s-0414)). `Guard.orchestrate` words the refusal and names the permission it needs. The table below is what the baseline file lists. A manifest it cannot read leaves every permission off, with a warning. The orchestrator's sub-agents are held as every sub-agent is.

The permissions may change while the orchestrator runs: the operator edits them on the Orchestrator page's settings panel, with `flai manifest set`, or by hand (S-0229, [ADR-0101](../adrs/0101-with-the-settings-host-action-on-the-dashboard-edits-the-strategic-agents.md)). A change does not restart it. Because the guard reads the manifest at each call, a permission turned on or off holds from the orchestrator's next call, whatever the orchestrator last read; `cmd/guard_permissions_change_test.go` turns one on and off between two calls of one session. Its prompt tells it to read its permissions, policy, and release policy again before each decision, and that the guard's verdict holds, as its section What it is told says above.

| Permission | Allows |
|------------|--------|
| none needed | The reads a sub-agent has, S-0217's and S-0219's evaluations among them (`order_by_policy`, `promote_candidates`, `release_evaluate`, `flai plan --candidates`, `flai promote --candidates` and `--drafts`, `flai order --by` without `--apply`, `flai release --evaluate`, since S-0403 `flai queue`, and since S-0491 `subprojects`, `flai subproject list`, and `flai subproject`); `inbox`, `activity_log`, `wait_for_events`, `thread_open`, and, since S-0556, `verify`; `thread new`, and `issue new` and `bump`; git's reads |

A call a permission would allow is refused while that permission is off, and the refusal names it: `the orchestrator cannot <call>: it needs orchestration.permissions.<name>, which is off`. Every other write is refused whatever the permissions, saying that the orchestrator never does it, and why: `Edit`, `Write`, and `NotebookEdit`; every other flai MCP tool, `item_new` among them; `item_edit` that changes anything but the draft flag or, under `plan_backlog_stories` or `set_cost_of_delay`, a story's cost of delay inputs, or under `set_cost_of_delay` an epic's; `plan` on anything but an epic or a story; `item_move` to any state but `ready`; `flai move` to any state but `ready`, and `done` but under `accept_reviews` with `--by orchestrator`; `flai edit` that changes anything but the draft flag or, under `plan_backlog_stories` or `set_cost_of_delay`, a story's cost of delay inputs, or under `set_cost_of_delay` an epic's; `flai order` that places a story by hand, which is the operator's (S-0219); `flai release` other than `--evaluate`, `flai push`, `git push`, and `git tag`, since it publishes through the `publish` formula or, with none, `release_publish` alone (S-0222, S-0423); every other flai command that writes; and git's other writes. Each refusal ends by telling it to ask the operator with `thread_open` on the item. The guard refuses `release_publish` to every session but the orchestrator's, its sub-agents included. Other shell commands pass, as a sub-agent's do (ADR-0060).

Thread calls are held by who opened the thread as well (S-0220). On a thread it opened, the orchestrator follows up and resolves whatever its permissions, but never recommends or answers its own question. On another's, it replies only as `answer_threads` allows, and never resolves it, save a thread a story's planner opened while `plan_backlog_stories` is on, which it may answer and resolve. It never confirms a recommendation, which is the operator's alone, and never writes as another (`--by`). The confirmation by timeout is `flai serve`'s, not the orchestrator's: the guard still refuses the orchestrator `flai thread confirm`. It lets `operator_only` and `--operator-only` through with a recommendation wherever it lets the recommendation through. The guard reads who opened a thread from the thread itself, and takes a thread it cannot read as another's ([Answering threads](#answering-threads-s-0220)). The MCP tool `plan` and `flai plan`, asked by the orchestrator, are also checked in flai (`orchestratorPlans`): the item must be an epic `flai plan --candidates` lists, with `plan_backlog_epics` on, or a story it lists, with `plan_backlog_stories` on ([What it does with each permission](#what-it-does-with-each-permission-s-0219)). The orchestrator is journalled as who asked. The `plan` host action must be on as well, since the planner is started as `serve.Plan` starts any. Every other agent `flai serve` started is still refused the tool.

Each refusal of the orchestrator's own call is appended to `wip/agents/orchestrator.md` under `## Refusals`, after `## Log`, by `Repo.AppendRefusal`: a heading with the time to the second, `- Call:` with the call refused in one code span, and `- Needs:` with the permission, or `none`. A refusal has no seconds or cost and adds nothing to the document's totals. A refusal that cannot be logged is warned of and refused all the same. Each writer of an activity document takes a lock per activity kind in `.flai-cache`, so that flai serve logging a run and the guard logging a refusal at the same time do not lose each other's entry. The lock is an operating-system lock on the file, freed when the writer exits, so no lock is left behind and none is broken for its age (I-0140).

The guard judges each command of the orchestrator's shell calls by its arguments, its redirections and their targets left out, as it does every role's ([Role files](#role-files-s-0414); S-0613). So `flai order --by throughput --apply 2>&1` passes under `order_ready` as the line without the redirection does, and `flai board --json 2>/dev/null` passes as a read. I-0230 counted 41 such calls refused in two weeks. `flai serve status` passes too, with or without a redirection: since S-0680 the guard counts the read forms of `flai serve` that [ADR-0220](../adrs/0220-flai-guard-refuses-every-sub-agent-and-every-session-flai-serve-started-the.md) leaves open among the reads of every agent it holds to them, the orchestrator, the planner, the analyzer, the curator, a defined role, and a sub-agent alike (I-0318). `flai serve` alone, `start`, `stop`, `agent start`, `restart`, `stop`, `commit`, and `stream`, `orchestrate`, `project`, `usage`, and `settings` stay refused, as does every form that writes the host configuration.

`.claude/settings.json` runs the guard on `Edit|MultiEdit|Write|NotebookEdit` whenever `FLAI_ROLE` is set, `orchestrate` among them ([The guard](#the-guard)).

### The run and how it ends

The run is recorded in `serve/agents.json` under `orchestrator`, the project's newest run alone, with the fields a story's run has and neither `story` nor `item`. `Running` and `Last` never name it, and the in-progress limit does not count it. Its output is in `serve/agents/<key>-orchestrator-<start>.log`, beside the other agents' logs, each run with a log of its own.

When the process ends, or the next look finds it gone, flai serve settles the run (`orchestrateEnded`):

| Outcome | When |
|---------|------|
| `stopped` | the `orchestrate` action was turned off and flai serve stopped it, or the operator stopped it |
| `stopped` | it ran past `orchestration.run_timeout` and flai serve stopped it; `why` is `stopped: ran past orchestration.run_timeout (<timeout>)` ([ADR-0209](../adrs/0209-the-orchestrator-runs-for-a-reason-and-ends-started-by-flai-serve-on-the-events.md) §4, `orchestrate_timeout.go`) |
| `failed` | its log ends on the harness's usage limit (`runLimit`), whether its exit was seen or not; `why` names the limit and its reset time, and `usage_limited` is set (S-0534) |
| `failed` | it exited with a code other than 0, or could not be started |
| `worked` | otherwise, an exit nobody saw included |

It then logs the run's activity since the last entry in `wip/agents/orchestrator.md` with `serve.LogRunEnd`: the run's final reply as the summary, or `stopped: orchestrate turned off`, or `stopped: stopped from the dashboard` when the operator stopped it, or the run timeout's why, and the seconds and cost measured from the log. Each decision the orchestrator logs with `activity_log` during the run covers its own span, so the end logs only what came after the last one.

A run stopped for `orchestration.run_timeout` is journalled and logged by `flai serve` as it stops it. It is no failure: `orchestrateRetry` does not hold the next start, and the reasons queued while it went start the next run once their coalescing window has passed.

A run on the usage limit is not started again after the minute: its end sets or extends its provider's budget state, and the first look once the state no longer holds starts the next run ([ADR-0209](../adrs/0209-the-orchestrator-runs-for-a-reason-and-ends-started-by-flai-serve-on-the-events.md) §5, [flai-cli.md](flai-cli.md#the-hosts-budget-state)).

Since S-0532 ([ADR-0209](../adrs/0209-the-orchestrator-runs-for-a-reason-and-ends-started-by-flai-serve-on-the-events.md) §6) each run's start and end is an `agent` event with `id` and `title` `orchestrator`, `type` `role`, and `fields.role` `orchestrate`: `started`, each retry too, with a `why` that names its reasons and how the last run ended, when it was held or failed, then `ended`, `failed` with its exit, or `stopped` when the operator stopped it, turned `orchestrate` off, or it ran past `orchestration.run_timeout`. The analyzer and the operator see it in `inbox` and `wait_for_events`; the orchestrator is not told of its own runs ([flai-cli.md](flai-cli.md#the-events-wait_for_events-and-inbox-report)).

### What it costs on the items (S-0226)

Each orchestrator activity is charged to the work items its entry names, when it is logged, through `activity_log`, through `thread_reply`'s own entry, or as the run ends ([ADR-0095](../adrs/0095-an-orchestrator-activity-s-usage-is-charged-evenly-to-the-work-items-it-named.md)). The usage apportioned to its span, the same share its entry's cost is, as for the planner ([The run and how it ended](#the-run-and-how-it-ended)), is split evenly between the epics, stories, and tasks it names that exist, archived ones included, each once; a thread, an issue, or anything else named takes no share. Tokens and seconds are split in whole numbers, the remainder to the first items named, and cost by the count, so that the shares add up to the entry. Each share goes under the `orchestrator` entry of `usage.strategic` on its item and on every item above it, up to its epic, at once ([work-hierarchy.md](work-hierarchy.md)). A charge that fails leaves the entry logged and is warned of.

These are the rule `named`, the orchestrator's `charge`, and any role whose file names it is charged the same way under its own name (S-0425, [ADR-0249](../adrs/0249-strategic-usage-is-per-role-a-role-s-activity-is-charged-by-its-role-file-s.md)).

An activity that names no work item charges no item: its cost is the orchestrator's project strategic total. That total, for every role, is what the kind's activity document accrued that no item or issue carries: its `accrued_cost` and `accrued_seconds` less that kind's `strategic` figures on the items with no parent, which carry every charge made below them, and on the issues no story was made from. It is worked out by `flai stats`, which reports it per role beside what the items and the issues carry ([metrics.md](metrics.md#strategic-agents-s-0206)), not written anywhere, so that the three always add up to the document. It also holds the planner's activities with no planned item, those logged before S-0225, the analyzer's that named no issue ([What the analyzer's run costs](#what-the-analyzers-run-costs-s-0227)), and every activity of a role whose rule is `none`, such as the curator's ([What the curator's run costs](#what-the-curators-run-costs)).

Every start, end, failure, and stop is a journal entry with action `orchestrate` and method `serve.orchestrate`; a start's entry names its reasons, the count and the first five. `agent.status` carries the run as `orchestrator`, null before the first, with `held` while the operator holds it, and up to 20 earlier runs as `past_orchestrators`; `agent.stream` with `role: orchestrate`, or `orchestrator: true` as before S-0228, reads its log as it reads a story's agent's (`RoleStream`). When the run starts, cannot start, or ends, `flai serve` tells the dashboard with an `agent` notification that carries the project and `role: orchestrate`; a hold or a start made in a process of its own is told at the next look.

### On the dashboard

The Activity page lists the orchestrator's run and its stream. The Settings page lists the `orchestrate` action with the others, to turn on and off while `settings` is on. The Orchestrator page (`/workflow/orchestrator`) shows the action's state, on, off, or held; the run under way and its stream; its last decisions with their reasons above its whole activity log; and its runs with their cost and outcome; with **Stop** and **Start** (S-0228). Below them is its settings panel (S-0229): the permissions, each with what it lets the orchestrator do and its risk, `orchestration.policy`, and the `orchestration.release` keys, written through `flai manifest set` while `settings` is on. `orchestration.agent` is not on it and stays a hand edit. See [flaiover-dashboard.md](flaiover-dashboard.md).

## The analyzer

The analyzer looks at the whole project, writes what it finds in one report, and ends (S-0223, [ADR-0099](../adrs/0099-the-analyzer-runs-behind-the-analyze-host-action-and-writes-one-report-under.md)). It reads the metrics, the design, the code, and the issues, and looks for what its focus names: bottlenecks in the flow of work, gaps between `design/system` and the code (`intent`), or technical and security risks (`risk`), or all three when it is given no focus. It writes one report under `design/analysis/` and adds it to the folder's index. It files each actionable finding as an issue with its impact, or bumps the open issue that records it, through flai, and links each issue from its report (S-0224, [How the analyzer files its findings](#how-the-analyzer-files-its-findings-s-0224)). It edits nothing else and authors no stories: the issue step makes draft stories from its issues when the operator chooses it ([continuous-improvement.md](continuous-improvement.md#cadence)).

### Starting an analysis

| Way | For | What it runs |
|-----|-----|--------------|
| `flai analyze [--focus bottlenecks\|intent\|risk] [--json]` | a shell on the host | `serve.Analyze` |
| The host API's `analyze.run` `{focus?}` | a dashboard | `flai analyze [--focus=<focus>] --json`; a focus none of the three is refused before anything runs |
| The MCP tool `analyze` `{focus?}` | the operator's own agent | `serve.Analyze`, as `flai analyze` does; journalled as `mcp.analyze` with the agent that asked |
| A setting the role file's `{schedule}` entries name, `analysis.schedule` in the baseline | `flai serve`, on its own | the launcher's `analyze` with no focus, after the checks `serve.Analyze` makes, or, with `analysis.formula` set, that formula's instance ([The analysis schedule](#the-analysis-schedule)) |
| A formula's role step naming `analyzer` (S-0424) | the agent of the formula's instance | `serve.Analyze` with the instance's `focus`, on the instance ([Working an instance](#working-an-instance-s-0422)) |

Each needs the host action `analyze` on for the project: `flai serve enable analyze`, or the dashboard's Settings page while `settings` is on. It is off by default. A holder of the dashboard token can then start the analyzer whenever none runs. `flai analyze` starts the run itself, as `flai plan` does, and hands the process over: the command does not wait, and the serving flai settles the run. With no `flai serve` running it says so on standard error, and the analyzer still runs. Turning the action off starts no more runs; it does not stop one under way, which ends when the analyzer does.

`serve.Analyze` (`analyzeCheck`) refuses, saying why:

- while the `analyze` action is off for the project;
- a focus that is none of `bottlenecks`, `intent`, and `risk`;
- while an analyzer runs for the project, naming its focus, what started it, its PID, when it started, and its log: one analyzer runs per project at a time;
- when the analyzer's harness is `command` and no command is set for the project, or is one flai cannot start; an agent that names no harness falls back to the host's command, then to flai's built-in `claude-code` ([ADR-0261](../adrs/0261-a-story-or-strategic-agent-that-names-no-harness-falls-back-after-the-project-s.md));
- while the host's budget state holds the agent's provider, after a run on it ended on the usage limit: `held: <provider> usage limit (<limit>) until <until>; flai serve starts it when the limit resets`, with nothing recorded (S-0534, [flai-cli.md](flai-cli.md#the-hosts-budget-state)).

The MCP tool `analyze` also refuses an agent `flai serve` started (`FLAI_STARTED_BY=flai-serve`): an analysis is the operator's to ask for, or the schedule's. `flai guard` refuses the tool and `flai analyze` to a sub-agent, the planner, the orchestrator, and the analyzer.

### The analyzer's agent

`analysis.agent` in `system-flow.yaml`, merged over the project's `agent` as `planning.agent` is (`Manifest.AnalysisAgent`), gives the analyzer's harness, model, config, and roles. With neither set, the host's command starts it. `flai check` reports an `analysis.agent` or an `analysis.schedule` that is not valid as `manifest.analysis`. See [project-manifest.md](project-manifest.md). Its harness may be `container`: [In a container](#in-a-container-s-0509) says what the container mounts.

### How the analyzer runs

The launcher's `analyze` starts it through the harness adapter with a `harness.Request` whose `Role` is `analyze` and whose `Focus` is the focus, or empty for all three, with no `Item` and no `Story`.

- **Where.** In the project's main checkout. No branch, no worktree.
- **As whom.** `FLAI_AGENT` is `analyzer`. The environment carries `FLAI_ROLE=analyze`, `FLAI_SESSION`, and `FLAI_STARTED_BY=flai-serve`, and no `FLAI_ITEM` or `FLAI_STORY`. `roleEnv` refuses an analyzer request that names a story or an item, or a focus none of the three, and a focus given to any other agent. `flai serve` drops `FLAI_FOCUS` from its own environment, with `FLAI_STORY`, `FLAI_ROLE`, and `FLAI_ITEM`, before it adds a run's (`runMarks`).
- **claude-code.** The session is named `<key> analyze`, with the focus after it when there is one, such as `sf analyze risk`. It runs with `--agent analyzer` over the definition flai generates from its role file, `design/workflows/roles/analyzer.md`, the project's or flai's baseline, with the project's additions below the marker, but for its `### Start prompt` section, in its prompt and the analyzer's agent's model when it names one. It is passed in `--agents` beside the sub-agents whose roles the agent gives a model, and nothing under `.claude/` is read for it. `startOf`, the start every run goes through, gives it the file ([Role files](#role-files-s-0414)). Its permission handler is flai's `permission_prompt`, as for every session `flai serve` starts.
- **The operator's command.** It gets `FLAI_ROLE`, and `FLAI_FOCUS` when the run has a focus, since a command has no prompt to be told it in. `{story}` is empty.

### What the analyzer is told

`harness.Prompt` gives the analyzer the start prompt of its role file, `analyzer.md`'s `start` rendered over the run's fields, `.Focus` among them, with the project's `### Start prompt` additions ([Its start prompt](#role-files-s-0414)). The baseline's says: analyze the project and do nothing else, as the convention's section "As the analyzer" says; prime with `--role analyze`; call `inbox`. Look for the findings its focus names and nothing else, or for all three kinds with none:

| Focus | It looks for |
|-------|--------------|
| `bottlenecks` | Bottlenecks in the flow of work, from the cumulative flow, the time items spend in each state, the time they wait, and the holds on them |
| `intent` | Gaps between what `design/system` says and what the code does: a design section the code does not meet, and code the design does not describe |
| `risk` | Technical and security risks in the code and in how it is built, tested, and released |
| none, recorded as `all` | All three |

Read the metrics with `flai stats --json` and take every figure from it. Read the design with `doc_search` and `doc_get`, and the section a finding rests on before relying on it. Read the issues under `design/issues`, `summary.md` first. Hand wide search of the code to the explorer. Write one report, `design/analysis/<date>-<focus>.md` ([The report and its index](#the-report-and-its-index)), and add it to `design/analysis/README.md`. File each actionable finding as an issue, or bump the open issue that records it, and link each issue from its finding ([How the analyzer files its findings](#how-the-analyzer-files-its-findings-s-0224)); never run `flai issue story` or `flai issue close`. Edit nothing else, no code, design, issue, or work item, since flai writes the issues it files, author no stories, and never work around a refusal. When an input the operator owns is missing, ask with `thread_open` on the report, the recommended answer first, analyze what needs no answer meanwhile, and hold `wait_for_events` until it is answered. End with a one-line summary that names the report, which becomes the run's activity entry.

`analyzer.md`, which the template ships, says the same in short, and since S-0419 its prompt is the body of `design/workflows/roles/analyzer.md` with the project's additions ([Role files](#role-files-s-0414)). It lists its tools: `Read`, `Grep`, `Glob`, `Edit`, `Write`, `Bash`, `Agent`, and flai's MCP tools `prime`, `inbox`, `board`, `item_get`, `doc_get`, `doc_search`, `thread_get`, `who_touches`, `activity_log`, `thread_open`, `thread_reply`, `wait_for_events`, `issue_new`, and `issue_bump`. It lists no `NotebookEdit` and no tool that writes a work item, `issue_story` among them.

### The report and its index

A report is `<date>-<focus>.md` in the design folder's `analysis/` (`analysis.Dir`, `analysis.ReportPath`): the date is the run's UTC day as `YYYY-MM-DD`, and the focus one of the three or `all`. Two runs on one day with one focus name the same file.

| Front matter | What it holds |
|--------------|---------------|
| `title` | The report's title |
| `updated` | A date, `YYYY-MM-DD`, or a timestamp, `YYYY-MM-DDTHH:MM:SSZ` |
| `status` | The documentation standard's: `draft` while the analyzer writes it, `active` once the run has ended, `deprecated` when a later report replaces it |
| `focus` | The focus the file is named for |
| `from`, `to` | The window its metrics cover, as dates, `from` not after `to` |

The body has one section per finding: its evidence (the metric figures as flai gave them, the file paths, and the design sections quoted), its severity, and its estimated impact, the time it loses per cycle, or the revenue or penalty it puts at stake where the design states them. An actionable finding links the issue filed or bumped for it, as `[I-nnnn](../issues/<file>)`.

`design/analysis/README.md`, which the template ships, says what the folder is for and has a row per report: its link, focus, window, and status. Only the analyzer writes in the folder. `flai check` leaves the folder out of the design documents' own rules and checks it by its own (`checker.analysis`):

| Finding | Level | When |
|---------|-------|------|
| `analysis.report` | error | A report not named `<date>-<focus>.md` with a real date and a known focus; with no front matter, or front matter that does not parse; missing a field; with an `updated` that is neither a date nor a timestamp, a `status` none of the three, a `focus` none of the four or not the one the file is named for, a `from` or `to` that is not a date, or a window that ends before it starts. Each is reported on its field's line |
| `analysis.index` | warning | A report the README does not link, and a row of the README that links a report not there |

A project with no `design/analysis/` has nothing checked there. flai checks a report's status but does not change it: the analyzer writes it, `draft` while it writes the report and `active` once it is done, as its prompt and its definition tell it.

### How the analyzer files its findings (S-0224)

Each actionable finding becomes an issue in `design/issues/` with its impact, so that the issue step can turn it into a draft story with its cost of delay in place ([continuous-improvement.md](continuous-improvement.md)). The analyzer's start prompt and the body of `analyzer.md` tell it, for each one:

1. List the open issues, with `flai issue list --json` or from `design/issues/summary.md`.
2. When an open issue already records the finding, under whatever title, bump it: `flai issue bump <id> --report <its report>` with the finding's impact, or the MCP tool `issue_bump`.
3. Otherwise file one: `flai issue new "<title>" --class <class> --report <its report> --json`, or the MCP tool `issue_new`. The class comes from the finding: `defect`, `efficiency`, or `impression` for a risk with no measured instance. The impact is the figures the report gives the finding, as `--time-lost-per-cycle` (a duration such as `4h`), or `--revenue-per-week` or `--penalty-per-week` (an amount in `planning.currency`), and `--evidence`, the evidence behind them.
4. Link the issue from its finding in the report, as `[I-nnnn](../issues/<file>)`, the file name of the `path` flai returns.

`--report` deduplicates by title as well. An open issue of exactly the title given is bumped rather than a second opened, and one an instance of which already names the report is left as it is, so that filing a report's findings again counts nothing twice; `outcome` says `opened`, `bumped`, or `already recorded`. Either way the issue's instance names the report in a `Report:` line, and its `## Remediation` links it, once. A report path that is not a markdown file under `design/analysis/`, or a figure that does not parse, is refused and nothing is written. The analyzer runs in the main checkout as `analyzer`, with no `FLAI_STORY` and no story branch, so its instances name no story and its issues are written in the main checkout beside its report; `summary.md` is regenerated and nothing is committed.

The analyzer writes its issues through flai alone, never by editing a file under `design/issues/`, and authors no stories: it never runs `flai issue story`, which is the operator's choice at acceptance or an agent's when the operator asks, nor `flai issue close`.

### The analyzer's guard

`flai guard` reads `FLAI_ROLE` from the hook's environment. With `analyze`, the command opens the project from the working directory and sets the guard's `Root` and `Reports`, the reports folder, and checks the session's own calls, which carry no agent ID, against the analyzer's role file, `design/workflows/roles/analyzer.md`, or flai's baseline copy when the project has none ([Role files](#role-files-s-0414)); `Guard.analyze` words the refusal. The baseline file lists these, its `files` entry being `{design}/analysis/`:

| Kind | Passes | Refused |
|------|--------|---------|
| File tools | `Edit`, `Write`, and `NotebookEdit` on a file inside the reports folder: its report and the folder's README | the same on any other file, a file under `design/issues/` among them, and on every file when the project cannot be read |
| flai MCP tools | the reads a sub-agent has; `inbox`, `activity_log`, `thread_open`, `thread_reply`, and `wait_for_events`, and since S-0224 `issue_new` and `issue_bump` (`guard.MCPAnalyzes`) | `item_new`, `item_edit`, `item_move`, and `issue_story`, since the analyzer authors no stories; every other tool, `plan`, `analyze`, and `release_publish` among them |
| flai commands | the reads, `flai stats` and `issue list` among them; since S-0224 `issue new` and `bump` (`cliAnalyzes`) | `story`, `epic`, `task`, `issue story`, and since S-0421 `formula run`, which makes a story and its tasks (`cliAuthors`), since the analyzer authors no stories; every other command that writes, `issue close`, `plan`, and `analyze` among them |
| git | the reads a sub-agent has | every other git command |

A file's path is taken from the project's root when it is relative, cleaned, and resolved along the part of it that exists, symbolic links followed, as the folder's is (`inReports`), so that neither `..` nor a link leads out of the folder. A refused edit names the folder. Each refusal says that the analyzer files or bumps an issue for each actionable finding with `flai issue new` and `bump` and edits nothing but its report and the index, and to put what it found, and the stories it would suggest, in its report, or ask the operator with `thread_open`. Other shell commands pass, as a sub-agent's do (ADR-0060), so a file written through the shell is not seen. The analyzer's sub-agents, the explorer among them, are held as every sub-agent is.

The analyzer writes as itself alone, as the planner does ([The guard](#the-guard), [ADR-0143](../adrs/0143-flai-guard-refuses-a-story-s-agent-the-planner-and-the-analyzer-a-call-that.md)): a `--by` or `--placed-by` naming another, an assignment of `FLAI_AGENT` or `FLAI_SESSION` other than its own, and `unset` of either are refused. Its own name is the hook's `FLAI_AGENT`, or `analyzer`.

`.claude/settings.json` runs the guard on `Edit|MultiEdit|Write|NotebookEdit` whenever `FLAI_ROLE` is set, `analyze` among them ([The guard](#the-guard)). A project that keeps its old settings has an analyzer whose file edits the guard does not see.

### The analysis schedule

`analysis.schedule` in `system-flow.yaml` is a five-field cron expression in UTC, or `daily`, read as `planning.schedule` is ([The schedule](#the-schedule)); unset, there is none. An analysis scheduler per served project (`internal/serve/analysis_schedule.go`) looks whenever the project's launcher does: when its work items or threads change, when an agent ends, and every minute, so it sees the schedule come round at most a minute late. At each look it reads the analyzer's role file, the project's or the baseline flai carries, and follows each setting the file's `{schedule}` entries name, each with a cadence of its own: `analysis.schedule`, in the baseline's `{schedule: analysis.schedule}` (S-0554, [Its triggers](#role-files-s-0414)). A file without a schedule entry starts no analysis on any schedule, though the operator's word still does. A file that cannot be read is warned of once and starts nothing. Each time a setting comes round with the `analyze` action on, it starts the analyzer with no focus and the trigger `schedule <spec>`, the schedule as written, such as `schedule daily`, after the checks `serve.Analyze` makes. Settings that come round at one look start one run, with the first's trigger in the file's order. A start they refuse, such as while an analyzer runs, is logged at info as `scheduled analyzer not started` with the reason, and is not tried again until the schedule next comes round. A start the host's budget state holds is not lost: the run stays due, each look tries it again until it starts, and the hold is logged once per state (S-0534, [flai-cli.md](flai-cli.md#the-hosts-budget-state)).

Times missed between two looks come round once. A schedule set or changed comes round first at its next time from then. What the scheduler has seen is kept in memory: a time that passed while `flai serve` was down does not come round. While `analyze` is off it starts nothing and keeps up with the schedule, so turning the action on does not act on the past. A schedule that is not valid is warned of once in flai serve's log, and nothing is started for it until it is fixed. The scheduler follows its schedule as the replanner follows `planning.schedule` (`cadence`).

**A formula in its place (S-0424).** `analysis.formula` names a formula ([project-manifest.md](project-manifest.md)). When it is set, each time the schedule comes round with the `analyze` action on, the scheduler makes that formula's instance in place of starting the analyzer: `flai formula run <name> --ready --autocommit --json` in the main checkout, with no inputs, so each takes its default. It is journalled under the `formula` action, as the formula scheduler's instances are, with the trigger `analysis.schedule <spec>`. A run `flai formula run` refuses is logged and not tried again until the schedule next comes round. The template ships `analysis-cadence` for it. Its first step, `role: analyzer`, starts the analyzer with the instance's `focus`, empty for all three, through the checks `serve.Analyze` makes ([Working an instance](#working-an-instance-s-0422)). Its second, `flai issue list --report latest --json`, `in: main`, lists the open issues the newest report names, for the operator to choose stories from at acceptance ([continuous-improvement.md](continuous-improvement.md#cadence)). `flai check` reports as `manifest.analysis` a name not in kebab-case, a formula no file defines, and one with an input that has no default. `flai manifest set` and the Analyzer page's settings panel write it, and refuse, writing nothing, what that check reports (S-0692).

### The analyzer's run and how it ended

The run is recorded in `serve/agents.json` under `analyzer`, the project's newest run alone, with the fields a story's run has, neither `story` nor `item`, and `focus` (one of the three, or `all`), `trigger` (`asked`, or the schedule's), and, once it has ended, `report`. `Running` and `Last` never name it, and the in-progress limit does not count it. Its output is in `serve/agents/<key>-analyzer-<start>.log`, beside the other agents' logs.

When the process ends, or the next look finds it gone, flai serve settles the run (`analyzeEnded`). Its report is the Markdown file directly in the reports folder, the README aside, changed last, and changed no earlier than the second the run started (`newestReport`); there is none when no such file changed.

| Outcome | When |
|---------|------|
| `failed` | its log ends on the harness's usage limit (`runLimit`), whether its exit was seen or not; `why` names the limit and its reset time, and `usage_limited` is set (S-0534) |
| `failed` | it exited with a code other than 0, or could not be started; or it ended without writing a report, which `why` says, naming the folder |
| `worked` | otherwise: it wrote a report, whether its exit was seen or not |

A run on the usage limit is not started again: the operator asks again, or the schedule comes round, once its provider's budget state clears ([flai-cli.md](flai-cli.md#the-hosts-budget-state)).

It then logs the run's activity in `wip/agents/analyzer.md` with `logRunEndSaying`: the time since the last entry, the seconds and cost measured from the log, and the run's trigger as the entry's `- Trigger:` line. The summary is the first line of the run's final reply, the one-line summary its prompt asks for: as it is when it names the report, with `(report <path>)` added when it does not, and with `(no report written under design/analysis)` added when there is no report. The entry's items are the issues that name the report, open or closed, in ID order (`issues.NamingReport`): those an instance names with its `Report:` line, and those whose `## Remediation` links the report. When there is no report, or the issues cannot be read, which is warned of, the entry names none.

Every start and failure to start is a journal entry with action `analyze` and method `serve.analyze`; `analyze.run` and the MCP tool `analyze` are journalled as well, under the same action. `agent.status` carries the run as `analyzer`, null before the first. When the run starts, cannot start, or ends, `flai serve` tells the dashboard with an `agent` notification that carries the project and `role: analyze`. Since S-0532 ([ADR-0209](../adrs/0209-the-orchestrator-runs-for-a-reason-and-ends-started-by-flai-serve-on-the-events.md) §6) it also logs an `agent` event with `id` and `title` `analyzer`, `type` `role`, and `fields.role` `analyze`: `started` with its trigger and focus as `why`, then `ended`, or `failed` with its `why` and exit. The orchestrator and the operator see it in `inbox` and `wait_for_events`; the analyzer is not told of its own runs ([flai-cli.md](flai-cli.md#the-events-wait_for_events-and-inbox-report)).

### What the analyzer's run costs (S-0227)

An analyzer activity is charged to the issues its entry names ([ADR-0100](../adrs/0100-an-analyzer-activity-s-usage-is-charged-evenly-to-the-issues-it-names-under.md)), as an orchestrator's is to the work items its entry names ([What it costs on the items](#what-it-costs-on-the-items-s-0226)): when its run ends, to the issues that name the report it wrote; through `activity_log`, to the issues the call named. The usage apportioned to its span is split evenly between the issues named that exist, each once, the remainder of tokens and seconds to the first, and each share goes under the `analyzer` entry of the issue's own `usage.strategic`. A work item, a thread, or anything else named takes no share. An activity that names no issue charges nothing: its cost stays in the analyzer's project strategic total. A charge that fails leaves the entry logged and is warned of. This is the rule `issues`, the analyzer's `charge`; a role whose file names it is charged the same way under its own name (S-0425, [ADR-0249](../adrs/0249-strategic-usage-is-per-role-a-role-s-activity-is-charged-by-its-role-file-s.md)).

When the issue step makes a story from an issue, the story carries the issue's strategic usage, summed up to its epic. `flai stats` counts each charge once: on the issue until a story is made from it, then on the story ([metrics.md](metrics.md#strategic-usage)).

### The analyzer on the dashboard

The documents page lists the reports under `design/analysis/` beside the folder's README and shows each as it shows any design document ([flaiover-dashboard.md](flaiover-dashboard.md)). The Settings page lists the `analyze` action with the others, to turn on and off while `settings` is on. The Analyzer page (`/workflow/analyzer`) shows the action's state; the run under way with its focus and its stream, which `agent.stream` reads with `role: analyze`; its activity log, each entry linking the report it wrote; and its runs, the newest and up to 20 before it (`past_analyzers`), with their focus, report, cost, and outcome. **Run** with a focus, or with none for all three, is `analyze.run` (S-0228). Below them is its settings panel (S-0229), `analysis.agent` and `analysis.schedule`, written through `flai manifest set` while `settings` is on.

## The curator

The curator keeps the digest: it takes in what the archive and the threads gained since its last run as digest entries, and ends (S-0431, [ADR-0196](../adrs/0196-the-curator-runs-behind-the-curate-host-action-and-takes-in-what-the-archive.md)). The digest is one fact per file under `design/digest/` ([ADR-0191](../adrs/0191-the-digest-is-one-markdown-file-per-entry-under-the-design-folder-s-digest.md)), and a story's pack loads the entries its topics or claim select ([agent-context.md](agent-context.md)). `flai digest seed` writes an entry for each raw candidate. The curator judges instead: it writes an entry for a fact the digest lacks, merges a candidate into the entry that holds its fact, and records a thread that asked again what an entry answered. An operator's answer on a thread is an entry already, written as it is given ([Answers written at once](#answers-written-at-once-s-0433)). In every run it also marks absorbed the entries a design document now records, and compacts the active entries no work item, narrative, or thread cited within `digest.compact_after` (S-0432, [ADR-0199](../adrs/0199-the-curator-runs-after-acceptances-coalesced-and-on-digest-schedule-marks.md), [Absorption and compaction](#absorption-and-compaction)). It writes through `flai digest new`, `edit`, `absorb`, `cited`, and `compact` alone, edits no file, and authors no work items. Nothing in the digest is deleted.

### Starting a curation

| Way | For | What it runs |
|-----|-----|--------------|
| `flai curate [--since <day or time>] [--json]` | a shell on the host | `serve.Curate` |
| The host API's `curate.run` `{since?}` | a dashboard | `flai curate [--since=<since>] --json`; a since in neither form is refused before anything runs |
| The MCP tool `curate` `{since?}` | the operator's own agent | `serve.Curate`, as `flai curate` does; journalled as `mcp.curate` with the agent that asked |
| A story accepted, under the role file's `{event: accepted}` | `flai serve`, on its own | the launcher's `curate` with no since, after the checks `serve.Curate` makes ([The curator after acceptances and on a schedule](#the-curator-after-acceptances-and-on-a-schedule)) |
| A setting the role file's `{schedule}` entries name, `digest.schedule` in the baseline | `flai serve`, on its own | the same |

A since is a `YYYY-MM-DD` day in UTC or an RFC 3339 time. Each way needs the host action `curate` on for the project: `flai serve enable curate`, or the dashboard's Settings page while `settings` is on. It is off by default. A holder of the dashboard token can then start the curator whenever none runs. `flai curate` starts the run itself, as `flai analyze` does, and hands the process over: the command does not wait, and the serving flai settles the run. With no `flai serve` running it says so on standard error, and the curator still runs.

`serve.Curate` (`curateCheck`) refuses, saying why:

- while the `curate` action is off for the project;
- a since that is neither a `YYYY-MM-DD` day nor an RFC 3339 time;
- while a curator runs for the project, naming its since, what started it, its PID, when it started, and its log: one curator runs per project at a time;
- when the curator's harness is `command` and no command is set for the project, or is one flai cannot start; an agent that names no harness falls back to the host's command, then to flai's built-in `claude-code` ([ADR-0261](../adrs/0261-a-story-or-strategic-agent-that-names-no-harness-falls-back-after-the-project-s.md));
- while the host's budget state holds the agent's provider, after a run on it ended on the usage limit: `held: <provider> usage limit (<limit>) until <until>; flai serve starts it when the limit resets`, with nothing recorded (S-0534, [flai-cli.md](flai-cli.md#the-hosts-budget-state)).

The MCP tool `curate` also refuses an agent `flai serve` started (`FLAI_STARTED_BY=flai-serve`): a curation is the operator's to ask for, or an acceptance's or the schedule's. `flai guard` refuses the tool and `flai curate` to a sub-agent and to the curator, and the analyzer's guard refuses them as it refuses every tool and command it does not name.

### The curator's agent

`digest.agent` in `system-flow.yaml`, merged over the project's `agent` as `analysis.agent` is (`Manifest.DigestAgent`), gives the curator's harness, model, config, and roles. With neither set, the host's command starts it. `flai check` reports a `digest.agent`, a `digest.schedule`, or a `digest.compact_after` that is not valid as `manifest.digest`. See [project-manifest.md](project-manifest.md). Its harness may be `container`: [In a container](#in-a-container-s-0509) says what the container mounts.

### How the curator runs

The launcher's `curate` starts it through the harness adapter with a `harness.Request` whose `Role` is `curate` and whose `Since` is the run's since, with no `Item` and no `Story`. The since is the one it was started with; else the time of the newest entry in `wip/agents/curator.md`, in UTC (`lastCurated`); else none, on its first run, which takes in everything.

- **Where.** In the project's main checkout. No branch, no worktree. Its entries are left there uncommitted.
- **As whom.** `FLAI_AGENT` is `curator`. The environment carries `FLAI_ROLE=curate`, `FLAI_SESSION`, and `FLAI_STARTED_BY=flai-serve`, and no `FLAI_ITEM` or `FLAI_STORY`. `roleEnv` refuses a curator request that names a story or an item, or a since in neither form, and a since given to any other agent.
- **claude-code.** The session is named `<key> curate`. It runs with `--agent curator` over the definition flai generates from its role file, `design/workflows/roles/curator.md`, the project's or flai's baseline, with the project's additions below the marker, but for its `### Start prompt` section, in its prompt and the curator's agent's model when it names one. It is passed in `--agents`, and nothing under `.claude/` is read for it. `startOf`, the start every run goes through, gives it the file ([Role files](#role-files-s-0414)). Its permission handler is flai's `permission_prompt`, as for every session `flai serve` starts.
- **The operator's command.** It gets `FLAI_ROLE`, and `FLAI_SINCE` when the run has a since, since a command has no prompt to be told it in. `{story}` is empty.

### What the curator is told

`harness.Prompt` gives the curator the start prompt of its role file, `curator.md`'s `start` rendered over the run's fields, `.Since` among them, with the project's `### Start prompt` additions ([Its start prompt](#role-files-s-0414)). The baseline's says: keep the digest and do nothing else, as the convention's section "As the curator" says; prime with `--role curate`; call `inbox`. Its pack's topics are `digest` and `planning`. List the candidates with `flai digest harvest --json --since` the run's since, or with no `--since` on its first run. Read the digest with `flai digest list --json`, and an entry whole with `flai digest show`, before writing.

For each candidate, decide what fact it holds. When no entry holds it, write one with `flai digest new`, with its kind, its sources, the topics and paths it bears on, and a short body that links its sources. When an entry holds it, merge the candidate into that entry with `flai digest edit`. When a thread asked what an entry answered, add it to that entry's `asked_again`. Each list flag of `flai digest edit` replaces its list, so the curator gives the entry's own with what it adds. A body goes on standard input with `--body-file -`, since the curator cannot write a file. Never write a secret's value, only where the operator said it lives: `flai digest` refuses text with the shape of a key or token. Edit nothing else, and never work around a refusal. When an entry needs the operator's judgement, ask with `thread_open` on the item the candidate comes from, the recommended answer first, curate what needs no answer meanwhile, and hold `wait_for_events` until it is answered.

Then, in every run, whatever started it, look for absorption: list the active entries with `flai digest list --status active --json`, search the design with `doc_search` on each one's title, and read what it finds with `doc_get`. Mark an entry absorbed with `flai digest absorb <id> --by <path>`, and `--heading` when one section states it, only when a design document, convention, or ADR states its fact. After the absorptions, run `flai digest compact` once ([Absorption and compaction](#absorption-and-compaction)). End with a one-line summary that names the entries written, merged, absorbed, and compacted, or says that nothing was found to take in. The baseline start prompt's first line says the run may have been started by an acceptance, the schedule, or the operator.

`curator.md`, which the template ships, says the same in short, and since S-0419 its prompt is the body of `design/workflows/roles/curator.md` with the project's additions ([Role files](#role-files-s-0414)). It lists its tools: `Read`, `Grep`, `Glob`, `Bash`, `Agent`, and flai's MCP tools `prime`, `inbox`, `board`, `item_get`, `doc_get`, `doc_search`, `thread_get`, `who_touches`, `activity_log`, `thread_open`, `thread_reply`, and `wait_for_events`. It lists no `Edit`, `Write`, or `NotebookEdit`, and no tool that writes a work item.

### The curator after acceptances and on a schedule

A curate scheduler per served project (`internal/serve/curate_schedule.go`) looks whenever the project's launcher does: when its work items or threads change, when an agent ends, and every minute, as the analysis scheduler does ([The analysis schedule](#the-analysis-schedule)). At each look it reads the curator's role file, the project's or the baseline flai carries, whose entries with no condition say what starts it: `{event: accepted}`, acceptances, and each `{schedule}` entry, its setting, `digest.schedule` in the baseline, followed with a cadence of its own (S-0554, [Its triggers](#role-files-s-0414)). Without `{event: accepted}` an acceptance starts nothing, and without a schedule entry no schedule does. Settings that come round at one look start one run. It starts nothing while the `curate` action is off ([ADR-0199](../adrs/0199-the-curator-runs-after-acceptances-coalesced-and-on-digest-schedule-marks.md)).

| Trigger | When | What starts |
|---------|------|-------------|
| `accepted S-nnnn` | a story is seen moved to `done` | one run; stories accepted at one look start one run, naming them all in ID order |
| `accepted S-nnnn, S-nnnn` | stories were accepted while a curator ran | one run once it ends, at the look its end brings, naming every one, however many |
| `schedule <spec>` | `digest.schedule` comes round, such as `schedule daily` | one run; when acceptances are due at the same look, one run with the acceptances' trigger |
| the retried run's trigger, with the acceptances held meanwhile joined | the first look at or after the `resets_at` of a run that ended on the usage limit | one run, from that run's since, marked `retry` ([The usage limit](#the-usage-limit-s-0514)) |

`digest.schedule` is read as `analysis.schedule` is: a five-field cron expression in UTC, or `daily`; unset, there is none. Each start goes through the checks `serve.Curate` makes, with no since, so it takes in from the curator's last activity. A start they refuse is logged at info as `curator not started on its own`, with the trigger and the reason, and is not tried again: for the schedule, until it next comes round. Times missed between two looks come round once, and a schedule set or changed comes round first at its next time from then. What the scheduler has seen is kept in memory only: acceptances and times that passed while `flai serve` was down do not count. The hold and the retry on the usage limit are the exception: they are read from the curator's run in `serve/agents.json`. A start the host's budget state holds uses nothing up: the acceptances stay queued, the retry stays untried, and a time come round stays due, each tried again at the next look until the state lets the start go (S-0534, [flai-cli.md](flai-cli.md#the-hosts-budget-state)). While `curate` is off it keeps up with the acceptances and the schedule, so turning the action on does not act on the past. A schedule that is not valid is warned of once in flai serve's log.

#### The usage limit (S-0514)

A curator run whose log ends on the harness's usage limit is recorded `failed` with its `resets_at` ([The curator's run and how it ended](#the-curators-run-and-how-it-ended), [ADR-0214](../adrs/0214-a-curator-run-that-ends-on-the-harness-s-usage-limit-is-recorded-failed-with.md)). The scheduler reads that run at each look (`limitResetAt`):

- **Held.** While the curator's last run ended on the limit and its `resets_at` is ahead, the scheduler starts nothing. Acceptances seen meanwhile are held. A schedule time that comes round meanwhile is taken as seen; the retry stands for it.
- **Retried once.** At the first look at or after `resets_at`, it starts that run again, from the run's since, marked `retry: true`. The journal entry's detail adds `started again after the usage limit reset at <time>`. The trigger is the retried one with the held acceptances joined (`retryTrigger`): `accepted S-0498, S-0501` with S-0510 held gives `accepted S-0498, S-0501, S-0510`, in ID order; a `schedule <spec>` trigger gives way to the acceptances' trigger; `asked` is kept, with `; accepted S-nnnn` after it. With none held, the trigger is the retried one.
- **Not retried.** A retry that ends on the limit again, and a run whose limit names no reset time, are raised on a thread instead. After a retry on the limit, the scheduler still holds until its reset; then acceptances held meanwhile start a run as any acceptances do. A retry the checks refuse is logged as any refused start is, and not tried again while that scheduler lives.
- **Across a restart.** The state is the run in `serve/agents.json`. A `flai serve` started during the hold still holds, and retries at its first look after the reset.
- **Behind the action.** While `curate` is off, nothing is retried and no acceptance is held. Turned on again after the reset, the first look retries, since the last run still ended on the limit.
- **Not the operator's.** `flai curate`, `curate.run`, and the MCP tool `curate` do not go through the scheduler and are not held by it; the host's budget state refuses them while it holds the curator's provider. A run they start that ends on the limit is the last run, and the hold and the retry follow from it.

This is the curator's part of [ADR-0209](../adrs/0209-the-orchestrator-runs-for-a-reason-and-ends-started-by-flai-serve-on-the-events.md) §5, built ahead of the host-wide budget state. Since S-0534 that state holds every role's start on the provider too ([flai-cli.md](flai-cli.md#the-hosts-budget-state)). The two stand together: the scheduler waits for the run's `resets_at`, and the budget state for its `until`, so the retry starts at the first look both allow.

### Answers written at once (S-0433)

An operator's answer on a thread does not wait for the curator. Once a thread entry is saved, `digest.OnAnswer` (`internal/digest/onanswer.go`) reads the thread's newest entry. When `digest.Answers`, the rule `flai digest seed` uses, takes it for the operator's answer, it writes the entry there and then, in the main checkout's `design/digest/`, as seed would: the same title, body, and kind, the thread as its source, the topics and paths of the thread's anchored item, dated by the answer. The operator is the manifest's `owner`. An answer is their reply on a thread someone else opened (`answer`), their confirmation of a recommendation (`answer`, holding the recommendation's text), or their reply over a pending recommendation (`recommendation`, naming what it overruled). A recommendation, an agent's reply, a resolution, the operator's reply on their own thread, and a thread `permission_prompt` opened write nothing.

| When | What it does |
|------|--------------|
| An entry citing the thread already holds the answer's time | Nothing, so the next `flai digest seed` writes no duplicate. |
| No entry cites the thread, or only absorbed or compacted ones | Writes a new entry (`written`). |
| An active entry cites the thread | Adds the answer, and the recommendation it overruled, to the highest-numbered such entry, the one a curator's merge leaves, keeping what its body says, before its source line (`updated`). |
| The answer has a secret's shape | Nothing. The warning names `digest.secret`, never the text, and the thread is left as it is. |
| The write fails, or the check refuses it | Nothing. The warning says why. |

A failure never fails the answer: the answer is saved first, the warning is logged at warn, and the next `flai digest seed` or curator run takes the answer in. Nothing is committed, as a thread entry is not.

Every way of answering runs it: `flai thread reply` and `confirm`, the MCP tool `thread_reply`, and the host API's `thread.reply` and `thread.confirm`, which run the CLI as the owner. Each result names the entry under `digest`: `id`, `path`, and `action` (`written` or `updated`), or `warning` alone ([flai-cli.md](flai-cli.md#commands)). The next story's pack loads the entry, and `doc_search` finds it, before the curator has run. The curator's next run sees the answer's candidate cited by the entry, and merges the entry with what the digest holds as it merges any other.

### Absorption and compaction

An entry's `status` is `active`, `absorbed`, or `compacted` ([ADR-0191](../adrs/0191-the-digest-is-one-markdown-file-per-entry-under-the-design-folder-s-digest.md)). A story's pack loads an active entry whole, a compacted one as its title, and an absorbed one never ([agent-context.md](agent-context.md)). The curator moves entries out of `active` with three commands (`internal/digest/decay.go`):

| Command | What it does |
|---------|--------------|
| `flai digest absorb <D-nnnn> --by <path> [--heading <heading>]` | Sets `status: absorbed` and `absorbed_by` to the path, from the project root, of the design document, convention, or ADR that now records the fact, or `<path>#<anchor>` with a heading, found as `flai doc show --heading` finds it. Keeps the body. Refuses a path that names no file and a heading the document lacks, and writes nothing then. An entry absorbed again names the newer document. |
| `flai digest cited` | Finds each entry's citers and its latest citation, and writes each entry's `cited` as its citers, in ID order, where that changed. |
| `flai digest compact [--dry-run]` | Runs `cited` first, then turns each active entry whose latest citation, or its own `date` when that is later or it has none, is older than `digest.compact_after` into `compacted`: its body is emptied below its `# D-nnnn <title>` heading. `--dry-run` lists what it would compact and writes nothing. |

A citation is an entry's ID, `D-nnnn` in any zero padding, written in a work item's file, on the board or in the archive, in a narrative, which counts as its story, or in a thread. Its date is the citing file's `updated`. Entries citing one another do not count. A later edit of a citing file moves its `updated`, so a citation can read newer than it is; that errs toward keeping an entry whole.

`digest.compact_after` is a Go duration, `720h` when unset; `0` turns compaction off, and a value that is not a duration is refused, naming it. An absorbed or compacted entry is left as it is, so a second run compacts nothing more, and a compacted entry stays compacted when it is cited later. Nothing is deleted: no file is removed, and git keeps every earlier text. The curator runs these in the main checkout, and leaves what they write there uncommitted, as its other entries are.

### The curator's run and how it ended

The run is recorded in `serve/agents.json` under `curator`, the project's newest run alone, with no past runs kept. It has the fields a story's run has, neither `story` nor `item`, and `role` (`curate`, so that it is never taken for the orchestrator's run), `since` (empty on its first run), `trigger` (`asked`, `accepted S-nnnn`, naming every story when several, or `schedule <spec>`), and, once it has ended, `entries`. `Running` and `Last` never name it, the in-progress limit does not count it, and it holds no story back. Its output is in `serve/agents/<key>-curator-<start>.log`, beside the other agents' logs.

When the process ends, or the next look finds it gone, flai serve settles the run (`curateEnded`). Its entries are the IDs of the entry files directly in the digest folder, `D-nnnn-<slug>.md` and the README aside, changed no earlier than the second the run started, in number order (`changedEntries`).

| Outcome | When |
|---------|------|
| `failed` | its log ends on the harness's usage limit (`runLimit`), whether its exit was seen or not; `why` names the limit and its reset time, such as `ended on the harness's usage limit (usage_limit_reached, 429); it resets at 2026-10-28T08:00:00Z`, or ends `it named no reset time` |
| `failed` | it exited with a code other than 0, or could not be started |
| `worked` | otherwise, whether it wrote or merged an entry or found nothing to take in, and whether its exit was seen or not |

A run on the usage limit also has `resets_at`, an RFC 3339 time in UTC, when the harness named one ([ADR-0214](../adrs/0214-a-curator-run-that-ends-on-the-harness-s-usage-limit-is-recorded-failed-with.md)). A run the scheduler started again at the reset has `retry: true` ([The usage limit](#the-usage-limit-s-0514)). flai serve's log line `curator ended` adds the limit, its status, and `resets_at`.

It then logs the run's activity in `wip/agents/curator.md`: the time since the last entry, the seconds and cost measured from the log, the run's trigger as the entry's `- Trigger:` line, the first line of the run's final reply as the summary, and the entries as its items. Entries that cannot be looked for are warned of, and the activity names none. A run on the usage limit spent nothing and logs no activity, so the next run's since stays at the last activity, and it takes in what this run never did.

A retry that ends on the limit again, or a run whose limit names no reset time, is raised to the operator (`raiseCurateLimit`). `flai serve` opens one thread on `system-flow.yaml`, by `flai serve`, titled `The curator ended on the harness's usage limit twice; start it when the limit allows`, or `... with no reset time; start it when the limit allows`. It names the run, its trigger, its `why`, and its log, quotes the harness's text at the end of the run, and says that `flai curate` starts the curator at any time, and the next acceptance or `digest.schedule` once the limit resets. The thread's ID is the run's `limit_thread`, so it is opened once. The opening is journalled under `curate`. One that cannot be opened is warned of and journalled `failed`. No retry follows either way.

Every start and failure to start is a journal entry with action `curate` and method `serve.curate`, whose detail names the trigger; `curate.run` and the MCP tool `curate` are journalled as well, under the same action. `agent.status` carries the run as `curator`, null before the first. When the run starts, cannot start, or ends, `flai serve` tells the dashboard with an `agent` notification that carries the project and `role: curate`. Since S-0532 ([ADR-0209](../adrs/0209-the-orchestrator-runs-for-a-reason-and-ends-started-by-flai-serve-on-the-events.md) §6) it also logs an `agent` event with `id` and `title` `curator`, `type` `role`, and `fields.role` `curate`: `started` with its trigger as `why`, a retry's naming the usage limit's reset, then `ended`, or `failed` with its exit, a run on the usage limit naming the limit and its reset time. The orchestrator, the analyzer, and the operator see it in `inbox` and `wait_for_events` ([flai-cli.md](flai-cli.md#the-events-wait_for_events-and-inbox-report)).

### What the curator's run costs

A curator activity charges no item: digest entries are not work items, and the curator's `charge` is `none` ([ADR-0249](../adrs/0249-strategic-usage-is-per-role-a-role-s-activity-is-charged-by-its-role-file-s.md)). Its cost stays in the curator's project strategic total, which `flai stats` reports per role as it reports the analyzer's ([What it costs on the items](#what-it-costs-on-the-items-s-0226), [metrics.md](metrics.md#strategic-agents-s-0206)).

### The curator on the dashboard

The Settings page lists the `curate` action with the others, to turn on and off while `settings` is on. A dashboard starts the curator with `curate.run`. No page shows the curator's runs yet.
