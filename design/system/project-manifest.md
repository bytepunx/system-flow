# Project manifest

A conforming repo has `system-flow.yaml` at its root. It is how `flai` and `flaiover` recognise a project, find its folders, and know which template it came from.

```yaml
# system-flow.yaml
version: 1                                   # manifest schema version
name: system-flow                            # project name, used in titles
key: sf                                      # short key, used in generated IDs when a project opts into prefixed IDs
description: Agentic lean project management system
template:
  repo: https://github.com/bytepunx/system-flow-template
  ref: main                                  # the ref last applied: branch, tag, or commit; main or a version tag follows releases (ADR-0103)
  version: 0.1.0                             # template version last applied, from template.yaml
  applied: 2026-09-15T16:00:00Z
layout:                                      # folder names, defaults shown, renameable at import
  design: design
  docs: docs
  wip: wip
projects:                                    # releasable components at the repo root
  - name: flai
    path: flai
    kind: go
    tags: [cli]                              # story tags that mean "delivers to flai"
  - name: flaiover
    path: flaiover
    kind: sveltekit                          # sveltekit or svelte: flai reads its components (S-0437)
    tags: [dashboard]
    components:                              # optional (S-0437): where its components are found; flai components config writes it
      include: ["src/lib/**/*.svelte"]       # globs from the sub-project's folder, as claims.shared; default src/lib/**/*.svelte
      exclude: ["src/lib/internal/**"]       # globs of files include finds that are not components; default none
      setup: src/app.css                     # a module of the sub-project the harness imports before any component; default none
    install:                                 # optional (S-0483): what flai accept runs in the main checkout when an acceptance changes paths
      command: ["../scripts/flaiover-install.sh", "--if-needed"]  # argv, no shell, run in the sub-project's folder
      paths: ["package.json", "pnpm-lock.yaml"]  # globs from the sub-project's folder, as components' globs
  - name: template
    path: template
    kind: template                           # released by bumping template.yaml and CHANGELOG.md, not by tag
    tags: [template, conventions]
dashboard:
  image: ghcr.io/bytepunx/flaiover
  tag: latest
  port: 4242
  autocommit: true                           # optional, default true: commit documents saved from the dashboard (ADR-0023)
  notify_url: ""                             # optional, default unset: POST new inbox entries here as JSON (S-0042)
  allow_unsigned: false                      # optional, default unset, the host's dashboard.allow_unsigned; true or false overrides it here (S-0239)
tests:                                       # optional (S-0273): the test tiers, cheapest first, that flai test runs; default one plain tier, scripts/test.sh
  - name: unit                               # unique among the tiers
    command: [go, test, -json, "{packages}"] # an argument list; {packages}, {importers}, or {files}, an argument of its own, stands for what the paths selected
    dir: flai                                # optional: the folder it runs in, from the root; default the root
    paths: ["flai/**", "!flai/testdata/**"]  # globs from the root that select it, as claims.shared; ! takes paths out; required unless all_only
    format: go-test-json                     # go-test-json, vitest-json, golangci-json, gofmt-list, or plain; default plain
    all_command: [go, test, -json, ./...]    # optional: what runs instead under --all, with no placeholder
    fix_command: [gofmt, -w, "{files}"]      # optional (S-0367): rewrites the files it selects before flai commits them; its exit status is ignored
  - name: smoke
    command: [scripts/smoke.sh]
    all_only: true                           # runs only under --all
    covers: [unit]                           # optional (S-0342): the tiers whose tests this one runs too; skipped when both are selected
    queue: true                              # optional (S-0405): left to the merge queue's batch while the queue can batch; default false
agent:                                       # optional (S-0103): the agent every new story gets; flai agent set writes it
  harness: claude-code                       # what runs the agent
  model: claude-opus-5-5
  provider: litellm                          # optional (S-0349): the host's provider the model's calls go to; default the harness's own
  config:                                    # optional: options for the harness, passed on as they are
    effort: high
  roles:                                     # optional (S-0189): the sub-agents' agents, by role
    explore:
      model: haiku
    verify:
      model: sonnet
providers:                                   # optional (S-0349): this project's override of the host's provider entries, by name
  litellm:                                   # api, base_url, and models only; key_env and spend_key_env are the host's alone
    api: anthropic-messages                  # anthropic-messages, openai-chat, or openai-responses
    base_url: https://litellm.example.com    # an absolute http or https URL with no user or password
    models:                                  # the harness's model aliases and their names on the provider
      opus: anthropic/claude-opus-5-5
prime:                                       # optional (S-0146): how flai prime --story builds context packs
  budget: 80KB                               # the size a story's pack fits; default 80KB
issues:                                      # optional (S-0198): how flai check treats open issues
  story_after: 168h                          # how long an issue may stay open with no open story linking it; default 168h, 0 turns the warning off
planning:                                    # optional (S-0199): what items' planning data is counted in
  currency: USD                              # ISO 4217 code of every amount; default USD
  hour_rate: 95                              # what an hour of work costs, in currency; default unset, meaning unknown
  cycle: 168h                                # the period time lost is counted over; default 168h
  default_duration: 1h                       # optional (S-0210): a story's forecast duration with too little history; default 1h
  agent:                                     # optional (S-0208): the planner's agent, over agent above
    model: claude-sonnet-5
    config:
      effort: medium
  replan: deterministic                      # optional (S-0211): what flai serve does when work ahead completes or the order changes: never, deterministic, or agent; default deterministic
  schedule: daily                            # optional (S-0211): when flai serve plans the ready column, a cron expression in UTC or daily; default none
orchestration:                               # optional (S-0217): how the ready column is ordered and when a release is due
  policy: wsjf                               # cod, wsjf, throughput, or fifo, as flai order --by; default fifo
  release:                                   # when accepted stories not yet released are due a release
    policy: threshold                        # judgement, threshold, or theme; default judgement
    value: 500                               # threshold: the unreleased cost of delay per week, in planning.currency
    count: 5                                 # threshold: the accepted stories not yet released
    whole_epics: true                        # optional (S-0222): hold a batch back while a story's epic is in neither review nor done; default off
  permissions:                               # optional (S-0218): what the orchestrator may do without the operator; each off when unset
    promote_to_ready: true                   # also plan_backlog_epics, plan_backlog_stories, finalize_drafts, order_ready, accept_reviews, publish
    answer_threads: recommend                # off, recommend, or autonomous; default off
    confirm_after: 48h                       # optional (S-0502): how long a recommendation of the orchestrator's may await the operator before flai serve confirms it, a Go duration; default unset, none confirmed
  agent:                                     # optional (S-0218): the orchestrator's agent, over agent above
    model: claude-sonnet-5
  coalesce: 30s                              # optional (S-0536): how long after the first queued reason flai serve starts an orchestrator run, a Go duration; default 30s
  run_timeout: 20m                           # optional (S-0536): how long an orchestrator run may hold before flai serve stops it, a Go duration; default 20m
  schedule: "0 * * * *"                      # optional (S-0536): when flai serve starts an orchestrator run for a periodic look, a cron expression in UTC or daily; default none
analysis:                                    # optional (S-0223): the analyzer's agent and schedule
  agent:                                     # the analyzer's agent, over agent above
    model: claude-sonnet-5
  schedule: "0 6 * * 1"                      # when flai serve runs the analyzer, a cron expression in UTC or daily; default none
digest:                                      # optional (S-0431): the curator's agent, schedule, and compaction window
  agent:                                     # the curator's agent, over agent above
    model: claude-sonnet-5
  schedule: daily                            # optional (S-0432): when flai serve runs the curator besides after each acceptance, a cron expression in UTC or daily; default none
  compact_after: 720h                        # optional (S-0432): how long an active digest entry may go uncited before it is compacted, a Go duration; default 720h, 0 off
roles:                                       # optional (S-0416): the settings of each role a role file under design/workflows/roles/ defines, by its name
  reviewer:
    agent:                                   # optional (S-0417): the role's agent, over agent above
      model: claude-sonnet-5
    permissions:                             # optional (S-0416): what it may do without the operator, as orchestration.permissions; each off when unset
      promote_to_ready: true
threads:                                     # optional (S-0498): when flai serve reminds the operator of a thread that awaits them
  remind_after: 4h                           # how long a thread may await the operator before they are reminded, a Go duration; default unset, no reminders
  remind_every: 24h                          # how often they are reminded again while it still awaits them, a Go duration; default 24h
claims:                                      # optional (S-0295): how stories' touches claim paths
  shared:                                    # glob patterns of paths whose overlaps hold no story; flai shared edits them
    - docs/users/flai.md
    - design/adrs
    - design/issues
design:                                      # optional (S-0381): where the project's design system is kept
  tokens: design/system/design-system.tokens.json # the design token file, a DTCG file; default design-system.tokens.json in the design folder's system folder
  stylesheet: web/src/theme.css              # optional (S-0385): the Tailwind v4 stylesheet flai design css --write writes the tokens to, under a sub-project; unset, none
acceptance:                                  # optional (S-0392): how a story in review is accepted
  mode: pull-request                         # local or pull-request; default local
  forge: github                              # the forge pull-request acceptance goes through; github, the default and only one
  merge_method: squash                       # merge, squash, or rebase; default merge; unused under local
merge_queue:                                 # optional (S-0399): the merge queue flai serve runs behind the merge-queue host action
  batch_max: 4                               # the most enqueued stories one batch holds, a whole number of one or more; default 4
flai:                                        # optional (S-0181): what the project asks of the flai that reads it
  minimum: 1.27.0                            # the oldest flai release that may read it; a publish raises it, no higher than the flai publishing
  command: scripts/flai.sh                   # optional (S-0495): the program that runs the flai the tree builds; task done checks a story with it
```

Rules:

- `flai` refuses to run project commands in a directory tree with no `system-flow.yaml` above the current directory, except `flai new` and `flai import`.
- `layout` is the only place folder names live. Everything else resolves through it. Subfolders such as `design/conventions` are fixed names under their layout folder.
- `template.ref` and `template.version` are the ref and version last applied ([ADR-0103](../adrs/0103-flai-new-import-and-upgrade-follow-the-template-s-releases-the-newest-version.md), [template.md](template.md#which-version-is-applied)). A `ref` that is empty, `main`, or a version tag follows releases: with no `--ref`, `flai upgrade` applies the template's newest version tag. Another branch or a commit is used as given. `flai upgrade --ref` writes its ref here. Editing `ref` or `version` here, so that it differs from the lock and from the newest tag, makes the next `flai upgrade` ask which version to apply: the one named here, the newest, or none; a changed `version` names the tag `v<version>`. The version a project is at is the lock's, not this one, unless there is no lock.
- `system-flow.lock.yaml` beside the manifest records the hash of every rendered file so upgrade can tell project edits from baseline (ADR-0015), the `topics` the template gave each marker file so upgrade keeps a project's own (S-0134), and under `vars` the value of every template variable the project was last rendered with, so upgrade renders a fork's own variables again (S-0185).
- `name`, `key`, `description`, `owner`, and `repo` are read back by `flai upgrade` as the template variables `project_name`, `project_key`, `description`, `owner`, and `repo_url`, ahead of the values the lock recorded, so an edit to them here reaches the next upgrade. `flai upgrade --var` refuses them and names the key to edit ([template.md](template.md#upgrading-a-project)).
- `projects` are the components `flai release` versions, one item at a time or, since S-0087, batched by `flai release --pending`: code kinds get `<name>/vX.Y.Z` tags, kind `template` gets its version file bumped. `flai accept` versions nothing. `tags` are aliases a story or epic tag may use to say which component it delivers to.
- `projects[]`, an entry of the list, is one sub-project (S-0491, [ADR-0195](../adrs/0195-with-edit-subprojects-on-the-orchestrator-adds-changes-and-removes-a-sub.md)). It has:
  - `name`, unique among the entries. It is the prefix of the sub-project's release tags, `<name>/vX.Y.Z`, the folder of its components' examples, `design/components/<name>/`, and what `flai components --project` and the host API's `sub_project` name it by.
  - `path`, its folder, relative to the repository root, unique among the entries.
  - `kind`, what it is. flai knows `go`, `node`, `python`, `rust`, `sveltekit`, `svelte`, and `template`, and accepts any other.
  - `tags`, optional, as above.
  - `components` and `install`, optional, below.

  `Manifest.ProjectErrors` reports, each by the entry's index and field: a `name` that is empty or repeats another's; a `path` that is empty, the repository root (`.`), absolute, not clean, leaves the repository, or repeats another's; and a `kind` that is empty. `flai check` reports them, and a `path` that names no folder, as `manifest.projects` errors. `flai manifest set` refuses a manifest that has one, with no folder checked.

  `flai subproject add`, `set`, and `remove` write an entry's `name`, `path`, `kind`, and `tags` through `manifest.SetProjects`, keeping every other line and comment, and refuse anything `ProjectErrors`, `ComponentErrors`, or `InstallErrors` finds in the manifest as it would be, folders checked, writing nothing. `add` and `set` create a missing folder with a `README.md` naming the sub-project and its kind; `remove` leaves the folder. The dashboard writes the list through the host API's `settings.subproject` ([dashboard-host-channel.md](dashboard-host-channel.md)), and a story's agent through the MCP tool `subproject_edit`, in its worktree, committing nothing. The orchestrator runs `flai subproject ... --autocommit` in the main checkout, only with `orchestration.permissions.edit_subprojects` on. How to use them is in [flai.md](../../docs/users/flai.md#manage-sub-projects).
- `projects[].components` (S-0437) says where flai finds the components of a sub-project whose `kind` is `sveltekit`, a SvelteKit app, or `svelte`, a Svelte project that is not one, such as a component package built with Vite. Sub-projects of any other kind have no components flai reads (`manifest.ComponentKinds`, `manifest.SupportsComponents`). It has:
  - `include`, globs of the component files, relative to the sub-project's folder, with the syntax of `claims.shared`: `*` within one segment, `**` zero or more whole segments, `?` one character. Unset or empty, it is `src/lib/**/*.svelte`, so the app's routes are left out.
  - `exclude`, globs of files `include` finds that are not components to list, written the same way. Unset, nothing is excluded.
  - `setup`, a module of the sub-project, relative to its folder, that the harness imports before any component, such as the app's stylesheet. Unset, there is none.

  `Project.ComponentSettings` gives the settings in effect, the key over those defaults, and false for a kind it does not take. `Manifest.ComponentErrors` reports, each by the sub-project's index, field, and name, such as `projects[1].components.include (sub-project "web") pattern "src/[" is not a valid glob …`: a glob that is empty, absolute, has a `.` or `..` segment, has `**` inside a segment, or does not parse; a `setup` that is absolute, not clean, or leaves the sub-project, or names no file under the sub-project's folder; and `components` on a sub-project of another kind. `flai check` reports them as `manifest.components` errors, and `flai manifest set` refuses a manifest that has one, with no file checked. `flai components config <sub-project> [--include] [--exclude] [--setup] [--unset]` writes the key whole, or removes it, through `manifest.SetComponents`. It keeps every other line of the manifest, the order of its keys, and its comments, and refuses an unknown sub-project and any problem `ComponentErrors` finds in the manifest as it would be, writing nothing. `manifest.EditComponents` gives the bytes it would write, for a caller that checks them first. A key it cannot edit in place, such as a sub-project written on one line, is refused with what to write instead.
- `projects[].install` (S-0483, [ADR-0185](../adrs/0185-flai-accept-runs-a-sub-project-s-install-command-in-the-main-checkout-when-the.md)) is how a sub-project of any kind installs its dependencies, for `flai accept` to run in the main checkout after an acceptance that changed them. It has:
  - `command`, the argument list, run with no shell in the sub-project's folder. Required, and its first element not empty.
  - `paths`, globs relative to the sub-project's folder, written as `components.include` is. Required, at least one. An acceptance that changed a path one of them matches runs `command`.

  `Manifest.InstallErrors` reports a missing or empty `command` or `paths` and a glob `components` would refuse, each by the sub-project's index, field, and name. `flai check` reports them as `manifest.install` errors. Unset, `flai accept` installs nothing for the sub-project. This repository sets flaiover's to `../scripts/flaiover-install.sh --if-needed` on `package.json` and `pnpm-lock.yaml`.
- `dashboard.notify_url`, when set, makes the dashboard's server POST `{ project, entry: { key, kind, title, href, at } }` to that URL for each inbox entry that appears after it started: one attempt, a short timeout, a warning in the log on failure. The token and file contents are never sent. Unset by default.
- `threads.remind_after` is how long a thread may await the operator, a pending recommendation or a last entry by neither the project's owner nor its story's agent, before `flai serve` reminds them of it through the channel the host configuration keeps, writing nothing on the thread: a Go duration such as `4h`. Unset, or `0`, nothing is reminded. `threads.remind_every` is how often the reminder is sent again while the thread still awaits them: a Go duration, `24h` when unset. A new entry on the thread starts the count over (S-0498, [ADR-0205](../adrs/0205-flai-serve-reminds-the-operator-of-a-thread-that-awaits-them-past-threads.md)). `Threads.RemindAfterDuration` and `Threads.RemindEveryDuration` read them. `flai check` reports each thing wrong with `threads` as a `manifest.threads` error on its line: a value that is not a duration, a negative one, or a `remind_every` of zero. `flai manifest set` writes both keys; no dashboard page has a panel for them yet. The reminder's body extends the one `dashboard.notify_url` receives, so one receiver can take both.
- `dashboard.autocommit: false` leaves documents saved from the dashboard uncommitted; the default commits each save on the main checkout, one path per commit (ADR-0023).
- `dashboard.allow_unsigned`, when set, is this project's allowance for unsigned builds, over `dashboard.allow_unsigned` in the host's flai configuration (S-0239, [ADR-0070](../adrs/0070-releases-are-signed-with-a-cosign-key-pair-verified-before-they-are-installed.md)): `true` allows them for this project, `false` refuses them though the host allows them, and unset leaves the host's. `flai serve` reads it before each dial, and `flai dashboard` when it starts the container. What the allowance lets through and how it is shown is in [release-signing.md](release-signing.md#the-development-case). An older flai ignores it.
- `tests` lists the project's test tiers, cheapest first, which `flai test` runs for the paths each selects (S-0273), and `flai verify` runs for what a story's branch changed against the main branch (S-0270). A tier has:
  - `name`, unique among the tiers.
  - `command`, an argument list run as it stands, never through a shell. `{packages}`, `{importers}`, and `{files}`, each as an argument of its own, stand for what the tier's paths selected, and `flai test` fills them. `{packages}` is the Go packages that hold the selected files, and `{files}` is the files. A tier whose placeholder comes to nothing, such as `{packages}` for files no Go package holds, is left out. Under `flai test --all`, with no `all_command`, `{packages}` and `{importers}` are `./...` and `{files}` is `.`. Any other argument that is a word in braces, such as `{story}`, and a placeholder inside a longer argument are refused.

    `{importers}` (S-0364) is the packages `{packages}` names and every package of the same Go module that imports one of them, directly or through other packages. An import counts in a package's own files and in its test files, external `_test` packages included. Each package is written `./x/y`, relative to the tier's `dir`, and the list is sorted. flai reads the module path from the `go.mod` in the tier's `dir`, and each `.go` file's imports from the checkout. It skips the folders the go tool ignores: `testdata` and names beginning with `.` or `_`. It ignores build constraints, so the set is never smaller than the go tool's. With no `go.mod` in the tier's `dir`, `{importers}` is what `{packages}` is.

    This repository's `vet` tier runs `go vet "{importers}"` in `flai`. `go vet` type-checks test files, so a change that breaks a package importing the changed one fails `flai test` and the close-out's `vet` tier. Before, only the integration tier found it ([I-0128](../issues/I-0128-flai-test-vets-and-tests-only-the-changed-go-packages-so-a-change-that-breaks-a-package-importing-them-is-found-only-by-the-integration-tier.md)). `go-test` and `golangci-lint` keep `{packages}`: running every importer's tests or lint on each change would cost most of the integration tier, and `vet` already catches the build break.
  - `dir`, the folder the command runs in, relative to the root and inside it. Unset, it is the root.
  - `paths`, glob patterns relative to the root with the syntax of `claims.shared` (below); one beginning with `!` takes paths out again. Required, with at least one pattern without `!`, unless `all_only` is set.
  - `format`, how the command's output becomes findings: `go-test-json`, `vitest-json`, `golangci-json`, `gofmt-list`, or `plain`, which reads no findings from the output: a failing `plain` tier is one finding, its exit status after its last 20 lines, and ahead of them, at most 20 lines naming a failure that the last lines left out, `go test`'s `--- FAIL:` lines with the indented lines under them, its `FAIL<tab><package>` lines, and `panic:` lines (S-0313), so a `plain` tier running `go test` over many packages still names the failing test. A format that finds nothing in a failing tier's output falls back to the `plain` finding. Unset, it is `plain`. The list is `manifest.TestFormats`. This repository's `integration` tier runs `scripts/integration.sh -json` in `flai` as `go-test-json`, so its findings name each failing test by file and line.
  - `all_only`, set for a tier that runs only under `flai test --all`, such as integration and smoke tests, and `all_command`, an argument list with no placeholder that runs instead of `command` under `--all`.
  - `fix_command` (S-0367, [ADR-0139](../adrs/0139-a-test-tier-s-fix-command-rewrites-the-files-a-story-changes-before-flai-task.md)), an argument list that rewrites in place the files the tier selects, so that what flai commits is fixed. It runs as `command` runs: never through a shell, in `dir`, with the same placeholders, filled for the existing files the tier's `paths` select among the paths flai is about to commit. Its exit status is ignored: a command that cannot start or exits non-zero is logged at warn and stops nothing, and the tier's `command` still reports what is left. flai runs it in three places:
    - `flai task done`, over the paths it is about to commit, before it commits them.
    - `flai stream sync`, and the rebase `flai accept` runs on the story's branch, after a clean rebase, over every file the branch changes against the main branch. What it changed is committed on the branch as `chore: [S-nnnn] fix the lint of the files the branch changes, after the sync`.
    - `flai accept`, in the main checkout, over the paths it has not committed, at preflight and again just before its `git add -A` and commit.

    What a fix leaves refuses an acceptance ([ADR-0140](../adrs/0140-flai-accept-refuses-an-acceptance-whose-files-a-tier-with-a-fix-command-still.md)): `flai accept` runs the `command` of each tier that has a `fix_command` over the main checkout's uncommitted files at preflight, and over the files the branch changes after its rebase and fix, and refuses when one fails, naming each file, line, and error.

    This repository's `markdown` tier has `fix_command: [scripts/lint-md.sh, --fix, "{files}"]`. The template's manifest has none.
  - `covers`, the names of the tiers whose tests this one runs too (S-0342).
  - `queue` (S-0405, [ADR-0174](../adrs/0174-while-the-merge-queue-can-batch-flai-verify-and-the-close-out-leave-the-test.md)), `true` for a tier that `flai verify` leaves to the merge queue's batch while the queue can batch for the project. It is a boolean, may go on any tier, and needs no other key. Unset, it is `false`.

  When a run selects a tier and a tier that covers it, by naming it in `covers` or through a chain of tiers that each name the next, the covered tier is not run. It is listed in its place with the state `skipped` and `covered_by` naming the tier that runs instead: the nearest selected tier that covers it and is not covered itself. A skipped tier never fails the run, and it stays `skipped` after a tier or step before it failed, where the tiers after a failure are `not-reached`. A tier that only unselected tiers cover runs as before. This repository's `integration` covers `go-test`, since `scripts/integration.sh` runs the whole Go suite, and `flaiover` covers `flaiover-lint` and `vitest`, since `scripts/flaiover-test.sh` runs the lint and the whole vitest suite. `integration` is `all_only`, so `flai test` on a few paths under `flai/` still runs `go-test`, and `flai test --all`, and `flai verify` on a story that changes `flai/`, run `integration` in its place. The template's manifest covers nothing; the comment on its `integration` tier says to add `covers: [test]` once `scripts/integration.sh` runs the behaviour tests too.

  `flai test` without `--all` never runs an `all_only` tier, whatever its `paths`. `flai verify S-nnnn`, which the close-out runs, runs the tiers `flai test` selects for the paths the story's branch changed, and then each `all_only` tier whose `paths` select one of those paths, or that has no `paths`, as it runs under `--all` (`verify.SelectStory`). So `paths` on an `all_only` tier says which changes need it before review: this repository gives `integration` and `smoke` `flai/**`, `template` `template/**`, and `flaiover` `flaiover/**`, and a story that changes only documents runs none of them. Each also selects the scripts it runs, so a story that changes only a script runs the tests that exercise it ([I-0199](../issues/I-0199-no-test-tier-selects-scripts-so-a-story-that-changes-only-shell-scripts-and-the-script-tests-it-adds-pass-flai-verify-and-the-merge-queue-without-any-of-them-running.md)): `template` `scripts/template-test.sh`, `flaiover` `scripts/flaiover-*.sh` and `scripts/env.sh`, whose pnpm settings only flaiover's scripts use, `integration` `scripts/integration.sh`, and `smoke` `scripts/**/*.sh`, which holds the scripts every tier shares, such as `env.sh` and `flai.sh`. The `shellcheck` tier, not `all_only`, lints the changed scripts in `flai test` too. An `all_only` tier with no `paths` runs for every story.

  While the merge queue can batch for the project, `flai verify` leaves each tier it selects that has `queue: true` to the batch, which runs it. The queue can batch when the `merge-queue` host action is on for the project in the configuration the running flai reads, `orchestration.permissions.accept_reviews` is on, and acceptance is local; a hold does not count. The tier is listed as `queued`, after the rest, and the run passes without it. A tier that only a `queue` tier covers runs, since the covering tier does not. `flai verify --all` leaves none out, and `flai test` ignores the key. The batch's verification runs every tier the batch's paths select, those marked `queue` included ([flai-cli.md](flai-cli.md#the-merge-queue-pass)). This repository marks `integration` and `smoke`, about twelve minutes together, so while the queue can batch, a close-out that changes Go files under `flai/` runs `go-test` and leaves those two to the batch. This repository's `go-test` therefore runs `go test -json -race -count=1 -skip ^TestGateway {packages}`, without `-short`: the changed packages' real-git and monorepo tests run in `flai test` and in that close-out, not first in the batch, and only the paid gateway tests, which `scripts/integration.sh` skips too, are left out ([I-0201](../issues/I-0201-flai-test-runs-go-test-with-short-so-a-real-git-test-a-task-adds-is-skipped-until-the-integration-tier-runs-in-the-merge-queue-s-batch.md)). The template's manifest marks none. An older flai ignores the key and runs every tier; its `flai manifest set tests=<JSON>` refuses a tier that carries it.

  Unset, the project has one `plain` tier named `test` that runs `scripts/test.sh` for every path when that file exists, and none when it does not (`Manifest.TestTiers`), so a project made before the key still has a tier. `tests: []` means none. A project made from the template starts with `scripts/lint-md.sh` as `markdown`, for its markdown files (S-0270), its `scripts/test.sh` as `test`, and `scripts/integration.sh` and `scripts/smoke.sh` as `integration` and `smoke`, both `all_only` with no `paths`, so `flai verify` runs them for every story; all four are `plain`. `flai check` reports each thing wrong with a tier as a `manifest.tests` error, by its index, its field, and its name, such as `tests[1].format (tier "unit") "junit" is not a format flai reads; write …` (`Manifest.TestErrors`). For `covers` they are a name that names no tier, the tier itself, a name given twice in one `covers`, and a cycle of tiers that cover one another, reported once on the first of its tiers and naming them in the list's order. `TestTiers` refuses such a list, so `flai test` runs none of it. `flai manifest set tests=<JSON>` writes the list whole (below).
- `agent` is the project's default agent (S-0103, [ADR-0037](../adrs/0037-a-story-carries-its-agent-copied-from-the-project-s-default-when-it-is-made.md)): a harness, a model, and `config`, a flat map of options for the harness. A story made while it is set gets a copy in its front matter, which the story may change. A change to the default reaches new stories only. `flai agent` shows it, `flai agent set --harness --model --config key=value --unset key` changes only what is given, and `flai agent clear` removes it. Each rewrites the `agent:` block alone. A harness is a lower-case name; a model may also hold `.`, `:`, `/`, and `@`; config keys are lower-case words and values are one line. `flai check` reports a default that is not (`manifest.agent`). `roles` (S-0189) maps a sub-agent role (`explore`, `verify`) to its own harness, model, and config, checked the same way; a story gets them merged role by role, and `flai agent set --role-harness role=h --role-model role=m --role-config role.key=v --unset-role role` changes them. `provider` (S-0349, [ADR-0129](../adrs/0129-a-story-s-agent-names-a-provider-beside-its-harness-and-model-and-the-providers.md)) names the host's provider the model's calls go to, a name of the harness's shape; unset, the harness's own default stands. It is copied into a new story with the rest, merged as the harness is, and set with `flai agent set --provider`. A role has none. The `planning`, `orchestration`, and `analysis` agents take it too. It is also the key the host's budget state holds starts by, or the harness when it names none: once a run ends on the usage limit, no agent with the same key starts on any project the host serves until the limit resets (S-0534, [ADR-0209](../adrs/0209-the-orchestrator-runs-for-a-reason-and-ends-started-by-flai-serve-on-the-events.md) §5, [flai-cli.md](flai-cli.md#the-hosts-budget-state)). Two projects that name one provider share its hold; an agent on another provider is not held.
- `providers` overrides, for this project, entries of the host's providers map (S-0349, [ADR-0129](../adrs/0129-a-story-s-agent-names-a-provider-beside-its-harness-and-model-and-the-providers.md)). The host holds each entry whole in flai's configuration, `agent.providers.<name>`, set with `flai serve agent provider <name>` ([flai-cli.md](flai-cli.md#commands)): `api`, `base_url`, `key_env`, `models`, and, optionally, `spend_key_env`, the name of the variable of a key that can read the gateway's spend log where the agent's own key cannot (S-0357, [ADR-0132](../adrs/0132-a-story-s-cost-comes-from-its-provider-s-spend-log-when-it-has-a-provider-from.md), [flai-cli.md](flai-cli.md#pricing-a-run-from-its-providers-spend-log)). A project may override the values that are not secrets and name none:

  | Key | Values | Over the host's entry |
  |-----|--------|-----------------------|
  | `providers.<name>.api` | `anthropic-messages`, `openai-chat`, `openai-responses` | replaces it |
  | `providers.<name>.base_url` | an absolute `http` or `https` URL with no user or password in it | replaces it |
  | `providers.<name>.models.<alias>` | a model ID on the provider, such as `anthropic/claude-opus-5-5`, for an alias of the harness such as `opus` | merged alias by alias, the project's winning |

  `key_env`, the name of the variable that holds the key, is the host's alone: it names a variable of the host's environment, which a committed manifest cannot know. `flai check` refuses it here as a `manifest.providers` error, as it does a name, an `api`, a `base_url`, or a model that is not valid, and `flai manifest set` refuses a manifest that has one; each names `flai serve agent provider <name> --key-env`. `spend_key_env` is the host's alone for the same reason, and refused here the same way, naming `--spend-key-env`. `manifest.ResolveProvider` lays the project's entry over the host's: a provider the host has no entry for is refused, naming `flai serve agent provider <name>`, and so is a merged entry that lacks `api`, `base_url`, or `key_env` or holds a value that is not valid. `flai serve` calls it at each start of an agent that names a provider (S-0350), and when it prices a run through one (S-0357).
- `prime.budget` is the size a story's context pack fits, `flai prime --story` and the MCP `prime` tool alike ([ADR-0049](../adrs/0049-a-story-s-context-pack-fits-a-size-budget-what-the-story-names-loads-whole-what.md), S-0146): bytes, or a number with `KB` or `MB` (1024-based). `--budget` overrides it for one run. It is the project's, not the host's, because a pack is the same for every agent that works the project. Unset, it is 80 KB.

  - **Values.** A boolean is `true` or `false`; a number is written in digits, a count a whole one; a duration is a Go duration such as `168h`; a cron expression has five fields in UTC, or is `daily`; a choice is one of its values; a text is one line; an agent is JSON, such as `{"harness":"claude-code","model":"claude-sonnet-5","config":{"effort":"medium"}}`, written whole as a block, and `{}` unsets it; a list of test tiers is JSON too, such as `[{"name":"test","command":["scripts/test.sh"],"paths":["**"]}]`, written whole as a block, one tier an item, and `[]` writes a list of none. An empty value, a value on more than one line, and a key given twice are refused. `--unset <key>` removes the key, so that its default applies.
  - **Not among them.** `planning.currency` is refused with its reason: changing it re-denominates every amount on the items, which flai does not convert, so it stays a hand edit. So are `orchestration.agent`, `roles.<name>.permissions`, and every key outside the strategic blocks but `tests`, `acceptance`, `merge_queue`, `threads`, `roles.<name>.agent`, and `roles.<name>.schedule`, named in the refusal with the keys it writes.
  - **How it writes.** Each key's line, or an agent's block, is replaced where it is, or added at the end of its block, adding the blocks above it that are missing; every other key, the order, and the comments are kept, a replaced line's comment included. A block written on one line, such as `release: {policy: theme}`, is refused, naming it, rather than rewritten. The result is read back, and a key that does not read back as given is refused, leaving the file as it was.
  - **How it checks.** The manifest is checked whole, as it would be after the change, with the validation `flai check` uses: the project's `agent`, `issues.story_after`, `planning`, `orchestration`, `roles`, `analysis`, `digest`, `threads`, `acceptance`, `tests`, `providers`, and `claims`. Any problem is refused with its field and its reason, such as `orchestration.release.value: -1 is not an amount of zero or more; write …`, and nothing is written; the exit status is 1, as for a workflow rule. So a problem elsewhere in the manifest blocks every change until it is fixed by hand. With `--json` a refusal is `{"refused": [{"field": ..., "reason": ...}]}` and a change `{"set": [{"key": ..., "value": ...}], "unset": [...]}`, with `commit` when it was committed.
  - **Committing.** With `--autocommit`, and unless `dashboard.autocommit` is false, it commits `system-flow.yaml` alone as `chore: change the manifest's settings: <keys>`, with each `--trailer`. `settings.manifest` runs it so, with the dashboard's trailer.
  - **While the orchestrator runs.** A change does not restart it. `flai guard` reads the permissions at each of its calls, so a change holds from its next call, and its prompt tells it to read its permissions, policy, and release policy again before each decision ([strategic-agents.md](strategic-agents.md#its-permissions-and-the-guard)).
- `claims.shared` lists the paths that many stories change in separate sections or new files, as glob patterns (S-0295, [ADR-0096](../adrs/0096-a-story-in-review-holds-nothing-an-overlap-inside-the-manifest-s-shared-paths.md)). An overlap whose narrower entry lies wholly inside a pattern holds no ready story, is not a `wip.overlap`, and is not told as a grown claim; the trial merge at sync and the notice at acceptance still report it ([workflow.md](workflow.md#branches-and-collisions-adr-0019)).
  - Patterns are relative to the repository root and separated by `/`. `*` matches any characters within one segment, `**` zero or more whole segments, and `?` one character within a segment. A pattern with no glob character matches the path and everything below it, so `design/adrs` and `design/adrs/**` mean the same. A folder entry lies inside a pattern only when the whole folder does: `docs/users` is inside `docs/users/**` but not inside `docs/users/*.md`.
  - `flai check` reports an empty pattern, an absolute path, a `..` segment, or a malformed glob as an error on its line. A pattern that is not valid frees nothing.
  - Unset, the list is empty and every overlap holds. A project made from the template starts with `adrs` and `issues` under its design layout folder, `design/adrs` and `design/issues` by default. This project's list adds `docs/users/flai.md`, `docs/users/flai-reference.md`, `design/system/flai-cli.md`, and `template/CHANGELOG.md`.
  - `flai shared list`, `check`, `add`, and `remove` read and change it ([flai-cli.md](flai-cli.md#commands)), as do the host API's `settings.get`, `settings.shared_check`, and `settings.shared`, the dashboard's project settings, and the MCP tools `shared_paths` and `shared_paths_edit`. Add and remove rewrite only this key, keeping the file's other keys and comments. Only the operator's own session may change it: `flai guard` refuses every session flai serve starts.
  - A flai older than S-0295 ignores the key, as the manifest is decoded leniently, and holds every overlap. The key is not a front-matter field, so it raises no `flai.minimum`.
- `design.tokens` is the repository path of the project's design token file, a W3C Design Tokens Community Group (DTCG) file, beside the guidance in `design/system/design-system.md` (S-0381, [ADR-0146](../adrs/0146-a-project-s-design-tokens-are-a-dtcg-file-the-manifest-names-beside-its.md)). A project has one design system. Unset, it is `design-system.tokens.json` in the `system` folder of the `design` layout folder, `design/system/design-system.tokens.json` by default (`Manifest.DesignTokens`, `manifest.DefaultDesignTokens`). The path is relative to the repository root: `manifest.Load` refuses one that is absolute, leaves the repository, or is not clean, naming `design.tokens` and what to write, so every command stops until it is fixed by hand. The key is not a front-matter field, so it raises no `flai.minimum`; a flai older than S-0381 ignores it.
- `design.stylesheet` is the repository path of the generated Tailwind v4 stylesheet the design tokens are written to, the one a UI sub-project imports its theme from after `@import "tailwindcss";` (S-0385, [ADR-0152](../adrs/0152-agents-build-ui-from-a-tailwind-v4-stylesheet-flai-generates-from-the-tokens.md), [ADR-0159](../adrs/0159-the-generated-design-stylesheet-puts-the-dark-values-under-data-theme-dark-and.md)). Unset, there is none: nothing is written and nothing is checked (`Manifest.DesignStylesheet`).
  - **Where.** It is a file under a sub-project, one whose `projects` entry's path is a folder above it (`Manifest.DesignStylesheetProject`): with a project at `web`, `web/src/theme.css` lies under it and `website/theme.css` does not. The path is relative to the repository root: `manifest.Load` refuses one that is absolute, leaves the repository, or is not clean, naming `design.stylesheet` and what to write, as for `design.tokens`. One outside every sub-project loads, and `flai check` reports it.
  - **What writes it.** `flai design css --write` writes it from the token file, and `flai design init` writes it with the token file when the manifest names one. Its content is a header naming the command and the token file, Tailwind's `dark` variant following `[data-theme='dark']`, the `@theme` block of the light values, and a `[data-theme='dark']` rule of the dark values that differ ([ADR-0159](../adrs/0159-the-generated-design-stylesheet-puts-the-dark-values-under-data-theme-dark-and.md)).
  - **What checks it.** `flai check` reports `design.stale` when the stylesheet differs from what `flai design css --write` would write, naming that command, so a token change that leaves the stylesheet behind stops a story's close-out. A project whose manifest names no stylesheet passes.
  - The key is not a front-matter field, so it raises no `flai.minimum`; a flai older than S-0385 ignores it.
- `acceptance` says how a story in review is accepted: merged on this machine, or through a pull request on the project's forge (S-0392, [ADR-0165](../adrs/0165-a-project-chooses-local-or-pull-request-acceptance-in-its-manifest-flai-reaches.md)). Unset, a story is accepted as before. Each key empty means its default (`Acceptance.ModeOrDefault`, `ForgeOrDefault`, `MergeMethodOrDefault`).

  | Key | Values | Default | Meaning |
  |-----|--------|---------|---------|
  | `acceptance.mode` | `local`, `pull-request` (`manifest.AcceptanceModes`) | `local` | `local` merges the story's branch on this machine, as `flai accept` does; `pull-request` accepts it through a pull request on the forge |
  | `acceptance.forge` | `github` (`manifest.Forges`) | `github` | The forge pull-request acceptance goes through, at the repository the `origin` remote names |
  | `acceptance.merge_method` | `merge`, `squash`, `rebase` (`manifest.MergeMethods`) | `merge` | How the forge merges an accepted pull request: with a merge commit, squashed into one commit, or with the branch's commits rebased onto the base |

  - **Refused at load.** `manifest.Load` refuses a value outside its key's values, naming the key, the value, and the values it takes, such as `acceptance.mode "pull_request" is not an acceptance mode; write local (merge on this machine) or pull-request (merge through a pull request on the forge), or remove it for local` (`Acceptance.Errors`). It never falls back to `local`: a project that meant to gate on a pull request must not have a story merged locally because of a typing error. So every command that loads the manifest stops until the value is fixed or removed by hand. `forge` and `merge_method` are allowed under `local`, and unused.
  - **What reads it.** Nothing acts on `pull-request` yet: `flai accept` merges on this machine whatever the mode. The later stories of E-0021 open or update the pull request (S-0393), read its checks and reviews (S-0394), gate acceptance on them (S-0395), and merge it by `merge_method` (S-0397). Today `flai forge check` reads `forge`, under either mode, to say whether the host's token can read and push to the repository ([flai-cli.md](flai-cli.md#reaching-the-forge)).
  - **The token is the host's.** The manifest names neither the token nor the variable that holds it. The host names the variable with `flai serve forge <forge> --token-env <NAME>`, `GITHUB_TOKEN` for `github` when it names none, as it names a provider's `key_env` ([ADR-0129](../adrs/0129-a-story-s-agent-names-a-provider-beside-its-harness-and-model-and-the-providers.md)). A clone carries the mode and the method, never a token or a variable's name.
  - `flai manifest set` writes each key (below). The key is not a front-matter field, so it raises no `flai.minimum`; a flai older than S-0392 ignores it and accepts locally.
- `merge_queue.batch_max` is the most enqueued, eligible stories one batch of the merge queue holds, 4 when unset (`Manifest.BatchMax`, `manifest.DefaultBatchMax`; S-0399, [ADR-0173](../adrs/0173-a-merge-queue-in-flai-serve-with-no-model-runs-behind-the-merge-queue-host.md)). The queue runs in `flai serve` behind the `merge-queue` host action, while `orchestration.permissions.accept_reviews` is on, under local acceptance only ([flai-cli.md](flai-cli.md#the-merge-queue-pass)). `manifest.Load` refuses zero, a negative number, and a value that is not a whole number, such as `2.5` or `"4"`, naming the key (`MergeQueue.Errors`), so every command that loads the manifest stops until it is fixed or removed. `flai manifest set` writes it (below). It is not a front-matter field, so it raises no `flai.minimum`; a flai older than S-0399 ignores it.
- `flai.minimum` is the oldest flai release, `X.Y.Z`, that may read the project (S-0181): one that knows every front-matter field its items, threads, and issues carry. `manifest.Load` refuses the manifest for a flai below it, so every command, `flai serve` (which leaves the project unserved and says why, once the requests in flight have answered), and `flai mcp` stop before reading any item, with `manifest.TooOldError`: the version needed, the running one, and the upgrade (`flai host upgrade`, or `flai self-upgrade` where no flai host runs). A dev build (`dev`) is never below it, and one that is not a release version is a load error. A publish raises it to the newest flai release whose `flai/internal/workitem/front-matter-fields.txt` changed, no newer than the flai doing the publish (`release.RaiseMinimum`, in the publish commit; I-0107, S-0321), so it never names a release whose binaries are not built yet. A release that adds a front-matter field waits until a publish from a flai at or above it, then becomes the minimum. A flai that is not a release build raises nothing, and the minimum never falls. The rule in full is in [flai-cli.md](flai-cli.md#versions-the-hosts-flai-and-the-tree). A flai older than S-0181 does not know the key and ignores it, as the manifest is decoded leniently; what keeps such a flai reading is that it is told it is behind ([flai-cli.md](flai-cli.md#versions-the-hosts-flai-and-the-tree)). Unset, any flai reads the project.
- `flai.command` is the repository path of a program that runs the flai the tree builds, such as `scripts/flai.sh` in this repository (S-0495, [ADR-0201](../adrs/0201-when-the-manifest-names-flai-command-task-done-s-check-step-runs-that-command-s.md)). When the manifest in a story's worktree names it, task done's check step runs `<command> check --strict --story <S-nnnn> --json` there in place of the running flai's own check, so the branch's rules check the branch, and a command that gives no result stops the close ([flai-cli.md](flai-cli.md#versions-the-hosts-flai-and-the-tree)). Only a project that builds flai sets it; the template's manifest does not. `manifest.Load` refuses an absolute path, one that leaves the repository, or one that is not clean, naming the key. It is changed by hand. The key is not a front-matter field, so it raises no `flai.minimum`; a flai older than S-0495 ignores it and checks in-process.
- The manifest is human-edited YAML. `flai` rewrites only the keys it owns (`template.*`, `projects` with `flai import`, `flai subproject`, and `flai components config`, `agent` with `flai agent set`, `claims.shared`, `flai.minimum`) and the strategic agents' settings, `tests`, `acceptance`, and `merge_queue` with `flai manifest set` (S-0229, S-0273, S-0392, S-0399), and preserves comments where the YAML library allows it.
