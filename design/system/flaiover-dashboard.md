# flaiover dashboard

`flaiover` is the web view of a conforming repo. It renders every markdown document, searches `design/` and `wip/`, shows the kanban board, and charts the flow metrics defined in [metrics.md](metrics.md). It runs locally in Docker with the repo mounted read-write and is started by `flai dashboard`.

Source: `./flaiover` in this monorepo. Image: `ghcr.io/bytepunx/flaiover`, one multi-platform manifest for `linux/amd64` and `linux/arm64` under each tag (S-0119).

## Shape

SvelteKit with `adapter-node`. The browser side is a single-page app (`ssr = false` at the root layout) so navigation is instant and state lives in the client. The server side is a thin set of `+server.ts` endpoints under `/api` that ask flai on the host for everything they show and change (ADR-0029); the container holds no file of the project ([ADR-0031](../adrs/0031-the-dashboard-s-container-holds-nothing-of-the-project-a-port-and-two-secrets.md)). "SPA" here means the UI, not the deployment. See ADR 0007.

```mermaid
flowchart LR
    B[Browser SPA<br/>Svelte 5 + Tailwind] -->|/api/*?project=| S[SvelteKit server<br/>adapter-node]
    F[flai serve<br/>one per user] -->|one connection per project, hello names it| S
    F -->|read, watch, write, git| R[repository]
```

## Views

Every page but the login page has a top bar and a nav rail (S-0458, replacing S-0172's two-tier site menu in the header). The layout is `+layout.svelte`. Icons are lucide's ([icons.md](../tech/icons.md)).

The top bar holds only:

- the flaiover name, a link to Overview at `/`;
- the project picker (`ProjectSwitcher.svelte`);
- the theme setting;
- the status pills at its right: `HostFlai.svelte`, a link to `/host`, which is Updates.

Overview and License are in no group: the top bar links Overview, and the rail's foot links License. Updates, at `/host`, is the Host page of Configuration (S-0489); the host flai pill links it too.

The rail (`NavRail.svelte`) lists five groups in a column. The groups, their pages, and which group and page a path belongs to are `$lib/sitemenu.ts` (`SITE_MENU`, `locate`).

| Group | Pages, in order |
|-------|-----------------|
| Flow | Board (`/board`), Inbox (`/inbox`, with its count), Charts (`/charts`), which expands to its charts by group (S-0484), and Workflow, marked coming soon and not a link |
| Agents | Orchestration (`/workflow/orchestrator`), Planning (`/workflow/planner`), Analysis (`/workflow/analyzer`), Activity (`/activity`), Threads (`/threads`), Messages (`/messages`) |
| Design | System (`/design`), Components (`/design/components`) |
| Documentation | System (`/docs/design/system/README.md`), Conventions (`/docs/design/conventions/README.md`), ADRs (`/adrs`), Issues (`/docs/design/issues/summary.md`), Search (`/search`) |
| Configuration | Features (`/settings/features`), Agents (`/settings/agents`), File System (`/settings/file-system`), Projects (`/settings/projects`), Harnesses (`/settings/harnesses`), one page each of the host's settings (`/settings/:page` in [Views](#views)), then Host (`/host`), the one page of the group that is not a settings page (S-0489) |

A Documentation page answers its whole folder, so any document under `design/system/` marks System current. Within a group `locate` picks the page with the longest path a path falls under, so `/design/components` is Components, not System. `/items`, `/review`, and `/new` belong to Flow, the rest of `/docs` and `/edit` to Documentation, and `/settings` itself and an unknown page below it to Configuration, each with no page current. No page answers a hash.

A page may carry `children`, labelled groups of things it lists below it in the rail. Charts is the one that does (S-0484): its charts, by the groups of `CHART_GROUPS` in `$lib/viz/catalog.ts`, each a link to `/charts/<kind>` labelled with its title from `TITLES`. The catalogue imports nothing, so `sitemenu.ts` takes it without the charts' builders; `viz/charts.ts` re-exports it. `locate` returns `{ group, page, child }`: the child is the chart kind of a `/charts/<kind>` path, and null for an unknown kind, with Charts still the page.

| Rail behaviour | How |
|----------------|-----|
| Expanding a group | Each group is a button, its icon and label, that expands or collapses its pages, each an icon and a label (`aria-expanded`, `aria-controls`) |
| A group's state | An expanded group's icon is in the accent colour, a collapsed one's muted. A collapsed group shows its pages' indicators beside its name (`groupBadges`), so Flow carries the Inbox count |
| A page with children | A button, not a link, that expands or collapses its children as a group does (`aria-expanded`, `aria-controls`), with a chevron; its icon is in the accent colour while expanded and muted while collapsed. Expanded, it lists each group as a muted label, not a link, with its links under it. Collapsed, nothing below it is drawn. Charts so lists flow, usage, planning (the forecast charts, the claims charts, then the cost of delay charts), and strategic, each chart by its title, the spend charts by their titles for a day, Tokens / Day and $ / Day, whatever bucket the page shows |
| The current page | Bold in the accent colour, with `aria-current="page"`. Arriving on a page expands its group, without storing that. The chart `locate`'s `child` names is current the same way, and Charts is bold while any chart is shown; arriving on a chart expands Flow and Charts, without storing that |
| Remembering | The groups the operator expands or collapses, and whether Charts is expanded, are kept per browser in `localStorage` under `flaiover-nav-rail` (`$lib/navrail.svelte.ts`), the keys `RailKey`, a group's or `charts`. One never chosen starts collapsed |
| The foot | License |
| Links | Keep `?project=` (`withProject`) |

From Tailwind's `md` width (768 px) the rail is docked at the left, the height of the window. Below it, a menu button at the start of the top bar opens the rail as a drawer, a native `<dialog>` opened modal. Choosing a page or a chart, Escape, or a click outside closes it, and focus returns to the button. Widening the window to `md` closes an open drawer. Only one rail is in the DOM at a time. The login page has no rail and no menu button.

A page may carry a sidebar of its own sections at the left of its content, `PageSidebar.svelte` with its state in `$lib/pagesidebar.svelte.ts` (S-0460). The page gives it a label, its accessible name, and a list of entries, each an `id`, a `label`, an optional `count`, a mode, `pane` or `scroll`, and optional children listed under it. Each entry is a link to `#<id>`. Since S-0461 an entry may carry an `href` instead, a link to another page, and an entry with neither `href` nor mode is a label over its children (`kindOf`). The page may also give a `header` snippet. The item page, the review page, and the Docs page use it. The charts page used it for its list of charts from S-0461 until S-0484, when the charts moved to the rail; no page gives a link entry since.

| Sidebar behaviour | How |
|-------------------|-----|
| A pane entry | Shows its pane, which the page draws through the `pane` snippet given the id, and hides the others: one pane at a time. Its link is followed as the browser follows any hash link, adding a history entry |
| A scroll entry | Scrolls to the element with its id, smoothly unless the reader asks for reduced motion, replacing the hash. It is current while that section is in view, which an `IntersectionObserver` reports |
| A link entry | A plain link to its `href`, which the page `resolve()`s and the router follows. It writes no hash, and it is current, with `aria-current="page"`, while the page's bound `current` names its id |
| A label | Muted text over its children, not a link, never chosen or current |
| The header | Drawn in the sidebar's column above the entries, such as a tree of documents. Below `md` it sits above the row of entries and scrolls within itself |
| The entry shown | Bold in the accent colour, with `aria-current="true"` on the current entry |
| The URL | The chosen entry is the hash, so back, forward, and a shared link open the same pane. A hash that names no entry is given to the page's `match`, which names the entry that holds it, such as a conversation's anchor; otherwise the page's `fallback`, or the first entry, is shown. A hash that names a pane the page has not drawn yet chooses it once the entries arrive. A page whose entries are all links and labels does not follow the hash (`hashless`), so its `current` is the page's alone |
| Choosing from the page | The page binds `current`: setting it chooses an entry without changing the hash |
| Width | From Tailwind's `md` the list is a column `w-48` wide, `w-64` with a header, sticky at the top beside the content. Below `md` it is one row above the content that scrolls within itself, so the page never scrolls sideways |
| Keyboard | Every entry but a label is a link: Tab reaches it and Enter follows it |

A pane's id should not be an element id on the page, or following its link scrolls to that element.

## Writes (S-0075, ADR-0029)

Every write is a named method of flai on the host, asked over the channel; nothing runs in the container, and the image holds no `flai`, no `git`, and no `ssh`. flai validates the arguments as data, builds the command line itself, and runs the same command the CLI has, so its rules are the only rules ([ADR-0016](../adrs/0016-dashboard-delegates-to-flai.md), [ADR-0023](../adrs/0023-documents-are-saved-through-flai.md)). The previews, the diff, the statistics, and the pending push change nothing and are answered by `flai serve` from the code those commands print with, with the answer the command gave (S-0159). The mount is still given to the container and is no longer used; S-0077 removes it.

- **The routes** map a request body to a method and pass the answer through: `item.move` (and `item.move.preview` for a cancellation's dry run), `item.order`, since S-0343 `board.archive`, `item.block`, `item.unblock`, `item.new`, `item.template`, `accept.preview`, `accept.run`, `stream.diff`, since S-0388 `stream.restore`, `stream.log`, `stream.answer`, since S-0198 `issue.list` and `issue.story`, `thread.new`, `thread.reply`, `thread.resolve`, `doc.show`, `doc.save` (each with an optional `story`, run in that story's worktree since S-0378), `doc.lint` (a read, answered in process), since S-0383 `file.get` and `file.save` for the design token file, `adr.new`, `adr.template`, `adr.accept`, `stats.get`, since S-0087 `publish.preview`, `publish.run` (`push.pending` and `push.run` until S-0195), since S-0399 `queue.add`, `queue.remove`, and `queue.hold` under the `merge-queue` host action, and since S-0081 `dashboard.status`, `dashboard.check`, `dashboard.restart`, `dashboard.upgrade`, `dashboard.stop`, and since S-0298 `dashboard.versions`. They name nobody: flai records a change as the manifest's owner, so a request cannot sign a move with another name (`by` in a body is ignored).
- **`Repo.write()`** adds a request ID and a 60 second limit (ten minutes for an acceptance). When the connection is lost before the answer and flai is back within five seconds, the same request is sent once more with the same ID, and flai answers from its journal if it had already done it. A detached write (a restart or upgrade, a checks run, an import) is recorded before it acts in `serve/requests.json`, which outlives flai serve, so a repeat that reaches the next serve after the write ended the one that took it is answered from that record, and a repeat while it runs is told it is under way (S-0109). The host panel still sends serve, all, and upgrade with `retry: false`, because it may be answered by a flai older than that record. `Repo.run()` is for what changes nothing (previews, templates, the diff, statistics, the pending push) and carries no ID. After a write everything asked before is forgotten.
- **Errors** keep their meaning: a workflow rule is 400 with flai's sentence, an argument that is not what it should be is 400, a document that changed since it was loaded is 409 with the current version and its hash, content the check refuses is 422 with the findings, a method the host's flai does not offer is 501 on every route (S-0378), no flai is 503, no answer in time is 504, and anything else flai reports is 500 with its message.
- **Acceptance** (`POST /api/items/:id/accept`) streams NDJSON as before. The steps arrive as `$/progress` notifications for the request while flai runs the acceptance, and the hub hands them to the route. When the connection is lost on the way the last line is an error that says the acceptance may have completed on the host and how to find out, because the dashboard cannot know.
- **A branch that undoes main's change (S-0388, [ADR-0155](../adrs/0155-a-rebased-story-branch-that-undoes-main-s-change-to-a-path-is-recorded-at-sync.md)).** Two writes resolve a path the review page shows as a card. `POST /api/items/:id/restore` `{ path }` is `stream.restore` with that one path. The accept route passes `keep_removals` on to `accept.run`, which records each reason in the story's Notes. Only the operator keeps a removal: flai refuses `keep_removals` with `by: orchestrator`, so the orchestrator never keeps one. Send back is no write of its own: the page asks `thread.new`, then `item.move`.
- **An older flai.** The image no longer brings a flai of its own commit, so the flai on the host can be older than the dashboard. flai names the methods it offers when it connects; the hub compares them with `REQUIRED_METHODS` (`doc.lint` among them since S-0378) and `/api/agent` reports what is missing as an error, which the banner shows on every page with the advice to upgrade flai. A Go test (`contract_test.go`) fails when that list and flai's table drift.
- **`/mcp`** is gone since S-0076: MCP is flai's on the host ([ADR-0030](../adrs/0030-mcp-is-served-by-flai-on-the-host-over-stdio-and-http-and-the-dashboard-s-api.md)), the bridge and its settings were removed, and the route answers 410 with where to go. With it went the last thing in the dashboard's server that started a process; a test keeps it so.
- **Agents started by flai (S-0079).** `GET /api/host-agent` is flai's `agent.status`, asked each time because the state lies on the host. No button on the notice acts on the agent. The dashboard cannot configure an agent. The starts it can ask for are `StoryAgent`'s **Retry** (S-0116, S-0118) and **Start agent** (S-0115): `POST /api/items/<id>/agent {action: 'restart' | 'start'}`, flai's `agent.restart` and `agent.start`, gated by the `agent` action. - **Each story's agent (S-0104, [ADR-0038](../adrs/0038-flai-serve-starts-a-story-s-own-agent-through-an-adapter-with-what-the-operator.md)).** `agent.status` carries `stories`: for each story flai started an agent for, its newest run and what it is doing, as `working`, `waiting` (running with a question of its own open on the story or the story blocked, ended asking, to be started again on the answer, or queued by a retry until there is room, S-0118, S-0243), `failed` with `why`, or `worked`. With the in-progress limit or review full (S-0243), flai queues the agent ([ADR-0044](../adrs/0044-a-retry-of-a-failed-agent-on-a-ready-story-with-the-in-progress-limit-full-is.md)). - **An agent's stream (S-0142).** The activity page asks `/api/host-agent` beside `/api/activity`, again on each change event and every 15 s while an agent runs, and hands every story's activity to `ActivityView.svelte`. A card whose story's run has `started` (a held story's stand-in has none) shows its dot, its activity line, and `AgentStream.svelte`: a `<details>`, opened when the agent is working or waiting and closed only by the reader (S-0178), holding a scrolled list of the entries flai reads from the agent's log (`agent.stream`, `$lib/activity.ts`'s `AgentStreamRead`). - **Editing a story or an epic (S-0085).** `GET /api/items/:id/edit` is flai's `item.show` (fields, the body below the heading, the hash, whether it may be edited and why not, the natures and the open parents it may be given). `PUT` is `item.edit`: `{ hash, title?, nature?, tags?, topics?, touches?, after?, parent?, agent?, cost_of_delay?, body? }`, only what is given is changed, a story's `agent` is replaced whole or, as `null`, removed (S-0103), and a story's `after` and a story's or epic's `topics` are replaced, or removed as `[]` (S-0130, S-0135); 409 `{ hash, current }` when the item changed after it was read, 422 `{ findings }` when the check refuses and nothing was changed, 400 for what is not allowed, 404 for an item or parent that is not there. `ItemEditor.svelte` sends only the fields that differ from what it loaded (for a story's agent, the four agent fields as one, `null` when all are emptied; for a story's or epic's cost of delay, in the same closed panel as `/new` labelled in the currency `item.show` gives, only the inputs that changed as text, an emptied one as `""`, which flai removes, so that clearing all three removes the inputs and leaves the planner's value, never sent, S-0204), keeps the text on a refusal, and on a conflict offers to load the current version or to save over it with the hash the conflict gave, which overwrites only the fields being sent. - **Pushing (S-0078, removed in S-0195).** The standing `UnpushedNotice` on the board and a done item's page, its **Push now** (`push.run`, `flai push --pending --publish`), and `/api/unpushed` were removed when publishing became the one way accepted work reaches the remote ([ADR-0067](../adrs/0067-accepted-work-reaches-the-remote-only-when-it-is-published-and-agents-publish.md)). - **Publishing (S-0087).** Acceptance stopped computing or applying a release; `GET /api/publish` (`publish.preview`) answers what publishing now would release, per component, and `push_enabled`, whether the push host action that gates it is on ([ADR-0032](../adrs/0032-accepting-a-story-merges-it-publishing-is-a-deliberate-batched-step-over.md)). `POST /api/publish` (`publish.run`) applies, tags, and pushes everything pending: 403 with what enables it while the push host action is off, 409 with the reason when the remote has moved. - **The host's settings (S-0105).** `GET /api/settings` is flai's `settings.get`. `POST /api/settings` with `{kind, ...params}` runs `settings.<kind>` for a `kind` in `SETTINGS_KINDS` (else 400) and passes flai's 403 through, with `enable` and `hostwide`. `shared` is `settings.shared`, `{action: add|remove, pattern}`, which flai runs as `flai shared add` or `remove --autocommit` and answers with `{added|removed, shared}`; a refused pattern is a rule error (S-0295). A `kind` in `SETTINGS_READS`, only `shared_check`, is no write: the route asks `settings.shared_check` with `{paths?, story?}` and no request ID or host action, as a read, and answers `{entries, warnings}`, each entry `{entry, path, shared, pattern?, story?}` as `flai shared check --json` gives it. For `dashboard_token` the route calls `setToken` with the token flai answered with (unless authentication is off) and sets the asking request's cookie to it: the rest of the sessions end, this one goes on without a restart. The answer carries the `login_url`, never the token alone. `manifest` is `settings.manifest`, `{set, unset}`, the strategic agents' settings (S-0229): its refusal keeps flai's `refused`, each `{field, reason}`, in the body beside `error`, 422 for flai's own refusal and 400 for a key or a value the host API refuses before it runs flai; 403 with `enable` while `settings` is off ([Strategic agents' settings](#strategic-agents-settings-s-0229)). `provider` is `settings.provider` (S-0359, [ADR-0129](../adrs/0129-a-story-s-agent-names-a-provider-beside-its-harness-and-model-and-the-providers.md)): `{name, api?, base_url?, key_env?, models?}`, which flai runs as `flai serve agent provider <name>` with a flag for each field given, an empty `models` leaving the aliases as they are, or `{name, reset: true}`, which removes the entry. It is host-wide (`HOSTWIDE`), as `harness` is, and flai's refusal of an entry is a rule error with flai's reason. It is in `REQUIRED_METHODS`. `settings.get`'s `host.agent.providers` gives each entry by name with its `api`, `base_url`, `key_env`, `models` (alias to name), and `key_set`: whether the variable `key_env` names is set and not empty in `flai serve`'s environment, never its value.
- **This project's sub-projects (S-0491).** `POST /api/settings` with `{kind: 'subproject', op, name, path?, subproject_kind?, tags?, new_name?}` runs `settings.subproject` ([dashboard-host-channel.md](dashboard-host-channel.md)), which runs `flai subproject add`, `set`, or `remove --autocommit` on the host, creating a folder the project lacks with a `README.md` and committing it with `system-flow.yaml`. `kind` names the setting, so the sub-project's own kind is sent as `subproject_kind` and the route passes it to flai as `kind`. `add` needs the kind, and a path left out is the name's; `set` sends only the keys that changed, `tags: []` removing them; `remove` sends the name alone. The answer is flai's `{action, project, from?, created?, written, commit?}` with `project`, the entry as written, renamed `subproject`, since every answer's `project` is this project's name and key (ADR-0024). It is per project, not `HOSTWIDE`: it needs `flai serve enable settings` for the project, else 403 with `enable`. A field the host API refuses is a 400 and flai's own refusal a 422, each with flai's message, which names each field and why, and, for a field, `refused`; the panel shows the message. The list is `project.info`'s `projects`, read through `GET /api/manifest`. `settings.subproject` is in `REQUIRED_METHODS` (`lib/server/agent.ts`), so a host flai without it is reported as too old, as for every other method there.
- **Managing the dashboard from its own page (S-0081).** `GET /api/dashboard` (`dashboard.status`) answers what the shared container is running and `dashboard_enabled`, the `dashboard` host action; `POST /api/dashboard` with `{action}` in `check`, `restart`, `upgrade`, `stop` — `check` is `dashboard.check`, a read that compares the configured release's verified digest list with what is running, pulling nothing for a flaiover release ([Verifying a dashboard release before it is run](flai-cli.md#verifying-a-dashboard-release-before-it-is-run)), and changes nothing; the other three gate on the `dashboard` action, the same 403 shape `publish.run` uses. Since S-0298 the action may also be `versions`, `dashboard.versions`, a read, and `upgrade` takes an optional `tag` ([Deploying a chosen release](#deploying-a-chosen-release-s-0298)). `HostPanel.svelte`, at `/host` (linked from the header's host flai badge), shows the running image, Check for updates and Versions, the reads, whatever the action says, and, once enabled, Restart, Upgrade, and Stop (S-0314). Restart always, a swapping upgrade, and a stop that is the last project stop the very container answering the request that asked for it: the client races each of those three fetches against a short timeout and treats a network error or that timeout as "proceeding", not a failure, then (restart and a swap) polls `GET /api/dashboard` until it answers again and reports whether the image changed, or (stop) says the container is gone, since there is nothing left to reconnect to. `check`, a no-op upgrade, and a refused write all behave like an ordinary route. An upgrade never stops the running container until a temporary one, started from the new image, has answered `/_health`; a failed upgrade is therefore an ordinary error, the running container untouched, not a partial state the page has to reconcile. Real Docker, not the fake-runner unit tests, found that the command backing these three writes was itself getting killed mid-run by the very connection death it causes (T-0325): `internal/hostapi`'s `spec.detachTimeout` runs them with a background context instead of the request's, so completing the swap no longer races its own cancellation.
- **The processes flai host keeps (S-0107).** `GET /api/host` answers flai's `host.status`: the host's pid and version, and its `children`, each `serve` or `mcp` with a `root`, a `state`, a `version`, and `restarts`. It also answers `host_enabled`, the `host` host action from `project.info`. No flai connected (503), or a serve that runs without a host, reads as `running: false` with the reason and not as an error. `POST /api/host` takes `{action, process}`. `check` is `host.check`, a read. `start`, `stop`, and `restart` of `serve`, `mcp`, or `all` are `host.process` with `{process, action}`, and `upgrade` is `host.upgrade`. Since S-0298 `versions` is `host.versions`, a read, and `upgrade` takes an optional `version` ([Deploying a chosen release](#deploying-a-chosen-release-s-0298)). All four writes gate on the `host` action; a bad action or process gets a 400. `HostProcesses.svelte`, on `/host` below `HostPanel`, shows one row for serve and one for the MCP servers as a group, because the host acts on them as one process. Each row has Start, Stop, and Restart, each disabled when it would do nothing, and the area has one Check for upgrade and one Upgrade. The dashboard reaches the host through serve, so a serve stop asks first and says only `flai host start serve` on the host brings serve back. A serve restart and an upgrade race their fetch against a short timeout, as `HostPanel` does, then poll `GET /api/host` until it answers and report the version that came back. The route sends those writes, and `host.process` for `serve` or `all`, with `retry: false` (`WriteOptions` in `$lib/server/repo.ts`). A lost connection is the expected outcome for them, and the serve that comes back has no record of the request: tried live, the usual one retry restarted serve a second time. The page takes the route's 502 for these writes as the work going ahead, not as a failure. It then waits for a new serve pid, or for a newer version after an upgrade, rather than taking the old process still answering.
- **The hosts the dashboard accepts (S-0489, [ADR-0193](../adrs/0193-the-dashboard-accepts-a-browser-origin-naming-one-of-the-hosts-in-dashboard.md)).** `POST /api/settings` with `{kind: 'dashboard_hosts', hosts}` runs `settings.dashboard_hosts`, which runs `flai config set dashboard.allowed_hosts <hosts>` on the host. `hosts` is host names, each with an optional port, separated by commas; an empty string clears the list. It is host-wide (`HOSTWIDE`), so it needs `flai serve enable settings --all-projects`. An entry that is not a host name is refused with flai's reason, a 400, and nothing is written. `HostAddresses.svelte`, the Addresses area on `/host` between `HostPanel` and `HostProcesses`, reads the configured list from `GET /api/settings` (`host.allowed_hosts`) and the list the running container was started with from `GET /api/dashboard` (`allowed_hosts`). It says in one line what the list is for: the address a request comes to is always accepted, and a tunnel's or a domain's host name is listed to reach the dashboard through it. While the settings action is on for every project it shows the list in a field with Save, and flai's refusal under the field. A save says that the running container keeps its old list until it is restarted, and points at Restart in the Dashboard area above, which the `dashboard` host action gives. While the action is off the area shows the list and the command that allows changing it, with no Save. When the two lists differ, the area says so.
- **A write on an item that is not there** answers 404 with flai's words, as a read does (S-0077). Until then it answered 500: the command runs as a process, its exit code for that is the generic one, and `outcome()` knew only mapped codes and `rule:`. It now recognises workitem's "<ID> not found", and a test takes the wording from the lookup itself so the two cannot drift apart.

### Deploying a chosen release (S-0298)

The Updates page lets the operator go back to an earlier release, or forward to any published one, for the dashboard and for flai on the host. What is published, what the dashboard may name, and why a chosen dashboard release is not pinned are decided in [ADR-0117](../adrs/0117-the-host-api-installs-a-release-the-dashboard-names-only-when-flai-lists-it-as.md); flai's side is in [Listing and installing a published release](flai-cli.md#listing-and-installing-a-published-release).

- **Versions.** The Dashboard area (`HostPanel.svelte`) and the flai host area (`HostProcesses.svelte`) each have a Versions control beside their check (Check for updates, Check for upgrade). It asks its route for `versions` (`dashboard.versions`, `host.versions`) and lists the published releases newest first, marking the running one and the newest, and for flai any release below a served project's `flai.minimum`, with a warning when one of those is chosen.
- **Not deployable.** A dashboard release that `flai dashboard versions --json` marks `unverifiable`, with no digest list the host's flai can verify, such as one from before signing, is shown as `not deployable:` with flai's `reason`, and has no Deploy (S-0236). flai would refuse it anyway: the host API passes `--published`, which refuses such a release before anything is pulled, and `flai dashboard` runs a flaiover release only by the digest its verified list names. The route passes the list through unchanged. The flai host area marks a release it cannot install `not installable` the same way.
- **Deploying one.** Choosing a release and confirming it posts `upgrade` with that `tag` to `/api/dashboard`, or with that `version` to `/api/host`. It goes as Upgrade does for the newest: the same host action (`dashboard`, `host`), the same confirmation, the same "Reconnecting…" handling of the connection the deploy drops, and the same report of what came back. The host API refuses a value that is not a bare `X.Y.Z`, and flai a release that is not published, naming the published ones, or, for the dashboard, one not deployable; either refusal is shown like any refused write.
- **Once, not pinned.** A dashboard release chosen here applies to that container, not the configuration. It keeps running through restarts until the next Upgrade, which goes to the configured tag, or a start after a stop ([ADR-0118](../adrs/0118-a-dashboard-release-chosen-on-the-updates-page-keeps-running-through-restarts.md)). The confirmation and the result say so, and the page has no control to pin one; pinning stays `flai config set dashboard.tag` on the host.

### Editing design tokens (S-0383)

The Design page's **Edit tokens** button turns on Edit mode: the operator changes tokens with the preview following, then saves through flai on main. It is option 1 of [Working on it together](design-system-tool.md#working-on-it-together). The preview stays on the left, sticky on a wide screen, beside one `TokenEditor.svelte` per namespace, in the token sheet's order: colours, font stacks, type scale, spacing, radii, then any other.

- **The edit model** is `$lib/design/tokens.ts`. An edit is a DTCG `$value` kept apart from the saved themes, keyed by theme and path (`editKey`). One set back to its saved value is dropped (`pruneEdits`). `editedThemes` applies the edits to `design.get`'s themes and renders each token as flai does (`renderToken`). An alias follows the token it names. A light edit reaches dark where the dark context does not override the token, as flai's resolver does ([ADR-0146](../adrs/0146-a-project-s-design-tokens-are-a-dtcg-file-the-manifest-names-beside-its.md)).
- **The fields.** A colour has a picker and a text field per theme, `#rrggbb` or `oklch(L C H)` with an optional alpha ([ADR-0148](../adrs/0148-a-design-token-s-colour-is-in-the-srgb-colour-space-with-its-hex-or-in-oklch.md)). A length has a number and a unit, `px` or `rem`. A type step has its font size as a length and its line height as a number or a length. A font family is its stack, comma separated. A token other than a colour has one field for both themes when they render alike. Shadows, aliases, and other types are read-only. Text flai would refuse (`valueProblem`) stays in its field, marked with the reason, and makes no edit. A changed token is marked and has **Reset**.
- **Following before saving.** The preview frame ([ADR-0149](../adrs/0149-the-design-page-previews-a-project-s-tokens-in-a-blank-same-origin-frame-it.md)), the token sheet, and the contrast are drawn from the edited themes. `rolePairs` in `$lib/design/preview.ts` works out each theme's role pairs as flai does, and a test holds it to flai's `show.json.golden`. A colour in a failing pair says so beside its field: the threshold, the other token, the theme, and the ratio.
- **Saving.** Edit mode reads the token file's raw text and hash from `GET /api/design/tokens`. Save writes each edit into that text with `composeTokenFile`: a light edit replaces the `$value` the light theme takes the token from; a dark edit replaces the dark context's, or adds one to the dark context's first source when it has none. Every other byte stays. A dark edit to a plain token file, which has no dark context, is refused before sending, with what to do. The text is sent to `PUT /api/design/tokens` with the hash and the optional "What changed" line. flai checks, saves, and commits it on main as it does a document ([ADR-0147](../adrs/0147-the-dashboard-reads-and-saves-a-text-file-that-is-not-markdown-through-file-get.md)), and the page reads the design system again.
- **The answers.** A 409 shows the diff, with **Load the current version** and **Save mine over it**, as the document editor has. Unlike the editor, loading the current version keeps each edit that still has a place in it, and says how many it dropped. A 422 lists flai's findings, such as `design.tokens`, with the edits kept. A 501 shows "This flai cannot save the token file yet; upgrade flai on the host.", keeps the edits, and turns Save off.
- **Not yet in flai.** flai's side of `file.get` and `file.save` is a later story under E-0020. Until it lands, every host flai answers 501: the page edits and previews, and cannot save. The save is tested against a stubbed host. The two methods are not in `REQUIRED_METHODS`, so a flai without them raises no banner.
- **Leaving.** **Discard changes** goes back to the saved tokens. **Done** leaves Edit mode, and is off while changes are unsaved. Leaving the page or the tab with unsaved changes asks first. A `document` change reads the saved tokens again and keeps the edits.
- **The kept draft (S-0441).** `$lib/design/draft.ts` keeps the unsaved edits in `localStorage` under `flaiover-design-draft:<project>`, so a reload keeps them ([ADR-0151](../adrs/0151-the-operator-and-agents-change-a-design-system-by-edits-on-the-design-page.md)). The draft is the edits that differ from the saved tokens (`pruneEdits`), written on each change (`saveDraft`); a save or a discard leaves none, which clears it. When the page loads and has saved tokens to edit, it prunes a kept draft against them, turns Edit mode on with it, and says "Your unsaved changes, kept in this browser, are restored: save or discard them." A draft that does not parse is dropped. `onDraft` follows the `storage` event, so a draft another tab writes, or the Components page drops, is taken up here. The draft is not a save: leaving with it still asks.

### Proposals and requests (S-0384)

Two sections below the guidance, for a project with a token file, carry choices 2 and 3 of [ADR-0151](../adrs/0151-the-operator-and-agents-change-a-design-system-by-edits-on-the-design-page.md): a change an agent proposes is a story's branch, and the operator asks for one by making a story. Nothing outside git holds a proposal ([Working on it together](design-system-tool.md#working-on-it-together)).

- **Proposals** lists `GET /api/design/proposals`: each story's ID, linked to its item, its title, its state, and which of the token file and the guidance it changes, with **Compare**. A 501 says "This flai cannot list the proposals yet; upgrade flai on the host." The list is read again on a `document` or an `item` change, so a story accepted or cancelled leaves it, and its comparison closes with it.
- **Compare** reads the story's design system from `GET /api/design?story=` and shows `ProposalCompare.svelte`: the gallery previewed with the main branch's tokens and with the proposal's, side by side, each in a `PreviewFrame` of its own, then a table per theme of the tokens that differ, each `changed`, `added`, or `removed`, with both values. `diffDesign` in `$lib/design/diff.ts` compares them: two tokens differ when their `css` or their custom properties differ, what the preview reads, so an alias made literal at the same value is no difference. The proposal's problems are listed, and a token file that is missing or does not parse says so rather than list every token removed. flai's refusal is shown in its words. **Compare** is off while editing tokens, and turning Edit mode on closes the comparison, because it shows saved tokens.
- **Accepted.** Accepting the story merges its branch, so the token file on main changes and the `document` change it makes reads the design system again: the proposal's tokens are the project's, with no step of the page's own.
- **Request a change** is `ProposeChange.svelte`: an open epic, a nature, a title, and the request in the operator's words. It posts to `POST /api/items` a story with topic `design`, the request as its goal, three fixed criteria (the tokens as asked; the stylesheet in step, `flai design css --write` run and no `design.stale`; the UI's tests passing), and the token file and, when `design.get` names one, the stylesheet in its touches. Then it moves the story to ready through `POST /api/items/:id/move`. The operator wrote it, so it is not a draft. A refused create keeps the words and lists flai's findings; a refused move leaves the story in backlog and says so.

### The Components page (S-0439)

`/design/components` renders the project's Svelte components live, each from its sub-project's own Vite dev server and the harness flai serves there ([ADR-0163](../adrs/0163-flai-runs-a-sub-project-s-own-vite-dev-server-on-127-0-0-1-behind-the.md), [component-library.md](component-library.md#the-dev-server-and-its-harness-s-0438)). The dev server listens on 127.0.0.1, and the page frames it directly, cross-origin, so the frame loads only in a browser on the host; the container never reaches it.

- **The page** is `routes/design/components/+page.svelte`. It reads `GET /api/components` on arrival, every minute, and on a `document` change. The minute's ask keeps the dev server from the idle stop and is what finds a component added or removed: flai serve watches only the manifest and the three folders, so a change under a sub-project sends no event. A failed read keeps what was shown. The pick and its props are kept in the URL as `?p=<sub-project>&c=<path>&props=<values>`, replaced in place (S-0440). `props` is the JSON of the props' values, base64url without padding (`toQuery`, `fromQuery`), and is left out when there are none. On arrival the URL's props are the picked component's when its `p` and `c` match, so a link opened in another tab renders the same. Picking another component drops the URL's props, the panel's edits, and the events. While any control's text does not parse, the URL is not written. The dev server's controls are for the picked sub-project, else the first supported one: **Start** and **Stop** post to `/api/components/start` and `/stop` and take the status they answer. A 403 shows the notice with the answer's `enable`, also shown while `status.enabled` is false; a 501 shows the upgrade notice in place of the page; any other refusal of a start or a stop is shown whole, then the page reads again for `last_error`. A server's `last_error` shows while nothing is running and no start error is shown.
- **The list** is `ComponentList.svelte`: each sub-project with its kind, its components grouped by the directory part of their path, the folders sorted, and one filter on name and path that hides the sub-projects without a match. An unsupported sub-project is listed with its kind and no components. A component whose props flai could not read is listed, marked, and can be picked.
- **The frame** is `ComponentFrame.svelte`, one per theme: one for Light or Dark, two side by side for Both. Its width is 375, 768, or 1280 px, or the panel's. Its `src` is `harnessUrl(url, location.origin, component)`, the server's `url` with `?origin=` and the first component as `?c=`, so the frame loads once per dev server; a later pick is a `select` and a theme change a `theme`, neither of which reloads it. Its height is the harness's `size` height rounded up, 160 px until the first, and its width the one chosen; the harness's height takes in its margin and a horizontal scroll bar (S-0449). The frame's border is its wrapper's, which clips nothing, so content wider than the frame scrolls on the frame's own scroll bars. The frame takes a `rendered`, an `error`, or an `event` only about the component it last sent a `select` for: one about another is a late answer to the pick before, and is dropped (S-0449). An `error` hides the frame, which stays loaded, and shows the message and `file:line:column` in its place; the next `rendered`, or another pick, clears it. A pick's `select` carries the component's props, its function props in `functions`, and its snippet props in `snippets`; a change of props alone is a `props` message with the same three, and props equal to those last sent are not sent again (S-0440). The required props without a value, which the page gives it as `missing`, hide the frame the same way, with "`<path>` needs a value for a, b." in its place; the props are still sent. Its `event`s are handed to the page.
- **The controls model** is `$lib/explorer/controls.ts` (S-0440, [component-library.md](component-library.md#controls-for-props-s-0440)). `controlFor` gives a prop's control by its kind, or none for a function. The page keeps each prop's control as text: `parse` reads it as a value, none, or an error, and `format` writes a value back. `initial` is a prop's default where the source writes it as a literal. Otherwise, for an array, object, or unknown prop, it is the catalogue's `skeleton`, the empty value of the prop's type (S-0449); a catalogue from an older flai has none, and the field starts empty. `toTexts` gives each prop's text from the URL's values or an example's, else from `initial`, and is the reset. `toValues` gives the props to send, those whose text parses to a value. `missing` says whether a required prop lacks one. A skeleton is a value like any other: it is sent, and a required prop that has one is not missing.
- **The props panel** is `PropsPanel.svelte`: each prop's name, `required`, its type as written or its kind, its default as written, and its control. Text that does not parse shows its error and "not sent"; a required prop without a value shows "Required: give it a value". **Reset** hands up the defaults and the skeletons. It holds no texts of its own: each change is handed up whole, and the page sends the props only once every text parses.
- **Examples (S-0443)** are `ExampleList.svelte`, above the props panel, keyed by the picked component so its state starts afresh with each pick ([component-library.md § On the page](component-library.md#on-the-page)). It lists the catalogue's `examples` for the component and marks the one chosen; choosing one hands it up, and the page's `chooseExample` sets the panel's texts from its props with `toTexts`, writes the URL, and sets the theme and the width when the example gives them. **Save as example**, shown only when the catalogue gives `examples_path`, asks for a name, says when it replaces an example of that name, and says the file and the branch the save goes to. `exampleFrom` builds the example from the panel's values, the theme when one is shown, and the width when one is picked, and the page's `saveExample` puts it to `PUT /api/components/examples` with the source's `story`. A 200 replaces the component's examples with the answer's; a failure shows flai's `error`, its `findings`, and for a 409 that the file changed meanwhile, and keeps the name and the panel.
- **The event log** is `EventLog.svelte`: the last 50 calls (`MAX_EVENTS`), newest first, each with the time the page took it, to the millisecond, the prop's name, and its arguments as JSON, and **Clear**. The panel and the log sit beside the frames from the `xl` breakpoint up, below them on smaller screens.
- **The protocol client** is `$lib/explorer/protocol.ts`, the page's side of [the protocol](component-library.md#the-protocol). `connect(frame, server, handlers)` takes a message only from the dev server's origin and from the frame's own window, with `source: 'flai-components'`, `version: 1`, and the fields its `type` requires (`harnessMessage`); it posts only to that origin. It keeps the last message of each kind and sends nothing before `ready`. On `ready`, and again on every later `ready`, since the harness reloads when a component is added or removed, it sends them in the order `theme`, `tokens`, `select`, `props`. A `select` drops the `props` kept for the component before it. `select` and `props` take `functions` and `snippets` (S-0440). `close` stops listening and sending.
- **Tried tokens (S-0441)** are the Design page's kept draft laid over the saved tokens ([component-library.md § Live tokens](component-library.md#live-tokens-s-0441)). The page reads the draft with `loadDraft` and follows it with `onDraft`. While it holds edits, the page reads `GET /api/design`, and `GET /api/design/tokens` for a resolver file, whose text says which tokens dark overrides; a plain file is read as `{}`, so a light edit reaches dark. It reads them again on a `document` change, which a save is, and forgets them with the draft. `editedThemes` lays the draft over the saved themes, and `stylesheetDeclarations` in `$lib/explorer/tokens.ts` gives the custom properties `flai design css --write` writes for them: every light one, for `:root`, and each dark one whose value differs, for `[data-theme='dark']` ([ADR-0159](../adrs/0159-the-generated-design-stylesheet-puts-the-dark-values-under-data-theme-dark-and.md)). A test holds it to flai's Tailwind golden. A name or value `unsafeVariable` refuses is left out. Each `ComponentFrame` is given them as `tokens` and sends a `tokens` message when they change, and an empty one once they are gone. While there are any, the page shows "Showing tried tokens: the Design page's unsaved edits, kept in this browser." with **Drop tried tokens**, which clears the draft (`clearDraft`). A failed read shows "Could not read the saved tokens to lay the tried ones over:" with why, and keeps what was last read.

#### Sources (S-0442)

The page reads the main checkout or a story's worktree ([component-library.md § Sources](component-library.md#sources)).

- **The picker** is `SourcePicker.svelte`: a select of Main and the stories in progress or in review, which `openStories` takes from `GET /api/board`'s two columns, stories only. A story the URL names that the board no longer lists is still offered, so the picker shows what the page reads. The choice is kept in the URL as `?story=S-nnnn`, Main as none, and stays when a component is picked. Choosing another source clears the catalogue and reads again.
- **The reads.** With a story, the page asks `GET /api/components?story=<id>` and posts `story` beside `project` to `/api/components/start` and `/stop`; the routes check the ID with `storyParam` and answer 400 for a malformed one before asking flai. The frame takes only the server whose `story` is the source's, so main's dev server is never framed for a story. An answer that arrives after the source changed is dropped.
- **What the branch changes.** The page reads `GET /api/items/<id>/diff`, flai's `stream.diff`, with each load. `$lib/explorer/changed.ts` gives the paths it changes (`diffPaths`, a rename's old path included), the catalogue's components among them (`changedComponents`, by `componentFile`, the file's path in the repository), and a list with those first (`changedFirst`). The picker lists them under "Changed on its branch", marked and pickable; `ComponentList.svelte` marks them and lists them first in their folder. A diff that cannot be read says so under the picker, and the catalogue still shows.
- **The review page.** `Review.svelte` reads `GET /api/components?story=<id>` for a story in progress or in review and, from the diff it already holds, names the components the branch changes under **Changes on the branch**, with **Open in Components** linking to `/design/components?story=<id>`. A branch that changes none, or a catalogue that cannot be read, shows nothing.

## Strategic agents' pages (S-0259, S-0228)

The Planner, Orchestrator, and Analyzer pages share one panel, `StrategicAgentPanel.svelte`, and one module, `$lib/strategic.ts`. Each page gives the panel its agent, its host action, and its runs. It adds what is its own through snippets: the action's state and controls, fields of the run under way, columns of the runs table, what a log entry shows besides its own, and sections before the log.

| Section | What it shows |
|---------|---------------|
| The host action | Whether it is on; while it is off, the command that turns it on, `flai serve enable <action>`. The page's controls follow |
| Running now | The newest run that has neither ended nor failed to start (`currentRun`): its agent, harness and model, start, and trigger, and its stream in `AgentStream.svelte` |
| Activity | The activity document, `wip/agents/<kind>.md`: its totals (accrued cost and time, activities, last run) and its entries newest first, each with its trigger, its items linked, its duration, and its cost |

It names the orchestrator's and the analyzer's runs, whose notifications carry `role: orchestrate` or `role: analyze` and no story or item, as `orchestrator` and `analyzer` (`ORCHESTRATOR` and `ANALYZER` in `$lib/server/agent.ts`). The Planner page also reads again on a work item change and every 15 s while a run goes. A reload that fails says so above what was last shown. ## Strategic agents' settings (S-0229)

The orchestrator's, the planner's, and the analyzer's settings in `system-flow.yaml` are edited on their own pages, the Orchestration, Planning, and Analysis pages of the rail's Agents group, while the `settings` host action is on for the project ([ADR-0101](../adrs/0101-with-the-settings-host-action-on-the-dashboard-edits-the-strategic-agents.md), refining [ADR-0039](../adrs/0039-a-settings-host-action-turned-on-only-in-a-shell-lets-the-dashboard-change-the.md)). Every save is `flai manifest set` on the host, so the dashboard writes no YAML and judges no value itself ([project-manifest.md](project-manifest.md)).

- **What the pages read.** `settings.get`'s `host.strategic` is `{editable, enable, settings}`: `editable`, whether `settings` is on for the project; `enable`, the command that turns it on; and `settings`, each key `flai manifest set` writes, in the catalog's order (`manifest.Settings`), with its `key`, `kind` (`boolean`, `choice`, `number`, `duration`, `cron`, `agent`, or `text`), `values` for a choice or a boolean, `default` as it would be written, `meaning`, `risk` for a permission, `whole` for a count, its `value` as the manifest has it, and `set`. A permission written `false` reads as unset, as it acts. The block is left out when the project cannot be opened, and a page then says so.
- **The panel.** `StrategicSettings.svelte`, told its block (`orchestration`, `planning`, or `analysis`), lists that block's keys, grouped under `permissions` and `release` for the orchestrator. Each key has an input by its kind: a switch for a boolean; a list of its values for a choice, with "default (…)" or "unset" first; a number field, whole for a count; a text field for a duration, a cron expression, or a text; and for an agent a harness, a model, and its config one `key=value` a line. Beside it are its meaning and, for a permission, its risk, and while it is unset its default, or "the project's agent". An agent's `roles` and `provider` are not shown and are kept as they are on a save.
- **Saving.** **Save** sends only the keys whose fields changed (`strategicChange` in `$lib/settings.ts`). An emptied field, or an agent with every field emptied, is sent in `unset`, so that its default applies; a boolean is sent as `true` or `false`, a number as a number, and the rest as typed. A number that is not one, or a config line that is not `key=value`, is said under its field without asking flai. A save flai takes says its commit, `saved in <hash>`, and the page reads the settings again.
- **A refusal.** flai's refusal, or the host API's, comes back with `refused`, each `{field, reason}`. The panel keeps what was typed, marks each refused field (`aria-invalid`), and says its reason under it. A reason about a key the panel does not show, such as a problem elsewhere in the manifest, which blocks every save because the manifest is checked whole, is said at the top of the panel with its field.
- **Read-only.** While `editable` is false every input and **Save** are disabled, and the panel says why: the `settings` host action is off for this project, so the dashboard may not change `system-flow.yaml`; on the host, in the project, the command `enable` names turns it on. A 403 on a save says the same with flai's `enable`.
- **Reading again.** A page reads `/api/settings` on arrival, after a save, and when a change to the project's manifest arrives, never on a timer, so that a read does not refill a form being typed in. The Agents page's Planning again section links to the Planner page and edits nothing.

## Runtime

- The image is built by `release-flaiover.yml` on an amd64 runner for both platforms, with QEMU for arm64 (S-0119). The Dockerfile's build stage runs on `$BUILDPLATFORM` for every target: the SvelteKit output and the production `node_modules` are plain JavaScript, so only the runtime stage's `apk add tini` runs emulated. A production dependency that ships a native binary would break the arm64 image and would need the build stage to run on the target platform instead. `flai dashboard` pulls the image for the Docker daemon's platform (`docker version`), not flai's own architecture, and pulls again when the image it has was built for another platform.
- Container listens on `3000`, named `flaiover` for every project on the host, not for one of them: `flai dashboard` starts it once and every later call, from any project, registers with the running one. It is published on the configured host port, default `4242`, on every interface by default (`dashboard.bind` or `--bind` restricts it, for example to `127.0.0.1`), and runs as the host user (`--user uid:gid`), so that it can read the two secret files, which are the host user's alone; the image must work as an arbitrary non-root UID: no privileged ports, no writes outside `/tmp`, and a writable working directory is not assumed.
- `flai dashboard` gives the container a published port and two secrets mounted read-only under `/run/secrets` (the login token and the agent credential), and nothing else: no project volume, no `PROJECT_DIR`, no git identity, excludes, or push key (S-0077, [ADR-0031](../adrs/0031-the-dashboard-s-container-holds-nothing-of-the-project-a-port-and-two-secrets.md), which supersedes ADR-0022, ADR-0026, and ADR-0027). Since S-0080 both secrets are per user, kept beside `flai serve`'s own state, not any one project's `.flai-cache`; every project registered with the same `flai serve` is handed the same two files ([ADR-0033](../adrs/0033-one-login-token-and-one-agent-credential-per-user-serve-every-project.md)). `PROJECT_DIR` remains only as how tests and development outside Docker name the directory that `testing.ts` asks flai about. `flai dashboard status` reads a running container's mounts, says when one was started by an older flai and still has a project mounted, and lists every project it currently serves.
- The image has a `HEALTHCHECK` that asks its own `/_health` every 15 seconds, so docker marks a container that stops answering unhealthy. `flai dashboard status` probes the published port itself and says running, not answering, or gone, with docker's verdict beside it. flai host restarts a dashboard that is gone or not answering, from the image reference `flai dashboard` recorded, with a back-off, unless `dashboard.no_restart` is set ([ADR-0062](../adrs/0062-flai-host-restarts-the-dashboard-container-flai-dashboard-recorded-when-it-is.md), S-0184); the container still runs `--rm`, with no docker restart policy.
- Everything the dashboard shows and everything it changes is asked of flai on the host (S-0073 to S-0075, below); the image holds no `flai`, `git`, or `ssh`, and `/_ready` is not ready without a connected flai.
- The scheme of a request (S-0083). adapter-node builds `event.url` from a protocol header and, when none is configured, assumes `https`. With none configured, `isSecure()` was always true, the session cookie was always `Secure`, and a browser kept it only on `http://localhost`: from any other plain-HTTP address a correct token led back to the login page. `server.js` now sets `PROTOCOL_HEADER` (default `x-forwarded-proto`) before it imports the handler, and `scheme.js` leaves every request with exactly `http` or `https` in that header: the first value a proxy sent when it is one of the two, else what the socket is (`encrypted`). Anything else is replaced, because adapter-node answers an odd value with an error per request. An operator's `ORIGIN` still overrides. The header is trusted from anyone on purpose: a client that lies about it only loses its own cookie. `scheme.js` lies beside `server.js`, outside the build, and is copied into the image with it; its test imports it from `src/lib/server/scheme.test.ts`. The login page asks for `/api/agent` after a successful login and says when the token was right and the cookie was not kept.
- The image's entry is `node server.js`, not `node build`: see the channel to flai on the host, below. `FLAIOVER_AGENT_KEY_FILE` names the agent credential `flai dashboard` mounts. `FLAIOVER_ALLOW_UNSIGNED=1`, which `flai dashboard` sets when it starts the container allowing unsigned builds, serves a flai with no release stamp (S-0239, below).
- File watching is flai's on the host (S-0073): its `change` notifications invalidate what was asked and the search index, and push updates to open tabs over the `/api/events` WebSocket.
- No authentication. It is a local tool bound to localhost by `flai`. Operators exposing it further are told not to in `docs/operators`.

### Times (S-0329)

flai records and returns every time in UTC, `YYYY-MM-DDTHH:MM:SSZ`, and the dashboard shows each in the browser's zone through `src/lib/localtime.ts`: `localTime` to the minute with the zone's short name (`2026-10-07 15:35 EDT`), `localDate` as the date there, and `localTimes` for each time inside a text flai wrote, which `DismissibleNotice.svelte` applies to every notice. No component formats a time of its own. What goes back to the API, and keys and comparisons, stay UTC; a document's text and front matter show as written. The charts keep flai's buckets, per UTC day and per UTC week from Monday ([metrics.md](metrics.md), [ADR-0056](../adrs/0056-time-in-state-is-one-stacked-bar-per-day-of-the-window-the-mean-hours-per-state.md)), and set no `useUTC`: `place` in `charts.ts` draws a day or a week at the local midnight of its own date, so its mark sits on that date's tick in any zone, an hour at its moment, and `bucketLabel` names an hour in local time and a day or a week by its date. The tests run in `America/New_York` (`vite.config.ts`), so a time shown in UTC fails them.

## What the container can reach (S-0077, [ADR-0031](../adrs/0031-the-dashboard-s-container-holds-nothing-of-the-project-a-port-and-two-secrets.md))

Nothing of the project. While the clone was mounted (ADR-0022) a process in the container could leave something git would later run on the host as the operator (I-0022); S-0064 closed the routes git itself offers with read-only mounts (ADR-0027) and left three open by necessity: refs and the index, tracked files, and ignored files the host executes. S-0077 removed the mount, and with it every one of those routes, closed and open alike. Tried from inside a container started the new way: see the story's narrative.

| Within the container's reach | What it allows |
|------------------------------|----------------|
| Its published port and the network | Serving the dashboard |
| `/run/secrets/flaiover_token`, read-only | Checking a login; a compromised container could present it, which gains it nothing it lacks |
| `/run/secrets/flaiover_agent_key`, read-only | Proving itself to `flai serve`, and so asking for the channel's named methods |
| The channel's methods (`internal/hostapi`) | Reads of Markdown under the manifest's three folders and the manifest; moves, blocks, saves, thread entries, new items, and the acceptance of a story in review, each validated and performed by flai on the host. No command line, no path outside those folders, no git |
| `/tmp` | Its only writable place; gone with the container |
| `/app/LICENSE.md`, copied in at build (S-0231) | Showing the license the image is distributed under on Host › License; the dashboard's own file, nothing of the project |

## Workbench (E-0006)

The dashboard becomes the designer's workbench: authenticated (ADR-0018), able to edit documents and commit through flai, host threads anchored to documents and items (ADR-0020), show who is working on what (`touches`, ADR-0019), review and accept stories, and expose `flai mcp` over HTTP for remote agents.

- Authentication: one login token per user, shared by every project the container serves, kept beside `flai serve`'s own state and mounted read-only (S-0080, [ADR-0033](../adrs/0033-one-login-token-and-one-agent-credential-per-user-serve-every-project.md)); `Authorization: Bearer` primary, HttpOnly cookie set by `/login` from a URL fragment; `/_health` and `/_ready` open; `/metrics` behind the token unless `FLAIOVER_METRICS_PUBLIC=true`.
- Editing: body editable, flai-owned front matter read-only, save validated by `flai check`, committed on `main` with the designer as author, content-hash conflict detection.
- The editor over any page (S-0378, [ADR-0145](../adrs/0145-a-dashboard-save-may-name-a-story-and-is-then-committed-on-that-story-s-branch.md)): `EditorDialog.svelte`, mounted once in the layout, holds `DocEditor.svelte` over the current page. `openEditor({ path, line, story, onsaved })` in `$lib/editor.svelte.ts` opens a file with the caret on its line, and with a story reads and saves it on `story/S-nnnn`; the editor then says `saves on branch story/S-nnnn`. It asks before replacing or closing a document with unsaved changes. `/edit/<path>?line=&story=` opens the same in a tab of its own.
  - Where it opens from: `$lib/filelinks.ts` and `addEditControls` in `$lib/markdown.ts` put a pencil control beside each rendered link to a markdown file and each code span naming a design, docs, or wip markdown path as `path`, `path:line`, or `path:line:column`; the link itself still opens the rendered document. Pages, thread entries, their anchors and Source links, and the analyzer's reports get them, and refusal text on the board, the item page, and the review page links the files it names. No control for what flai gives mode `none` by path: `wip/archive/`, `wip/threads/`, `design/issues/`, and `wip/agents/index.md`. On the page of a story in progress or in review, files named in its body and threads open on its branch. A wip file always opens on the main checkout ([ADR-0019](../adrs/0019-story-branches-and-touches.md)).
  - Live lint: on load and after each 400 ms pause in typing the editor posts the content to `/api/docs/lint` and lists each finding as its line, `rule/alias`, and message; a click puts the caret on the line. A note says these are flai's subset of the rules and the markdown tier decides at acceptance. When the host's flai has no `doc.lint` (501) the list is left out.
- Threads: `wip/threads/*.md` rendered beside their anchor, each entry as markdown with the explorer's renderer and relative links resolved from the repository root (S-0126); the operator's entries on the right in the primary tint and agents' on the left in the neutral one, each naming its author and time (S-0127); one thread at a time, with a pager `← n of m →` beside the Threads heading and again under the thread, whose Left and Right keys page while one of its arrows has focus (S-0153), a thread of more than two entries showing its last two with a per-thread toggle for the earlier ones (S-0153, TH-0035), the thread being read held by ID across reloads, the one in its place shown when it is resolved away, and a thread just opened shown (S-0133); a recommendation marked as one, its source a link to the document and heading, and, under a thread whose recommendation is pending, **Confirm** on a writable dashboard, which makes it the answer (ADR-0090); posting writes through `flai thread`.
- Review: branch diff against `main`, criteria, narrative, threads, `flai accept` and send-back. An acceptance refused for markdown the fix left ([ADR-0140](../adrs/0140-flai-accept-refuses-an-acceptance-whose-files-a-tier-with-a-fix-command-still.md)) carries its findings in the stream's error `data`, and `Review.svelte` lists them: each `file:line` opens the editor at the line, on the story's branch for a finding whose `checkout` is `story` and on the main checkout otherwise, with `rule/alias` and the message, and is marked saved once a save succeeds. Accept is enabled again when every listed file the editor can open has been saved, without a reload (S-0378).
- Presence and inbox: derived from `wip/agents` and threads; optional notifications.
- Hub readiness: every `/api/*` response carries `project: { name, key }`. MCP was served at `/mcp` until S-0076 and is flai's on the host since ([ADR-0030](../adrs/0030-mcp-is-served-by-flai-on-the-host-over-stdio-and-http-and-the-dashboard-s-api.md)); how a dashboard and a host reach each other was decided by ADR-0029.

## Project identity in responses

Every `/api/*` response names the project it came from (ADR-0024, S-0043; carried forward by [ADR-0030](../adrs/0030-mcp-is-served-by-flai-on-the-host-over-stdio-and-http-and-the-dashboard-s-api.md), under which `flai mcp` over HTTP sends the same two headers): JSON object bodies carry `project: { name, key }` from `system-flow.yaml`, and every response, arrays, streams, and errors included, carries `X-Flai-Project-Key` and `X-Flai-Project-Name` (URI-encoded). List endpoints that answer with an array (`/api/items`, `/api/threads`, `/api/docs/tree`, `/api/docs/adrs`) keep their shape and are identified by the headers. `flai check` warns when the manifest has no `key`.

## The channel to flai on the host (S-0072, ADR-0029)

The first step of reaching a project only through flai on the host: the channel exists, one method is asked over it, and the mount is unchanged.

- **The endpoint.** `/agent`, a WebSocket that `flai serve` opens. SvelteKit cannot upgrade a connection, so the image runs `flaiover/server.js`: adapter-node's `handler` on a plain `http.Server`, whose `upgrade` event goes to `globalThis.__flaioverAgentUpgrade`, set by the server's `init` hook (`exposeAgentUpgrade` in `$lib/server/agent.ts`). Since S-0454 it is a router by path for the two upgrades: `/api/events`, the live events of a page ([ADR-0182](../adrs/0182-the-dashboard-s-live-events-reach-the-browser-over-a-websocket.md)), ahead of the registry, and every other path to the registry, which answers `/agent`. A Vite plugin in `vite.config.ts` hands the same two paths to it in the development server and leaves Vite's own upgrades alone. On SIGTERM `server.js` closes idle connections and, through the router, every live-events socket with 1001 at once, and closes every connection `SHUTDOWN_TIMEOUT` seconds later (default 5), so that an open socket or stream cannot keep a server that no longer listens alive (I-0025). A proxy in front of the dashboard must pass WebSocket upgrades on `/api/events` as it does on `/agent`.
- **The hub.** `AgentHub` in `$lib/server/agent.ts`, one per process, reads the credential once from `FLAIOVER_AGENT_KEY_FILE`. It refuses any path but `/agent` (404), any request with an `Origin` (403), everything when it has no credential (503), and a fifth unproven socket (429). The handshake: flai's `hello` (protocol 1, its nonce, its version, the project), the hub's answer (its nonce, `HMAC(key, "dashboard|c|s")`, its version), flai's `hello.prove` (`HMAC(key, "flai|s|c")`), compared in constant time, within five seconds, or the socket is closed (4401 not proven, 4408 timed out, 4400 malformed). A newer proven connection for a project that has one is judged first ([ADR-0063](../adrs/0063-the-dashboard-refuses-a-second-flai-for-a-project-with-close-code-4409-while.md), S-0184): the hub pings the one it has, and while that answers within two seconds (`probeMs`) the newcomer is closed with 4409 (`CLOSE_HELD`, "the project is held by a flai that answers"); a holder that does not answer, or has closed, is closed with 4000 and the newcomer adopted. Adoptions are judged one at a time, and what a newcomer sends while judged is handled once it is adopted. flai waits a minute before it dials again after 4409. Pings every 4 seconds; a missed pong terminates.
- **Release stamps (S-0237, [ADR-0070](../adrs/0070-releases-are-signed-with-a-cosign-key-pair-verified-before-they-are-installed.md)).** The handshake is protocol 2: flai's `hello` carries `release: {statement, signature}`, and the answer carries the dashboard's own from `helloStamp`, absent when the image holds none. `AgentRegistry` checks flai's stamp with `verifyPeerStamp` for the component `flai` before it sends its nonce; a protocol 1 hello is read far enough to be refused as `missing stamp`. A stamp that fails is closed with 4403 (`CLOSE_UNSIGNED`) and `unsigned peer: <fault>`, logged once as the `warn` `host flai refused: unsigned peer`, and kept on the project's hub as `refused` (`{at, reason, flai}`) until a signed flai for it is adopted. A project known only from a refusal is kept too, at most eight of them, since `hello` names its project before any proof. The details are in [release-signing.md](release-signing.md#the-exchange-as-built-s-0237).
- **A refused flai on the page (S-0237).** While no flai is connected and one was refused, `/api/agent` answers the refusal with an `error` that names the flai's version (or "a flai"), the reason, and the commands that install a release of flai. `HostFlaiBanner.svelte` shows it under "This dashboard refused the flai on the host as unsigned, so the project cannot be shown.", and `HostFlai.svelte` shows "host flai: refused (unsigned)" with the error as its title, where an outdated flai shows its own. While a flai is connected no refusal is shown.
- **Unsigned allowed (S-0239, [release-signing.md](release-signing.md#the-development-case)).** `allowsUnsigned` in `$lib/server/release.ts` reads `FLAIOVER_ALLOW_UNSIGNED` once, when the registry is made, and allows only when it is exactly `1`. With it, `admitsPeerStamp` serves a flai whose stamp is `missing`; `invalid signature` and `wrong component` are closed with 4403 either way, and the credential is proven either way. `unsignedSides` gives the sides the allowance let through: `flai` when flai sent no stamp, `dashboard` when this image holds none. The connection keeps them as `unsigned`, `/api/agent` and `/api/projects` carry them, and the hub logs one `warn` per connection, `host flai connected unsigned`, with `project`, `flai`, and `unsigned`. `UnsignedBanner.svelte`, beside `HostFlaiBanner` in the layout on every page but `/login`, shows them for the picked project while it is connected, with no way to dismiss it: the heading `unsigned allowed: <sides>` (`unsignedLabel` in `$lib/project.svelte.ts`, the sides joined by "and"), "The flai on the host is a development build, with no release stamp." for `flai`, "This dashboard is a development build, with no release stamp." for `dashboard`, and then "The host lets it through on purpose, with `dashboard.allow_unsigned`; a release of flai with the published dashboard image needs no allowance and shows no banner." A signed pair shows nothing, with the variable set or not.
- **Asking.** `agent().ask(method, params, timeoutMs)` sends a JSON-RPC request with the connected project's key added to the params and resolves with the result. It rejects with `AgentError`: 503 when no flai is connected (the message names the commands that start one), 504 when the answer does not come in time (and sends `$/cancel`), 502 when flai answers with an error (its message and code kept) or goes away first. Messages are capped at 16 MiB.
- **Status.** `GET /api/agent` answers `{ configured, connected, since, flai, serves, info }`, where `info` is `project.info` asked over the channel with a two second limit, so connected means it answers; `error` replaces `info` when it does not. `HostFlai.svelte` in the header polls it every ten seconds: "host flai: connected", or "not connected" with the command in its tooltip; nothing when `configured` is false, which is a container started by an older flai.
- **Tests.** `agent.test.ts` runs the hub on a real HTTP server with a `ws` client as flai: the handshake, a wrong credential, an `Origin`, another path, no credential, a request in flight when flai goes, a timeout and its cancel, flai's error passed on, a newer flai refused while the holder answers, a holder that does not answer replaced, one that closed replaced at once, and a flai that stops answering pings.

## One dashboard for every project (S-0080)

One `flaiover` container, one login, one credential `flai serve` proves itself with, for every project on a host that serves more than one ([ADR-0033](../adrs/0033-one-login-token-and-one-agent-credential-per-user-serve-every-project.md)).

- **The container is named for what it is, not a project.** `flai dashboard` starts `flaiover` only when it is not already running; when it is, it registers the calling project with it and starts nothing. `flai dashboard stop` unregisters and only stops the container once no project is left registered.
- **The two secrets are per user, not per project**, kept beside `flai serve`'s own state; see Runtime, above.
- **`AgentRegistry`** (`$lib/server/agent.ts`) replaces the single `AgentHub` of S-0072: it performs the one shared-key handshake and then keeps a per-project `AgentHub`, chosen by the `project.key` each connection's `hello` names. `solo()` is the backward-compatible path: while exactly one project has ever connected, every request with no `?project=` is handed that one hub, so a single-project dashboard needs no configuration change at all.
- **flai still refuses a mismatch.** Every ordinary request repeats its project's key; flai's `Client.call()` compares it against the project that connection's `hello` named and refuses (`CodeUnknownProject`) a different one, unchanged since S-0072 and now exercised with two projects sharing one credential. Sharing a credential proves who flai is, not which project a connection may answer for.
- **Routing per request, server-side.** `hooks.server.ts` reads `?project=` from the URL and runs the rest of the request inside `withProject(key, ...)`, an `AsyncLocalStorage` that `repo()` and `agent()` read to pick the right project's cache and connection. No parameter falls back to `solo()` (agent) and a `defaultProjectKey` bucket (repo cache), so a single-project dashboard's URLs are unchanged.
- **Each `Repo` is bound to its own project (S-0095).** `repo()` makes a `Repo` for the key current when it is first asked for, and that `Repo` asks `agentFor(key)` at every call, so it answers for its own project even outside a request (the inbox webhook, a change handler). Its watcher listens at the registry, which re-emits every hub's `connected`, `gone`, and `change` with the project's key first, and keeps those that `concerns(key, from)`: its own project, or, for the default key, whichever project is the only one known when the event arrives. Before S-0095 a `Repo` bound to the hub `agent()` resolved when it started watching; the default `Repo`, watched at startup before any flai had connected, bound to `solo()`'s never-connected placeholder and heard nothing afterwards, and so did the inbox webhook's start-on-connect. `project-events.test.ts` holds both cases with real connections.
- **Every `Repo` watches from the moment `repo()` makes it (S-0117).** Until S-0117 only the default `Repo` was watched, by `hooks.server.ts` at startup, and `/api/events` and `/api/stats` watched the `Repo` of the project they were asked for; a `Repo` made for a request naming its project (`?project=sf`) that neither of those had reached kept its answers until the container restarted, so stories accepted and archived on another machine stayed in its done lane. `repo()` now calls `watch()` on each `Repo` it makes. `watch()` stays idempotent and does nothing for a `Repo` given its own source, as tests give. `project-events.test.ts` asks a named project's board, reports a removed story file from its flai, and asks again.
- **Repositories offered for import (S-0098, [ADR-0035](../adrs/0035-repositories-under-folders-the-operator-names-can-be-imported-from-the-board.md)).** A connection whose hello says `kind: candidate` is adopted as a candidate (`ConnInfo.candidate`, kept on the hub as `candidate` once it goes). Its missing methods are never counted, since it answers only the import methods by design. `list()` leaves it out once it is not connected: it was imported, or its folder is no longer named. `solo()` never counts it, so one project and several candidates still leave a request with no `?project=` meaning the project; the client likewise picks the one project when nothing is chosen. The switcher and the overview's project list show it as "(not imported)". The layout shows `ImportPrompt` in place of the page while the current project is a candidate. The prompt says what an import does and which tests it runs, then offers Import or Not now. Not now says to pick a different project, and is the prompt's own state, not remembered, so picking the repository again asks again. Import streams its steps and, once committed, waits for the project the repository became to connect and picks it. When a test failed it shows each failure's output and "not committed", with Open the project. While it shows what became of an import, `projectState.hold` keeps the candidate in the list after `flai serve` stops offering it. `/api/agent` does not ask a candidate for `project.info`, the host flai badge and banner say nothing on a candidate's page, and the inbox is not asked for one.
- **A project flai serve no longer serves (S-0121).** The notification `removed` on a hub's connection marks the hub `removed`; `list()` leaves a removed hub out while it is not connected, and `solo()` does not count it, so the switcher drops a project taken out with `flai serve project remove` or `flai dashboard stop` on its next refresh, with no restart. A project whose flai only went away (a restart of `flai serve`) is not removed and stays listed as not connected. `adopt()` clears the mark, so a project added again comes back.
- **Choosing a project, client-side.** `projectState` (`$lib/project.svelte.ts`) holds the known projects and the chosen one, remembered in `localStorage` and reflected in the URL; `api()` and every live-events WebSocket tag their path with it. Since S-0095 `ProjectSwitcher.svelte` always names the active project in the top bar, and since S-0102 it is always a `<select>`, even with one project: the projects, then an `<optgroup>` "Not imported yet" with the candidates (S-0098), and, with nothing connected, disabled and saying so. It was a plain label with one project, which left the operator with no control to switch or import with, and a pick switches every screen in place rather than reloading: `+layout.svelte` renders the page inside `{#key projectState.current}`, so the page remounts, its `onMount` asks again for the project picked, and the WebSocket its listeners opened closes with the last of them and opens again tagged for the new one; the header's badges outlive the page, so the layout restarts the inbox (`inboxState.restart()`, which also forgets the old project's entries so none of the new one's is announced as new) and re-asks the host flai status. Nav links carry `?project=`, so a copied link shows the same project, and the list is asked for again every 30 seconds and whenever the switcher gets focus, so a project whose flai connects later joins it without a reload.
- **Serving and removing projects from the Projects page (S-0122).** The Projects section of `SettingsPanel.svelte` shows `settings.get`'s `host.projects`: each served project with its key, name, root, and `health()` (connected since, the last error, why it is unavailable, or that `flai serve` is not running), and under "Below the import folders or the folder flai serve was started in, not served" each project `flai serve` does not serve, with why; one the operator removed has `removed: true` and says so (S-0123). Serve posts `serve` (`settings.serve`): on a removed project `flai serve project add` takes it off the list of removed projects and it is served from below again; on the others (no key, a key served already) it shows flai's refusal. On success it asks `projectState.refresh()` again every half second, up to thirty times, until the project is in the switcher and connected, then reads the settings again, every half second up to six times, until `flai serve`'s state, written once a second, says it is connected too. Remove is offered on every served project, asks first in place (saying no file is touched, and, where `below` is set, that it will be listed as removed and Serve brings it back, otherwise how to serve it again on the host), and posts `unserve`; it then asks the switcher again until the project has left it, and reads the settings again. `below` is set for every served project below a folder `flai serve` serves from, registered or not (`servedBelow`), since removing any of them lists it. A project served from below a folder also says which folder serves it (TH-0014, TH-0016). Each action is disabled, with the command that allows it, where the project's own `settings` is off. `ProjectSwitcher.svelte` labels a served project that is not connected "(served, not connected)", with `lastError` as the option's title, and while any project is not connected shows a link to `/settings/projects` (S-0459) saying how many; from a project that is itself not connected the link picks a connected one first, since the Projects page asks the current project's flai.
- **Signed, unsigned, or refused, per project (S-0237).** `GET /api/projects` gives each project `signed` while it is connected and `refused` (`{at, reason, flai}`) while its last flai was refused as unsigned, and lists a project whose only flai was refused, not connected. `ProjectSwitcher.svelte` labels a connected project "(signed)" or "(unsigned)" after its name, and a refused one "(refused: unsigned flai)" in place of "(served, not connected)". `refusalText` in `$lib/settings.ts` gives the option's title and its line in the "N not connected: why?" link's title, such as `Quay: refused: unsigned flai: missing stamp (flai 1.43.0)`. Since S-0239 a connected project whose connection the allowance let through carries `unsigned`, its sides, and the switcher labels it `(unsigned allowed: <sides>)` in place of `(signed)` or `(unsigned)`.
- **The root page** shows a list of every known project, each with a glance (`GET /api/projects`), while more than one is known and none is chosen; otherwise the single-project overview it always showed (T-0309, see Views above).
- **How the projects and their glances are loaded (S-0186, I-0033).** `projectState` is the one place a page asks `/api/projects`, and it keeps each answer whole, glances included (`review`, `threadsAwaiting`, `agentAttending` on each `Project`); the root page's list reads `projectState.list` and asks nothing of its own. So the list includes a repository being imported, which `projectState` keeps (S-0098), and its glances update with every refresh, not only on mount. `refresh()` returns the request already in flight when there is one, so callers that ask together share one answer: on a page load the layout (once signed in) and the root page (on mount, for fresh glances when it is reached by a link) ask in the same flush, and one request goes. A call made after that answer has come makes a new request. That covers the switcher getting focus, the 30-second look, and the Projects page and import prompt asking every half second until a project connects. Each answer gathers every connected project's glance on the 3 s timeout, so before S-0186 a slow project was paid for once per caller. `refresh()` gives up on a request after 15 s, so one that never answers does not hold every later call. It also asks with `cache: 'no-store'`. Measured in Chromium against a server answering after 1 s: three concurrent GETs of one URL took 1, 2, and 3 s, and the server never held more than one, because the HTTP cache lock sends a GET of a URL already in flight only once the first has answered. A `cache-control: no-store` on the response does not change that; `no-store` on the request makes the three take 1 s together. That lock, not the dashboard, was I-0033's "N concurrent calls take N × 3 s". The dashboard serves concurrent calls side by side. `hub.ask` sends at once and matches answers by id. flai answers each request on a goroutine of its own and locks only the socket's write. A route test pins it: three concurrent calls against a flai that takes 300 ms over each answer finish in under three times that. On flai's side, `board.get` reaches `release.PendingIDs`, which takes the process-wide release history lock. Publishing takes it too, but only while it reads local git history; `git ls-remote` runs before the lock is taken. So concurrent glances can wait on each other there only for local git reads.

## Where the data comes from (S-0073)

Everything the dashboard shows is asked of flai on the host over the channel: the project, work items, threads, and the board since S-0073, and documents, the ADR list, narratives and activity, the designer's inbox, and search since S-0074. flaiover's server reads no file of the project and parses none: no front matter parser, no YAML, no search library, no file watcher, no path guard of its own. `no-project-files.test.ts` fails when server code imports `node:fs` outside a short list with a reason for each entry (the two secrets handed to the container, the lookup of the flai binary that still performs writes until S-0075, and test support). The mount is still there for those writes only; with it removed by hand, every page that reads worked (tried, S-0074).

- **`Repo`** (`$lib/server/repo.ts`) takes an `Ask`, by default the hub's. `docsTree()` is `docs.tree` and `docFile()` is `doc.get`; flai decides what a document is (a Markdown file under the manifest's three folders, by its real location) and refuses the rest as a bad argument, which the route answers as 400. `search.ts`, `inbox.ts`, and `activity.ts` ask `search.query`, `adrs.list`, `inbox.designer`, and `activity.get`, and add only what is the dashboard's own: the route of a search hit, the link of an inbox entry (`hrefFor`), and an age counted from `updated` at the time of the request. `manifest()` is `project.info`, `items()` is `items.list` without bodies, by type and state, with the archive only when asked, each query kept on its own, and `itemCount()` is `items.count` (S-0162), `itemById()` is `item.get` with the body, `threads()` and `threadsFor()` are `threads.list`, `messages()` and `messagesFor()` are `messages.list` (S-0336), and `boardView()` is `board.get` with epics and tasks. Each answer is kept until flai says a file changed, and none is kept from a flai that has gone: the hub's `gone` forgets them, so a missing flai is a 503 and never yesterday's board. flai's refusals become the statuses the routes answer with: not found 404, a bad argument 400, no flai 503, no answer in time 504.
- **`board.ts`** maps flai's board view to the shape the page uses and counts a card's age from `entered_at`. The pull order and the columns are flai's; the TypeScript copy of the ordering rule is deleted.
- **Changes.** `flai serve` watches each project's design, docs, and wip folders and its manifest and sends `change` with the repository-relative path. The hub emits it, `Repo.changed()` forgets the answers that path affects and re-emits it with its kind, and the `/api/events` sockets, the search index, the stats and inbox caches, and the notifier listen as they did to chokidar, which is gone. A flai that connects is announced as a change to `system-flow.yaml`, so open pages look again by themselves. The inbox webhook starts when a flai first connects, because its address is in the manifest.
- **What a change forgets (S-0161).** `$lib/changes.ts` gives a path its kind against the manifest's layout, and `/api/events` sends it beside the path as `{ path, kind }`. The `Repo` forgets only the answers read from that kind, by a table of what each is read from in flai:

| Kind | Path | Forgets |
|------|------|---------|
| `project` | `system-flow.yaml` | everything |
| `item` | under `<wip>/kanban` (`board.md` included) or `<wip>/archive` | `board.get`, `items.list`, `items.count`, `item.get`, `stats.get`, `threads.list` (a thread's view names its story), `messages.list` (a conversation reads as closed once either story is done), `inbox.designer`, `activity.get`, `docs.tree` |
| `narrative` | under `<wip>/agents` | `inbox.designer`, `activity.get`, `docs.tree` |
| `thread` | under `<wip>/threads` | `threads.list`, `inbox.designer`, `docs.tree` |
| `adr` | under `<design>/adrs` | `adrs.list`, `docs.tree` |
| `document` | any other file under the three folders, a conversation under `<wip>/messages` among them | `docs.tree`, `messages.list` |
| `other` | anything else | everything |

`doc.get` of a file is forgotten by a change to that file alone, and `project.info` only by `project` and `other`. An answer the table does not name is forgotten by every change. Until the `Repo` has read the manifest, every path but the manifest is `other`, and the first change asks for the manifest so the next is told apart. A write through the dashboard still forgets everything. `repo-forget.test.ts` pins which paths forget which answers.

- **Without a flai.** `/api/manifest`, `/api/board`, `/api/items`, `/api/items/:id`, `/api/threads`, and whatever composes them answer 503 with "no host flai is connected; run flai dashboard in the project, or flai serve start"; `/_ready` has a `host_flai` check and is not ready. `HostFlaiBanner.svelte` under the header says on every page what is missing and the commands that bring it back, and tells a container started by an older flai apart; it and the header badge share `$lib/hostflai.svelte.ts`, which looks every three seconds while flai is away and every ten while it is there.
- **Tests.** `flaiAsk(root)` in `$lib/server/testing.ts` answers a `Repo` by running `flai hostapi` from this tree on a fixture folder, so the tests read what the dashboard will be served, by the same code; `useRepo()` swaps the process-wide `Repo` for route tests. `repo-channel.test.ts` covers the keeping and forgetting (`repo-forget.test.ts` what each kind of change forgets), the item shape, the statuses, and the board mapping with a fake `Ask`.
- **Measured** on a copy of this repository (350 items, 428 Markdown files under wip), the published 0.19.1 image reading the mount against this story's image asking flai, thirty requests each after the first:

| Request | 0.19.1, mount: first, then median | S-0073, channel: first, then median |
|---------|-----------------------------------|-------------------------------------|
| `/api/board` | 56 ms, 41 ms | 81 ms, 2 ms |
| `/api/items/S-0070` | 40 ms, 39 ms | 59 ms, 2 ms |
| `/api/items` (217 KiB) | 41 ms, 41 ms | 69 ms, 5 ms |
| `/api/threads?all=1` | 7 ms, 5 ms | 14 ms, 2 ms |
| `/api/manifest` | 3 ms, 2 ms | 5 ms, 2 ms |

The first request after a change costs more, because flai reads every item file again and the answer crosses the channel; every request after it costs a twentieth of what it did, because the mount was stat-ed file by file on every request. A move made on the host reached an open page's live events in about half a second (the watcher's 300 ms look plus one tick of debounce).

## Hub shape

Sketched here, then built differently by S-0080 (above): ADR-0024's hub is superseded by [ADR-0030](../adrs/0030-mcp-is-served-by-flai-on-the-host-over-stdio-and-http-and-the-dashboard-s-api.md), and [ADR-0029](../adrs/0029-the-dashboard-reaches-a-project-only-through-flai-on-the-host.md) has flai dial the dashboard rather than the reverse. What follows is the sketch as it stood before either story, kept for its identity ideas: a hub fronts several projects for one designer, each project's flaiover dialling out over a websocket and the hub routing a request to a connection by project key. The direction did not survive (flai dials out, not the dashboard's projects), but the identity model mostly did: `project: { name, key }` in every response, and a hub (`AgentRegistry`) that routes by the key a connection names — one credential per user, though, not one bearer token per project.
