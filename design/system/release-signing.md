# Signing releases and verifying the peer

The finding of S-0193, for E-0015. The operator asked that the dashboard and the CLI be signed in CI with a private key, that the CLI verify a release with the public key before it installs it, and that each component use the same mechanism to refuse the other when it is not a signed release: flai closes its connection to an unsigned flaiover, and flaiover closes the connection from an unsigned flai. This document says how the two are released, upgraded, and connected today, what can be signed and how it can be verified, what a running process can and cannot prove about itself to a peer, and ends with one recommendation. Nothing here is built. The decision and the stories that follow are at the end.

Every statement about this repository comes from its files, read on 2026-10-02. Nothing was tried on this host, and no page was fetched when S-0193 wrote this: what it said about GoReleaser, cosign, minisign, GPG, Sigstore, and GitHub's attestations was from their documentation as the author knew it, and the story that adopts a tool checks it against the tool's current documentation first. Where a claim matters to the choice and could be wrong, it is marked **to check**. S-0232 checked every claim in [Signing releases](#signing-releases) about cosign, GoReleaser, and GitHub's attestations and environments on 2026-10-07, against cosign v3.1.3 and v2.6.5 (their source and `doc/`), sigstore/cosign-installer v4.1.2, GoReleaser v2.18.2 (its `signs` documentation and source), actions/attest and actions/attest-build-provenance v4.2.2, and docs.github.com; each finding names its source, and nothing was run. The claims about minisign and GPG were not checked and stand as S-0193 wrote them, their **to check** marks with them. S-0234 checked on this host on 2026-10-12 which digest Docker records for a pulled image, and read what Docker's classic image store records in moby's source; [The digest list](#the-digest-list) says which was seen and which was read.

## Today

### How flai is released

- `release-flai.yml` runs GoReleaser on a tag `flai/v*` with `--clean --skip=validate`, under `permissions: contents: write`, and publishes to the GitHub release of `bytepunx/system-flow` named `flai vX.Y.Z`.
- `flai/.goreleaser.yaml` builds `flai` for linux, darwin, and windows on amd64 and arm64 with `CGO_ENABLED=0`, `-trimpath`, and `-s -w`, and sets `buildinfo.Version`, `Commit`, and `Date` by `ldflags`. It archives each build as `flai_<version>_<os>_<arch>.tar.gz` (`.zip` on windows) and writes `checksums.txt`, SHA-256 of every archive. When this was written it had no `signs`, no `sboms`, and no `docker_signs` section, and nothing was signed. Since S-0232 its `signs` section signs `checksums.txt` into `checksums.txt.sig`, and the release publishes the key's public half as `cosign.pub`.
- `flai version` prints the three build values and the Go version; a build without `ldflags` falls back to `debug.ReadBuildInfo` for the commit (`flai/internal/buildinfo/buildinfo.go`). A build from this tree by `scripts/flai.sh` has no version.

### How flaiover is released

- `release-flaiover.yml` runs on a tag `flaiover/v*` and on every push to `main` that touches `flaiover/`, `flai/`, or itself, under `permissions: contents: read, packages: write`. It builds `flaiover/Dockerfile` with buildx for linux/amd64 and linux/arm64 and pushes to `ghcr.io/bytepunx/flaiover` with the tags `docker/metadata-action` gives it: `latest` on `main`, the version and its major on a tag, and `sha-<short>` always. It uses `docker/build-push-action` with its default `provenance`, so the registry holds a buildx provenance attestation it never asks anyone to check; there is no cosign step and no `actions/attest-build-provenance`.
- The image gets `FLAIOVER_VERSION` and `FLAIOVER_COMMIT` as build arguments from the newest `flaiover/v*` tag and the commit, kept as environment variables of the running container, and reports them as `flaiover_build_info` on `/metrics` (`flaiover/src/lib/server/metrics.ts`). The image carries no flai, no git, and nothing of any project ([ADR-0031](../adrs/0031-the-dashboard-s-container-holds-nothing-of-the-project-a-port-and-two-secrets.md)).
- An image built on this host with `flai dashboard --build` or `make flaiover-image` is `flaiover:local`, with the same build arguments taken from the newest tags (`flai/cmd/dashboard.go`).

### How the template is released

The template is a git repository, `bytepunx/system-flow-template`, versioned by `template/template.yaml`; `flai new` and `flai upgrade` clone it and record what they rendered in the lock file ([ADR-0015](../adrs/0015-template-lock-file.md)). It is not part of this finding: a clone over SSH or HTTPS to GitHub is authenticated by the transport, and nothing of it is executed.

### How a release is verified before it is installed

Since S-0233, a flai release is installed only when its `checksums.txt` was signed by the release key ([ADR-0070](../adrs/0070-releases-are-signed-with-a-cosign-key-pair-verified-before-they-are-installed.md)). The code, its refusals, and the version lists are described in [flai-cli.md](flai-cli.md#verifying-a-release-before-it-is-installed); what each refusal means to the operator is in [the flai guide](../../docs/users/flai.md#what-an-upgrade-verifies).

- `flai self-upgrade` (`flai/cmd/selfupgrade.go`, `flai/internal/selfupgrade`) lists the releases through the GitHub API (`FLAI_RELEASES_API`, default `https://api.github.com`), takes the newest `flai/v*` that is neither a draft nor a pre-release, or the one `--version` names, and downloads `checksums.txt` and `checksums.txt.sig` as release assets. It verifies the signature with `crypto/ecdsa` against the public key embedded in the binary (`flai/internal/buildinfo/cosign.pub`), before it downloads anything else. Then it downloads the archive for its platform, checks its SHA-256 against the line in `checksums.txt`, and replaces the binary atomically: a temporary file beside the target, mode 0755, then a rename, with the old binary moved aside on windows. A token from `GITHUB_TOKEN`, `GH_TOKEN`, or `gh auth token` is sent when the repository is private.
- A release it cannot verify is refused, naming it and why: it has no signature, its signature does not verify, or it is signed by a key the binary does not know. For the last, it names the newest published release the binary can verify, to install first. The key is never taken from the release: the release's own `cosign.pub` is read only to tell an unknown key from a bad signature.
- `install.sh` does the same from a shell, with `curl`, `openssl`, and `sha256sum` or `shasum`, into `FLAI_INSTALL_DIR`, default `~/.flai/bin`. It carries the public key as a PEM string, verifies with `openssl dgst -sha256 -verify` after decoding the signature with `openssl base64 -d -A`, and refuses when `openssl` is absent, the release has no signature, or the signature does not verify.
- `flai host upgrade` runs the same upgrade for the host's flai, with the key in the host's flai, and restarts `flai serve` and the MCP servers on it (`flai/cmd/host.go`). A refusal restarts nothing.
- `flai self-upgrade --list`, `flai host versions`, and the dashboard's Updates page mark each release the installing flai cannot verify, and the page offers no way to install it. The lists may answer from a cache of each release's verdict, kept under `cache_dir` and checked again when the release's assets or the trusted keys change (S-0379, [The verdict cache](flai-cli.md#verifying-a-release-before-it-is-installed)). An install never reads it: it verifies from the network every time.
- The signature proves that `checksums.txt`, and through its hashes the archive, is what the holder of the release key published. Whoever can write the release's assets without the key, a holder of a token with `contents: write` or a workflow that runs with it outside the `release` environment, can no longer substitute a release that installs. It proves nothing about who holds the key ([Keys](#keys)).
- The first signed release is flai 1.42.0; every release before it has no signature and is refused, so `--version` cannot go back past it. The check itself came in a later release. A flai without the check installs any release unchecked, the one that brings the check included; every upgrade made by a flai that carries the check is verified.

### How the dashboard's image is chosen and run

Since S-0236, the flaiover image is run only by a digest that a release's signed digest list names ([ADR-0070](../adrs/0070-releases-are-signed-with-a-cosign-key-pair-verified-before-they-are-installed.md)). The code and its refusals are described in [flai-cli.md](flai-cli.md#verifying-a-dashboard-release-before-it-is-run); what each refusal means to the operator is in [the flai guide](../../docs/users/flai.md#what-the-dashboard-verifies).

- `flai dashboard` takes the image and tag from its flags, then the project's `system-flow.yaml`, then the host's configuration (`dashboard.image`, default `ghcr.io/bytepunx/flaiover`; `dashboard.tag`, default `latest`), and starts one container named `flaiover` for every project on the host ([ADR-0033](../adrs/0033-one-login-token-and-one-agent-credential-per-user-serve-every-project.md)).
- For `ghcr.io/bytepunx/flaiover`, the tag names a flaiover release: `latest` is the newest published GitHub release tagged `flaiover/vX.Y.Z`, not the registry's `latest`, and `X.Y.Z` is that release. flai finds it through the release client `self-upgrade` uses, downloads `flaiover_X.Y.Z.digests` and its `.sig`, and verifies the signature with the key embedded in the binary, telling an unknown key from a bad signature by the release's own `cosign.pub`, which it never trusts. It pulls and runs `ghcr.io/bytepunx/flaiover@sha256:…`, the list's index digest, so Docker's content check completes the chain. Any other tag, a release with no list, a list that does not verify, is malformed, is for another version, or names another repository is refused, and nothing is pulled or started.
- Each verified list is kept with its signature under `flai serve`'s state, `dashboard-digests/<version>.digests`, and verified again whenever it is read. When the releases cannot be reached, the kept list of the release is used, and the command says so. `flai dashboard status` matches the running image's `RepoDigests` against the kept lists and shows its digest and release, or that it is unsigned. Since S-0238 `flai serve` matches them the same way before every dial, and `flai dashboard status` shows its verdict too ([flai measures the container before it dials](#flai-measures-the-container-before-it-dials)).
- `flai dashboard check` compares the running image's `RepoDigests` with the release's list and pulls nothing. `flai dashboard upgrade` resolves before it pulls anything, then pulls by digest, starts the new image beside the old one, waits for it to answer `/_health`, and only then swaps. The restart record keeps the reference by digest, so `flai dashboard restart` and `flai host`'s watch start the same release again ([ADR-0062](../adrs/0062-flai-host-restarts-the-dashboard-container-flai-dashboard-recorded-when-it-is.md), [ADR-0118](../adrs/0118-a-dashboard-release-chosen-on-the-updates-page-keeps-running-through-restarts.md)).
- `flai dashboard versions` and the Updates page mark each release with no list this flai can verify as not deployable, and `flai dashboard upgrade --published` refuses it.
- `flai dashboard --build` builds `flaiover:local` from this monorepo and runs that; it is how this repository runs its own dashboard. `--image` naming another repository runs its tag as given. `flai dashboard` reports both unsigned and still runs them. Since S-0238 `flai serve` does not dial them ([flai measures the container before it dials](#flai-measures-the-container-before-it-dials)), unless `dashboard.allow_unsigned` is in force for the project, since S-0239 ([The development case](#the-development-case)).

### How the two authenticate each other on the channel

- flai dials the dashboard; the dashboard never dials the host ([ADR-0029](../adrs/0029-the-dashboard-reaches-a-project-only-through-flai-on-the-host.md)). `flai serve` opens one WebSocket per registered project to `/agent` on the container's published port and speaks JSON-RPC 2.0 over it (`flai/internal/channel/channel.go`, `flaiover/src/lib/server/agent.ts`).
- Both sides hold one agent credential, a random secret `flai dashboard` generates once per user and keeps beside `flai serve`'s state, and gives the container as a file under `/run/secrets`, mode 0600, read-only ([ADR-0031](../adrs/0031-the-dashboard-s-container-holds-nothing-of-the-project-a-port-and-two-secrets.md), [ADR-0033](../adrs/0033-one-login-token-and-one-agent-credential-per-user-serve-every-project.md)). The credential never crosses the connection. The handshake is `hello`, in which flai sends the protocol number, a nonce, its version (`flai`), the project, the methods it serves, and its kind; the dashboard answers with its own nonce, its version (`dashboard`), and an HMAC-SHA256 over its role and both nonces keyed with the credential; flai checks it and sends `hello.prove`, the same construction for its role, which the dashboard checks. A wrong proof is closed with `4401`, a malformed hello with `4400`, a slow one with `4408`; a second flai for a project a connected one still answers for is closed with `4409` and backs off ([ADR-0063](../adrs/0063-the-dashboard-refuses-a-second-flai-for-a-project-with-close-code-4409-while.md)).
- The dashboard compares the methods flai named with `REQUIRED_METHODS` and tells the designer which a project's flai lacks (S-0098). Nothing else is made of either version: the two numbers are shown, not checked.
- So the channel today authenticates the *installation*: the connection is between the flai and the flaiover the same `flai dashboard` set up, because only those two hold the credential. It says nothing about whether either of them is a build anyone released. A flai built from a branch, or a `flaiover:local` image, proves itself exactly as a release does.

## Signing releases

What the epic asks of a release is two things: a signature made in CI with a private key only CI holds, and a check with the public key wherever the release is consumed, before it is installed or run. The consumers are `flai self-upgrade` and `flai host upgrade` (Go, inside flai), `install.sh` (a shell with `curl` and whatever else a fresh machine has), and `flai dashboard` with its `check` and `upgrade` (Go, with `docker`). The dashboard's own code never consumes a release; it is the thing released.

Two properties decide most of the choice. First, **what the consumer needs to verify**: a public key in the binary and the standard library, or a library, or a tool on the path, or the network. flai is a single static binary installed by a shell script on machines that have nothing else; a verification that needs cosign installed, or the Sigstore trust root fetched, is a weaker promise than one that needs nothing. Second, **where the private key lives**, because the key, not the format, is what a compromise is about.

### What is signed

For flai, the right thing to sign is `checksums.txt`, not each archive: it already names every archive with its SHA-256, GoReleaser already publishes it, and `self-upgrade` and `install.sh` already download it and check the archive against it. One signature over that file turns the check they made from "the archive matches a file published beside it" into "the archive matches a file the release key signed"; S-0233 built that check ([How a release is verified before it is installed](#how-a-release-is-verified-before-it-is-installed)). GoReleaser's `signs` section does exactly this with `artifacts: checksum`, running any command with the checksum file as its input and uploading what it writes as a release asset. The archives themselves are then covered through their hashes and need no signature of their own. Checked against GoReleaser v2.18.2 ([its `signs` documentation](https://goreleaser.com/customization/sign/) and [`internal/pipe/sign/sign.go`](https://github.com/goreleaser/goreleaser/blob/main/internal/pipe/sign/sign.go)): `signature` names the output (default `${artifact}.sig`), and `cmd`, `args`, `env`, `stdin`, and `stdin_file` drive the command. The command runs with GoReleaser's whole environment, so a secret set on the workflow step reaches it, and `env` entries are templates that can say `{{ .Env.X }}`. A command that exits non-zero fails the release ("could not sign artifact"); a command that exits zero without writing `signature` only draws the warning "the signer did not write", which v3 will make an error. Signatures are among the release-uploadable artifact types, so the `.sig` is published beside `checksums.txt`.

For flaiover, the artifact is an image in GHCR and the thing that identifies it is its digest, `sha256:…`, which Docker checks on pull against the content it receives. Signing the digest signs the image. There are two ways to publish that signature, under [How the image's signature is published](#how-the-images-signature-is-published).

### The ways to sign

#### Ed25519 in the minisign format

[minisign](https://jedisct1.github.io/minisign/) is a small signing tool with a fixed format: Ed25519 keys, a public key that is one base64 line carrying a key ID, and a signature file of four lines, an untrusted comment, the base64 signature, a trusted comment, and a global signature over both. The private key is a file protected by a password. GoReleaser runs it through `signs` with `cmd: minisign`.

- **Verifying in flai**: `crypto/ed25519` in the standard library, after decoding the signature line and checking the key ID. No dependency; `aead.dev/minisign` is a small pure-Go library if the format's edge cases are not worth owning. **To check**: whether the default signature is over the file or its BLAKE2b-512 prehash (minisign signs the prehash with `-H`, and newer versions by default), because a prehashed signature needs `golang.org/x/crypto/blake2b`, a dependency, though a well-known one.
- **Verifying in `install.sh`**: needs `minisign` on the path, which almost no machine has, or OpenSSL 3 with `pkeyutl -rawin` for Ed25519, which macOS does not ship (its `openssl` is LibreSSL; **to check** whether its version verifies Ed25519). So the script would most likely have to say "verified only where minisign is installed", which is the current state with a different wording.
- **Verifying in flaiover** (for [Verifying the peer](#verifying-the-peer)): Node's `crypto.verify` with an Ed25519 key, standard library.
- **Key**: a password-protected file. In CI it is a GitHub Actions secret written to disk for the step, with the password in another secret.

#### cosign with a key pair

[cosign](https://docs.sigstore.dev/cosign/) is Sigstore's signing tool. Its current release is v3.1.3, of 2026-08-06, with v2.6.5 still maintained beside it ([releases](https://github.com/sigstore/cosign/releases)); what follows is checked against both.

`cosign generate-key-pair` makes an ECDSA P-256 key pair by default. `cosign.key` is the private key as PKCS #8, encrypted with the password, in a PEM block typed `ENCRYPTED SIGSTORE PRIVATE KEY`; older versions wrote `ENCRYPTED COSIGN PRIVATE KEY`, and both are read. `cosign.pub` is a PKIX `PUBLIC KEY` PEM ([`pkg/cosign/keys.go`](https://github.com/sigstore/cosign/blob/v3.1.3/pkg/cosign/keys.go)). The password comes from `COSIGN_PASSWORD` when it is set, from a prompt otherwise. `cosign generate-key-pair github://owner/repo` takes a token from `GITHUB_TOKEN` and writes three *repository* Actions secrets, `COSIGN_PASSWORD`, `COSIGN_PRIVATE_KEY`, and `COSIGN_PUBLIC_KEY`, and `cosign.pub` in the current directory; the private key is not written to disk, and `github://owner` alone writes organisation secrets instead ([`pkg/cosign/git/github/github.go`](https://github.com/sigstore/cosign/blob/v3.1.3/pkg/cosign/git/github/github.go)). cosign documents no scope for the token; the endpoints it calls need `repo` on a classic token ([GitHub's REST reference](https://docs.github.com/en/rest/actions/secrets#create-or-update-a-repository-secret)). It cannot write environment secrets; see [Keys](#keys).

Signing changed in v3. `cosign sign-blob` now defaults to `--new-bundle-format=true` and `--use-signing-config=true`: it writes a Sigstore bundle, refuses to run without `--bundle`, and takes its services, Rekor and a timestamp authority, from the signing config Sigstore publishes over TUF ([v3.0.0 in the changelog](https://github.com/sigstore/cosign/blob/v3.1.3/CHANGELOG.md)). `--output-signature` and `--tlog-upload` are deprecated: v3 still accepts them, hides them from `--help` and [the generated reference](https://github.com/sigstore/cosign/blob/v3.1.3/doc/cosign_sign-blob.md), and prints a warning; "the deprecated flags will be removed in a future Cosign v4 release" ([`options/signblob.go`](https://github.com/sigstore/cosign/blob/v3.1.3/cmd/cosign/cli/options/signblob.go), [v3.1.1 release notes](https://github.com/sigstore/cosign/releases/tag/v3.1.1)). `--tlog-upload=false` beside a signing config is refused; the replacement cosign names is a signing config with no transparency log, made with `cosign signing-config create` ([`signcommon/common.go`](https://github.com/sigstore/cosign/blob/v3.1.3/cmd/cosign/cli/signcommon/common.go)). So in v3 the old output, one base64 signature in a file of its own and no Rekor entry, takes three flags where v2 took one:

```sh
cosign sign-blob --key env://COSIGN_PRIVATE_KEY \
  --use-signing-config=false --new-bundle-format=false --tlog-upload=false \
  --output-signature checksums.txt.sig --yes checksums.txt
```

The encrypted PEM is in `COSIGN_PRIVATE_KEY` and its password in `COSIGN_PASSWORD`. With a key and no upload nothing is fetched from TUF and nothing prompts, since the one prompt is Rekor's privacy notice; `--yes` is there so that a later change cannot leave CI waiting on a terminal. In v2.6.5 the first two flags already default to false and `--tlog-upload` is not deprecated, so `--tlog-upload=false` alone does it there. The file holds the base64 of an ASN.1 DER ECDSA signature over the SHA-256 of the file: the key hashes the data with SHA-256 and signs the digest with `ecdsa.SignASN1` ([sigstore's `signature/ecdsa.go`](https://github.com/sigstore/sigstore/blob/v1.10.8/pkg/signature/ecdsa.go)), and `sign-blob` writes that signature base64-encoded, on one line ([`sign/sign_blob.go`](https://github.com/sigstore/cosign/blob/v3.1.3/cmd/cosign/cli/sign/sign_blob.go)). When v4 removes the flags, the step moves to `--bundle` with a signing config that names no log, and the consumer reads the same base64 signature from the bundle's `messageSignature.signature`; that is inferred from the source and not tried. GoReleaser's documented cosign example signs `artifacts: checksum`, but keylessly with `--bundle`, not with a key pair ([GoReleaser's `signs`](https://goreleaser.com/customization/sign/)); it also signs images with `docker_signs`.

- **Verifying in flai**: `encoding/pem`, `crypto/x509.ParsePKIXPublicKey`, `crypto/sha256`, and `crypto/ecdsa.VerifyASN1` over the file's SHA-256, all standard library, with the public key as a PEM string in the source. That matches the key and signature formats above. No dependency, no network beyond the download itself. The Rekor entry, when one is made, is not needed to verify and is not consulted. Built so in S-0233, with the key embedded as a file.
- **Verifying in `install.sh`**: `openssl dgst -sha256 -verify cosign.pub -signature checksums.txt.der checksums.txt`, after decoding the base64 into `checksums.txt.der`; `dgst -verify` takes a DER ECDSA signature and a PEM public key, which every OpenSSL and LibreSSL does. That is the one line that makes the script's check real on a fresh machine, and the reason this option beats minisign for this repository. Built so in S-0233; the script refuses to run without `openssl`. `install.sh` is `sh`, so the decoding goes to a temporary file rather than bash's `<(base64 -d …)`, and `openssl base64 -d -A` avoids the difference in `base64`'s flags between GNU and macOS (not tried). Anyone with cosign can also run `cosign verify-blob --key cosign.pub --signature checksums.txt.sig --insecure-ignore-tlog checksums.txt`; v3 deprecates `--signature` in favour of `--bundle`, falls back to the old format when no bundle is given, and needs `--insecure-ignore-tlog` for a signature that is in no log ([`cosign verify-blob`](https://github.com/sigstore/cosign/blob/v3.1.3/doc/cosign_verify-blob.md)).
- **Verifying in flaiover**: Node's `crypto.verify('sha256', data, pem, der)`, standard library.
- **Key**: an encrypted PEM and its password, two GitHub Actions secrets. Rotation means a new pair and a release of flai that carries both public keys; see [Keys](#keys).

#### cosign keyless

The same tool, with no key of ours: the workflow authenticates to Sigstore's Fulcio with its GitHub Actions OIDC token and receives a short-lived certificate that names the workflow (`https://github.com/bytepunx/system-flow/.github/workflows/release-flai.yml@refs/tags/flai/v1.2.3`) and the issuer (`https://token.actions.githubusercontent.com`); the signature and the certificate are recorded in Rekor; verification checks the certificate chain to Sigstore's root, the identity and issuer against what the verifier expects, and the Rekor entry's inclusion. GoReleaser's cosign example is this form: `sign-blob --bundle=${signature} ${artifact} --yes`, writing `checksums.txt.sigstore.json`, checked with `cosign verify-blob --certificate-identity … --certificate-oidc-issuer https://token.actions.githubusercontent.com --bundle …` ([GoReleaser's `signs`](https://goreleaser.com/customization/sign/)).

- **What it buys**: no private key to keep, rotate, or lose. The signer is the workflow, and a compromise of the repository that could run the workflow is the only way to sign.
- **What it costs the consumer**: the verifier needs Sigstore's trust root, fetched over TUF and refreshed, and the Rekor entry; in Go that is `sigstore-go`, a large dependency tree for a CLI that is otherwise standard library, and verification needs the network, which the download needs anyway, but to a second party, Sigstore's public instance, whose availability becomes flai's. `install.sh` would need cosign installed. This is heavy for what flai is.
- **Where it fits**: as a second signature anyone can check with public tooling, beside a key the binaries verify themselves. Not as the only one.

#### GitHub artifact attestations

`actions/attest-build-provenance` signs a SLSA provenance statement for an artifact with the workflow's identity, in Sigstore's bundle format, and stores it with the repository, where `gh attestation verify <file> --owner bytepunx` checks it. It is keyless signing with GitHub as the trust root: public repositories use Sigstore's public instance, private ones GitHub's own, which "does not have a transparency log and only federates with GitHub Actions" ([GitHub's artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations)). It describes *how the artifact was built*, not only that the key holder approved it, which is the stronger supply-chain statement.

Checked on 2026-10-07: "As of version 4, `actions/attest-build-provenance` is simply a wrapper on top of `actions/attest`", and new workflows should use [`actions/attest`](https://github.com/actions/attest) itself; both are at v4.2.2, and the wrapper pins `actions/attest` v4.2.2 by commit ([its README and `action.yml`](https://github.com/actions/attest-build-provenance)). GitHub's examples give the job `id-token: write`, `contents: read`, and `attestations: write`, with `packages: write` for an image and `artifact-metadata: write` for the storage record ([Using artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)). `subject-path` takes a glob or a list of paths, comma- or newline-separated, up to 1024 subjects, and `subject-checksums` takes a checksums file, so `subject-checksums: dist/checksums.txt` attests every archive in one step.

**Not available to this repository while it is private on Team.** GitHub says, on the page above and in the README of `actions/attest-build-provenance`: "If you are on a GitHub Free, GitHub Pro, or GitHub Team plan, artifact attestations are only available for public repositories. To use artifact attestations in private or internal repositories, you must be on a GitHub Enterprise Cloud plan." `bytepunx/system-flow` is private and the `bytepunx` organisation's plan is `team` (`gh api`, 2026-10-07), so the step cannot run here until the repository is public or the organisation is on Enterprise Cloud.

- **Consumer**: `gh` or `sigstore-go`, and the network to GitHub's attestation API. The same objection as keyless cosign for flai and for `install.sh`, with GitHub as the only external party. It can attest the image too, by its digest, and the image's attestation can be verified from the image alone with `gh attestation verify oci://…`.
- **Where it fits**: a cheap addition to both release workflows for anyone with `gh`, and the right thing to offer auditors, once the plan or the visibility allows it; not the mechanism flai verifies with.

#### GPG

GoReleaser's default `signs` command is `gpg --detach-sign`. The format is OpenPGP; the key lives in a keyring.

- **Consumer**: in Go, `golang.org/x/crypto/openpgp` is frozen and deprecated and the maintained fork is ProtonMail's, both large for one signature; in a shell, `gpg` is widely installed but needs the public key imported into a keyring first, and users are used to being told to trust a key ID. The format and tooling were made for people and email, not for a binary checking itself. Not recommended.

### Comparison

| | Ed25519, minisign | cosign, key pair | cosign, keyless | GitHub attestations | GPG |
|--|--|--|--|--|--|
| Signs in CI with | `minisign`, secret key file | `cosign`, secret key in env | `cosign`, OIDC identity | `actions/attest`, public repository or Enterprise Cloud | `gpg`, secret key in keyring |
| Private key | ours, a file | ours, a file | none, Sigstore issues per run | none, GitHub issues per run | ours, a keyring |
| flai verifies with | stdlib (`crypto/ed25519`), maybe blake2b | stdlib (`crypto/ecdsa`) | `sigstore-go`, TUF root, Rekor | `sigstore-go` or `gh`, GitHub API | OpenPGP library |
| `install.sh` verifies with | `minisign`, rarely present | `openssl dgst -verify`, present | `cosign`, rarely present | `gh`, often present | `gpg`, often present, needs import |
| Network to verify | none | none | Sigstore | GitHub | none |
| Rotation | new key, release carries both | new key, release carries both | nothing to rotate | nothing to rotate | new key, release carries both |
| Compromise means | whoever holds the file and password signs | same | whoever can run the workflow signs | same | same as a file |
| Also signs the image | no, digest list only | `cosign sign` in GHCR, or digest list | `cosign sign` in GHCR | yes, by digest | no |

### How the image's signature is published

**A signed digest list as a release asset.** `release-flaiover.yml` already knows the digest it pushed (`docker/build-push-action` outputs it). On a `flaiover/v*` tag the workflow writes one file, `flaiover_<version>.digests`, with the digest for each platform and the tag it was pushed under, signs it with the same key and tool as `checksums.txt`, and uploads both to a GitHub release `flaiover vX.Y.Z`, which does not exist today and would be created by the workflow. `flai dashboard` then resolves the version it is to run through the same release client `self-upgrade` already has, downloads the list and its signature, verifies with the key in the binary, and pulls and runs `ghcr.io/bytepunx/flaiover@sha256:…` by digest, so that Docker's own content check completes the chain. One mechanism, one key, one client, no new dependency; the dashboard's version becomes something flai chooses from a signed list rather than a tag it trusts.

**cosign on the image.** `cosign sign --key cosign.key ghcr.io/bytepunx/flaiover@sha256:…` stores the signature in GHCR, and anyone verifies with `cosign verify --key cosign.pub ghcr.io/bytepunx/flaiover:1.2.3`. Up to v2 the signature was an OCI artifact under a tag derived from the digest; v3 stores a Sigstore bundle as an OCI 1.1 artifact that refers to the image ([v3.0.0 in the changelog](https://github.com/sigstore/cosign/blob/v3.1.3/CHANGELOG.md)). For flai to verify it without cosign, it would speak the registry's HTTP API (a token exchange with GHCR, a referrers or manifest fetch, a blob fetch) and check the ECDSA signature in the bundle: a few hundred lines of standard library against a layout cosign owns, or `go-containerregistry` plus `sigstore-go` as dependencies. It is the right thing to publish for the ecosystem and the wrong thing for flai to depend on.

**Notary (Docker Content Trust) and notation** sign tags in a registry-side trust server; GHCR does not run one. Not an option here.

A consequence either way: `latest` is pushed on every merge to `main`, and `sha-*` tags with it. Those builds are not releases and carry no signature. Once `flai dashboard` runs only what a signed list names, `dashboard.tag: latest` has to mean "the newest flaiover release", resolved from the releases, not the registry's `latest` tag; and an unreleased `main` build is run only as a development image, the way [Verifying the peer](#verifying-the-peer) describes. Since S-0236 `latest` means the newest release ([How the dashboard's image is chosen and run](#how-the-dashboards-image-is-chosen-and-run)).

### The digest list

On a `flaiover/v*` tag, `release-flaiover.yml` writes `flaiover_<version>.digests`, signs it as flai's `checksums.txt` is signed, into `flaiover_<version>.digests.sig`, and uploads both to the `flaiover vX.Y.Z` release. On the same tag it signs the image with `cosign sign --key` and attests it with `actions/attest`, both by the index digest and not by each platform's manifest (no `--recursive`); the attestation waits on the plan or the visibility, as [GitHub artifact attestations](#github-artifact-attestations) says. Builds of `main` get no list, no signature, and no attestation.

The file is plain text, UTF-8, LF line ends, with a final newline, and no blank lines or comments. Each line is three fields separated by one space: the digest, the reference it was pushed under, and what it is.

```text
sha256:0dce07ffc38f1fecc91cbb659524525db687eb12030bea40209f2ecf3636f15d ghcr.io/bytepunx/flaiover:0.42.3 index
sha256:b3c17aafc5f6026830b885843021a783cc6e129937cc4f1f1dc44e546ff38ec0 ghcr.io/bytepunx/flaiover:0.42.3 linux/amd64
sha256:b8ec2bdf93dfbd0cdbe8b756bdd0ce30d66242a93bd99d5e869f0668a475eb0c ghcr.io/bytepunx/flaiover:0.42.3 linux/arm64
```

- **Digest**: `sha256:` and 64 lower-case hex characters.
- **Reference**: `ghcr.io/bytepunx/flaiover:<version>`, the version without its `v`. The other tags the workflow pushes, the major and `sha-<short>`, name the same index and are not listed.
- **Kind**: `index` for the image index, `<os>/<arch>` for a platform's manifest, with `/<variant>` when the index gives one.
- **Order**: the `index` line first, then the platform lines sorted by kind in byte order. The same index always gives the same file, byte for byte.
- **What is listed**: the index digest, which `docker/build-push-action` outputs, and every manifest in the index whose platform is not `unknown/unknown`. The attestation manifests buildx adds, platform `unknown/unknown` and annotation `vnd.docker.reference.type: attestation-manifest`, are left out.

A shell reads it with `while read -r digest ref kind; do …; done`, and Go with `strings.Fields` on each line, a line of any other number of fields being an error. A consumer matches an entry of `RepoDigests`, `ghcr.io/bytepunx/flaiover@sha256:…`, by splitting it at its `@`: the part before must equal the reference with its `:<version>` cut off, and the part after must equal a digest on the list. The image is a signed release when any of its `RepoDigests` entries matches; the kind does not matter to the match. `flai dashboard` pulls by the `index` line's digest; the platform lines are there for an image someone pulled by platform.

What a pull leaves behind, observed on this host on 2026-10-12 with Docker 29.2.1 and its containerd image store (`docker info` driver type `io.containerd.snapshotter.v1`), pulling `ghcr.io/bytepunx/flaiover:0.42.3` (index `0dce07ffc38f`, linux/amd64 `b3c17aafc5f6`):

| Pulled by | `RepoDigests` | Image ID, and a container's `.Image` |
|-----------|---------------|--------------------------------------|
| the index digest | `[…flaiover@sha256:0dce07ffc38f…]` | `sha256:0dce07ffc38f…` |
| the tag, after that | `[…flaiover@sha256:0dce07ffc38f…]`, the same image, now tagged too | `sha256:0dce07ffc38f…` |
| the linux/amd64 manifest digest | `[…flaiover@sha256:b3c17aafc5f6…]` | `sha256:b3c17aafc5f6…` |
| the tag, after that | a second image: `[…flaiover@sha256:0dce07ffc38f…]` | `sha256:0dce07ffc38f…` |

In this store an image is the digest it was pulled by: its ID is that digest, and `RepoDigests` holds the repository at that digest, once ([`daemon/containerd/image_inspect.go`](https://github.com/moby/moby/blob/docker-v29.2.1/daemon/containerd/image_inspect.go), `collectRepoTagsAndDigests`). A pull by an attestation manifest's digest succeeds here, but its image has no platform and an empty configuration, and `docker create` from it fails with "no command specified", so no container runs one.

Read in moby's source, not tried: in the classic store (`overlay2` without the containerd snapshotter) an image's ID is its configuration's digest, which is on no list. A pull through an index, by tag or by its digest, records the index digest ([`pullManifestList`](https://github.com/moby/moby/blob/docker-v29.2.1/daemon/internal/distribution/pull_v2.go) returns `manifestListDigest`, which `pullTag` adds as a digest reference), and a pull by a platform's manifest digest records that digest. Both point at the same image ID, so an image pulled both ways carries both, and `RepoDigests` lists every digest reference to that ID ([`daemon/images/image_inspect.go`](https://github.com/moby/moby/blob/docker-v29.2.1/daemon/images/image_inspect.go)). So flai reads `RepoDigests` and not `.Image`, which is the listed digest in one store and the configuration's digest in the other.

### Keys

- **One key for both components**, held as two GitHub Actions secrets, `COSIGN_PRIVATE_KEY` (the encrypted private key) and `COSIGN_PASSWORD`, in the `bytepunx/system-flow` repository, used only by `release-flai.yml` and `release-flaiover.yml`. A repository secret is readable by any workflow run, a branch's included, and a tag can be pushed by anyone with write access. Checked on 2026-10-07 for a private repository on Team: required reviewers are not available. GitHub: "If you are on a GitHub Free, GitHub Pro, or GitHub Team plan, required reviewers are only available for public repositories" ([deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)). Environment secrets and deployment tags are: "For access to environment secrets in private or internal repositories, you must use GitHub Pro, GitHub Team, or GitHub Enterprise", and "For users on GitHub Pro or GitHub Team plans, deployment branches and tags are also available for private repositories" (same page). So the two secrets go in an environment, `release`, whose deployment tags are `flai/v*` and `flaiover/v*`, which no branch run can read; and a tag ruleset limits who may create those tags, since rulesets are available in private repositories with Team ([about rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)). Only the job that signs runs in the environment; flaiover's `main` builds do not. `cosign generate-key-pair github://` writes repository secrets only, so the pair is generated locally and set with `gh secret set --env release`, and the local `cosign.key` is deleted.
- **The public key is in both sources**, as a PEM constant in `flai/internal/buildinfo` (or a sibling package) and in `flaiover/src/lib/server`, with the key's SHA-256 fingerprint in `docs/operators` so an operator can compare, and published as a release asset too. It is not fetched from anywhere at verification time: a key fetched over the same channel as the artifact proves nothing.
- **Rotation**: generate the new pair, release a flai that carries both public keys, then switch the workflows to the new key; a flai older than that release cannot verify a newer release and `self-upgrade` tells the operator to install the bridging release first, by its version. As built in S-0233, the bridge it names is the newest published release whose signature a key the binary knows verifies; `install.sh`, which carries one key, tells the operator to get the newest script instead. A signature file is tried against every key the binary knows; nothing in the format needs a key ID.
- **Compromise**: rotate as above, and the release that carries the new key is signed with the old one, which an attacker also holds. So a compromise is announced in `CHANGELOG.md` and the release notes with the fingerprint of the new key, and `install.sh` and the documentation tell the operator to compare it. There is no stronger recovery without a second, offline root key; that is deliberate for a project of this size, and said here so that nobody expects otherwise.
- **Snapshot and local builds** (`scripts/flai.sh`, `goreleaser --snapshot`, `flai dashboard --build`) are not signed. They are development builds and are treated as such by the peer check.

### Recommendation

Sign `checksums.txt` and the image digest list with **cosign and a key pair** (ECDSA P-256), through GoReleaser's `signs` for flai and a step in `release-flaiover.yml` for the image, with no Rekor entry at first so that nothing depends on Rekor, and verify in flai with the standard library and in `install.sh` with `openssl`. In cosign v3 that takes `--use-signing-config=false --new-bundle-format=false --tlog-upload=false` with `--output-signature`, all accepted and the last two deprecated, to be removed in v4; so the workflows pin cosign, through `sigstore/cosign-installer` v4.1.2 (whose default is cosign v3.0.6) with `cosign-release: v3.1.3`, the newest release and the one with the fix for GHSA-fx35-mq7g-6g98 ([cosign-installer](https://github.com/sigstore/cosign-installer), [cosign v3.1.3](https://github.com/sigstore/cosign/releases/tag/v3.1.3)). For flai the `signs` entry is:

```yaml
signs:
  - id: checksums
    artifacts: checksum
    cmd: cosign
    signature: "${artifact}.sig"
    args:
      - sign-blob
      - --key=env://COSIGN_PRIVATE_KEY
      - --use-signing-config=false
      - --new-bundle-format=false
      - --tlog-upload=false
      - --output-signature=${signature}
      - --yes
      - ${artifact}
```

with `COSIGN_PRIVATE_KEY` and `COSIGN_PASSWORD` set on the GoReleaser step from the environment's secrets; a missing key or password makes cosign exit non-zero, which fails the release. Publish the image's digest list as a release asset of a `flaiover vX.Y.Z` release and make `flai dashboard` run by digest from it. Add `actions/attest` (or its wrapper `actions/attest-build-provenance`, v4.2.2) to both workflows as a second, keyless statement for anyone with `gh`, costing one step each and nothing in flai, once the repository is public or the organisation is on Enterprise Cloud; on a private repository on Team it is not available. Keep the template out: it is a clone.

The reasons, in order: the consumer verifies with nothing but what it already has (stdlib, `openssl`, `docker`), on every platform flai is built for, without a second service; the private key is the operator's, which is what the epic asked; cosign is the mainstream tool for exactly this and GoReleaser's documented example, in its keyless form, so the CI side is a few lines; the same key, format, and client cover both components, which is what lets [Verifying the peer](#verifying-the-peer) be one mechanism; and the keyless statement is kept for what it is good at, provenance for auditors, without making flai depend on it. minisign is the runner-up and would be chosen over cosign only if `install.sh` were allowed to skip verification where `minisign` is absent, which it should not be.

## Verifying the peer

The epic asks for the same mechanism to make each component refuse the other when it is not a signed release: flai closes its connection to an unsigned flaiover, flaiover closes the connection from an unsigned flai. This section says what that can and cannot mean, and what reaches as far as the facts allow.

### What a running process can prove about itself

A signature is a statement about bytes at rest: this archive, this image, was approved by the key holder. It is checked by whoever receives the bytes before running them, which is what [Signing releases](#signing-releases) arranges for `self-upgrade`, `install.sh`, and `flai dashboard`. A running process has no such thing to show a peer. Whatever it sends over the connection, a hash of its own executable, a version, a signed statement it was built with, is data it chose to send; a modified build can send the same data, copied from a real one. Proving to a remote party which code is running needs a measurement made by something the code does not control, such as a hardware root of trust, and nothing in flai's or flaiover's environment offers one. The design below is therefore honest about three levels:

| Level | Who checks | What it proves | What it does not |
|-------|-----------|----------------|------------------|
| Artifact verified before it runs | `self-upgrade`, `install.sh`, `flai dashboard` | the bytes installed or started are a signed release | nothing about what runs later |
| Peer's artifact measured by a trusted substrate | flai, through `docker inspect` | the container flai talks to runs an image the release key signed | nothing where flai cannot ask Docker |
| Release stamp exchanged on the channel | both, in `hello` | the peer carries a statement the release key signed, naming its component and version | that the peer *is* that release, against anyone who holds a release binary and the credential |

The threat each level stops: the first stops a substituted download or image, which is what signing is for. The second stops a dashboard container that was started from, or replaced by, an image nobody signed, including the `latest` tag moving to an unreleased `main` build. The third stops the honest mistakes, a flai built from a branch pointed at a production dashboard, a `flaiover:local` left running, a release of one talking to a snapshot of the other, and makes them visible by name. What none of them stops is an attacker who already holds the agent credential and can run code on the host or in the container: they can replay a real stamp. The credential is the boundary there, as [ADR-0031](../adrs/0031-the-dashboard-s-container-holds-nothing-of-the-project-a-port-and-two-secrets.md) already says, and signing does not move it.

### The agent credential, as it is

The HMAC handshake already proves to each side that the other was set up by the same `flai dashboard`, because only those two hold the credential, which never crosses the wire. It is the thing that makes the channel the operator's and not anyone's, and it stays. It does not say whether either side is a release, and that is the gap the two designs below fill.

### flai measures the container before it dials

`flai serve` dials the container `flai dashboard` started on this host. It knows the container's name, `flaiover`, and asks Docker what it runs. S-0238 built the check (`CheckImage` in `flai/internal/serve/imagecheck.go`). This is a real check: Docker, not the peer, says what the container runs, and flai already trusts Docker to run the container at all.

- **What it reads.** `docker inspect --type container flaiover` gives the container's ID, its image ID, and its `FLAIOVER_VERSION`. `docker image inspect` of the image ID gives `RepoDigests`, the registry digests the image was pulled under. Both run through `execx.Runner`.
- **What it compares.** Each `RepoDigests` entry against every verified digest list cached beside `flai serve`'s state ([The digest list](#the-digest-list)), each verified again as it is read. When none names the image and no list of the container's version is cached, flai fetches and verifies that version's list, as `flai dashboard` does when it chooses the image, caches it, and compares again.
- **When it runs.** The channel client asks a gate, `Client.BeforeDial`, before every dial and every reconnection. Every client `flai serve` dials has it: each served project's, and each candidate connection that offers repositories for import.
- **The verdicts.** `listed`: a list names one of the image's digests, and flai dials. `unlisted`: no list names it, or the image has no `RepoDigests`, as a local build has none; flai does not dial, unless the allowance of [The development case](#the-development-case) is in force. `not-measured`: the dashboard URL's host is not `localhost` or a loopback address, `docker` is not on `PATH`, no container `flaiover` exists, `docker inspect` or `docker image inspect` fails, or `flai serve` cannot load the release keys that verify the lists; flai dials, and the stamp check alone admits or refuses the dashboard ([The exchange as built](#the-exchange-as-built-s-0237)).
- **A refusal.** The gate's error, `the dashboard runs an unsigned image <image ID> (<RepoDigests>): <reason>`, is the connection's `refused_reason`, with `refused_by` `flai`. The client logs one `error`, `flai refused to dial the dashboard`, once per distinct refusal, and waits `HeldBackoff`, a minute, before it asks the gate again. Each retry measures again, so a container restarted from a listed image is dialled at the next.
- **What it records.** Each project's last verdict, by root, in `flai serve`'s state as `images`: `kind`, `container`, `image`, `version`, `repo_digests`, `digest`, `release`, `reason`, and `allowed`, set on an unlisted image dialled under the allowance. A new verdict is logged once. `flai serve status` prints it under each project as `image: signed, flaiover <release>, <digest>`, `image: the dashboard runs an unsigned image <image ID> (<RepoDigests>); flai does not dial it` (`; dialled, as unsigned is allowed` under the allowance), or `image: not measured: <reason>; the release stamp alone is checked`. `flai host status` prints the same line after the root, under `serve`. `flai dashboard status` prints `flai serve: dials it, signed`, `flai serve: refused it: …; it does not dial it` (`flai serve: dials it as unsigned is allowed: …` under the allowance), or `flai serve: image not measured: …`, beside its own digest line, and `serve_image` in `--json`. The words are in [flai-cli.md](flai-cli.md#commands) and, for the operator, [the flai guide](../../docs/users/flai.md#flai-serve-flai-on-the-host-for-the-dashboards).

Its limits: it needs Docker where `flai serve` runs, so a dashboard reached over the network on another machine cannot be measured and falls back to the stamp; `RepoDigests` is empty for a locally built image, which is the development case and is refused unless [The development case](#the-development-case)'s allowance is in force; and the list must name every digest a pull can leave behind, the index digest and each platform's manifest digest, because which one `RepoDigests` records depends on how the image was pulled. S-0234 checked it: a pull by tag or by the index digest records the index digest, and a pull by a platform's manifest digest records that manifest digest; Docker's classic store can hold both on one image. Details under [The digest list](#the-digest-list). Since `flai dashboard` already runs the image by digest from the signed list, this check at dial time is a second look at a decision flai itself made, and it catches what happened in between: a container restarted from a different image, a tag that moved, an operator's `docker run`.

### A release stamp in `hello`

The stamp is a small statement CI signs with the release key before the build, and the build carries: the component name, the version, and the commit, as one line, with its signature. For flai the workflow signs the line and hands the signature to GoReleaser through the environment, which `ldflags` write into `buildinfo` beside `Version`; for flaiover the workflow signs the line and passes it as a build argument that the image keeps as a file. The statement cannot cover the finished artifact's hash, because the artifact does not exist yet when it must be embedded; it covers what the release *is*, and the artifact checks of the first level cover what it *contains*.

`hello` grows one field each way: flai sends `release: {statement, signature}` with the fields it sends today, and the dashboard answers with its own. Each side verifies the other's signature with the public key it carries, checks that the statement names the component it expects (`flaiover` from the dashboard, `flai` from flai) and that the version is one the protocol number already admits, and then goes on with the credential proof. A missing, unverifiable, or wrong-component stamp closes the connection with a close code of its own, `4403 unsigned peer`, from whichever side found it; flai backs off a minute on it as it does on `4409` ([ADR-0063](../adrs/0063-the-dashboard-refuses-a-second-flai-for-a-project-with-close-code-4409-while.md)), logs once, and shows the state everywhere the measured check does. The dashboard shows a project whose flai was refused with the reason, where it shows a flai that lacks a required method today, so that the designer sees "unsigned flai" and not a connection that never comes.

The stamp is what lets flaiover say anything about flai at all, since the container can measure nothing on the host; and it is what covers flai's side when Docker is out of reach. It is checked by both for symmetry and because it costs nothing more once the key is in both sources. Its promise is stated above and should be written the same way in the operator documentation: it names the peer's release and refuses builds that are not one; it does not defend against someone who holds the credential.

### The stamp as built (S-0235)

S-0235 builds the stamp into both components, and each checks its own at start. S-0237 exchanges the stamps in `hello` and refuses an unsigned peer; see [The exchange as built](#the-exchange-as-built-s-0237).

| | flai | flaiover |
|-|------|----------|
| Statement | `flai <version> <commit>`, one line, no newline | `flaiover <version> <commit>`, the same |
| Version and commit | the tag less `flai/v`, and `git show --format=%h`, the command GoReleaser takes `.ShortCommit` from | the tag less `flaiover/v`, and `git rev-parse --short HEAD`, as the image job computes `FLAI_COMMIT` |
| Signed by | `release-flai.yml`, step "Sign the release stamp", before GoReleaser | `release-flaiover.yml`, job `release-key`, step "Sign the release statement", on a `flaiover/v*` tag only, in the environment `release` |
| Signature | `cosign sign-blob` with the release key and the three flags that sign `checksums.txt`: base64 of an ASN.1 DER ECDSA P-256 signature over the statement's SHA-256 | the same |
| Carried as | `buildinfo.ReleaseStatement` and `buildinfo.ReleaseSignature`, set by `flai/.goreleaser.yaml`'s `ldflags` from `FLAI_RELEASE_STATEMENT` and `FLAI_RELEASE_SIGNATURE` | `/app/release-stamp`, two lines, the statement and the signature, written by `flaiover/Dockerfile` from the build arguments `FLAIOVER_STAMP_STATEMENT` and `FLAIOVER_STAMP_SIGNATURE`; `FLAIOVER_RELEASE_STAMP` names another file |
| Checked by | `buildinfo.OwnStamp`, against every release key flai carries, and the build's own `Version` and `Commit` | `checkReleaseStamp` in `flaiover/src/lib/server/release.ts`, with `node:crypto`, against the image's `FLAIOVER_VERSION` and `FLAIOVER_COMMIT` |
| Shown | `flai version` (`release: signed`, `development build, no stamp`, `missing stamp`, or `invalid stamp: <reason>`), and `release` in `flai version --json` | the label `signed` (`true` or `false`) on `flaiover_build_info`, and `release_stamp` on the `server started` line |
| Warns | `flai serve`, once at start: `release stamp not valid`, with `state` and `reason` | the server, once at start: `release stamp not verified`, with `state`, `reason`, and `path` |
| A development build | version `dev`, empty, or starting `0.0.0`: no stamp, never warned about | `FLAIOVER_VERSION` unset, `0.0.0`, or `0.0.0-…`: the same |

A stamp is in one of three states: `signed`, `missing`, or `invalid`. It is invalid when its signature does not verify against the release key, when it is malformed, or when it names another component, version, or commit than the build reports. The last check is why each workflow builds the statement from the same values the build reports: `release-flaiover.yml` fails the image job when the statement does not name the build ("Stamp names this build"), and so does the Dockerfile. A stamp that named another build would make every start of the release warn about itself.

Only release tags carry a stamp. `latest` and `sha-*` from `main`, a `goreleaser --snapshot`, `scripts/flai.sh`, and an image from `flai dashboard --build`, `make flaiover-image`, or `scripts/flaiover-image.sh` carry none. A flai from `scripts/flai.sh` is a development build and says nothing. An image built from `main` or by `flai dashboard --build` reports the newest `flaiover/v*` tag as its version, so it warns once at start. [The development case](#the-development-case) below, built by S-0239, is where such a build is allowed on purpose. The Dockerfile fails a build given one of the two build arguments without the other.

### The exchange as built (S-0237)

S-0237 exchanges the stamps in `hello`, as [A release stamp in `hello`](#a-release-stamp-in-hello) designed, with two differences. Neither side checks the version or the commit a stamp names, only its signature and its component. And S-0237 had no allowance for a development build, so a development build of either side was refused; since S-0239 [The development case](#the-development-case) admits a missing stamp on purpose.

| | flai | flaiover |
|-|------|----------|
| Sends | `release: {statement, signature}` in `hello`, from `buildinfo.ReleaseStatement` and `ReleaseSignature`; absent for a development build | `release` in its answer to `hello`, from `/app/release-stamp` when it holds one well formed (`helloStamp`); absent otherwise |
| Checks | the dashboard's, with `buildinfo.VerifyPeerStamp`, for the component `flaiover`, after the dashboard's proof and before it sends `hello.prove` | flai's, with `verifyPeerStamp`, for the component `flai`, before it sends its nonce, so an unsigned flai has nothing to prove against |
| An older peer | a protocol 1 dashboard answers without `release` and is refused as `missing stamp` | a protocol 1 `hello` is read far enough to be refused as `missing stamp` |
| Refuses with | close code 4403 (`CloseUnsigned` in `internal/channel`), reason `unsigned peer: <fault>` | the same (`CLOSE_UNSIGNED` in `$lib/server/agent.ts`) |
| After a refusal | waits a minute before it dials that project again (`HeldBackoff`), from either side's refusal, as after 4409 | keeps the refusal on the project's hub as `refused`, `{at, reason, flai}`, until a signed flai for it is adopted; at most eight projects are known from a refusal alone, since `hello` names its project before any proof |
| Logs | one `error` per refusal, `connection refused as unsigned`, with `refused_by`, `reason`, and `peer_version`, not repeated at every retry | one `warn` per refusal, `host flai refused: unsigned peer`, with `project`, `flai`, and `reason` |
| Records | `refused_by` (`dashboard` or `flai`), `refused_reason`, `peer_version`, and `peer_signed` in the connection's state, cleared once a connection is proven; since S-0239, `unsigned`, the sides the allowance let through | `signed` on a connected flai, and `refused`; since S-0239, `unsigned` on a connected flai |
| Shows | `flai serve status`, `flai host status`, and `flai dashboard status`: `the dashboard refused this flai: unsigned` or `flai refused the dashboard: unsigned`, then `(<reason>, dashboard <version>)` after a space, each part left out when not known; since S-0239, `unsigned allowed: <sides>` for a connection the allowance let through | `/api/agent`'s error, shown by the banner and the header badge `host flai: refused (unsigned)`; `signed` and `refused` on each project in `/api/projects`, shown by the project switcher as `(signed)`, `(unsigned)`, or `(refused: unsigned flai)`; since S-0239, `(unsigned allowed: <sides>)` and a banner for a connection the allowance let through ([The development case](#the-development-case)) |

The fault is `missing stamp`, `invalid signature` (malformed, or signed by no release key flai or the image carries), or `wrong component <name>`. The version a refusal names is the stamp's when it names one, else the one `hello` gave. A dashboard that flai refuses keeps nothing of it: to the dashboard it is a socket closed before the proof, and it shows only that no flai is connected. The operator documentation states the promise and its limit as the table under [What a running process can prove about itself](#what-a-running-process-can-prove-about-itself) does, in [docs/operators](../../docs/operators/index.md#the-release-stamp).

### The development case

This repository runs flai from `scripts/flai.sh`, with no version and no stamp, and its dashboard from `flai dashboard --build`, an image with no digest on any list. Every contributor, and every project on the template that builds its own flai, is in the same position. So unsigned is allowed on purpose, in one place, and visibly. S-0239 built it as designed here; what the operator sees is in [docs/operators](../../docs/operators/index.md#allowing-unsigned-builds-s-0239).

- **The allowance is the operator's, on the host.** `dashboard.allow_unsigned` in the host's flai configuration, default `false`, set with `flai config set dashboard.allow_unsigned true`. A project's manifest may set `dashboard.allow_unsigned`, `true` or `false`, over it for that project (`manifest.Dashboard.AllowUnsignedOr`, [project-manifest.md](project-manifest.md)).
- **It admits a missing stamp and an unlisted image, nothing else.** flai dials a container whose image is on no list, and accepts a dashboard that sends no stamp. The dashboard accepts a flai that sends no stamp. A stamp that does not verify, or names another component, is refused with `4403` either way. The credential proof is made either way.
- **flai reads it before each dial.** `serve.Options.AllowUnsigned` reads the host configuration at each call, and `allowsUnsigned(root)` loads the project's manifest over it. `guard` gives each client, a served project's or a candidate's, the image gate and `Client.AllowUnsigned`, both asked before every dial and every reconnection. So turning it on takes effect at the next dial, within the minute a refusal waits, with no restart. An unlisted image is still recorded as `unlisted` in `images`, with `allowed` set (`ImageVerdict.Allowed`), and its new verdict is logged once at `info`, `dashboard image is on no verified digest list; dialled as unsigned is allowed`. `flai serve status` says of it `image: the dashboard runs an unsigned image <image> (<digests>); dialled, as unsigned is allowed`, and `flai dashboard status` `flai serve: dials it as unsigned is allowed: the dashboard runs an unsigned image <image> (<digests>)`, in place of the lines that say flai does not dial it.
- **The container is told by the thing that started it.** `flai dashboard` gives the container `--env FLAIOVER_ALLOW_UNSIGNED=1` when the allowance is in force for the project, with `--build`, or with `--allow-unsigned`, which allows it for that start and writes nothing to the configuration. The dashboard reads the variable once, at start (`allowsUnsigned` in `flaiover/src/lib/server/release.ts`), and allows only when it is exactly `1`. Nothing in the image decides for itself.
- **Restarts keep it.** The container record, `dashboard-container.json` beside `flai serve`'s state, keeps `allow_unsigned`. `flai dashboard restart`, `flai dashboard upgrade` (`keepAllowance`), and `flai host`'s watch start the container again the same way, and `restart` and `upgrade` add it when the allowance is in force now. None of them removes it: only a new start after `flai dashboard stop` does. `flai dashboard` on a container already running without it changes nothing and says `unsigned not allowed: flaiover already runs, started without FLAIOVER_ALLOW_UNSIGNED=1, which only a start gives; set dashboard.allow_unsigned and run flai dashboard restart`.
- **Each side records its own missing stamp, and the peer's it let through.** A side is `flai`, the flai on the host has no release stamp, or `dashboard`, the dashboard sent none; both can be. A proven connection with an unstamped side was let through by the other side's allowance, so the side without a stamp records itself whatever its own allowance, and records the peer only when its own allowance admitted it. flai's `Client.unsignedSides` gives `flai` whenever its own build sent no stamp, and `dashboard` when the dashboard's stamp is missing and flai's allowance is in force; the connection's state keeps them as `unsigned` until it ends. The dashboard's `unsignedSides` gives `dashboard` whenever its own image holds no stamp, and `flai` when flai's stamp is missing and `FLAIOVER_ALLOW_UNSIGNED` is `1`; the connection keeps them, and `/api/projects` and `/api/agent` carry them as `unsigned`. So both sides name the same sides of a connection, whichever allowance admitted it, and a signed pair records nothing.
- **Allowed is not silent.** For a connection with an unsigned side, `flai serve` logs one `warn`, `connection allowed unsigned`, with `component` `channel`, `url`, `project`, and `unsigned`; the dashboard logs one `warn`, `host flai connected unsigned`, with `project`, `flai`, and `unsigned`. `flai serve status`, `flai host status`, and `flai dashboard status` say `unsigned allowed:` and the sides, `flai`, `dashboard`, or `flai and dashboard`, and `flai dashboard status` says of the container `unsigned allowed: started with FLAIOVER_ALLOW_UNSIGNED=1, it serves a flai with no release stamp` ([flai-cli.md](flai-cli.md#allowing-unsigned-builds)). The dashboard shows a banner on every page but the login page naming the sides, and the project switcher says `(unsigned allowed: <sides>)` in place of `(signed)` or `(unsigned)` ([flaiover-dashboard.md](flaiover-dashboard.md#the-channel-to-flai-on-the-host-s-0072-adr-0029)). A release of flai talking to a release image with the allowance on shows nothing: the allowance permits, it does not downgrade.
- **The default is to refuse**, for a release build of either side. An operator who installed flai with `install.sh` and runs the published image is never asked, and never shows the banner; the one who builds either side is told what they built.
- **Release builds are never allowed to be unsigned.** A `flai/v*` tag whose workflow runs without the key fails the release, and a `flaiover/v*` tag likewise; the stamp is not optional for a build that claims a version. `goreleaser --snapshot` and `flai dashboard --build` give a version of `0.0.0-<commit>` or none, and that is what "development build" means in both places.

### Recommendation

Do all three levels, in this order of worth: verify every artifact before it is installed or started, as [Signing releases](#signing-releases) recommends; have flai measure the container's image digest through Docker against the signed list before it dials and refuse an unlisted one; and exchange a signed release stamp in `hello`, checked by both, closed with `4403` when it fails. Allow unsigned only by the operator's setting on the host, passed to the container by `flai dashboard`, and show it wherever the connection is shown. Write the threat model into `docs/operators` in the words of the table above, so that the connection check is read as what it is: a check that the peer is a release, with the credential as the thing that keeps the channel the operator's.
